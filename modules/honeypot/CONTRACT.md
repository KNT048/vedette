# Honeypot Contract

> Tier: optional (off by default) · Story: S-HP-1, S-HP-2 · Last verified: 2026-11-21 (every sentence checked against the code)
> Source of the actual behaviour: `web/src/features/honeypot/{contract,types,mocks}.ts`. OpenAPI is generated from `contract.ts`; every difference below is a defect in one of the two sides.

## Invariants (always true)
- **INV-1** The trap only listens and writes a log; it never connects back to the source on its own and never runs a real service (LEGAL §3, S-HP-2). Tests: on the code side `TestContract_INV1_NoDialer` (the module does not import `net`/`os/exec`/`net/http`; `syscall` only in `tail.go` and only for the two file-open flags `O_NOFOLLOW`, `O_NONBLOCK`); on the packet side (no packet leaves the `honeypot` container towards the source IP) there is no automated test, it is checked in the lab. On the network side: the container's `vedette-hp` namespace has a constant nft ruleset that blocks every **new** outbound connection (`ct state new drop` at the output hook, `hpOutputRules` in `host/ops/decoyports.go`; it only answers inbound connections), installed by `vedette-host`; `TestHasEgressDrop` (`host/ops`), and in the lab `nft list ruleset` inside the namespace.
- **INV-2b** (S-HP-1) A hit is recorded according to what OpenCanary sees, and does not promise "every connection": SSH 4000-4002, HTTP and HTTPS 3000-3003 (HTTPS is separated by destination port 443; the configuration turns on `http.log_redirect_request` and `http.log_unimplemented_method_requests` when http or https is on, otherwise GET / leaves no line), SMB 5000 (Samba connect/openat), RDP 14001, MSSQL 9001/9002, FTP 2000 (only when USER+PASS are sent; 2001 is not enabled), Telnet 6001/6002 (`telnet.log_tcp_connection`: every connection), HTTP proxy 7001 (only requests that carry `Proxy-Authorization`), MySQL 8001/9003 (`mysql.log_connection_made`: every connection), TFTP 10001, NTP 11001 (only `monlist`), VNC 12001 (only when it answers the password challenge), SIP 15001, Git 16001, Redis 17001 (every command), SMTP (`tcpbanner`) 18001-18005 (every connection), MongoDB 20001 (connect, command, login, close). A bare TCP connection to SMB/MSSQL/FTP/VNC/HTTP proxy leaves no log line so there is no hit; TFTP/NTP/SIP are UDP, never answer (OpenCanary's module only logs), and their lines have the destination `0.0.0.0`: the hit carries the oldest Trap IP that has that service (including the event's `decoy`, so an incident may name the wrong Trap IP when two Trap IPs both have that service; left for later) and is not fed into `sweep` (an attempt recorded by the host has a real source and destination).
- **INV-2e** **A UDP hit does not confirm its source.** UDP has no handshake: a packet with any source address produces a line. A UDP service hit stores `handshake = 0`, its excerpt ends with "UDP has no handshake, so the source address may be forged.", and the event has `unconfirmed: true`. `SourceConnected` and the "may be forged" check of a scan hit count only `service` hits with `handshake = 1`; a UDP line does not enter `sweep`. `response` holds that hit for the reviewer (it does not run the pre-approved rules) and counts it toward the hourly scan cap; Respond proposes nothing for that source unless the source has a nearby TCP connection. A new UDP hit has its own budget `maxUDPHitsPerHour` (20 per hour), not taken from the cap of 500/poll, 2,000/hour for real hits, so forged packets with rotating sources cannot silence real hits. `TestAForgedUDPDatagramNeverConfirmsItsSource`, `TestForgedUDPHasItsOwnHitBudget`, `TestHoneypotUnconfirmedHitNeverPreApproved` (response), `TestResponseIncidentRespondReadsTheTrapSource` (cmd/vedette). Real samples of every line: `testdata/opencanary-0.9.10-lines.jsonl` (the image's OpenCanary, each service touched once; only the address and time changed). This content matches the wording in the interface (`serviceHint`) and the S-HP-1 criteria. `TestEveryNewServiceMakesAHitWithoutThePassword`, `TestAUDPLineNamesTheTrapIPWithTheService`.
- **INV-2c** **No password is stored, and nothing derived from a password is stored.** `ParseLine` does not read `PASSWORD`, VNC's answer and guessed password, Redis `ARGS` (AUTH carries a password; only the command name is shown), MongoDB `auth_data`; the HTTP proxy's NTLM token (`TlRMTVNT…`, which can carry a challenge answer) does not enter the hit ("proxy login attempt (NTLM)"). The bait account (INV-10) fires on every login line that has an account name: SSH, HTTP/HTTPS, MSSQL, RDP, FTP, Telnet, MySQL, MongoDB, HTTP proxy. `TestABaitAccountFiresOnTheNewLogins`, `TestTheProxyNeverStoresAnNTLMToken`.
- **INV-2d** **The HTTPS trap's certificate** is made by `core` (`https.go`): self-signed, RSA 2048, CN and DNS name = the name of the first Trap IP handed to the host that has HTTPS (lowercase), O = its vendor, 5 years; remade when that name/vendor changes or 30 days remain. It is never signed by the box CA or the sensor CA, and the issuer is never Vedette. The key + certificate are one `core_secret` row (purpose `hp_https.key`, not exported); `hp_config` key `https` holds only the id; it is kept across a `core` restart. `core` writes **one** file `https.pem` (key then certificate, replaced with a single rename: the container never sees a new key with an old certificate) into `config/` only when a Trap IP with HTTPS exists, and removes it when no Trap IP has HTTPS any more and when the module is turned off (including the purge path, which runs `Disable`); the `core_secret` row is lost together with every row on purge (the container needs the key to serve TLS: it is the decoy's own key, nobody trusts it; it never goes into a log). `opencanary.conf` points both `https.certificate` and `https.key` to the image's `/etc/opencanaryd/https.pem`. `TestTheHTTPSTrapHasItsOwnCertificate`.
- **INV-2** Ports and protocols are fixed per service (`types.go` `serviceDefs`): smb 445, rdp 3389, ssh 22, mssql 1433, http 80, https 443, ftp 21, telnet 23, mysql 3306, mongodb 27017, redis 6379, vnc 5900, git 9418, httpproxy 8080, tcpbanner 25 (label "SMTP"), TCP; tftp 69, ntp 123, sip 5060, UDP. Only these 18 services are in the `HpService` enum; snmp, llmnr (scapy GPL-2, raw socket) and portscan (iptables) are never services and are always `false` in `opencanary.conf`. Every `<service>.port` key is written, on or off (OpenCanary refuses to start when two keys have the same port). One banner per service for the whole box, following the first Trap IP that has that service (`Look`, as in INV-25). `TestContract_INV2_FixedPorts`, `TestBannersFollowTheTrapIPThatDecides`.
- **INV-3** Connections from the Vedette scanner itself (the box's IP) are excluded: no `hp_hits` row, no alert, only `ignored_7d` goes up (counted exactly once, even when a batch write fails and is read again). Broadcast creates no hit.
- **INV-4** A test hit (`is_test=true`: test-hit, test-scan, tokens/{id}/test) does not enter `summary`, `hits_7d`, `last_hit_at`, publishes no event and opens no incident. It sends a **test alert** (`Config.TestAlert`, notify `SendTrapTest` wired in `cmd/vedette`): the alert a real hit would send, marked Test, to the alert channels that are on; what each channel did is a line in the hit's events and `test_alert` in the test's answer (absent on every other read). `TestTestTrapSendsATestAlertAndStaysATest`, `TestTestTrapSaysWhenNoAlertWouldArrive`. The day of `summary.today` and of `hp_ignored_day` is computed in the organisation's time zone (`Config.Location`, `orgtime.Source` wired in `cmd/vedette`); stored times are UTC.
- **INV-5** **Trap IP** (`hp_trap_ips`): the list of the box's trap addresses, one address per row. Each Trap IP has: a name (a NetBIOS-style host name, ≤ 15 characters, letters/digits/hyphen, not all digits, not starting or ending with a hyphen, 400 `bad_name`; not equal to the host name of any device in the store or to another Trap IP, 409 `name_in_use`), an address, a preset (`file_server|nas|printer|camera|linux|database|custom`, 400 `bad_preset`), a vendor for the MAC prefix (in the `presets.go` table, or none; 400 `bad_vendor`), ≥ 1 service among the services of INV-2, each at most once (400 `bad_services`), and on/off. The address must be: a valid IPv4 without a leading zero (400 `bad_ip`); inside the box's network range (`HpOverview.lan`), and not the network/broadcast address (400 `ip_outside_lan`); different from the box's IP (400 `ip_is_box`) and from the box's default gateway when the host reports it (`gatewayReporter`, 400 `ip_is_gateway`, checked after the form's fields, also when re-enabling; `TestTheGatewayIsNoTrapIP`); not equal to any device in the store or to another Trap IP (409 `ip_in_use`). `lan = null` → 400 `no_lan`. The checks run in the order of the form's fields (preset, vendor, name, address, services), and the mock checks in the same order. **Checked again after acceptance**: `desired` and `Overview` treat an address equal to the box's IP, outside the LAN range, or equal to a device as `conflict` (not handed to the host). At most 32 Trap IPs (host-api 6.6; 409 `limit_reached`), checked inside the write transaction together with address/name duplicates, so two parallel requests cannot both get through; a row beyond 32 in the DB is left out of the host with a reason. `TestContract_INV5_IPValidation`, `TestTrapIPsStayWithinTheHostLimit`, `TestAddTrapIPLimitHoldsUnderConcurrency`.
- **INV-6b** **A device carrying the decoy's own MAC is not a device.** `hp_trap_ips.mac` remembers the MAC the host gave the address (`rememberMACs` on every `Apply`, from `DecoyLinks`; changing the IP or vendor forgets it); `deviceAt` ignores a store row whose MAC is a decoy MAC (held or remembered), so a "ghost" row that the store creates from the Trap IP's own frames never keeps the Trap IP in `conflict`, even after the address leaves the host. A row with a different MAC is still a `conflict`. `TestADeviceWithTheDecoysOwnMACIsNoConflict`.
- **INV-6** Enabling a Trap IP (`PATCH /honeypot/trap-ips/{id}` `enabled=true`) whose address now belongs to a device, to the box, or is outside the LAN → 409/400 with the same codes as INV-5, and it is not enabled. A Trap IP that is on, when a newly stored device takes the address → `state = conflict`, not listening, with `device_id`/`device_name` pointing at that device.
- **INV-7** `TrapIP.state` ∈ {off, listening, conflict, starting, stopping, failed} (S-HP-1; the state is what the host reports, not a switch). The `Trap.state` of a service is the best state (`stateRank`) among the enabled Trap IPs that have that service (`stopping` when no enabled Trap IP has it any more but the container still runs with it, before `Apply` finishes); `Overview.Problem` is present only when there is an address to hand to the host that the host/container cannot use and the state is not yet `starting`. `listening` ⇔ enabled ∧ no conflict ∧ the `honeypot` container has been **started** with a configuration that has that service on a host that is an appliance ∧ the host **confirms** it holds the IP (`hostCache.placed`: the host accepted it in this `Apply`, or accepted it in an earlier `Apply` and has not refused it since; an IP present only in the `applied` record, such as after an unclear result or after a `core` restart, does not count). It does not mean the port has been probed: the box never connects into its own trap (INV-1, FORBID-3), so `listening` is "the IP is handed over and the container is on", not "the port is open". `conflict` when the address has a problem (a device in the store, the box's IP, outside the LAN: `ipProblem`, not handed to the host) or the host refuses it **because of the address itself** (codes `ip_*`, `mac_in_use`, `limit_reached`); when the host refuses because of its own failure (`honeypot.ErrHostFailed`: `decoy_failed`, the host's namespace/state unusable, an ARP probe error, an unknown code) the Trap IP is `failed`, never `conflict`, with the reason in `TrapIP.reason`. `starting` = enabled but `Apply` has not yet answered the change (`kickGen > doneGen`, including while `container.start` is waiting), or the most recent `Apply` stopped only because the host was busy (`honeypot.ErrHostBusy`: `busy`, `rate_limited`, `pending_confirm`, `net_pending_confirm`, `install_in_progress`) at `container.start` or at the first IP when no IP has been handed over yet, and `startBusyFor` = 5 minutes have not passed since the first busy answer (`Config.Clock`, computed at read time; there is no `Overview.Problem` then); after 5 minutes it is `failed` with the reason "the host has been busy … for more than 5 minutes"; if `container.start` really fails while waiting it is `failed` at once and a later busy answer does not hide it; a `Status` read that gets 429/busy keeps the previous state; when the host accepts the command, answers definitively (not an appliance, not answering), or the module is turned off, the waiting ends (after an update the host is busy for ~2 minutes; `TestBusyHostStartReadsStartingForABoundedTime`, `TestBusyHostFirstAddressReadsStarting`); `stopping` = switched off but the host's configuration still has that service, before `Apply` finishes; `failed` = enabled, no conflict, `Apply` has run but it is not listening (the host does not answer, not an appliance, the container does not come up, the host could not build the IP, **the host has not yet confirmed it holds the IP**). A container that runs while the host has not confirmed it holds the IP of a Trap IP (an unclear result) → `failed`, with the reason "the host has not confirmed it holds the address yet; the box asks again". The reason is in `TrapIP.reason` (with `device_id`/`device_name` when a store device is at the address); the full list is in `Service.TrapConflicts()` and the log. `TestListeningNeedsTheHostToHoldTheAddress`.
- **INV-8** The source device (`src_asset_id`, `src_name`) is looked up from the store at read time; `src_name = null` ⇔ the IP is not in the store. A stored `hp_hits` row also has `source_ip` = `src_ip` (for `response` to read through an interface, see IMPACT).
- **INV-9a** `SourceConnected(ctx, src, at, window)`: is there a real (non-test) `service` hit **over TCP** (`handshake = 1`; a UDP hit never, INV-2e) from `src` within `at ± window`; read only. Response uses it to propose blocking the source of a `scan` hit or a UDP hit only when that source has completed a connection (a scan from attempts without a handshake and UDP packets can carry a forged address).
- **INV-9** `GET /honeypot/hits` returns newest first; `HitDetail.events` are the log events within `window_minutes` (60) around the hit; `mark=true` on exactly one line is the hit: the first line stored with the hit; later connections merged into the hit (INV-17) are not marked (`TestOnlyTheHitsOwnLineIsMarked`).
- **INV-10** `Token.password` exists only when `type=credential`, otherwise `null` (also when a stored password cannot be decrypted: the token is still listed, the error goes to the log, and the other tokens are not hidden). `HitKind=token` is produced only by a token that still exists; deleting a token → copies already planted no longer produce hits. **A bait password is shown in full only to operator and admin (secret hygiene per `security.md`)**: a viewer sees `••••••••` + the last 4 characters (no tail if shorter than 8), a missing identity → 401, an unknown role is masked. This does not hide the canary set from a viewer: the endpoint is still viewer. `TestTokenPasswordIsMaskedForAViewer`. **The bait account name is generated by the system** (`svc_` + 6 random letters), not taken from the token's display name, so a common-password guess against `admin` does not fire a token; only a list of stolen accounts fires it.
- **INV-11** Suggestions (`TrapSuggestion`) include only device kinds that really exist in the store; preset ∈ {file_server, nas, printer, camera, linux, database}. Presets and vendors are data (`presets.go` = `presets.ts`, `TestPresetsMatchTheGUI`); each vendor's OUI belongs to that vendor in the OUI table (`TestVendorOUIsBelongToTheVendor`).
- **INV-12** `excerpt`, `label`, `src_*` come from whoever touched the trap: untrusted (SYS-6): cut in length, not interpreted as a command, shown as text; control characters (Cc → space) and invisible/reversing characters (Cf: bidi, zero-width, BOM, soft hyphen, Unicode tag characters used to inject invisible commands into `ai`; Zl, Zp) are removed, by the same rule as `sensor-active/xml.go` and `sensor-passive/decode.go`; and variation selectors U+FE00–FE0F, U+E0100–E01EF (every Default_Ignorable_Code_Point, the table `observe.Ignorable` shared with `core/auth`). `TestHostileTextLosesVariationSelectors`.
- **INV-12b** The `src_port`/`dst_port` of a log line can arrive as a number **or a string** (OpenCanary's `smb` module writes `"src_port": "-1"`); `ParseLine` reads both, and every value that is not a plain decimal number in 1-65535 (signs, exponents, fractions, bool, null, too long, out of range) becomes 0 without rejecting the whole line; whitespace at both ends is removed. The image's real log line is the sample of `TestParseLineSMBPortsAsStrings`.
- **INV-13** Every mutation (config, trap on/off, decoy, token) writes `core_audit` (SYS-3).
- **INV-14** Nothing from the module leaves the box except through channels the customer configured (`notify` alerts, log export, SIEM): the box sends no anonymous signal (PRIVACY flow 2: nothing is sent) and the module imports no network package (INV-1).
- **INV-15** **Two directories** under `-honeypot-dir`: `config/` (`Config.ConfigDir`) belongs to `core`, and the container mounts it **read-only**; `log/` (`Config.LogDir`) is writable by the container, and `core` only reads it. `core` writes `opencanary.conf`, `honeytokens.json` through `os.OpenRoot(ConfigDir)` + a temporary `O_EXCL` file + rename, and **never reads back** anything in `config/` (it compares against the in-memory hash of the previous write). A failed file write (full disk, permissions) does **not** block host reconciliation: an IP that is no longer wanted is still removed, and the container stops when no trap is enabled (FORBID-1, POST-5); only adding IPs and starting the container wait for the configuration to be written. `TestApplyNeverReadsWhatIsInTheConfigFolder`, `TestApplyReconcilesTheHostWhenTheFilesCannotBeWritten`.
- **INV-16** **Reading the log never blocks, is never redirected, and is never overloaded.** `opencanary.jsonl` is opened through `os.OpenRoot(LogDir)` with `O_RDONLY|O_NOFOLLOW|O_NONBLOCK`, and `fstat` must show a regular file, otherwise it is skipped and counted (`Stats.NotRegular`, logged at most once a minute); a symlink is rejected. More than 64 MiB behind → jump to the end, count `Stats.SkippedBytes`, and drop the half-read line. The log produced by the container is rotated (`RotatingFileHandler`, 10 MiB × 3). Each batch of lines is stored **together with the read position in one transaction**, and the batch's events are published right after the commit: a failed batch does not lose the alerts of earlier batches and does not publish twice. `TestTailFIFOAtTheLogNameDoesNotBlockPoll`, `TestTailRefusesASymlinkAtTheLogName`, `TestTailJumpsToTheEndWhenFarBehind`, `TestIngestFailedBatchKeepsTheAlertsOfTheBatchesBeforeIt`.
- **INV-17** **Alert flood control.** One hit per (source IP, service, trap IP) per 10-minute window; a later connection in the window raises `conn_count` and adds a line to that hit's `events` (at most 20), adds no row and publishes no event, while the hit's incident is open: once that incident was resolved after the hit, by a person or by Vedette (`Config.Incidents`, notify `ResolvedSince`, asked once a batch per window), the connection starts a new hit that publishes `honeypot.hit.created` (notify opens a new incident), and the old hit gives up the window's `conn_key` so the later connections of the window join the new one (`TestAConnectionAfterTheHitsIncidentWasResolvedIsANewHit`). A line is new when the time or the text differs: a second SMB visit (a Samba line has no source port, the same text "share opened") is a line and one more connection; the same log line read again (a failed batch read again) changes nothing; a scan hit compares by text (one line per Trap IP touched) (`TestASecondSMBVisitIsALineOfTheHit`). Limit: times are stored to the millisecond, so when Samba writes two identical "share opened" lines for **one** session in two different milliseconds, `conn_count` rises by two (only a displayed number, adding no hit or alert). At most 500 new hits per poll and 2,000 per clock hour; beyond that `Stats.Suppressed` is counted and logged (at most once a minute), and nothing is stored or published. At most 200 lines from one source are processed per poll (`Stats.Flooded`). `TestIngestOneSourceStaysOneHitAcrossPolls`, `TestIngestCapsNewHitsPerPollAndPerHour`.
- **INV-18** **A line that a connection to a trap could not have produced is dropped and counted** (`Stats.Implausible`), and does not become a hit: the source is loopback, a trap IP, or the LAN's network address; the destination is not a trap IP currently handed to the host; the trap of that service is off; the time is older than 24 hours or more than 5 minutes in the future. (A source that is the box's IP is still INV-3.) `TestIngestDropsLinesNoConnectionToATrapCouldMake`.
- **INV-19b** The store treats as the box's own both `TrapIPAddrs` (the addresses of every enabled Trap IP while the module is on, whether handed to the host or not) and `ExpectedMACs` (for each enabled Trap IP: the MAC the host gave in the most recent `Apply`, the remembered MAC `hp_trap_ips.mac`, or `""` while it is being handed to the host, for at most 2 minutes: on every handover where the previous `Apply` has not confirmed that the host holds it with a MAC of the right vendor, even when an old MAC is known, because remove-then-add produces a new MAC; dropped at once when the host refuses; wired into `inventory.Config.BoxDecoyMACs`, which **wins over the host answer the store remembers**, which may be older than a decoy that was just rebuilt, `TestHoneypotARemadeDecoyIsNoDeviceBeforeTheCacheCatchesUp`): at a Trap IP address, a different MAC is a real machine. A device that `ForgetBoxOwned` deletes is reported like any device deletion, so `notify` removes it from the still-open "new device" incidents. Every `Apply` calls the store's `ForgetBoxOwned(ctx, TrapIPSince)` (`ghostForgetter`) before reading the state: only a row first seen after the Trap IP was enabled (`hp_trap_ips.enabled_at`, set on add, re-enable, address change; not earlier than the time the module was enabled) is deleted, so a "ghost" row does not keep the Trap IP in `conflict` while a real machine seen before is kept. The decoy link turns IPv6 off before coming up (host), so there is no IPv6 frame carrying a decoy MAC without an IPv4. `TestHoneypotTrapIPAddressesAndDevices` (cmd/vedette).
- **INV-19** **Trap IPs belong to the box** (open question 2): `Service.DecoyIPs(ctx)` returns the IPs handed to the host in the most recent `Apply` (the addresses of enabled Trap IPs that the host accepted; read from the `applied` record, correct right after a restart; an address that has a device or was refused by the host is not in it). `cmd/vedette` wires it into `inventory.Config.BoxOwnedIPs`: the store **never creates or updates a device** from an observation with that IP (an answer to ARP from the trap itself; counted as `BoxOwnedSkipped`), and `ProtectedIPs` (hence also `sensor-active`) lists them. `TestDecoyIPsAreTheAddressesTheHostHolds`, `TestBoxOwnedAddressIsNoDevice` (inventory), `TestHoneypotDecoyAddressesAreNotDevices` (cmd/vedette).

- **INV-21** **Each Trap IP answers only its own services.** OpenCanary is still one process listening on every address of the container and runs the union of the services of the enabled Trap IPs; `Apply` hands the host a `DecoySpec{OUI, Ports}` for each address (the fixed port and protocol of each service, INV-2: `udp` for TFTP/NTP/SIP; `TestTheHostGetsUDPPortsForTheUDPServices`) and the host keeps each address to exactly that list with the namespace's nft ruleset (host-api 6.6: any other port → TCP RST, UDP → port unreachable, like a real machine with the port closed). The adapter sends `ports` only when the host's `/v1/info` lists `decoy_ip.set_ports` (`KeepsPorts`); an older host → not sent, every address answers every running service, a listening Trap IP has a `reason` that says so and `open_services` = every running service (`openPortsNote`). A log line to a service that the destination Trap IP does not have cannot be real (INV-18) unless the host is old. `TestTheHostGetsTheVendorPrefixAndOnlyTheTrapIPsPorts`, `TestHoneypotHostSendsEachTrapIPItsPortsAndPrefix`, `TestHoneypotHostSendsNoPortsToAnOlderHost` (cmd/vedette).
- **INV-22** (S-HP-1) **Back-off when the host refuses an address**: an address refused with `ErrRefused` is asked again at the next `Apply` up to the 3rd time, and from then on every 10 minutes (`refuseBackoff`, clock `Config.Clock`); changing the set of wanted IPs/services resets it. During the back-off the reason from last time is still shown, with no host write, no audit and no log. `TestRefusedAddressBacksOff`.
- **INV-23** (S-HP-1) **A Trap IP says where it lives.** `mac` and `attachment` (`kind = macvlan`, `link = vdh<8 hex of the IP>`, `parent` = the management card) come from the optional interface `linkReporter.DecoyLinks` of `Host` (the `cmd/vedette` adapter reads `state/net`, in the same read as `held`; `fakeHost` does not need it), only for addresses the host has confirmed it holds; null when unknown. `mac_vendor` = the vendor that the OUI table (`content/oui`) records for the MAC prefix (what a scanner on the LAN sees), null for a locally administered MAC. `open_services` = the services the address is answering (its own when it listens; every running service for an old host; empty when not listening). `last_hit_at` = the most recent real hit (kind `service`) on that address. `device_id`/`device_name` = the store device at that address (when present the Trap IP is `conflict`). `TrapIPsResponse.spare_checked=false` when the store has no device in the network range yet: the GUI says it is only a guess. `spare_ips` are only addresses the store has not seen; the real check is the host's ARP probe at `decoy_ip.add`. `TestTrapIPShowsWhereItLives`.
- **INV-24** (S-HP-2) **A scan across the Trap IPs.** A source that touches two or more Trap IPs within 1 minute (`sweepWindow`, by the time of the log line; a real service, not a test hit, not the box) → **one** hit `kind=scan` for that source per 10-minute window (`conn_key` "sweep"): the label "Scan across the Trap IPs", `trap_ip` = the addresses, `trap_hostname` = the names of the Trap IPs, and the excerpt lists "NAME (IP)"; a Trap IP touched later in that window goes into the same hit (adds a line, `conn_count`, and goes into both columns `trap_ip`/`trap_hostname`), with no new hit/event. Each touch is still its own `service` hit. **An attempt that did not become a connection** (`nmap -sS` leaves no log line): `PollTouches` every 15 seconds reads the new TCP/UDP attempts to decoys that the host recorded (`touchReporter.Touches`, host `GET /v1/state/hp-touches`, time = the first attempt) and feeds them only into `sweep` (one attempt is not a hit; a source that is the box, a Trap IP, loopback, a network/broadcast address, or a destination that is not a Trap IP handed to the host is dropped; an attempt already fed in is not fed again for the 2 minutes the host keeps it; module off → the host is not asked). An old host (404) or a host that is not recording (`recording: false`, one warning log) → none. A scan hit from attempts has **its own budget** of 20 new hits per hour (`maxTouchScansPerHour`), never taken from the 2,000/hour cap for real hits, and its excerpt says "The handshake was not completed, so the source address may be forged." (the source of a forged SYN is possible); this sentence is present only when that source has **no** real `service` hit within 1 hour before or after (`connectedWindow`, the same rule as response's `SourceConnected`), and a real connection from that source removes this sentence from every scan hit of its own within 1 hour, whether the connection came before or after (read from `hp_hits`, so it stays correct after a `core` restart, `TestARealConnectionDropsTheForgedNote`, `TestAConnectionBeforeTheSweepKeepsTheForgedNoteOff`, `TestAConnectionNearTheSweepDecidesTheForgedNote`). When the source is forged with the address of a machine that has just connected for real, the scan hit does not have this sentence; that machine already has its own Critical incident. Every time the host reloads the ruleset (a Trap IP is added/edited/removed) the `touched` set is empty: a scan in progress at that moment may not become an alert. Limits: FIN/NULL/Xmas scans are not recorded (conntrack `invalid`), IPv6 is not recorded. A forged source can use up the 20 hits/hour of the attempts budget, and then a real SYN-only scan in that hour does not become a hit (a scan with real connections still does). `TestHostRecordedAttemptsAreASweep`, `TestAttemptScansHaveTheirOwnBudget`, `TestHoneypotHostReadsTheAttemptsToTheDecoys` (cmd/vedette). The who-touched-what memory is in RAM only (`Service.touches`, cap 4096 sources): a scan cut in two by a `core` restart does not become one. `notify` opens **one** High incident "<src> scanned the Trap IPs" per source while it is open (target `scan`); each touch is still a Critical incident. `TestTouchingTwoTrapIPsWithinAMinuteIsOneScan`, `TestNoScanWithoutTwoTrapIPsInAMinute`.
- **INV-25** **The limit of a box that tells the truth**: one NetBIOS name for the SMB share (`smb_name`: the name of the first Trap IP (in creation order) handed to the host that has SMB, written into `honeytokens.json` `netbios_name` and put into Samba by `init.py`) and one HTTP login page (`http_page`: `nas` when the first Trap IP with HTTP is a NAS, otherwise `login`). A different name is only a label; the GUI says so in the form and the Services tab. A hit carries the name of the Trap IP that was touched (`trap_hostname`).
- **INV-20** **The `honeypot` container's network is the `vedette-hp` namespace owned by `vedette-host`.** The Quadlet unit has `Network=ns:/run/netns/vedette-hp` and nothing else: no `vedette-int` bridge, no host network, no path to `core` (hits travel through a file). Each Trap IP is its own macvlan link with **its own MAC** (by default a locally administered MAC generated by HMAC over the IP and the install's key; the optional parameter `oui` of `decoy_ip.add` makes the MAC carry the vendor's prefix, `host-api.md` §6.6), so the container sees a new IP without needing a restart. The namespace's sysctls are set only by the host: the unit loads `ContainersConfModule=/usr/lib/vedette/honeypot-containers.conf` (`default_sysctls = [{append=false}]`), because with `UserNS=auto` crun may not write the sysctls of a namespace that belongs to the host, and the distribution default (`net.ipv4.ping_group_range`, Ubuntu 26.04) stops the container from starting. The namespace has `ip_unprivileged_port_start=0` (a per-namespace sysctl), so the container runs with `DropCapability=ALL` and needs no `NET_BIND_SERVICE` for the low ports of INV-2; plus the egress-blocking ruleset of INV-1. The unit keeps `UserNS=auto`; `podman inspect` reports `HostConfig.UsernsMode` = `private` for it (inspect has no value "auto"; the automatically allocated range appears in `HostConfig.IDMappings`; checked on Podman 5.7.0). The namespace is recreated by the host on every boot before the honeypot unit comes up (`vedette-host.service` `Type=notify`). macvlan does not work over Wi-Fi and is blocked by the MAC policy of a VMware/Hyper-V vSwitch (the trap is silent): the GUI must say so clearly (left for later, needs a story).

## Preconditions (before calling)
- **PRE-1** `POST /honeypot/test-hit`: an enabled Trap IP has that service (409 `trap_off`) and its address has no conflict (409 `ip_in_use`); a test hit records the name and address of that Trap IP.
- **PRE-2** `POST`/`PUT`/`PATCH`/`DELETE /honeypot/trap-ips*`: admin role; input goes through the schema before the service (SYS-2; an unknown vendor/preset is rejected by the schema as `invalid` before reaching `bad_vendor`/`bad_preset`).
- **PRE-3** The `honeypot` module is on, and `inventory` is on.

## Postconditions (after completion)
- **POST-1** The first real connection from a source into a trap that is `listening` within a 10-minute window: produces exactly one `hp_hits` (kind=service), publishes `honeypot.hit.created`, and within ≤ 60 s `notify` has an alert with the source IP, the source device, and 1 hour of events around it (S-HP-1). Later connections from the same source/service/trap IP in that window go into the same hit (INV-17).
- **POST-2** Touching a honey token / a scan across the Trap IPs (INV-24): produces a hit of kind=token / scan with a `label` that names what was touched (S-HP-2).
- **POST-3** A real hit is the source of the `honeypot` trigger in `response`: fields `source_ip`, `source_device`, `decoy`, `kind`.
- **POST-4** Creating a token of type `file` with `ext` (docx|xlsx) returns `value` as the file name to plant; `plant_at` is written by the box owner. A token of type `url`: `value` = `Config.BoxURL()` (the Box address, asked at creation time) + `/t/<10 characters>`; without it `https://<the store's box IP>:8443/t/…`; if neither is known → 409 `no_box_address`, nothing is written. **Never** use the box's machine name (usually `vedette`, which does not resolve). **A link that really fires**: `cmd/vedette` answers `/t/{id}` and `/t/{id}/{rest...}` (no session, no CSRF, behind the Host allowlist; punctuation stuck after the id is dropped) and calls `OpenURLToken(ctx, URLTokenOpen)`: the token is found by **path** (`value` ends with `/t/<id>`, so changing the Box address does not kill old links), only a URL token that still exists (INV-10); module off, a malformed id, or the box itself (loopback, the box's IP in the store per INV-3, on an appliance every address of the machine including the bridge gateway) → nothing is written. Container-only build: an open from the machine's address (a port proxy) records the source `unknown (container-only port proxy)` (`src_ip` stored as `unknown`); an IPv6 source stores `src_ip` as `unknown`, while the event and the incident carry the address. The write is separated from the request (5 s) and publishes the event with a fresh budget (30 s), with no limit on waiting for the request's writer. The hit goes through the same `upsert` as a log line (kind `token`, label `URL token <name>`, source IP, time, User-Agent sanitised to ≤ 200 characters per INV-12, one hit per token/source/10 minutes, an hourly cap, `honeypot.hit.created` published after the commit). The answer is always a text/plain `404 page not found` for every `/t/<x>` (a real token, an unknown id, a malformed one, a deleted one, module off, over the limit), never the SPA; the **first** open of a token/source/10-minute window is always recorded (the hourly cap and window merging have already blocked it); only a **repeated** open asks the limit of 10 per address per minute (`server.AddrLimiter`), so made-up ids do not silence a real link. `TestURLTokenOpenFiresThroughTheRouter`, `TestURLTokenOpenWhileTheModuleIsOff`, `TestURLTokenOpenIsLimitedPerAddress`, `TestURLTokenFakeIDsDoNotSilenceTheLink`, `TestURLTokenOpenWithATailFires`, `TestURLTokenOpenFromTheBoxItselfAndFromIPv6`, `TestURLTokenOpenThroughAContainerOnlyPortProxy`, `TestURLTokenOpenOutlivesTheRequest` (cmd/vedette). **A DNS token cannot fire**: the box has no DNS server and the project has no server; the GUI does not offer this type, and `AddToken` returns 409 `dns_unavailable` for `type=dns` and writes nothing (`TestContract_INV10_POST2_POST4_Tokens`); a DNS token created earlier can still be read (`Tokens`, `DeleteToken`). Token presets exist only in the interface: the API accepts fields, not presets.
- **POST-5** Deleting or disabling a Trap IP → the next `Apply` removes the address from the host (`decoy_ip.remove`) and it stops answering; changing services → `decoy_ip.set_ports`; changing the vendor → remove then add again (a new MAC); deleting a token → alerts stop; old `hp_hits` are not deleted.

## Forbidden (never)
- **FORBID-1** Listening on the box's management IP or on the IP of a device in the store.
- **FORBID-2** Returning the content of a real service (real files, the box's real banner, the box's real certificate); opening ports other than the ports of INV-2 on a trap IP.
- **FORBID-3** Calling network/OS commands directly; Trap IP addresses are built only through `vedette-host` (SYS-1).
- **FORBID-4** Sending the module's hits, IPs or device names to the project or a third party (INV-14).
- **FORBID-5** An endpoint that edits/deletes `hp_hits` (a hit is evidence).

## Events
- **Emits**: `honeypot.hit.created` (a 3-part name per `core/events`). Only for a **new** real hit (not for every connection), right after the commit of the batch that holds it; a test hit publishes nothing (INV-4; its test alert goes through `Config.TestAlert`, not the bus). Fields: `id, ts, kind, service, port, src_ip, label, decoy, src_asset_id, src_name`, and `unconfirmed` (only when `true`: a UDP service hit, INV-2e) (`decoy` = the name of the thing touched: the Trap IP's name, the token's label, the names of the Trap IPs that a scan touched (INV-24); the trap IP when the name is empty. `src_asset_id`/`src_name` = the inventory device at the source IP when the hit was stored, empty when there is none; `notify` records that device on the incident). Receivers: `notify`, `response`, `logs` (SIEM) and `inventory` (`src_asset_id` → `EarnReview`, wired in `cmd/vedette/wiring.go`).
- **Receives**: `inventory.asset.discovered|updated` (a hint: re-apply the state to the host; a new device that equals the address of a Trap IP → `conflict`). It reads the store (`inventory`) through the `Inventory` port to look up the source and check for duplicate IPs.
- **Entry path of a hit**: the only exception is the URL token: `cmd/vedette` answers `/t/{id}` on core's HTTPS port and calls `OpenURLToken` (POST-4); the container has no path to core. Everything else: the JSON-lines file `opencanary.jsonl` in `log/` under `-honeypot-dir`, which core only reads; no network port into core. Core writes the configuration into `config/` (mounted read-only by the container), INV-15.

## When the module is off (SYS-5)
No `/honeypot*` routes, the `honeypot` container stops, the Trap IP addresses are removed through `vedette-host`, and no port is open. **Convergence:** stopping/removing is called by `core/modreg.OffGuard` through `Service.EnsureOff` at startup when the module is off and after every disable, retried at 10 s, 30 s, 2 minutes, then every 10 minutes until the host confirms (`Disable` returns nil only when both stopping the container and removing the IPs succeed, or the host is not an appliance, the `applied` record is empty and the container is not running; a host that does not answer while the record still has IPs is an error and is retried; `Apply` and teardown use one lock, `Apply` exits early when the module is off, and `applied` is written before `AddDecoyIP` with a context that is not cancelled; otherwise the host state is "turning off"); it is not a job of the module. `TestEnsureOffConvergesOnlyWhenTheHostConfirms`, `TestEnsureOffAfterARestartRemovesWhatTheLastRunLeft`. The `hp_*` data is kept. The `honeypot` trigger in `response` no longer gets events; the UI shows "is off" on the Incidents/Rules pages (S-CORE-1).

## The `Host` adapter on the `core` side (`cmd/vedette/honeypothost.go`)
With `-host-socket` → `honeypotHost` over `host/client`; without it (dev, a bare box) → `notAnAppliance` (no trap listens, reason "not an appliance"). The `Host` port has `StartContainer(ctx, restart bool)`.
- `Status`: `GET /v1/state/containers`; the `honeypot` service has a unit (`installed`) → `Available`, `Running` = `unit_state` `active`. A missing socket (`ErrUnreachable` + `fs.ErrNotExist`) → `Available=false`, reason "not an appliance"; a host that does not answer (`ErrUnreachable`/`ErrDenied`) → `Available=false`, "not answering" (not an error); the unit not installed → `Available=false`, "not installed". Any other host error → error.
- **`AddDecoyIP(ctx, ip, spec)` sends only the difference**. `Service.syncIPs` calls it for **every** wanted IP on every `Apply`; the host accepts 10 write commands/minute. The adapter reads `decoys` of `GET /v1/state/net` (MAC, `ports`; remembered for 20 seconds): not there yet → `decoy_ip.add {ip, oui, ports}`; there but the MAC does not carry the wanted prefix (the vendor's OUI, or locally administered when no vendor) → `decoy_ip.remove` then `add`; there but `ports` differ → `decoy_ip.set_ports` (`not_a_decoy` → add); matching → no write. `duplicate_decoy` also counts as success. `ports` is sent only when `commands[]` of `/v1/info` has `decoy_ip.set_ports` (`KeepsPorts`, re-read every 5 minutes; a failed read → keep the previous answer). If it has never been read → **no address is added** (an add without `ports` would answer every running service): an unclear result, and the next `Apply` asks again; an address that already exists is left as it is. `DecoyLinks` returns the MAC, the link `vdh<8 hex>` and the management card (`config.mgmt.iface`, or the card with role `management`).
- `RemoveDecoyIP` → `decoy_ip.remove` (host: an IP that is not there → success).
- `StartContainer(ctx, restart)` → `container.start {service: "honeypot", restart}`, no `version`. `Service` sets `restart=true` when a file `opencanary.conf`/`honeytokens.json` has been written since the start that the host confirmed (an in-memory flag, INV-15; so the first `Apply` after each core start restarts the container once); a failed start keeps the flag.
- `StopContainer` → `container.stop {service: "honeypot", persist: true}`.
- **Result: refused or unclear.** Only a real answer of the host (4xx, a run `failed`/`refused` with the command's code) wraps `honeypot.ErrRefused`. A run cut off midway (`host_restarted`, `host_shutting_down`, `timeout`, `command_failed`, `internal`, or ending with no result) may have completed, so it is **unclear**; `pending_confirm`, `net_pending_confirm`, `install_in_progress` mean the host is busy. `syncIPs` removes an IP from the `applied` record, and shows `conflict`, only when `errors.Is(err, ErrRefused)`; a refusal that is not because of the address (every code other than `ip_not_in_mgmt_subnet`, `ip_is_*`, `ip_in_use`, `mac_in_use`, `limit_reached`) also wraps `ErrHostFailed`: it is still removed from the record but the Trap IP shows `failed`, not `conflict` (INV-7; `TestHoneypotHostRefusalsArePlain`). Every other error (host busy, 429, a lost answer, a timeout, a cancelled ctx) is an **unclear result**: the IP stays in the record (teardown will remove it), no `conflict`, and this `Apply` asks about no further IP. For the decision to run the container, an IP already in the record still counts (a slow answer does not stop the trap); for the displayed state only IPs the host has confirmed count (INV-7: this `Apply`, or an earlier `Apply` that has not refused it), so consecutive unclear results or one after a restart is `failed` "the host has not confirmed…", not `listening`. `TestListeningAfterARestartWaitsForTheHost`. Tests: `TestApplyTreatsOnlyARefusalAsARefusal`, `TestApplyStopsAskingAfterAnUnknownOutcome`, `TestHoneypotUnknownOutcomeIsNotForgottenByTheTeardown`.
- **Host cost per `Apply`** (host: 60 requests and 10 write commands per minute for all of `core`, one write command at a time; the `Run` loop re-applies every `applyEvery` = 1 minute, or earlier when the store changes): in steady state 2 reads (`state/containers`, and `state/net` read once and then remembered for 20 seconds), **no write command** (an IP that already exists is skipped, a container that is running with no `restart` gets no `container.start`; a container already stopped by a successful `container.stop` in this process and that `Status` has just seen not running gets no repeated `container.stop`; only when the unit is `inactive`/`failed`, not when `other`/`unknown`). A `container.start` (with `restart`) is not cut by `Apply`'s 2-minute cap: it may hold the `Run` loop up to `runFor` = 5 minutes, during which the log is not read (the price of not restarting halfway). Each write command adds 3 requests: the command, the event stream (SSE, as in `core`'s `waitRunTo`), and one read of the run (retried after 2 seconds if the run is not finished, up to 5 minutes). A busy host (`busy`, `rate_limited`) → `errHostBusy` **at once**, with no waiting and no spinning; the next `Apply` retries. Each `Apply` has a time budget for the host (`hostBudget`, 2 minutes) so a slow host does not block log reading.
- `actor: "system"`, one UUID request id per command. A host refusal becomes a clear sentence with a code (`ip_not_in_mgmt_subnet`, `ip_in_use`…), and the host's own words go only to the log (the adapter's warning is limited to once a minute per code).
- **Turning off when the unit is absent**: when `Status` has no error but `Available=false` (unit not installed), `disable` still removes the IPs in the `applied` record with `decoy_ip.remove`; it is finished only when all are removed and the container is not running. A host that does not answer → removing also fails → not finished, and `OffGuard` retries.

## Limits (inherent, stated plainly)
- The `honeypot` container faces attackers and can be taken over: it can write anything into `log/`. INV-16..18 prevent hanging, redirecting, overflowing or injecting absurd lines; **a sufficiently plausible forged line** (the source is any IP outside the exclusion list, the destination is a trap IP, on time) still becomes a hit. At most 500 new hits per poll and 2,000 per hour limit the damage and do not remove it.
- For that reason `response` **must never act on the box's IP, the gateway, DNS or the trap IPs** based on this hit: the never-touch list (`response` INV-10: gateway, DNS, domain controller, the box itself, the management IP) applies to the hit's `source_ip`, and the trap IPs (`Service.DecoyIPs`) must be in that list; a forged hit can set the source to any address.
- The 24-hour window: if `core` is stopped for more than 24 hours while the container keeps writing, older lines are dropped when read again (counted as `Implausible`); and beyond 64 MiB unread, the unread part is jumped over (`SkippedBytes`).
- Disk limit for `log/`: `log/` is the tmpfs volume `vedette-hp-log` of at most 64 MiB and 1024 files (the host writes `.volume`, DEPLOYMENT §6.1), not on the filesystem of `vedette.db`; if someone who has taken over the container reaches the cap, `ENOSPC` occurs inside the container. `RotatingFileHandler` bounds OpenCanary's log file (≈ 40 MiB including rotated copies). The log is lost when `core` and `honeypot` stop together (a reboot, or honeypot restarting while `core` is stopped: every unread line is lost); the reader (INV-16) starts again when the file is replaced or truncated.
