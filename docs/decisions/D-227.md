| D-227 | **A bad connection the firewall blocked is an attempt, said as one (S-LOG-4, logs L4, closes the deferred line of `feat-logs-l4-ioc.md` on "connected to" for `action=blocked`).** (1) **Where it is read**: a key=value profile may name `conn_blocked` (key → values, like `conn_when`): the connection of a line is blocked only when each key listed is written exactly once outside quotes (the D-213 site rule; a second `action` makes the line a line without a connection, as for every connection field) and holds one of the values. FortiGate: `action` ∈ {`deny`, `dropped`, `blocked`, `block`, `reset`} (traffic deny, IPS drop/reset, web-filter blocked, DNS-filter block); `accept`, `close`, `timeout`, `client-rst`, `server-rst`, `pass`, `passthrough`, `monitored`, `detected` went through. A template profile has no `conn_blocked`: a MikroTik firewall line carries the chain (`forward`, `input`), not the rule's action (a `log-prefix` is free text the owner chose), so it stays "connected to". A line the format does not settle is **not** blocked: never guess "blocked" (an overstated "blocked" makes a person stand down from a real infection). In a batch the pair is blocked only when every line of it was. (2) **Stored**: `logs_ioc_hits.blocked` (0/1, volume migration 0006, add-only D-151: an older binary writes 0), `IocHit.blocked` in the API, the event `logs.ioc_hit.detected` and the `known_bad` export. (3) **Said**: `logs.bad_address.detected` of a blocked hit: title "<device> tried to reach <dest> (blocked by <log source name>), which a threat feed lists", what "… tried to reach <dest> (<kind>; blocked by <source>) …", and an action that still asks what on the device made the request; an allowed hit keeps "connected to". The Logs digest list marks the row **Blocked** (with a hint that the line records an attempt) and the section says "connected to, or tried to reach". Severity is unchanged: a device that tries to reach a listed command-and-control address is the infected-host signal whether or not the firewall stopped it. (4) **Dedupe**: a blocked hit is a repeat of any hit of the pair in 24 hours; a hit that went through is a repeat only of one that went through, so a blocked attempt never hides the connection that follows it for 24 hours. (5) Not changed: response reads no `blocked` yet (its decoder ignores the field). The SIEM `bad_conn` record carries it since fix/logs-hagezi-subdomains-mlee: syslog/JSON `blocked` "true"/"false", CEF `act=blocked` only when true (CEF `act` is the device action; nothing is written when the line did not say, never "allowed"). | The connection-normalising schemas of the leading SIEMs keep the device's verdict as a field of its own and never read a logged attempt as a completed connection: Splunk CIM Network_Traffic `action` (allowed / blocked / teardown), Microsoft Sentinel ASIM network session `DvcAction` (Allow / Deny / Drop / Reset…) next to `EventResult`, Elastic ECS `event.outcome` and `event.action`; their threat-intel matches show that field so an analyst sees "blocked" before acting. All three map an unknown action to "unknown", not to "blocked", which is the "never guess" rule here. The FortiOS log reference lists the `action` values per log type (traffic: accept/deny/close/timeout/client-rst/server-rst/ip-conn; UTM: blocked/passthrough/monitored/reset/dropped/detected/pass/block). Why the source name and not the device kind in "blocked by": the source's name is the device the owner set up and the log that says so, and the incident already says "Seen in the log of <source>"; a kind word would need a table that every new blocking profile must extend.
