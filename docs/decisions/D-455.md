| D-455 | **vedette-host refuses a unit change that adds a busy host port, before it touches the running release (host, S-CORE-2, S-CORE-7; follows D-395 and D-214, D-316 (10)).** (1) **Gap**: D-395 adds `PublishPort=127.0.0.1:8765:8765` to core's unit, D-214 added `6514`. `install.sh` refuses a busy port on a fresh box, but an update in place never runs it: if another program listens on 8765, the new core unit cannot reserve the port, core does not start, and 8443 is gone until the revert. (2) **Rule**: the host never writes a unit that publishes a host port (same port and protocol, any address) which the unit on disk does not publish while another program listens on it. `container.start` (also the branch that only rewrites the current template, no restart) and `container.rollback` refuse **`412 port_in_use`** at `Check`, and again at the start of `Run`, before the transition journal, the `pre_update` backup and any write; the message names each port and the process (`8765/tcp (python3, pid 4242)`). The unit migration at host start (D-316 (10)) keeps the earlier unit, audits `container.start unit_migration_deferred` with `ports`, and looks again at the next start. (3) **How it looks**: the kernel's socket tables `/proc/net/{tcp,tcp6,udp,udp6}` (TCP in LISTEN, every bound UDP socket; a clash is the same address, or either side unspecified, `::` counting for IPv4 because the table does not show `IPV6_V6ONLY`), and, only for a clashing socket, `/proc/<pid>/fd` links `socket:[inode]` with the holder's `comm` (printable ASCII, 15 characters) and `cgroup`. A socket held by a process of the service's own systemd unit (`/system.slice/vedette-<service>.service` or below: its conmon, its container) is not a conflict. No program runs, no socket is opened, no probe bind. A table that cannot be read is logged and refuses nothing: the old revert path stays the safety net, and the check never blocks an update on its own misreading. (4) **Not covered (ponytail)**: ports the unit on disk already publishes are not looked at; a unit rewritten on disk whose container still runs the earlier text (migrated at start, port taken before the next restart) can still fail at that restart, as a reboot would. The migration checked the port when it wrote the unit. Core's update run gets the code as a final refusal of the step; its user-facing sentence is core's (deferred). | Why: the failure mode is the one Docker Compose shows when it recreates a container whose port was taken ("port is already allocated" after the old container is gone): the old release is down before the conflict is known. Top-tier installers and orchestrators check host ports **before** they act: kubeadm's preflight refuses `init`/`join`/`upgrade` when a control-plane port is in use (https://kubernetes.io/docs/reference/setup-tools/kubeadm/implementation-details/#preflight-checks), and the Kubernetes scheduler's `NodePorts` filter does not place a pod whose `hostPort` is taken on that node (https://kubernetes.io/docs/reference/scheduling/config/#scheduling-plugins). systemd and Podman have no such preflight: a `PublishPort=` that cannot bind makes the Quadlet unit fail at start (https://docs.podman.io/en/latest/markdown/podman-systemd.unit.5.html), so the host has to look itself. Reading `/proc/net/tcp` and `/proc/<pid>/fd` is what `ss -p`, `netstat -p` and `lsof` do (https://www.kernel.org/doc/html/latest/networking/proc_net_tcp.html, https://man7.org/linux/man-pages/man5/proc_pid_fd.5.html). Not chosen: a probe bind (`net.Listen`, kubeadm's way): the host may not open a network socket (FORBID-2), and a bind on 127.0.0.1 says nothing about a listener on another address; running `ss` (an external program for what two file reads give); checking every port of the new unit with the owner rule only (a cgroup layout we did not foresee for conmon would refuse every update, while the gap it closes needs a port taken in the minutes between the migration and the image step); refusing on an unreadable table (one odd `/proc` would block updates for good). | 2026-11-12 |
