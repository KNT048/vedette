| D-214 | **Syslog over TLS: a third listener (container 5515, published as 6514), server certificate only, sender identified by IP, nil config refuses (logs, #266).** (1) **Where TLS wraps.** `listen.Server` binds a TCP socket of its own for TLS and wraps it with `tls.NewListener` over `Config.TLS` (the box's HTTPS configuration cloned by `syslogTLS`: same `GetCertificate`, so a renewed certificate is served by the very next handshake with no restart, D-139; TLS 1.2 minimum). Accept, per-connection and per-sender limits, idle and frame timeouts, RFC 5425 octet-counting and LF framing, the rate bucket and the sender lookup are the plain TCP code (`acceptLoop`, `register`, `serveConn`), parametrised by the protocol ("tcp" or "tls"); only the source protocol that is looked up differs. The TLS port follows the plain one: 514 gives 6514, any other port p gives p+1 (core runs `-syslog-port 5514`, so 5515, which the core unit then publishes as `6514:5515/tcp`, Kiên's side of #266). The socket is open only while the box has a TLS config AND at least one enabled source has `proto: tls` (the same open and close with the sources as UDP and TCP; the module off closes it, SYS-5); with a nil config nothing listens on 5515 whatever the rows say. (2) **No client certificate: the sender's IP identifies it.** RFC 5425 section 4.2 specifies certificate-based mutual authentication; v1 deliberately deviates and asks for no client certificate (`NoClientCert`, D-167), as the receivers below offer in their anonymous-client modes, so TLS gives the device confidentiality and a server it can verify, not an authenticated source, exactly as for UDP and TCP (the TCP peer address; NAT and spoofing caveats are those of TCP, FORBID-5). Mutual authentication (per-source client certificate or fingerprint, RFC 5425 4.2) stays deferred. (3) **When the sender check runs: before the handshake.** `tls.NewListener`'s Accept returns the connection before any handshake, so the declared-sender check runs right after Accept and an unknown sender is closed with no handshake paid for and no byte read (counted as unknown like TCP); a handshake costs the box a signature, and an undeclared host must not be able to make the box do that. Not chosen: checking after the handshake (an anonymous scanner could burn CPU and learn the certificate). (4) **Handshake bound.** The handshake runs in the connection's own goroutine (never in the accept loop) under `Limits.HandshakeTimeout` (10 s default) through a connection deadline (`SetDeadline`, then `HandshakeContext` with the server context, so shutdown cancels it), so a client that connects and sends nothing, or trickles a hello, is closed after the bound and cannot hold a connection slot (the per-sender and total caps count it from Accept); a client that speaks plain text on the TLS port fails at the first record. A failed handshake is counted (`Stats.HandshakeFailed`) and logged as one Warn at most every `ErrorLogEvery` (10 s), the same limiter style as the sink warning, so a scanner or a device with the wrong protocol cannot flood the log; a handshake cut by shutdown is not an error. (5) **A box with no TLS config refuses.** `proto: tls` is accepted (201) only when `logs.Config.Syslog.TLS` is non-nil; on a loopback or dev box (plain HTTP, nil `deps.SyslogTLS`) create and edit keep answering 400 `tls_unavailable`, now worded "Syslog over TLS needs the box's HTTPS certificate; this box serves plain HTTP. Choose UDP or TCP." (D-203 (3) is carried out: the refusal is lifted exactly when the seam exists). A left-over `tls` row on such a box gets no socket and one Warn. Stored port: TLS sources keep storing the device-side port (default 6514, the published one), UDP and TCP keep 514, even though the box listens on 5514 and 5515 inside the container (the port of a source is only a hint for the device, as before). The API and GUI contract do not change (`ListenStatus` is not exposed by the API), so `contract.ts` and `openapi.json` are untouched. | Reason: reuse the TCP path so a TLS source has the same limits and the same bugs fixed once, and make the TLS-specific cost (the handshake) bounded and gated behind the sender check. Server-only TLS is the common deployment of device syslog and what the leading receivers offer first: rsyslog `imtcp` with the `gtls` stream driver and `StreamDriver.AuthMode="anon"` (server certificate only; `x509/name` and `x509/fingerprint` are the opt-in client checks), syslog-ng `tls()` with `peer-verify(optional-untrusted)` or `peer-verify(no)`, and the Graylog and Wazuh TLS syslog inputs, which take a server certificate and key and make client verification optional; FortiGate sends with `set mode reliable`, `set enc-algorithm high` and port 6514 and checks the server certificate against its trusted CAs, so the box certificate must be trusted on the device (a self-signed box needs it exported and pinned there; showing it in the GUI is deferred).
