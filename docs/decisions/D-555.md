| D-555 | **When a merged device and the kept one both had a person's decision on the same CVE, the people's history rows of the copy that goes are copied onto the copy that stays (findings INV-7, D-515 follow-up, review of #722).** `OnAssetMerged` still keeps one finding per CVE (decided > confirmed > suspected, tie keeps `into`'s) and names the dropped one in the `findings.merged_with_asset` audit row; now, before the dropped finding is deleted (its history cascades), each row of its history written by a person (`user <> system`: status changes, accept risk, notes) is appended to the kept finding with the same time, user, action and note, so the finding page shows both people's notes in time order. History is append-only (trigger), so the rows are copied with new ids, never moved. The kept finding's status is not changed. | Why: duplicate-record tools keep one record and fold the other's people-written data into it rather than dropping it (Lansweeper reconciliation, https://docs.lansweeper.com/docs/understand-the-reconciliation-engine; runZero asset merge, https://help.runzero.com/docs/understanding-assets/); before this fix the second person's note survived only as a finding id in an audit line. Not chosen: combining the two statuses (no rule says which person's decision wins; the kept one is the device people now look at); copying system rows (they describe the dropped copy's own matching and would read as duplicates). | 2026-11-14 |
