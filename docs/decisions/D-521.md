| D-521 | **`vedette-host` runs ZAP's passive baseline as the fixed command `zap.baseline` in a one-shot container fenced to the page's one address and port, pins the upstream image by digest only, and pulls it the first time a scan needs it (host-api §6.15, host INV-31; exposure INV-24, D-562; item 24 slice c, K-5).** (1) **The command**: not a write command (a scan of up to 8 minutes must not hold the global lock of `container.*`, the decoys and updates), one run at a time (`409 busy`); arguments checked at the edge (URL exactly `http(s)://host[:port]/`, a public IPv4 address by `egressip.IsPublicIPv4`, port 1-65535, host = the IP for an IP target or the verified domain or a name under it, the TXT token hex). Right before the run the host re-checks ownership **itself**, as the scan container does for nmap (D-514): an IP target must be the box's own egress (`core/egressip`, two of three services), a domain must still carry `vedette-verify=<token>` **and** the page's name must resolve (A records, system resolver, bounded) to the IP the fence opens, so core's word is not taken for that address either (review 1 M1); cannot check → `ownership_unchecked`, not the box's → `target_not_owned`, nothing sent. (2) **The fence**: a podman network `vedette-zap` made by the host (`--interface-name vedette-zap0 --disable-dns --label io.vedette.owner=vedette-host`, read back with `network inspect`: the label, no driver options, not internal, one IPv4 subnet; a network of that name without them is someone else's and is refused, not removed, here and at `--uninstall`), and an nft table `inet vedette_zap`, loaded in one transaction from a `netip.Addr` and a port (the text checked to be exactly that ruleset before nft reads it, since the runner's validator sees only the argv) and read back with `nft -j list`, whose forward and input chains (priority −10) drop everything entering the host from `vedette-zap0` except TCP to `ip:port`; the container gets `--dns none` and, for a name, one `--add-host name:ip`. So DNS, a redirect to another host or port, ZAP's call home or update check (also off by `-silent`) and the box's own services are unreachable from it. Container: `--rm --pull=never --read-only` (tmpfs for ZAP's home, podman's own for `/tmp` and `/run`), `--cap-drop ALL`, `no-new-privileges`, Vedette's AppArmor profile through `--module` (D-458: ZAP is several processes that signal each other), `--memory=1g --memory-swap=1g --pids-limit=256 --no-healthcheck` (the image's HEALTHCHECK would add a systemd timer), `--user 1000:1000`, `--label io.vedette.owner=vedette-host`, the work folder mounted `rw,nosuid,nodev,noexec` and accepted by the runner only at `<state>/zap/wrk`, `-Xmx512m` passed to `zap.sh` through `-z` (without it `zap.sh` takes a quarter of the **host's** memory on cgroup v2: it reads `/sys/fs/cgroup/memory/memory.stat`, a cgroup v1 file, so 1.75 GiB on the 7 GB N100, above the container's 1 GiB), `-m 1 -T 5`, never `-a`, `-u` or `-j`. The report is written to a bind-mounted `0700` work directory owned by the image's zap user (a tmpfs is gone when `--rm` removes the container) and read by the host as a regular file only (no link, no FIFO), at most 4 MiB, kept as `zap/<id>.json` until the next run or start and served by `GET /v1/zap/{id}/content`. Exit 0, 1 or 2 with a report is success (zap-baseline.py: no rule, a FAIL rule, a WARN rule); 3, 125-127, 137 (the memory limit) or no report is `zap_failed`; everything of a page up to the end of the run fits in 7 minutes counted from the start of the command (`zap_timed_out`), so core's 8 minutes never end before the host's run. **The fence outlives the container** (review 1 H1): on every path the host removes the container (only one that carries its label; one of that name without it stops the run and is never removed) and must then see `podman container exists vedette-zap` answer "no"; only then is the table deleted, then the work folder and the marker `zap/active`. A container that cannot be removed or proven gone (rm fails, does not answer within its bound, an answer that cannot be read) keeps the table and the marker, is audited `zap_cleanup_incomplete`, and the next run refuses `409 zap_cleaning_up` until its own cleanup works; a host start with the marker does the same. Core's adapter (`cmd/vedette/exposureweb.go`) maps the codes that hold for every page (busy, pulling, pull failed, not owned, unchecked, fence, an old host, no host on a container-only install) to `*exposure.Unavailable` sentences and the failures of one page to errors, and reads the report bounded to `MaxWebReport`+1 so an oversized one is refused by `ParseZAPReport`, not cut.
