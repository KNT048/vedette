| D-495 | **A finding that becomes more serious, or that Vedette reopens by itself, is told like a new one (S-ALERT-1, S-LOG-3).** After D-500/D-530 a re-match can raise an open finding's severity (findings emits it when the basis becomes a stronger one, in practice product to version with the installed version inside the NVD range, and the severity of that match is higher) or reopen one Vedette had closed as not affected, but findings emitted only `severity_raised` / `status_changed reason=matches_again` and nobody listened: a finding that just became critical stayed silent in Telegram, email, Zalo and the SIEM. notify now turns `findings.finding.severity_raised` into a vulnerability notice `nt-<finding>-raised-<to_severity>` ("CVE-… on NAS-01 is now critical (was medium)" plus a reason from `basis`: the installed version is in the affected range, otherwise "stronger evidence that this device is affected"; nothing the event lacks) and `status_changed` with `reason=matches_again` into `nt-<finding>-reopened-<YYYYMMDD, UTC>` (one per day, so a version flapping between scans does not message each time) ("Vedette reopened CVE-… on NAS-01: it matches again"). Both go through the same path as a new finding (channel severity floor, quiet hours, grouping/digest, "needs a matched device"); in a digest the line says what changed. Putting the new severity in the id makes one raise one notice and a later raise to a higher level a new one; a raise to a level already told is not repeated (the id is unique). A re-match that both reopens a finding and raises its basis emits only the reopening (findings does not emit severity_raised then), so the customer gets one notice. Not sent in the first CISA baseline (D-78). logs forwards `finding.severity_raised` to the SIEM with the new severity as the record severity and fields `id`, `asset_id`, `cve`, `basis`, `from_severity`, `to_severity`; `finding.status_changed` gains `reason`. No new data leaves the box: same channels and SIEM the customer configured, so no PRIVACY.md change. Sources: Dependabot alerts re-notify when an advisory's severity is updated (https://docs.github.com/en/code-security/dependabot/dependabot-alerts/about-dependabot-alerts); Snyk notifies on priority-score and severity changes of an existing issue (https://docs.snyk.io/manage-risk/prioritize-issues-for-fixing/priority-score); Tenable VPR changes and re-opened findings ("Resurfaced") are surfaced as new activity (https://docs.tenable.com/vulnerability-management/Content/Explore/Findings/Vulnerabilities.htm). | 2026-11-13 |
