# Host (`vedette-host`) — Change Impact Map

> The framework, the OS/backup/log-export commands, `net.*`, `decoy_ip.*`, `container.*`, `host.self_update`, `zap.baseline`, OpenVAS and the domain fence all have Go code (the packages below). Last verified: 2026-11-21 (every sentence checked against the code). A change here can make the box **lose administrative contact**: every change to the allowlist/parameters needs a contract test and a re-read of the CONTRACT.

## Main packages and signatures

## Modifying: `Client.Run(ctx, command, args, requestID, actor) (api.Run, error)` (the `core` side) — 6 groups of callers
- **core/updates** (`/core/updates/os*`): renaming a command or `OSRunResult` → the Updates screen, the `busy` state, and the live progress (`lines`) break.
- **core/network** (Box network, S-CORE-8; handler `core.NetworkHandlers`, `modules/core/CONTRACT.md` INV-25): management card/SPAN/secondary IP/NTP.
- **core/containers** (Vedette software updates: `container.pull`, `container.rollback`, A/B): changing it → an update may become impossible to undo.
- **core/backup** (`backup.create`) and **core/data** (export/delete).
- **inventory** (the package list for "This box").
- **exposure / OpenVAS** (`cmd/vedette/exposuregreenbone.go`, `exposure.GreenboneHost`, INV-32): `greenbone.up/down/sync_feed` through `Client.Greenbone`; changing a code (`greenbone_failed`, `greenbone_no_provider`, `greenbone_cancelled`) or a message → the OpenVAS status sentence on the Exposure page changes; changing `api.GreenboneSocket`/`GreenboneRunDir` requires changing the `core` unit template together (adding the old template to `quadlet_legacy.go`) and `deploy/greenbone/compose.vedette.yaml`.
- **deploy/greenbone override ↔ host/ops** (INV-32): `compose.vedette.yaml` names the password file (`gbPasswordShipped` = `/var/lib/vedette-host/greenbone/gvmd-admin-password`, so OpenVAS runs only with the default `-state-dir`), the secret name `vedette-gmp-password`, the user `admin` (`api.GreenboneUser`) and the `start-gvmd` command of the gvmd image; changing any of them (or the owner/permissions of the file, uid 1001 of the image) requires changing both sides in the same PR. Guarded by `TestGreenboneOverrideNamesThePasswordFile` (`host/ops`) and `TestOverrideGivesGvmdTheLoginAtItsCreation` (`deploy/greenbone`); a new gvmd image version (pinned in `pins.env`) must keep `start-gvmd` reading `$PASSWORD` before it creates the user (check on a test box).
- **deploy/greenbone override ↔ host/ops ↔ exposure, no SCAP/CERT** (INV-32): the override turns off `scap-data`, `cert-bund-data`, `dfn-cert-data` and drops gvmd's mounts/dependencies (`volumes: !override` copies Greenbone's gvmd list: a new `compose.yaml` that changes gvmd's mounts turns `TestOverrideOnlyHandsOverTheSocketAndRunsWhatVedetteUses` red, so fix the override in the same PR); `gbFeedServices` (four) must be feed services that still run; the volume/container/image names of `gbLean` are the names compose v2 assigns (`<project>_<volume>`, `<project>-<service>-1`), and changing the project name requires changing them too. A new gvmd image version must be read again: if gvmd changes how it handles an absent SCAP/CERT feed, check it again on a test box. **exposure** relies on never sending `get_info`/`get_resource_names`/`format_id` (`TestContract_INV25_NeedsNoSCAPOrCERTData`).
- **exposure** (`cmd/vedette/exposureweb.go`, `exposure.WebScanner`): `zap.baseline` and `GET /v1/zap/{id}/content`; `proven_at` comes from `exposure.ScanTarget.ProvenAt` (exposure's 90-day proof of the box's own IP) and is read under `core/egressip.ProofHolds`, the rule the scan container's worker applies too: changing either side alone makes ZAP refuse (or accept) a page the other steps treat differently; changing an error code → the "Not checked" sentence on the Exposure page is wrong; changing the argv or the network fence → review the scope of the passive scan and PRIVACY flow 9.
- Callers must use a stable `X-Request-Id` for each intent (retry with the same id, not a new one) and remember the pace of 60 requests/minute (use SSE, do not poll every second).

## Modifying: the command table (`ops.Commands()`, adding/removing a command) or a parameter type
- This widens the root surface. Every new command: CONTRACT, `host-api.md` §6, the list `documentedCommands` in the contract test, a test that rejects bad parameters (`; | & $ ...` and a wrong IP/name), and `THIRD_PARTY_NOTICES.md` if a tool is added.

## Modifying: how the caller's identity is checked (`host/peer`, socket permissions)
- **core**: if it is loosened, another container could give root commands. Tests: a process other than `core` is rejected (layer by layer), `TestContract_INV4_*`, `host/peer` fuzz.

## Modifying: the audit format or the hash chain
- It must match `core/chain` and the test vectors; `GET /v1/audit` is the source for "download every log of the box": changing a field breaks readers. A damaged file → the host blocks write commands (`audit_unavailable`).

## Modifying: `os.install`, `os.check`, the apt output parser
- **core/updates** (`OSState`, `OSRunResult`): renaming a field of `api.OSState`/`api.OSRunResult` breaks the Updates screen. `installed` and `security` are measured by simulating again; changing how they are measured changes the meaning of the displayed number. Changing the parser (`ParseSimulation`) can make `security` wrong (a fix package is treated as ordinary or the other way round): rerun the test table and the fuzz.
- Adding an argv for `apt-get` (for example a release upgrade, `remove`) = opening the root surface; the checker `validateApt`, `host-api.md` §16 and the test `…FORBID_ReleaseUpgradesAndSourcesAreOutOfReach` must be edited.

## Modifying: the snapshot contract (`<core_data>/snapshots/<id>/`, `snapshot.json`, the `snapshot` parameter)
- **core/backup, core/updates, core/data** (the `core` side): `core` must create a snapshot right before `backup.create`, `os.install`, `backup.restore` (the `vedette.db` file is self-sufficient, `vedette.key` when it exists, `snapshot.json` written last; a regular file owned by `core_uid`, one link; at most 10 minutes old). Changing file names, the write order, the size cap or the maximum age makes every backup command return `snapshot_required|invalid`. Changing the user that runs `core` without changing `core_uid`/`core_gid` in `host.conf` makes snapshots be rejected. Tests: `TestContract_Backup_RefusalsAndHostileCore`, `host/ops` `TestParseSnapshotMeta`.

## Modifying: the reboot gate (`Ops.WriteGate`, `Options.WriteGate`, `reboot.json.pending`)
- **Every caller of a write command** (core/updates, core/backup, core/network, core/containers): for up to 10 minutes after the host begins to reboot, every write command returns `409 rebooting`; they must treat it as "waiting for the machine to restart", not as an error. Removing the gate = a compromised `core` could interrupt dpkg/a restore by queueing a command just before shutdown.

## Modifying: backup and restore (`backup.*`, the tar.gz format, `core_data`)
- **`backup.purge`** (`purgeBackups` in `backup.go`): deletes every backup and `index.json`; **core/data** ("Delete all data", `POST /core/data/purge`) calls it through `client.BackupPurge(ctx, requestID, actor)`, turning `busy` into 409 and `transition_pending` into 412; it also deletes the host's `exports/` and `tmp/` (the systemd journal is not touched). After a purge, `container.rollback` of a `core` release with `rollback.safe=false` → `rollback_backup_missing`, and `backup.list` is empty: the Backups screen must tolerate an empty list. Renaming a file the host writes into the store (`<hex32>.tar.gz`, `index.json`, `.tmp-*`) without changing `archiveNameRE`/`hostTempRE` = a purge that leaves files behind; the test `…BackupPurge_DeletesEveryArchive…` catches that.
- **core/backup**, **core/data** (backup download, `GET /core/data/backup`), `os.install` (calls the internal `createBackup`), `backup.restore` (stops `core`): changing member names, order or the manifest makes old backups impossible to restore; `manifest.version` is the upgrade point. Changing `db_schema` changes the meaning of `schema_newer`.
- The names `vedette.db`/`vedette.key`/`snapshots` are constants that match the defaults of `cmd/vedette`; changing them in `core` without changing them here → `snapshot_required|invalid`. The installer (`deploy/install.sh`) must write `core_data`, `core_uid`, `core_gid` and keep the parent directory of `core_data` owned by root, not writable by group/others (otherwise every backup command returns `db_unreadable`).
- Retention (3 `pre_update`/`pre_os_update`, 3 separate `pre_restore`, 10 `manual`) deletes files: changing these numbers changes what the user can go back to.

## Modifying: `os.reboot`, timers, `reboot.json`
- **core/updates**: `reboot_scheduled_at` is read from `GET /v1/state/os`; after a change, the box could reboot unexpectedly (FORBID-3). Every reboot (including scheduled) counts toward the cap of 3 per 24 hours.

## Modifying: `logs.export`, the secret filter
- **core/data** ("download every log of the box"): adding a secret pattern to `redactRules` without adding a test lets something through; removing a pattern exposes something. A JSON line must still be valid after filtering (fuzz).

## Modifying: signature verification (`internal/release`), embedded keys, the registry
- **Every container** (`core`, `sensor`, `honeypot`, `scan`, `greenbone`): changing it → it cannot start, or (more dangerous) it runs an unsigned image. `internal/release` is shared with **core/updates** (checking the index/manifest for display): changing the index/manifest format (`images[].cosign`, `update-manifest.md` §4.2) requires changing the release CI (cosign `--new-bundle-format=false --use-signing-config=false`) and the test vectors at the same time. Adding/replacing an embedded key = a new binary; the offline backup key must stay in the binary for key rotation. Changing the registry constant `ghcr.io/knt048/vedette-<service>` → every old manifest becomes `registry_not_allowed`.
- Version order (SemVer through `golang.org/x/mod/semver`), `min_upgrade_from`, `rollback.min_version`: changing how they compare → a downgrade slips through or an update is blocked.

## Modifying: the `bundle` source of `container.pull` (`host/ops/bundle.go`)
- **core/updates** (`POST /core/updates/bundle` still returns 501 so there is no caller of `source: "bundle"` yet; once there is): `core` must write the bundle to `<core_data>/bundles/<bundle_id>.tar` (a regular file of `core`, 0600, one link, ≤ 8 GiB, `bundle_id` 32 random hex) and then call `container.pull` `{service, version, source: "bundle", bundle_id}` **without** the four documents (with them → `400`), for each service of the manifest; and delete the file itself afterwards. Renaming the `bundles` directory, the `.tar` suffix or the 8 GiB cap = changing both sides. `host/*.deb` goes through `host.self_update` (copied to `host-packages/<id>.deb`), not through this command.
- **The bundle builder** (`scripts/release/`, not yet present): `images/<service>.oci.tar` must be an OCI layout whose `index.json` names exactly one image with a digest equal to `images[].digest` (exported preserving the digest); otherwise → `archive_digest_mismatch` on every box. The list of tar member names is closed: adding a file to the bundle = changing `bundleMemberCap` at the same time, otherwise every new bundle gets `bundle_invalid`.
- **Podman**: relies on `pull oci:<dir>:<ref>` storing the image under the name `<ref>` with the index digest in `RepoDigests` (measured on Podman 5.7.0); if another Podman version does not do that, `image inspect <pull reference>` after the load command fails → `effect_not_verified`, no tag, nothing written.
- **Retaining images**: an image loaded from a bundle carries the extra name `ghcr.io/knt048/vedette-<service>:<version>` (a tag, not a digest); `ownedName` accepts it, so the image is still removed when nobody holds it.

## Modifying: `net.apply`/`net.confirm`/`net.revert`, the `/run` overlay, `net/pending.json`
- **core/network** (Box network, S-CORE-8): the GUI assumes that changing the management part → `awaiting_confirm` has `revert_at`, while DNS/NTP/SPAN alone finishes at once; `core` takes `run_id` from `state/net.pending` (it is not remembered in memory) so a restart in the middle of the window loses nothing; the old address is in `core_setting` `core_network_pending`. Changing the states/codes (`pending_confirm`, `not_awaiting_confirm`, `not_confirmed`, `reverted_by_reboot`, `address_conflict`, `gateway_outside_subnet`, `net_backend_unsupported`) → breaks the code mapping table of `core` and the GUI wording.
- **os.reboot** (`net_pending_confirm` through `Deps.NetPending`) and **the shared write lock**: a waiting run holds the lock; dropping that lets another write command squeeze into the window.
- **The installer (`deploy/install.sh`)**: the host must be the sole owner of netplan (cloud-init turns the network off, other files are moved away); if not → every `net.apply` gets `net_backend_unsupported`. Writing `/etc` outside `net.confirm` breaks INV-16 (a reboot keeps an unconfirmed configuration). For NTP, the installer installs chrony, owns `chrony.conf` with `sourcedir /etc/chrony/sources.d` and **not** the distribution pool; without chrony or without `sourcedir`, `net.apply` fails with `ntp_not_applied` (the effect check sees no source) and PRIVACY flow 10 is no longer true.
- **`ops.Notifier` and `server.Options.Resume`**: `Notifier.Claim` is the only path by which confirm, revert, a timer and `Start` end a waiting run (compare-and-swap before any effect); removing or changing it lets two sides both apply an effect (write `/etc` and then undo it). `Resume` must be wired in `cmd/vedette-host` (the test `TestServesAndStopsOnSignal` checks the command table; the test `…AHostCrashBefore…` checks the behaviour): forgetting to wire it makes the waiting run `failed host_restarted` and the `/run` overlay is undone by `Start` like an orphan note.
- **Time bound and a failed rollback**: `Spec.Awaits` depends on the 660 s bound measured on a monotonic clock (`liveRun.started`); the `net.apply` command depends on `RunContext.AfterFinish` running even when the park is refused or the command fails (dropping it → an overlay that nobody watches); a failed rollback calls the scheduled-reboot path (`setSchedule`) and writes `pending.reboot_at` (core needs to show it); `Check` reads `/sys/class/net/<card>/device` for `span_not_physical`.
- **`net/pending.json`** (written through `os.Root`, 0600; has `started_at`, `reboot_at`) is the only note that survives a host crash; changing the form of a field makes an old host treat the new note as untrustworthy and **roll back** (safe, but it loses the window in progress).
- **`vedette-host.service`**: does not use `ProtectSystem=strict` (`DEPLOYMENT.md` §12) because the host writes `/etc/netplan`, `/run/netplan`, `/etc/chrony/sources.d` and runs `netplan apply` (which pulls in `systemd-networkd`, `udevadm`); adding a sandbox that blocks writes to these directories or blocks that makes `netplan apply` fail and every `net.apply` is rolled back.

## Modifying: parked runs (`server.Parked`, `SettleParked`, `Options.Resume`)
- **`host.self_update`**: the run survives postinst's SIGTERM thanks to the parked run holding a lock on disk and to `Resume`; changing it so that `Shutdown` ends a parked run, or so that `recover()` does not ask `Resume` about it, makes every self-update end `failed` midway and release the lock while the applier is still installing. "Park first, hand over afterwards" relies on the run having been written to disk **before** `OnParked`: changing that order reopens the gap (a SIGTERM between the handover and the park leaves an applier with no run and no lock).
- **`Options.Resume`** is asked only for `awaiting_confirm` runs and parked runs; asking about an ordinary `running` run as well would make the network `(*Ops).Resume` mark an interrupted `net.apply` as "held" (when `net/pending.json` exists) and skip `recoverOrphan` (`host/ops/netpending.go`).
- **The shared write lock**: a parked run holds the lock until `SettleParked`; the framework does not end it by itself at `parked_deadline` (the command's goroutine does). An error in that goroutine holds the lock until a restart in which `Resume` answers no.
- **Ending twice after a crash**: if the host crashes between the final audit line and the run file of `SettleParked` → at the next start the run is still parked on disk, `Resume` may hold it, and the next ending writes a second final line with the same `audit_id` (like a waiting run). The ending goroutine must be idempotent against the journal (the result comes from `journal.json`, and the effect is not redone).
- **`api.Run.parked_deadline`**: a new optional field; the run file of a new host can still be read by an old host (the reader is not strict about unknown fields), matching the rule "no format change before the commit" of host-api §6.14.

## Modifying: `decoy_ip.*`, namespace `vedette-hp`, MAC
- **Code** (`host/ops/{decoy,decoyargv,decoystate,hpns,mac}.go`): changing `hpNS`, the link name `vdh<8 hex>`, the table range 100…131 or the shape of `validateIP` changes the contract with honeypot and with the written `hp/decoys.json` (the table and the parent card are stored per decoy; changing the range makes an old file rejected and then set aside as `.invalid`). `reapplyDecoys(ctx, hint)` is called by `net.apply`, by rollback and by `Ops.Start`, and never returns an error because of one decoy: changing that could make a network change get rolled back because of a decoy. `ensureHP` runs before `recoverNet` in `Ops.Start`; reversing the order makes the rollback at startup re-apply decoys into a namespace that does not exist yet.

## Modifying: `GET /v1/info` `hostname` (`api.Info.Hostname`, `api.ValidHostname`, `host/server/sysinfo_linux.go`)
- **core** (`cmd/vedette/boxname.go` `boxHostName`): the name of the box's own device row (inventory's `box` job), the `hostname` of the Logs source page (`logsBox`) and the HOSTNAME/`box` of the SIEM record (`logs.Config.Hostname`). Remembered for 10 minutes, asked again after 30 s when the host does not answer (the last good name is kept; when the caller's context expires it does not count as a host failure), `vedette` when the field is missing or breaks the rule; a host that has never answered since `core` started (`Get` returns `ok=false`) makes the `box` job keep the device-row name it has instead of writing `vedette`, and the Logs page and the SIEM record also use that row's name (`useRow`, read once, checked again with `ValidHostname`) and not `vedette`. The same name also goes into: **the self-signed certificate and the default Host list** (`cmd/vedette/tls.go` `certBoxName`, `transport` in `main.go`), **the display name of the passive sensor** (`sensorpassive.Config.Name`) and **the honeypot's box** when there is no device row yet (`honeypotInventory.Box`). The `core` unit **still keeps** `HostName=vedette` (INV-17) because of version skew: a new host may run an old `core`, which still reads `os.Hostname()`; the current `core` no longer reads it. The sensor reads `boxHostName.Cached` (it never asks the host; the `box` job and the certificate re-issuer refresh it), because `ensureSensor` runs on every batch, heartbeat and GET. Certificate: only a name reported by the host (`ok=true`; never the name of a device row), lowercase, checked again with `api.ValidHostname`, and it must not look like an IP (a last label of all digits, such as `10.0.0.5`, is dropped, so that the machine's name does not become an address that the box answers). It only **adds** to the old set of names: `localNames` always keeps `vedette` (the old container name that every earlier certificate and Host list had), loopback and addresses, so no name that ever opened the box is lost. The box name comes **after** `localNames` among the certificate's DNS names, so `vedette` is still the first non-loopback name left, and the links in notifications carry the box's address (`baseURL(addr, listen)`), never a name in the certificate (`TestLinksCarryTheBoxAddressNeverTheCertificateName`). **The default Host list accepts only names that nobody outside can own** (`defaultAllowed`): an address, a single-label name, or a name ending in `.local`, `.lan`, `.home.arpa`, `.internal`. A machine name can be set by DHCP (option 12), so a hostile DHCP that sets `rb.attacker.example` would let a page on that domain rebind to the box; such a name still goes into the certificate but is answered only when the administrator adds it to `-hosts` (`TestPublicDomainBoxNameIsNotAnswered`, `docs/DEPLOYMENT.md`). The filter is applied to **every** DNS name of the self-signed certificate when the list is built (otherwise the next start would take that name from the certificate); an old self-signed certificate has only `localhost`, `vedette` and addresses outside `-hosts`, so an appliance box loses no name; only a real domain name left over from a run with `-hosts` (and then dropping `-hosts`) or a dev machine's FQDN is no longer answered, and needs `-hosts`. The box owner's certificate (`-tls-cert`) is not filtered: the list consists of the names the box owner gave. First start: `transport` asks for the name once (at most 2 s; the host starts before `core`), puts it into the SAN and, when there is no `-hosts` and the name passes `defaultAllowed`, into the Host list; with `-hosts` the list is still just `-hosts` as before. An upgraded box (the certificate does not yet have the name): the name goes into the Host list at once, and into the certificate at the first `Check` of `selfSignedRenewer` (the same key, the same box CA; the leaf's fingerprint changes as on every re-issue for an address, and agent machines pin the **CA** so they are not affected; a browser where someone clicked "accept" for the self-signed leaf may ask again once). The host has not answered at startup: nothing is added; when the host answers, `Check` (every 10 minutes or when woken) adds the name to the certificate, and the Host list has it from the next start (the list of names is fixed within one process as before, a simplification in `transport`); a re-issue while the host does not answer keeps the leaf's current DNS names. The box owner's certificate (`-tls-cert`) is never touched. Per RFC 1123, a machine name with an underscore (`my_box`, which Linux allows) is **not** accepted: the host drops the field and the box carries the name `vedette` (likewise for whitespace, non-ASCII letters, a label > 63 or a total > 64 bytes). Loosening `ValidHostname` lets the machine administrator's text into the device row and the syslog record (the SIEM formatter still turns it into an ASCII token); tightening it makes a machine with a previously valid name become `vedette`. The field is optional and does not change `proto`: dropping the field makes `core` use `vedette`, with no error. Changing the source (the `uname` nodename) needs the host to still share the UTS namespace with the machine (`ProtectHostname=` is forbidden in the unit, `deploy/systemd/unit_test.go`).

Changing `fillFor`/`unitFill` (dropping a field that an old template uses) makes the old template impossible to build: `TestLegacyTemplatesMatchTheGoldenFilesOfTheirRelease` catches it. The unit of an old template is rewritten once each time the host starts (without a restart; `recoverTransitions(ctx, true)` only at `Start`): the new text takes effect only at a later restart, so a template change that needs to take effect at once (e.g. a new port) relies on the image step of the same software run. `install.sh` no longer gets `exit 5` after an upgrade because a template changed (a template older than that change still needs `-force-units`). A new template **must not carry an argv that an old image rejects**: the new unit may start an old image (a restart before the image step, a rollback builds the current template with the previous digest); new values are set through the binary's defaults (like `-mcp-listen` left empty).

## Modifying: `os.reboot` and logind's shutdown lock (`host/ops/inhibit.go`, `reboot.go` `tryReboot`)
- **The new code `409 reboot_inhibited`** (`api.CodeRebootInhibited`) of `os.reboot now`: `core` has not mapped it yet (`modules/core/oshost.go` `mapHostCode` falls into `502 host_error` "could not do this"), so until `core` adds it the user sees a general error; that and the GUI part are left for later. It is not `tryLater`: repeating at once is useless, the user waits for apt to finish.
- **The `rebooting` gate can live up to ~30 minutes** (instead of ≤ 10) when a reboot that has begun is waiting for a lock: every caller of `core`'s write commands (updates, backup, network, containers) gets `409 rebooting` for longer; `core` treats it as retry later (`tryLater`), so an install/restore run of `core` may wait longer than before. **The gate also refuses `os.reboot.cancel`**: a `now` reboot that has begun and is waiting for the lock **cannot be cancelled** during those 30 minutes (`core`'s cancel-schedule button gets `409 rebooting`); it ends itself with a reboot when apt is done, or `reboot_failed` when the 30 minutes run out.
- **`reboot.json` adds `pending.issued`** (a bool, omitted when false): an older host ignores the unknown field (the reader is not strict), so downgrading the host loses no state. A host that starts on the same boot with a `Pending` that is not `issued` (waiting for the lock) writes `reboot_failed` `host_restarted` instead of holding the gate; any test that builds a second host right after `systemctl reboot` must first wait for `"issued":true` in `reboot.json` (written after `systemctl` returns).
- **On systemd 255 (Ubuntu 24.04)** logind lets root reboot past APT's uid-0 lock: only the host's read check blocks it; changing `tryReboot` and dropping the read before each `systemctl reboot` reopens the path that cuts dpkg on 24.04.
- **A schedule waiting for the lock keeps `reboot_scheduled_at` in the past** (up to 24 hours): `core/updates` `updates_auto.go` treats a schedule earlier than `now + updateRunMax` as "a reboot is scheduled" and skips the automatic update round; that is intended (no more installs while a reboot is pending), but the GUI may show a reboot time that has already passed.
- **`busctl`** is the fifteenth binary of the runner (`/usr/bin/busctl`, in the `systemd` package that the `.deb` already `Depends` on); `opstest.Bins` has a fake `busctl` (by default it prints empty = an unknown list = let it pass, so old reboot tests do not change). Changing the argv requires changing both the checker `exactly(argsListInhibitors...)` and the table of §16 of `host-api.md`.
- **Timers:** the retry of a reboot that has begun uses `Deps.AfterFunc` (30 s) and the field `stopRetry` (under `rbMu`), separate from the schedule's `stopTick`; tests that count timers (`fakeTimers.active`) see one more 30 s timer only when the reboot is locked.
