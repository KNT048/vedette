| D-490 | **The weekly report says what to DO this week, with the fixed version, and what happened (S-REP-1, customer walk 1 follow-up to D-485/D-487/D-488).** Page 1 and the email gave a product and a count ("Update or apply the vendor's temporary fix to FortiGate"), not the step a person takes. Now (1) **Top risks are lines of work, not products**: open findings are grouped per device and product (the unit of an upgrade), and groups that need the same action merge (same product, same fixed release), so one upgrade that closes several CVEs is one line: "Upgrade FortiGate (FortiOS) on FortiGate-HQ from 7.4.1 to 7.4.3 or later — fixes 3 exploited vulnerabilities" (several devices: "Upgrade Apache to 2.4.52 or later on web-1 and 2 more — fixes 3 exploited vulnerabilities"; some findings of the line not closed by it: "fixes 2 of 3"). The release is `findings.FixedInFor` (D-488, NVD ranges) read through the `reports.Remedies` port wired in `cmd/vedette/reports.go`, never recomputed in reports; the release is the nearest one, going up from the device's version, that is outside the affected range of EVERY finding of that product on the device (`findings.FixedInForAll`), never the highest of the per-finding fixes (26.3 fixes one iOS CVE and is inside the range of another); "fixes N of M" counts only the findings the release closes, and when no release in NVD's ranges clears them all the line says to install the latest release of the device's line and check the advisory; a distribution caveat ("if you installed it from Ubuntu's packages, install its security updates instead") is carried. Fallbacks stay honest and are the words the page already had: a distribution package -> install the distribution's security updates; NVD names no fixed release (only a last affected version) -> check the vendor advisory and use the vendor's temporary fix; confirmed but no range -> update or apply the vendor's temporary fix; version unknown -> check the version to confirm or rule out. The same sentence is `TopRisk.action` (page) and `ActionItem.text` (to-do list, email). Ranking is unchanged and by product (confirmed first, worst severity, most open findings over all devices, name): a product whose devices need different steps gets one slot, the biggest step, and "N more devices need another step"; fixed releases are read only for the products the page names. (2) **"What happened this week"** from notify incidents through the `reports.Incidents` port (never notify tables; off when notify is off, then the section and the "incidents" source are absent): counts per kind (`notify.IncidentsSince`, in SQL, so a busy week is counted whole and not cut at the 500 of the list) of the incidents last seen in the week (honeypot touches, failed-login attacks from D-487, **logins ACCEPTED after failed attempts**, connections to known-bad addresses, other log anomalies; new-device incidents are left out because the Devices count says them), one sentence for page and email, and up to three lines ordered accepted login, trap, failed logins, bad connection, then severity and recency.
