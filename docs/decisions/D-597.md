The real fence is post-v1 issue #822: nuclei moves to a one-shot container on a fenced bridge.** (1) **The gap**: nuclei runs in the `vedette-scan` container, started by the sensor-active worker (`modules/sensor-active/worker/nuclei.go`). That container uses `Network=host` and `User=<sensor_uid>` (`host/ops/quadlet.go` `scanUnitText`). No nft rule on the host limits where nuclei connects while a job runs. ZAP's fence of D-521 (`host/ops/zap.go`: own network `vedette-zap` on bridge `vedette-zap0`, `--dns none`, per-run table `inet vedette_zap` that lets only TCP to the one `ip:port` pass) has no nuclei counterpart. A nuclei bug, a template that gets past the rules below, or a compromised scan container could reach a host that is not the job's target. (2) **Who runs nuclei, said plainly (this corrects "only the Preview scan module")**: the scan module (Preview, `default: false` in `modules/scan/MANIFEST.yaml`) runs it on LAN devices. The exposure module (v1, J6, `default: false` in `modules/exposure/MANIFEST.yaml`) also runs it on the box's own public IP. KEV templates marked own_ip run after Scan now, the commitment sentence of D-559 and the verification of the target. Deep templates (depth full, D-527) and domain_ip jobs (D-591) run only once the testing terms are accepted. Both modules need sensor-active on (`cmd/vedette/exposuretemplates.go` `on`). (3) **Mitigations that hold today**, each checked in the code: (a) **Only targets the customer approved or proved to own.** LAN: `lan_ranges` minus the exclusions, approved, and `VulnScanPolicy`, checked again right before each job (`modules/scan/CONTRACT.md` INV-1). The worker's grammar accepts only private IPv4 literals, 1 to 16 of them, never a name or the metadata address (`modules/scan/nucleiargv/argv.go` `validHost`). Own public IP: core's gate `ScannableIP` checks that the target is verified, committed and seen as the box's IP (`modules/exposure/scan.go`). The worker accepts exactly one public IPv4 (`validPublic`) and checks, with the public IP services, that the box goes out through it now (`modules/sensor-active/worker/external.go` `ownIP`). A domain_ip job must pass the domain fence of D-591 before it starts and again every 3 minutes while it runs (`modules/sensor-active/worker/nuclei.go` `domainFence`, `runWatched`; `core/domainfence/domainfence.go`). Full depth also needs the terms read again right before each run (`modules/exposure/terms.go` `ModeNow`). (b) **No out-of-band traffic and no other destination by flag**: `-ni` (no interactsh), `-duc` (no update check), `-dr` (no redirect followed), `-nh` (no httpx probing), `-pt http,tcp,ssl` (no dns, whois, javascript, headless, code or file templates), `-etags` of the forbidden tags, all fixed in `nucleiargv` `fixedFlags` and checked again by `Validate` inside `core/exec`. The environment is core/exec's own (PATH, LANG, HOME; no proxy, no upload key), and HOME is emptied before each run (`modules/sensor-active/worker/nuclei.go` `freshHome`). (c) **Rate and size limits**: `-c 1 -bs 1 -timeout 10 -retries 1`; LAN rate at most `MaxRate` 20/s with at most 32 templates and 16 targets; own_ip at `OwnIPRate` 5/s on one target; full at `FullRate` 20/s, `-c 10`, at most 200 templates; `-mhe` 2 to 20; a job at most `MaxNucleiTimeout` 3600 s (`modules/sensor-active/worker/worker.go`) (all in `modules/scan/nucleiargv/argv.go`). (d) **A closed template pack**: it is built from a pinned nuclei-templates release by `scripts/scanpack` and baked into the scan base image (`deploy/containers/scan-base/Containerfile`). The D-528 rules keep a template out if it writes, uploads, uses a refused tag, or sends a request to any other destination: an http path must start with `{{BaseURL}}` or `{{RootURL}}`, a network host must be `{{Hostname}}`/`{{Host}}`, and there is no `@Host:` and no third-party URL (`scripts/scanpack/nochange.go`). For every job the worker takes template ids only from the image's index, checks each file's SHA-256 against it and refuses links (`checkTree`, `checkFile`). It also runs `pack.NoChangeText` on each file (`modules/scan/pack/nochange.go`: no `@Host:`, `gopher://`, `dict://`, write method or upload), plus `pack.OwnIPText` for own_ip (GET or HEAD only) and `pack.FullText` for full (no interactsh/oast) (`modules/scan/pack/pack.go`). Core never sends an argv, a path or a URL. (e) **A hardened container**: `DropCapability=ALL` plus `NET_RAW` only, `NoNewPrivileges`, `ReadOnly`, Vedette's AppArmor module, a non-root uid, `--memory=1g --pids-limit=512` (`host/ops/quadlet.go`). (4) **Why the fence is not built for v1**: ZAP can be fenced by bridge because it runs alone in its own one-shot container. nuclei shares the scan container with nmap and SNMP. The worker runs one job of each kind at the same time (`modules/sensor-active/worker/worker.go` slots). They all use the host network namespace and the same `sensor_uid`, which the passive sensor container also uses (`sensorUnitText`). While nuclei runs, the worker itself still needs the core link at `127.0.0.1:8444`, the public IP services of the own-IP fence, and DNS for the domain fence's checks. So an nft rule matched on uid, or one over the whole container, cannot hold nuclei to its targets without breaking LAN discovery and the fences themselves. The real fence means moving nuclei into a one-shot container on its own bridge with a per-run table, as D-521 does, plus a new host op, a cleanup rule and lab proof on the N100. That is a new host feature, not a v1 fix (SHIP.md freeze, D-624). (5) **Residual risk, accepted**: a flaw in nuclei, or in a template the rules above miss, while the customer has turned on Vulnerability scans (Preview) or External exposure, could make a request to a host that is not the target, at the job's limited rate and for at most the job's time. A compromise of the scan container gets the network reach of the host. nmap in the same container already has that reach (its external and deep shapes are outside #822). (6) **Revisit**: #822 (post-v1).
