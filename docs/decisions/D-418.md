| D-418 | **Reinstalling after `install.sh --uninstall --yes --keep-data` brings Vedette back with its data, and a re-run bootstraps even while vedette-host runs (customer walk 2, W2-9 and W2-10).** What was wrong: `--keep-data` removes the Quadlet units and the images but keeps `/var/lib/vedette-host`, so `containers/versions-core.json` was still there and the next run said "already bootstrapped", skipped the bootstrap and failed on "vedette-core.service not found" (exit 7, N100, n4 over n3 data); after the records were moved away by hand, `vedette-host -bootstrap` refused with `daemon_running` (exit 6) because an earlier run (or the package's restart on upgrade) had started the host. (1) **The bootstrap is skipped only when core has both its record and its unit** (`versions-core.json` and `vedette-core.container`); a missing unit is installed again. (2) **Kept data with no unit of any container** (records in `containers/versions-*.json`, none of `vedette-{core,sensor,scan,honeypot}.container`) is what `--keep-data` leaves: the run clears the host's container records (`versions-*`, `pulled-*`, `transition-*`, `containers/units/`; never the data, the backups, the release index or the host's package records) and bootstraps its own release, same or newer, over the kept data, then records what runs. The records are cleared by the install, not by the uninstall, because until then they say which release last ran on the data. (3) **An older release than that is refused in preflight, before any change** (`dpkg --compare-versions` on the SemVer with `-`→`~`): core's migrations are forward-only and an older core would run on a newer database. (4) **The installer stops a running vedette-host before `-bootstrap`** and starts it after (`start_and_wait`), and again from `cleanup` when the run fails: the bootstrap stays a one-owner operation (D-142) rather than going through the socket, which the installer cannot use (not core). Not chosen: (a) the uninstall clears the records: it loses the downgrade guard; (b) the host re-renders missing units from its records at start: the images are removed by the uninstall, so it would still need the network, and it is new host behaviour for a state only the installer makes; (c) keeping the images on `--keep-data`: the uninstall promises to give the space back and the customer path downloads the package anyway, so a keep-data reinstall needs the network like a first install. Known limit: `min_upgrade_from` of the new release is not checked against the kept data (the bootstrap has never checked it). Verified by effect in `scripts/dev/install-check.sh` (setup through the API, `--keep-data`, older release refused, reinstall: setup still complete and the administrator signs in; then core's unit removed with the host running) and `TestInstallSh_KeepDataReinstallReadsAndClearsTheHostsRecords`. Like the leaders: GitLab's Linux package keeps the data on uninstall and a reinstall picks it up (https://docs.gitlab.com/install/package/); Grafana migrates its database forward at start and does not support running an older version on it, restore a backup instead (https://archive.grafana.com/docs/grafana/v8.4/installation/upgrading/, https://grafana.com/whats-new/2026-04-14-unified-storage-for-folders-and-dashboards/). | 2026-11-13 |
