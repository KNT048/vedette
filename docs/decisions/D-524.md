| D-524 | **osquery reports Windows's monthly update revision (UBR), and a Windows PC with osquery is matched against the CISA list by its patched build (TUNE-5, tool-tuning plan §5; S-INV-4; amends D-169 (7) schedule, D-504 (3) "or install the osquery agent"; findings part flagged for its owner).** (1) **Where the UBR comes from.** Not a new `registry` query: osquery 5.12 (the pinned 5.12.1) already reads `HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows NT\CurrentVersion\UBR` itself into `os_version.revision`, a Windows-only column. The schedule gains one Windows-only, read-only snapshot query `os_revision` = `SELECT name, version, revision, arch FROM os_version;` (3600 s, `platform: windows`, part of the first report's `os_version` answer). It is a query of its own because the column does not exist on Linux (adding it to `os_version` would fail that query there) and an osquery older than 5.12 then fails this query alone. D-169 (1)'s rule stands unchanged: snapshot-only, read-only tables, no `registry`, `exec`, `file`, `hash` or `curl` table; the registry table is never in the schedule. (2) **Intake.** The row is untrusted (INV-7): `version` must be `10.0.<5-digit build>` (Windows 10, 11, Server 2016 and later; NVD names 6.x releases without build ranges), `revision` a positive integer 1..999999 as osquery writes it (no sign, no leading zero; 0 or empty would place the machine at the first build of its release and so inside every range), the name 1..200 characters; anything else is dropped and the stored value stays. The node keeps the last good one (`intake_osquery_nodes.win_name`, `win_version` "10.0.22631.4460", `win_target`; migration 0006) because osquery's splay sends queries of one interval in different requests. With it the device's OS reads "Microsoft Windows 11 Pro 10.0.22631.4460" (instead of "… 10.0.22631 build 22631"), and every Windows package list carries the operating system's own software row: vendor `microsoft`, product the release ("Windows 11 23H2"), version the full build, KEV key `microsoft\|windows` (the key the catalog's Windows entries carry) and CPE `cpe:2.3:o:microsoft:windows_11_23h2:10.0.22631.4460:*:*:*:*:*:x64:*` (release by build, client or server by the name containing "Server": 10240, 14393, 17763, 19044, 19045, 20348, 22621, 22631, 25398, 26100, 26200; a build not listed gives no row, as before). target_hw from WMI's OSArchitecture ("ARM…" arm64, "…64…" x64, "…32…" x86, else any). A Wazuh agent whose `os.version` already carries the revision ("10.0.20348.2700") gets the same row (target any). Nothing new leaves the box (PRIVACY unchanged: the value goes from the agent to the box like the package list). (3) **Matching (findings, flagged for its owner).** With its own release's CPE the row is compared with NVD's ranges by the generic comparator (`windows_11_23h2 … versionEndExcluding 10.0.22631.5189`): below it is a version finding (high), at or above it an open suspected finding is proved not affected and closes (D-530). One minimal rule is added in `findings` (`windowsOthersOnly`, schemes.go): when the software is a Windows release by its CPE and the entry's NVD list names only **other** Windows releases (new style `windows_10_1809`, old style `windows_10:1607`, `windows_10:-` = 1507, `windows_11:-` = 21H2), the entry raises no finding and **proves nothing** (No without proof: nothing closes, FORBID-2 unchanged), so a current PC does not get one "not checked" product finding per older Windows entry of the 175 CISA has (the flood D-504 (3) avoided by not giving keys). `o:microsoft:windows` or a family with any version may cover the release: decided as before. **Not chosen**: the `registry` table query of the plan (the same value with a broader table in the schedule and a D-169 exception); appending the revision to the `os_version` query (fails on Linux); prefix aliases `microsoft\|windows` → `windows_*` in nvd-cpe.json (would compare a 23H2 build with 24H2's ranges and flag it); proving "not affected" from other-release lists (NVD can lag Microsoft's list for a release that just shipped). | osquery `os_version.revision` "Update Build Revision" on Windows (https://github.com/osquery/osquery/blob/5.12.1/specs/os_version.table) read from `HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows NT\CurrentVersion` value `UBR` (https://github.com/osquery/osquery/blob/5.12.1/osquery/tables/system/windows/os_version.cpp, osquery #8265, issue https://github.com/osquery/osquery/issues/8317); registry table: `path` is key + value name (https://github.com/osquery/osquery/blob/5.12.1/specs/windows/registry.table).
