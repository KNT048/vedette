| D-491 | **Telegram "Find my chat" fills the Chat ID (S-NOT-1, kien 2026-11-13).** Setting up Telegram asked the customer to open `https://api.telegram.org/bot<TOKEN>/getUpdates` in a browser and read JSON; now a **Find my chat** button under Chat ID does it: the customer types the Bot token, sends any message to the bot (or adds it to a group), presses the button and picks the chat (private chats by name and @username, groups by title; newest first, at most 10, one row per chat). Endpoint `POST /notify/telegram/chats` (admin, CSRF like the other channel routes): token in the body, or the saved channel's sealed token when the body is empty (never sent to the browser); one `getUpdates` call through the existing Telegram bot client (fixed `api.telegram.org`, no redirects, 10 s deadline, 1 MiB cap). **It must not eat updates the approval buttons need**: Telegram only confirms updates when a later `getUpdates` carries an `offset` above their `update_id` ([Bot API getUpdates](https://core.telegram.org/bots/api#getupdates)), so the call sends no `offset` (nothing is confirmed), `limit=100`, `timeout=0`. It also names `allowed_updates` (message, edited_message, channel_post, my_chat_member) because Telegram keeps the last list given: the approval poller sets `callback_query` only on each call and so re-sets its own list. `my_chat_member` makes a group show up as soon as the bot is added, before anyone posts (a bot in privacy mode sees only commands and mentions in a group). **When the box itself long-polls this bot** (channel on, approvals on, numeric chat, same bot id) the box is the one reader, and a second `getUpdates` would end its poll with 409 and change its update list: the button answers 409 `telegram_busy` with the steps (switch approvals off and save, press the button, switch them on; or type the Chat ID); the poller's own updates are not reused because it asks for button presses only, so they never hold a chat. Telegram's own 409 (a webhook is set, or other software reads the bot) gives the same code with a message for that case; 401 (and 404, how Telegram answers a malformed token) → 400 `bad_token` "The bot token is not valid", shown under the token field; any other failure → 502 `telegram_failed`; no message yet is a 200 with an empty list and the UI says what to do (not an error). Untrusted input: the answer is size-capped and decoded fail-closed; only `chat.id` (a number as written, accepted by the channel's own Chat ID rule), the chat type (private, group, supergroup, channel) and the title, first and last name and username (names cleaned to one line, bidi and control characters dropped, 64 characters; a username must match Telegram's form) are returned; the token is in no log and no error. **No new outgoing destination**: the call goes to `api.telegram.org`, already flow 5 in PRIVACY.md (the bot token already goes there on every send and poll); no field was added to any payload. Chosen over reading the poller's updates (they hold no chats) and over a `setWebhook`/`deleteWebhook` dance (it would change the bot's configuration). Sources: Uptime Kuma's Telegram notification "Auto Get" button, which calls `getUpdates` with the typed token and lists the chats found (https://github.com/louislam/uptime-kuma/blob/master/src/components/notifications/Telegram.vue); Telegram Bot API `getUpdates` (offset confirmation, `allowed_updates` persistence, 409 when a webhook is set or another `getUpdates` runs) (https://core.telegram.org/bots/api#getupdates). | 2026-11-13 |
