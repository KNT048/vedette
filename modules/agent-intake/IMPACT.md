# Agent-intake — Change Impact Map

> Last verified: 2026-11-21 (every statement checked against the code). Package `modules/agent-intake` (Go name `agentintake`): osquery `enroll`/`config`/`log`/`status`, service-level tokens, package mapping, Wazuh pull, the admin path, install script, `ca.pem`, package store.

## Modifying: where the Wazuh pull delivered (`intake_wazuh_agent`, `wazuhAgentSeen`, `WazuhAgentAddresses`)
- **inventory** (`Config.WazuhAgents`, wired in `cmd/vedette/inventory.go` `wazuhAgents`): the only way the Devices list says `wazuh` for a device (`source:wazuh` filter, `DeviceRow.sources`). Writing it before the agent's data, or not cleaning it at the end of a pass, makes a device that took over an old agent's address say Wazuh. `modules/core/export_policy.go` lists the table.

## Modifying: the device hint of a report (`hint` in `Log`, `nodeAgent`, INV-12)
- **inventory** binds `AssetHint.Agent` to a device (INV-31) and finds the device by it before the address: a key that changes per report (or names something other than this box's node id) makes every report a candidate for a second device; never put a value the machine sends (host_identifier, MAC) in it.

## Modifying: the agent state (`nodestate.go` `NodeHealth`, `Cadence`, `nextGap`, `supersededBy`; columns `last_call_at`, `call_every_s`, `call_gap_s`, `report_every_s`; `state`, `quiet_since`, `rhythm_s`, `os` of the device report and `nodes` of GET /inventory/agents)
- **Every reader of agent state calls `NodeHealth`**: `Nodes`, `ReportState` (osquery and Wazuh), and through them the device's agent row (inventory `DeviceSources` via cmd/vedette `sourceFacts.agent`) and findings (`agentReports`). A reader that judges an agent its own way brings back "quiet" beside a recent report. The row's `last_at` is the very time NodeHealth judged by.
- **web/features/inventory** (`DeviceSources.tsx` Agent row, `AgentsSection.tsx` machines table, `AgentQuiet.tsx` commands): `call_every_s` at enrolment is the install scripts' `--config_refresh=300` (`configRefresh`) or the package reporter's hourly run (`reporterEvery`, its timer/cron line in `scripts/osquery.sh`); change a flag or a timer and its constant together. `report_every_s` is the schedule's longest interval (`steadyEvery`, schedule.go): a longer query interval there makes a new agent's first silence longer before quiet. `nextGap` learns only from two config fetches in a row whose gap is the told refresh within ±10 s (`refreshSlack`); learning from result posts (irregular, splayed) or from two service starts would call an agent without config refresh quiet between its results (`TestAgentCadence_ReplayOfSevenAgents`, `TestAgentCadence_TwoServiceStartsAreNoRefresh`). A longer `--config_refresh` in the scripts needs `configRefresh` changed with it, or refreshing agents fall back to the report schedule.
- **findings** (`agent_gone` of GET /findings/plan, the finding page's agent line) and **mitigation** read `stale` through cmd/vedette `agentReports`: a wrong limit says "no agent reports this device now" about a device whose agent reports. `os` picks the service commands (`windows` or `linux`).
- **inventory** binds a device to the first node that read it and never rebinds: a machine enrolled again keeps `osquery:<old node>` on its device, so `reportState` reads the newest record bound to the same source address (`newestOf`; never matched by the name or MAC a node claims). `RemoveNode` and node-prune release the binding (`releaseNodes`).
- **Windows script** (`scripts/osquery.ps1` and its web copy): sets delayed-auto start and restart-on-failure, then reads them from the service's registry key; when they did not apply the agent still starts and enrols, and the run ends with a warning and exit code 4 (`TestInstall_WindowsServiceRestartsItself` holds the lines; no PowerShell in CI).

## Modifying: `IssueToken(ctx, actor, name, ttlDays) (Token, secret string, error)` / `IssueTokenFor(..., device)` — 1 caller: `AdminHandlers.InventoryPostInventoryAgentsTokens` (through `IssueTokenFor`)
- `device_id` (INV-26): the device's agent row shows the token under Show setup (`ReportState.Setup`, `setupToken`); merge moves it (`DeviceMerged`, registered in cmd/vedette `registerLifecycle`), delete clears it (foreign key).
- **web/features/inventory/AgentsSection**: `CreateTokenResult` shows the secret once; changing the token format (`vdt_osquery_` + 32 characters) → the regex in `parse.go`, the install script and `/intake/osquery/status` break.
- The error codes `bad_name`, `bad_expiry`, `too_many_tokens` (409, limit 500) belong to the GUI that creates tokens; `POST /inventory/agents/tokens/remove-unused` is the remove button in that same dialog.
- `actor` is stored in `created_by`: the device-approval audit line for every machine that enrols with this token records that person's name.

## Modifying: `RevokeToken` — revoking deletes the token row and (through the foreign key) its machines
- An enrolled machine gets `node_invalid` on its next call (POST-3); data already received in `inv_*` is kept. Switching to "mark as revoked" requires changing the lookup in `service.go` and the `node-prune` job.

## Modifying: the osquery protocol (`/intake/osquery/{enroll,config,log}`) — 1 caller: `osqueryd` on the customer's server
- **Install script and manual install** (`web/src/features/inventory/{scripts/*,agentConfig.ts}`): the `*_tls_endpoint` flags point to exactly these three paths; changing a path = the script's SHA-256 changes and every machine that already installed must install again.
- **Query schedule** (`schedule.go` = `OSQUERY_SCHEDULE` in `agentConfig.ts`; `schedule_test.go` matches each query, interval and platform): adding/removing a query requires changing `schedule.go`, the `columns` table in `parse.go`, the GUI and the mapper; `interfaces` is the machine-identifying query (INV-12), and removing it = no machine can record anything.
- **`os_revision`** (INV-20): a query for Windows only; the `revision` column does not exist on Linux, so it is not merged into the `os_version` query (that query would break on Linux). osquery < 5.12 makes this query fail on its own while the machine still reports as the old version (in the first hour it asks for it and `programs` every minute and then stops). It is its own answer `os_revision` of the first report (`firstReport`, `answers`; the `reported` column of ≤ 64 characters is still enough). The stored values (`win_*`, listed in `modules/core/export_policy.go`) give the OS text and the operating-system software row (below).
- **The `programs` query (INV-24)**: one combined SELECT (`programsQuery`) — the registry `PatchLevel` of earlier SQL Server versions, then `programs`; the `sql_setup` column tells them apart. Changing a column or the order of the branches requires changing `columns`, `mapPackages` (drop the `sql_setup` row), `agentConfig.ts` and the GUI test (`inventory.test.tsx`). Adding another machine-version source (Office C2R `VersionToReport`, Visual Studio) follows the same pattern: one exact value in the same query, not a wide `registry` table. Breaking the registry branch breaks **the whole** Windows list (one query): keep it plain SQLite SQL, with a single `key LIKE` constraint.
- **`sqlserver.go`**: `sqlFamilies` (year → build family) must go together with `sqlServerMajors` of findings (`schemes.go`, the year of the NVD CPE `sql_server:2014` → major); a new release (SQL Server 2025 = 17) is added to both. Dropping the KEV key from a component row (RsFx) only when PatchLevel is present: changing this condition changes which CVEs remain open after a CU.
- **Windows software row**: `windowsRow` reads `core/winrel` (the same table findings uses; including the version learned from the Microsoft page, the `windows-releases` feed): changing the NVD name, build or line (Line) of a release there changes both the row the agent sends and how findings reads the Windows entry (findings INV-15). A build outside the table and Azure Local/Azure Stack HCI give a row with no release CPE (findings: "not checked"); adding a release to the table turns that row into one read by patch. The row carries the key `microsoft|windows` and the release CPE: findings ignores a "Windows" row added by hand on the same device. `deliver` does not count `packages` for a `programs` list that lacks the OS row: changing that changes when the OS row appears after enrolment. Wazuh `select` has `os.arch`; the test's fake returns that field.
- **First report (INV-18)**: `nodeSchedule` changes `interval` per machine (60 s for a query not yet answered, in the first hour); adding a new query requires adding it to `firstReport` (`schedule.go`) and `answers` (`ingest.go`), otherwise a new machine asks for it every minute for the whole first hour. Removing `--config_refresh=300` from the script (`scripts/*`, `web/src/features/inventory/{scripts/*,agentConfig.ts}`) = a machine keeps the 60 s pace until osqueryd's next start (`TestInstall_ExitsZeroWhenEnrolledNotWhenFirstReportArrives` guards the flag). This flag makes each machine call `config` every 5 minutes (one `last_seen` write per round; limit 6/minute).
- **Approval + kind**: `Config.Approver` (inventory `ApproveEnrolled`, inventory INV-25) is required; `firstReport` passes the MAC of `binding` (the card carrying the source IP): changing `binding` or dropping the MAC changes the approval condition (with no MAC → only a row that has never seen any MAC is approved); `kindOf` (`mapper.go`) returns only kinds in the `inventory.Kinds` list (the store rejects an unknown kind, and the whole observation batch loses a row). Wazuh shares `observations`, so changing `kindOf` also changes the kind of Wazuh machines. `kindOf` is `core/observe.AgentKind`: a platform → kind table shared with the store's `AgentKindOfOS` (kind from the stored OS, the upgrade path), so changing one changes both.
- **Job `approve-enrolled` (upgrade path, INV-18 (d))**: `ApproveBound` shares `approve` with `firstReport`: changing the "done once" rule (`found` or an edge error → set `approved_at`) changes both paths. It trusts `bound_ip`/`bound_mac` written by `markResult` (the binding rule) only when `last_result_at` is within 7 days and the store sees an `agent`-source `mac` observation equal to `bound_mac` on that row (`agentSaw`); changing how binding works, how `last_result_at` is written, or dropping the agent's MAC observation in `observations` changes the approval condition at startup. Each run reads the unapproved nodes that have a binding (≤ 5,000, one `ApproveEnrolled` per node); a node for which the store has no device yet is retried on every run (daily).
- **core/server**: the four operations are `public`; the module gate (SYS-5) and `BodyLimits` are applied by `operationId` (`inventory_post_intake_osquery_*`); changing an `operationId` (changing the path in `contract.ts`) changes the body-limit key (`cmd/vedette/modules.go` receives `agentintake.BodyLimits`; `server.New` rejects a key that does not exist).
- **Reading the source address**: `Exchange.ClientAddr()` (`r.RemoteAddr`). Putting the box behind a reverse proxy/NAT makes every machine "not matched" (INV-12) and share one source budget (INV-14).

## Modifying: writes into `inventory` (`observe.Sink.Record`, `observe.SoftwareSink.ReplaceSoftware`, source `agent`) — 1 target
- **inventory**: receives `os`/`hostname`/`vendor`/`model`/`mac` observations and the package list (≤ 5,000, key `vendor|product` ≤ 400 bytes, version ≤ 100 characters). Changing the limits of `inventory.checkItems`/`cleanText` → `mapper.go` (`maxName`, `maxVersion`, `maxKeyBytes`) must change with them, otherwise the store rejects the whole list. Changing the confidence → how the store merges several sources and the "suspected"/"certain" column change with it. Changing the host identity key (MAC then IP) → duplicate devices.
- **`PkgVersion`/`PkgSource`**: `mapPackages` sets them for deb rows (osquery `deb_packages`, Wazuh deb, the box's `MapDebPackages`): the full dpkg version and the source package (`source` empty → the package name, `name (version)` → the name). Several binary packages merge into one row that keeps the **lowest** full version (`core/debver`), except kernel images (`kernelImageRE`): when the deb row has a `kernel` column attached by the box (the running kernel: a separate osquery `kernel_info` query, stored on the node `intake_osquery_nodes.kernel` and then attached to the package list (`withKernel`), the third field of Wazuh's `os.uname`, the box's `GET /v1/info` `os.kernel` through `DebPackage.Kernel`) and has its `linux-image-<release>` image, only that image gives the Kernel row its version; unknown → the lowest as for every package. A meta package (`linux-image-generic`) never gives a version or a source package. A source with a `(version)` different from the binary package's epoch/upstream → no full version (except `linux-signed*`). `TestMapPackagesKernelFollowsTheRunningKernel`, `TestMapPackagesSourceOfAnotherRelease`. findings compares against Ubuntu/Debian data; changing it → distro-package findings change (`TestMapDebPackagesKeepsFullVersionAndSource`).
- **`Packaged`**: `mapPackages` sets it for deb/rpm rows; findings (through inventory `MatchSoftware.Packaged`) advises "install your distribution's security updates" only for those rows. Adding another package table requires deciding the flag. The `upstream` flag of `content/catalog/products` (the vendor's own packages) drops `Packaged`: findings reads that row by the NVD range; wrongly marking a distribution's package loses the distribution's note (backport) for it.
- **`MapDebPackages`**: the caller is `cmd/vedette` `boxPackages` (the dpkg list of the box itself). Changing `mapPackages` for `deb_packages` also changes the software of "This box"; both sides must keep the same rows so that an osquery installed on the box does not flip the list back and forth. `mapPackages` takes a row cap: the agent and Wazuh pass `maxRows` (5,000), `MapDebPackages` does not cut (inventory stores all or rejects all).
- **core/productid** (`content/catalog/products`): package/program name → product, the key of the exploited list, the version stated in the name (Temurin "21.0.7+6" → 21.0.7; Zulu: its own build number is not taken). Changing a name or pattern there = changing the software row the agent sends (`TestMapPackagesGolden`, `TestMapPackages_JDKDistributions`, `TestCatalogueKeepsThePackageNames`); a `kev` key that is added must exist in `kev-products.json` (productid `TestCatalogue_Loads`).

- **`ReplaceServices`** (INV-22): `Config.Services` = inventory; the osquery and Wazuh port lists with source `agent` share one source row (`agent`) on the device, and the later writer wins, as with packages; the box's own ports are also written with source `agent` (inventory INV-3) but by the box's id, not through this module. The limits `maxServices`/`maxSvcName` in `services.go` must equal those of `inventory` (INV-23).

## Modifying: the pinned certificate (`GET /intake/ca.pem`, INV-11) — `install.go` (`anchor`), `Config.TrustAnchor`; cmd/vedette/boxca.go, tls.go
- **Every enrolled machine**: trust rests on the box's own CA; changing the CA key = every machine must install again. Renewing or changing the address only re-issues the leaf (machines are not affected). The CA lives in `core_secret` (core INV-33): restoring `vedette.db` + `vedette.key` keeps it; losing the master key does not.
- **`Config.TrustAnchor`** (cmd/vedette `deps.TrustAnchor`): nil = 404. The `CERTIFICATE` block filter in `anchor` (`install.go`) is the only guard that keeps the key of the box owner's file from going out (cmd/vedette passes the bytes of the `-tls-cert` file unchanged): removing it = exposing the box owner's TLS key on `ca.pem` and in the script, both of which are public (`TestContract_INV11_CaPemServesTheCertificateOnly`).
- **core**: the leaf re-issue logic must sign with this CA; a certificate supplied by the box owner is not touched.
- **GUI**: the script's SHA-256 changes when the pinned certificate changes (the script embeds it).

## Modifying: kéo Wazuh (`wazuh.go`, `wazuh_client.go`, `wazuh_handlers.go`, job `wazuh-pull`, `ScheduleOwner`)
- **core/jobs**: a 1-minute beat; the real cycle is the `core_schedule` row `agent-intake.wazuh` (an interval, at least 5 minutes, `wazuhLimits`); the form/API `interval_minutes` is that row (saved with `SaveTx`, read with `schedule.Lookup`), and when the schedule is due `askPull` sets `next_pull` = now (NULL = wait for the schedule). The first pull with an agent that has no `netaddr` yet sets `next_pull` = +1 minute once (changing `wazuhPullEvery` or `last_sync` breaks the test `FirstPullRetriesOnce`).
- **core/conn** (facade `Service.NewHTTPS`, `HTTPSTargetProblem`): changing the address or TLS policy of `core/conn` also changes Wazuh's; `TestWazuh_FormChecks` (loopback, metadata, the box) and `TestWazuh_PinMismatchStopsThePull` must be rerun. The Wazuh password lives in `core_secret` purpose `intake_wazuh.password`, opened with `Secrets.Open` like other modules (no `Reserve`/`Restrict`, so the two code-scanning tests do not change).
- **Settings → Privacy** (`modules/core/handlers_privacy.go` flow 14, `PrivacyFacts.WazuhConnected`, `cmd/vedette` `privacyFacts`, the mock `web/src/features/core/mocks.ts`, `PRIVACY.md` row 14): changing what is sent (path, fields, pace) requires editing all four in the same commit.
- **inventory**: the `agents`/`packages` counts shown on the Wazuh card; packages enter the store through `ReplaceSoftware` with an IP-only hint; changing how the store finds a device (MAC first) → review `agentIP`.
- **Wazuh server API** (external, v4.9.x per `api/api/spec/spec.yaml`): changing the field names `affected_items`/`total_affected_items`, `lastKeepAlive`, or syscollector columns → `wazuh_bad_reply` or the agent is dropped; a new Wazuh version needs one real run (a known follow-up).
- **`GET /inventory/agents`**: reads the card through `Service.Wazuh(ctx)`; it does not read tables directly outside the module.

## Modifying: the install script (`/install/osquery.sh|ps1`, the `install` block of `GET /inventory/agents`)
- Customer servers that already installed: the script runs only once; changing its **content** changes the SHA-256 in the GUI (the user compares again), changing its **parameters** requires editing the one-line command in the GUI and the uninstall instructions at the same time.
- **web/features/inventory** (`scripts/osquery.sh`, `scripts/osquery.ps1`, `installScripts.ts`): `modules/agent-intake/scripts/` is a copy; editing one side without the other turns `TestInstall_ScriptsEqualTheGUI` red (copy again with `cp`). Changing how the GUI fills `@@BOX@@/@@VERSION@@/@@CA@@` (the `const fill` line) also turns the test red: edit `fill` in `install.go` at the same time.
- **No address**: when `boxURL` yields a placeholder, the two scripts return 404 `no_box_address`; the GUI (`AgentsSection` `NoBoxAddress`, the constant `NO_BOX_ADDRESS` in `installScripts.ts`) recognises the placeholder in `server_url` and shows no command. Changing the placeholder text (`boxPlaceholder`) requires changing the GUI constant and the mock too.
- **Architecture**: the Linux script picks the package by `dpkg --print-architecture` (or `uname -m` when it is not there): amd64/x86_64 or arm64/aarch64; adding an architecture = adding a file to `PINS`, the Containerfile, `mirrorFiles`, the `SHA256SUMS` mock, the script's `case` branch (both copies), and a line in `THIRD_PARTY_NOTICES.md`.
- **TLS of the Windows script**: every request to the box goes through the C# class `VedetteBox` in `osquery.ps1` (`Add-Type`): a certificate-check function attached to each `HttpWebRequest`; the chain must contain exactly one certificate of the `@@CA@@` block (compared byte by byte), every signature and expiry still valid, EKU serverAuth, and a matching name (Windows's, or the SAN iPAddress entry when the box is an IP); revocation is not checked (the box's CA has no CRL/OCSP). Changing the certificate the box issues (`cmd/vedette` boxca/tls: adding CRL/OCSP, dropping the IP SAN, changing the EKU) requires revisiting this function; a redirecting reply must not be followed (`AllowAutoRedirect = false`). There is no PowerShell in CI: `TestInstall_WindowsPinsTheBoxCAWithoutCurl` checks only the text; the real behaviour can be proven only on a Windows Server test machine. `vedette-ca.pem` (the thing the running osqueryd pins) is written only **after** the package has passed its SHA-256 check and `msiexec` returns 0 or 3010 (any other code: stop, "Nothing was changed"), so a failed run does not break a working enrolment; PowerShell in Constrained Language Mode (WDAC/AppLocker) stops before `Add-Type` with a sentence that points to "Advanced: manual setup"; each rejection records its reason (`VedetteBox.Refusal`: no certificate, wrong address, invalid chain with its flags, not signed by the embedded CA) and the sentence "Could not download …" states that reason, so a negative trial on the test machine proves that the pinning itself rejected it. If the box raises the minimum TLS to 1.3, every Windows machine breaks (.NET 4.5–4.7 has no `Tls13`): `SecurityProtocol` must be revisited.
- **Re-enrolment**: the script compares the new token with the existing `enroll.secret`; if it differs (or does not exist) it stops osqueryd and deletes the osquery database (the default `--database_path`; the script does not set this flag). Adding `--database_path` to the flags = deleting exactly that path; removing the delete step = running again with a new token exits 3 because osqueryd keeps the old `node_key` (`TestInstall_NewTokenEnrolsAgain`).
- **Address in the script** (`boxURL`): the Box address (`Config.BoxURL func() string`, `cmd/vedette` `deps.BaseURL`) wins; changing the Box address in Settings → Box network changes the install command and the script at the next read (the SHA-256 in the GUI changes with it). Without a Box address, the request's Host may be used only when `Config.HostAllowed` (the server's Host list) accepts it; changing how `core/server` compares Host (`HostMatcher`) also changes what the script may carry. A box behind a reverse proxy/NAT: the Host is the proxy's name and must be in `-hosts`, otherwise the script carries the configured address or `<VEDETTE_BOX_IP>`.
- **cmd/vedette** (`trustAnchor`): the pinned certificate is read once at startup; changing the box owner's certificate file requires a restart so `ca.pem` and the script catch up (at the same moment the new listener serves the new certificate). A box on HTTP over loopback: 404 `no_certificate`.
- **core/updates**: the osquery package is in `managed`; changing the version = changing `osquery_version` in `AgentsResponse.install`.

## Modifying: `POST /intake/osquery/status` (optional body `host_identifier`, returns `host_last_seen`)
- Generated contract: `web/src/features/inventory/contract.ts` (`OsqueryStatusBody`, `bodyOptional`), `api/openapi.json`, `core/api/oas`, the mock `mocks.ts` (the mock keeps no machines: a machine with a name is considered enrolled when the token has a machine). The two copies of the script (`modules/agent-intake/scripts/`, `web/src/features/inventory/scripts/`, byte-identical, `TestInstall_ScriptsEqualTheGUI`) read `host_last_seen`; renaming the field breaks both. The script sets `--host_identifier=specified` + `--specified_identifier=<the filtered machine name>` (it does not let osquery find the name by itself, which could be the short or the full name) and then asks for exactly that name; two machines with the same name under one token still replace each other (this was already so).

## Modifying: kho gói osquery (`GET /install/osquery/{file}`, `deploy/osquery/PINS`, `deploy/containers/core/Containerfile`)
- Changing the osquery version = one commit that changes **four places**: `deploy/osquery/PINS` (the version + 5 SHA-256 values), `OSQUERY_VERSION` in `web/src/features/inventory/installScripts.ts`, `OsqueryVersion` in `install.go`, and the osquery line in `THIRD_PARTY_NOTICES.md`; `TestInstall_VersionsAgree` catches the first three numbers disagreeing, and the image build step catches a wrong hash. The file names in the script, in `mirrorFiles` and in the Containerfile must match (the test reads all three).
- **`core` image**: +~131 MiB (5 files: 136,841,525 bytes, measured 2026-11-13 with the `osquery` step of the Containerfile; the two arm64 packages add 57 MB; already compressed, so the image layer is about that size). The directory `/usr/share/vedette/osquery/` is the default of the `-osquery-dir` flag; changing one side makes the store return 404 `mirror_missing`. A build that does not go through the image (`make dev`) lacks that directory: the store returns 404 `mirror_missing`, and the install script on a customer server fails when it downloads the package.
- **Download**: one transfer per source address at a time (IPv6 /64), and at most 8 transfers for the whole box (429 `rate_limited`, `Retry-After: 5`); `SHA256SUMS` does not take a slot. A machine that reads slowly holds its address's slot for at most 10 minutes (also the time cap of one download: a server slower than ~51 KB/s cannot download a 30 MB package). Several servers behind **one NAT** share one slot: install one after another, or the script retries. More than 8 addresses installing at once: the excess transfers must retry. The script currently does not retry on its own on a 429 (a known follow-up). Known limit: an attacker with 8 source addresses can still fill all 8 slots, 10 minutes each, repeatedly; a minimum download speed is needed (a known follow-up, same class of issue).
- There is no new outbound data flow (nothing is downloaded at run time), so `PRIVACY.md` does not change.
- **Direct download in the agent dialog**: `GET /inventory/agents` `install.packages` reads `SHA256SUMS` and the file sizes of the store directory (`packages`, `readSums` in `install.go`); the GUI (`AgentsSection` `Downloads`, `agentConfig.ts` `osquerySteps`) builds a **relative** download link `/api/v1/install/osquery/<file>` and the manual install command (download from `server_url`, check that exact SHA-256, then `dpkg -i`/`rpm -Uvh`/`msiexec`). Changing a file name, adding an architecture or changing the `SHA256SUMS` format (Containerfile) = changing `mirrorPackages`, the enums `platform`/`format`/`arch` in `contract.ts` (OpenAPI + `core/api/oas`), the mock's `MOCK_PACKAGES` and the manual install command (names per `dpkg --print-architecture`/`uname -m`). An empty list → the GUI says the box has no package and shows no install step. Changing the Content-Type/Content-Disposition of the store = `TestMirror_DownloadHeaders`; the admin's own browser is also subject to the one-transfer-per-address limit (a second transfer gets 429 until the first finishes).

## Modifying: the `node-prune` job (`Prune`, an ordinary job) and the `intake_prune_clock` table
- It does not run while the module is off: when it is off every machine is "silent", so silence must not be counted. The last run is kept in the DB (`intake_prune_clock`): the first run after a gap of > 3 hours (module off, box off, restart, upgrade) adds the gap to the `last_seen` of every machine (no later than that moment). `last_seen` is used only for cleanup, so moving it changes nothing else. Switching to Housekeeping = a box that is off for 90 days would cut every machine permanently. Changing 90 days (`NodeSilentDays`), 30 days or the 3-hour threshold (`pruneGap`, which must be larger than the `pruneEvery` beat of 1 hour) = changing the promise in CONTRACT POST-4 and DATA_MODEL. Deleting the clock row (or restoring an old DB) = every machine gets 90 more days from the next run.
- **core/export** (`modules/core/export_policy.go`): `intake_prune_clock` is an exported table; adding a column requires classifying it there (`TestExport_PolicyClassifiesEveryColumn`).

## Modifying: `ScheduleOwner`, `WazuhScheduleKey`, `askPull` (the `agent-intake.wazuh` schedule in core/schedule)
- **core/schedule** holds the pull cycle (interval ≥ 5 minutes, default 15, `DefaultOn: false`; only an admin edits it): `cmd/vedette/wiring.go` registers the owner, and `saveInterval`/`pauseSchedule` store and turn it off together with the connection (the `intake_wazuh` table has no cycle column). Changing `wazuhLimits` or the default requires changing `web/src/features/core/schedulesMock.ts` and the `bad_interval` of the Wazuh form.
- **cmd/vedette `scanning.go`** (`wazuh`, `nextStart(…, agentintake.WazuhScheduleKey)`): the "Next" of the Wazuh engine in Scanning reads this schedule row; changing the key loses it.

## Modifying: `ListTokens`, `Wazuh(ctx)` (the two Scanning engines `osquery` and `wazuh`)

## Disabling this module
- The Agents section in Inventory shows "module is off"; the install script and `/intake/*` return 404 (the SYS-5 gate, test `TestContract_SYS5_ModuleOffIs404`); osquery on customer servers gets 404 on config/log (osquery retries by itself; cheap, through the gate); no enrolment/reporting is possible.
- `inventory`: devices with source `agent` are no longer updated; findings based on old packages may become stale, and the UI shows the age of the data. Tokens, machines and data are kept (`node-prune` also stops; the time spent off does not count toward the 90 days of silence).
- `reports` (PDPL): the inventory-sources entry no longer has a new `agent`.
- `inventory` (`retention.go`): the data-retention clock counts time only while agent-intake is on (`agentSince`); `core/server/modules.go` blocks `/install`, `/intake` and `/inventory/agents` by module.

- **inventory**: one `hostname` observation with source agent, once for each node (at any age) until `system_info` is received; the device name (`DisplayName`) changes from vendor/IP to the machine name on every page, message and report.

## Modifying: "ask the agent now" (`report.go`: `AskReport`, `ReportState`, `askOpen`, `answeredAsk`, `osAnswer`; INV-23)
- **The close rule**: the ask ends on a list taken after the node's own OS answer (`os_taken_at` >= `report_asked_at`). A change of how `nodeKernel`/`nodeWindows` read `kernel_info`/`os_revision`, or of which answer builds the Kernel or Windows row, must keep `osAnswer` in step, or an OS update's ask closes on a list with the old build.
- **web/features/findings** (`Updated.tsx` `AgentAsk`, `ToFix.tsx` `DeviceUpdated`, hooks `useAgentReport`/`useAskReport` in `web/src/features/inventory/api.ts`): the button, its busy state and the "Asked at …" line read `agent`, `asked_at` and `wazuh_interval_minutes`; renaming a value or the 409 `cannot_ask` / 429 `rate_limited` codes changes what the person sees. The To fix card shows one control per device, so the answer must be per device, not per software row.
- **Schedule** (`nodeSchedule`, `reportQueries`): adding a software query to the schedule (a new package table) must decide whether an ask speeds it up; `TestScheduleIsReadOnly` still pins every query, an ask only changes `interval`.
- **inventory** (`observe.AgentDevices`, `inventory.Service.AgentDevice`): the device → node link is `inv_asset.agent_key`. A device whose binding the inventory released (re-enrolment, revoke) is answered `none`/`wazuh` until its node reports again.
- **Wazuh marker** (`wazuhReads`): the same rows as `WazuhAgentAddresses` (current generation, IP or MAC); a change of how the pull records where it delivered changes which devices get the Wazuh line.
- **Timing words in the GUI** ("within about 5 minutes"): depend on `--config_refresh=300` in the install scripts, `firstReportInterval` and `sourceWindow`; changing any of them changes the promise. An old install without `--config_refresh` never re-reads its config: the ask then ends after 15 minutes without effect.
