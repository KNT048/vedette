| D-511 | **Device types have two levels, and Vedette says what a device most likely is from the signals it already holds (beta item 25, P0 journey A2 "know what each device is": on the N100, 11 of 20 devices were "Unknown" although their network card maker and open ports told a person at once: Fortinet + SSH, Juniper + web, Grandstream, VMware, a camera with RTSP, the box's own gateway, a MacBook).** (1) **Two levels, one list.** `content/devicetypes/types.json` holds 14 categories (Network, Security, Wireless, Servers, Computers, Phones and tablets, Printers and scanners, Cameras and video, Telephony, Storage, Smart devices and IoT, Building and industrial (OT), Web and cloud, Unknown) and 89 types (`id`, `label`, `category`, `acts_as`, `aliases`), curated by us (no third-party taxonomy copied). The 13 kinds of today are types with the same ids, so stored devices, settings, response rules, SNMP/nmap/passive observations and API clients stay valid. Go (`content/devicetypes`), the web (it imports the same file), the zod contracts, `api/openapi.json` and ogen all come from that one file; the hand copies (inventory, findings, scan, response FE, labels) read it. The SQL CHECK on `inv_asset.kind` becomes a format check (migration inventory 0004; Go validates against the list). (2) **Behaviour keeps the 13 kinds.** Each type `acts_as` one of the 13 kinds, and every place that branched on a kind branches on that: fragile defaults, "unknown means careful", never-touch gateways (D-177), honeypot decoy blending, SSH-credentialed candidates, PDPL controls, the response `device_type` condition. A laptop acts as a computer, a VPN gateway as a firewall, a modem as a router; every phone, embedded, OT, telephony and building type acts as `iot` (fragile by default), so a type a person picks never gets less care than the kind they would have picked before. Categories are for people: the Devices list shows "category · type", filters by category, and the type picker groups by category. (3) **Identification rules** (`content/devicetypes/rules.json`, ordered, first match wins): conditions on the network card maker or make, MAC prefix, open TCP ports (any / all), what services said (nmap product, extra info and device type, page title, certificate subject), host name, model, OS, "is the box's default gateway", and the last address byte; the result is a type, a confidence (0.25–0.6) and a sentence of evidence built from what matched ("Fortinet network card and SSH on port 22: most likely a FortiGate firewall (Fortinet also makes FortiAP access points and FortiSwitch switches)"), and a model when a certificate or title states it (CN FGT60F… → "FortiGate 60F"). It runs when the device list or a device is read, only for a device whose kind is still `unknown` (no person, agent, SNMP, nmap or passive kind), and is returned as `guess` (source "inferred"), never written into `kind`. So a guess changes no behaviour: scans still treat the device as unknown (careful), it is never a trusted kind for D-177 or any blocking decision, and a person's type always wins; the device page says "Most likely a FortiGate firewall — because …" with **Confirm**, which records the type as the person's (as picking it does). (4) **Why services had no banners, and the fix.** A device of unknown kind (or fragile) gets only the one gentle first scan (no `-sV`, D-45, D-84); `-sV` runs only for a known, non-fragile device or a person's pick (D-501). And where `-sV` did run, nmap's extra info and its service device type (`<service devicetype>`) were parsed and dropped (only product and version were kept, #668 kept banners out of software). Now the normal and versions scans also run nmap's `http-title` and `ssl-cert` (both in nmap's "default, safe" categories: one GET of / and one TLS handshake, on a port already open, which `-sV` probes anyway; gentle unchanged, no new category or wildcard), and each open service keeps a `detail` (at most 200 characters: extra info, device type, page title, certificate subject) as evidence for identification, shown under Open services, never software and never matched against KEV. **(4b) Lead decision (review of #714):** the one gentle scan of a device whose kind is unknown and that nobody made fragile (`gentle_titles`) also runs `http-title` and `ssl-cert` on the web and TLS ports it finds open (one TLS handshake and one GET of / per port, like runZero's default TLS/HTTP grab), each script capped by `--script-timeout 20s`, so a FortiGate's certificate or J-Web's title names the device without a Scan now; a fragile device (by a person, or by a kind a sensor or person gave it) keeps today's gentle scan exactly. Inventory migration 0004 clears `first_scan_at` of the unknown, not fragile devices that already had their gentle scan, and sensor-active's first tick after a start queues the devices still waiting for their gentle scan (inventory `PendingGentleScans`; only a new device's discovered event queues one otherwise), so each gets that one scan again (rate 1, top 100 ports). A titles scan stops if the device is made fragile while it runs. A long certificate subject or title is shortened (commonName first), never dropped. (5) nmap's own device types that had no kind now name one (phone → smartphone, VoIP phone → IP phone, VoIP adapter, media device → media player, power device → UPS; iOS/Android "general purpose" → smartphone), all acting as `iot` as before. (6) **Review of #714:** acts-as also drives the response `device_type` match, so a type marked `no_auto_isolate` (PBX, VoIP gateway, SCADA server, industrial switch, PLC, HMI, RTU, medical device, server management card, UPS, PDU, alarm, door access, building/HVAC controllers, power meter, solar inverter, EV charger) is never covered by a rule keyed on the kind it acts as ("camera,nvr,iot"): cutting those off harms more than it helps. A load balancer and a proxy/web filter act as **router**: they stand in front of everyone's traffic (a forward proxy is the source of every outbound connection), so never-touch keeps them, without counting as the PDPL "firewall" control. A guess carries the other types the same signals fit (`alternatives`, a Fortinet card: access point, switch) and the device page offers them next to Confirm, so confirming is a choice and a fragile access point is not silently made a firewall. Guesses (and the host's gateway, cached a minute including a failed read) are computed only for the Devices page and the device page, never for other modules' reads. **Not chosen:** categories driving behaviour directly (a switch would turn fragile with "Network", the saved fragile list and response rules would need migrating); writing a guess as an observation or into `kind` (it would lift a device out of "unknown, careful", feed never-touch and response rules, and stick after the signal is gone); Fingerbank, Satori, nmap-os-db or JA4D data (licences, v8 §4); SNMP (item 26, another PR). **Ceiling (ponytail):** a guess needs a rule; a maker whose devices vary (HP with web ports only) stays Unknown with no guess until a scan reads its page title or certificate or a person sets it.
