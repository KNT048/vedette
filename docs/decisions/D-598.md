| D-598 | **One machine is one device: a phone or laptop with a private Wi-Fi address is joined by its host name, an osquery node by the node the box enrolled; never two machines with burned-in MACs by name (issue #829, J2; inventory INV-31, agent-intake INV-12).** (1) **The N100 case.** kien's MacBook (private Wi-Fi address `b2:f0:09:…`, locally administered bit set) became three devices (.145, .137, .138), each with a "new unknown device" incident: the inventory finds a device by MAC then IP, and macOS, iOS, Android and Windows pick a new random MAC per network or per day, after which DHCP gives a new address. (2) **The name rule** (`sameMachine`, run with the D-515 join on every device a sensor batch touched): two rows are one machine when neither has a universally administered (burned-in) MAC, at least one has a locally administered one, both carry the same host name (first label, any case; not generic: `iphone`, `ipad`, `android`, `localhost`, `macbook-air`, `raspberrypi`, the D-515 defaults…; not shorter than 3, not a UUID, not built from an address), they state no other model or OS, and exactly one other row qualifies. Kept row: declared, else approved, else older; it takes the newer address unless a person declared it; the newest MAC wins by the usual observation rules; the approval never moves (review H1 of #722). A row created in the same batch is never announced; an older one is announced merged and deleted, so notify closes its incident (D-554) and findings moves its findings (D-515). (3) **Agent identity**: agent-intake hints a report with `osquery:<node id>` (the id the box gave the node, not a value the machine chose). Order for a report: node → address (the TCP source, checked against the node's interfaces, INV-12) → new row; never the MAC or host name the agent claims, which are self-declared (D-265 (4)). The node is bound to the device its report reached by address only when no source saw that device with a MAC the agent did not report (the INV-25 test). Its later reports find that device and move it to the new address. A row an agent made before it was bound, which then lost its address to the device that owns the MAC the agent named, joins that device (`agentOrphan`: three sources agree). Sensors keep MAC → IP (the MAC comes from the wire). SNMP answers attach by the address of the approved device the round targeted (no new rule needed); sysName feeds the name rule; engineID is not read today. Wazuh sends no key: its agent ids belong to one manager and are reused after a manager change. | Why: every top-tier inventory treats MAC randomization as a dedup problem it solves with other identifiers, and none merges burned-in MACs on a name alone. runZero correlates on MAC, IP, host names and fingerprints, says devices that change MAC (mobile devices) make duplicates and that weak data merges wrongly, and offers `name_overlap` / `mac_overlap` searches because those alone give false positives (https://help.runzero.com/docs/understanding-assets/, https://runzero.freshdesk.com/support/solutions/articles/70000636375). Lansweeper keys non-Windows assets on the MAC (IP when none) and added a serial check because dynamic MACs and virtual NICs merged wrong (https://docs.lansweeper.com/docs/understand-the-reconciliation-engine, https://community.lansweeper.com/t5/forum/merging-of-assets/m-p/48608). Portnox documents the symptom one-to-one ("multiple records for the same physical device") and the test we use: second hex digit 2, 6, A or E is a randomized address (https://doc.portnox.com/topics/kb_mac_address_randomization). A published patent on randomized-MAC identification compares DHCP host name, FQDN and OS across MACs (https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/11528252).
