| D-418 | **Reinstalling after `install.sh --uninstall --yes --keep-data` brings Vedette back with its data, and a re-run bootstraps even while vedette-host runs (customer walk 2, W2-9 and W2-10).** What was wrong: `--keep-data` removes the Quadlet units and the images but keeps `/var/lib/vedette-host`, so `containers/versions-core.json` was still there and the next run said "already bootstrapped", skipped the bootstrap and failed on "vedette-core.service not found" (exit 7, N100, n4 over n3 data); after the records were moved away by hand, `vedette-host -bootstrap` refused with `daemon_running` (exit 6) because an earlier run (or the package's restart on upgrade) had started the host. (1) **The bootstrap is skipped only when core has both its record and its unit** (`versions-core.json` and `vedette-core.container`); a missing unit is installed again. (2) **Kept data with no unit of any container** (records in `containers/versions-*.json`, none of `vedette-{core,sensor,scan,honeypot}.container`) is what `--keep-data` leaves: the run clears the host's container records (`versions-*`, `pulled-*`, `transition-*`, `containers/units/`; never the data, the backups, the release index or the host's package records) and bootstraps its own release, same or newer, over the kept data, then records what runs. The records are cleared by the install, not by the uninstall, because until then they say which release last ran on the data. (3) **An older release than that is refused in preflight, before any change** (`dpkg --compare-versions` on the SemVer with `-`→`~`): core's migrations are forward-only and an older core would run on a newer database. Before the records are cleared the release is noted in `/var/lib/vedette-install/kept-release`, removed only once the bootstrap wrote core's unit, so a run that stops half way keeps the guard. A newer release is allowed with a warning: unlike Settings → Updates this path takes no `pre_update` backup, so the way back is a backup made before the uninstall (RUNBOOK §1.3). (4) **The installer stops a running vedette-host before `-bootstrap`** and starts it after (`start_and_wait`), and again from `cleanup` when the run fails, with the honeypot when it ran (it `Requires=` the host and stops with it): the bootstrap stays a one-owner operation (D-142) rather than going through the socket, which the installer cannot use (not core). Not chosen: (a) the uninstall clears the records: it loses the downgrade guard; (b) the host re-renders missing units from its records at start: the images are removed by the uninstall, so it would still need the network, and it is new host behaviour for a state only the installer makes; (c) keeping the images on `--keep-data`: the uninstall promises to give the space back and the customer path downloads the package anyway, so a keep-data reinstall needs the network like a first install. Known limits: `min_upgrade_from` of the new release is not checked against the kept data (the bootstrap has never checked it), and there is no automatic backup before a newer core migrates kept data (deferred). Reviewed by an independent Opus reviewer (round 1: the guard lost after a failed run, the honeypot left stopped, `RELEASE` read from the environment, no backup on the newer path; all fixed or written down). Verified by effect in `scripts/dev/install-check.sh` (setup through the API, `--keep-data`, older release refused, reinstall: setup still complete and the administrator signs in; then core's unit removed with the host running) and `TestInstallSh_KeepDataReinstallReadsAndClearsTheHostsRecords`.
