| D-469 | **Blocklist honesty: a block on an address the list can never publish is refused when it is planned, and the empty Block list says what fills it (S-RESP-3, INV-17; beta feedback item 7, 2026-11-13).** (1) **Before**: the published list already dropped every non-public address (`publishable`, table `notPublishable`, INV-17), but `blocklist_add` on 192.168.x was accepted, approved, reported "Added to the block list … Read back: the entry is present" and never published; no `refused` line was written. (2) **Now**: `planAction` refuses a `blocklist_add` whose address is not publishable with **`not_public` (409)**, right after the never-touch check (the gateway or the box still answers `never_touch`), using the same `publishable` table (no new list; the IPv4 documentation blocks stay publishable as INV-17 already says, because the sample data uses them; IPv6 2001:db8::/32 is refused). `planAction` is the one planner of every path, so all refuse the same way and log `refused`: rule runs and manual runs (`fire`), AI proposals (`Propose`), requests from AI plans (`RequestProposal`), AI plans when stored (`savePlan`: `plan_invalid … (not_public)`); the simulation shows the error on that step. `carryOut` refuses an older pending item again before it runs (item `failed`, `refused` line), so "Added" is never said for an address that is not published. The publish-time filter stays as the last layer and stays silent: a line per firewall pull (every 5 minutes) would flood the append-only log; spec §5 now says so. Mock: the same check in `engine.ts` `planAction` (IPv4, the box's IPv4 rows). (3) **GUI**: the empty Block list says that only approved "block" actions fill it, that only public addresses are published, that the ready-made rule "Known-bad connection: add the destination to the block list" ships off, with a link to the Rules tab (template gallery); the address row stays so the firewall can be set up first. **Why refuse at the producer, loudly**: firewalls take whatever the feed holds (FortiGate's IP threat feed is one IP/range per line, private examples included, no filtering of its own), so the producer must keep the customer's own networks out; pfSense documents blocking private networks only on WAN because on a LAN it "can potentially block required local traffic"; pfBlockerNG's IP suppression drops RFC 1918 and loopback entries from downloaded feeds. Vedette did the filtering already, but silently; a person must learn at plan time that the block will do nothing, and that isolating a LAN device is a device action (blocklist-format §1).
