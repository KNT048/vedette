| D-504 | **A scan reads what a Windows device says about itself; a banner is not software; a box's first scheduled scan is tonight (customer walk 3 W3-4, W3-5, W3-6; S-SCAN-1, S-SCAN-4, S-INV-1).** (1) **Two pinned NSE scripts** join the `normal` and `versions` nmap shapes (`--script rdp-ntlm-info,http-ntlm-info`, exactly that list in that order; `nmapargv.Scripts`, checked by `ValidateNmapArgs` and the worker; no category, no wildcard, no `default`/`safe`, gentle has none). Each sends one NTLM NEGOTIATE (type 1) with no credentials and reads the CHALLENGE (type 2), which carries the device's Windows version and build and its names; neither ever sends an AUTHENTICATE (type 3), so nothing logs in. rdp-ntlm-info runs only on an open RDP port, http-ntlm-info only on an open HTTP port (a GET of `/`; nmap's http library follows a few redirects, only on the same host, port and scheme, never with credentials). The probe log's `flags` column (INV-9) holds the line with the scripts. They are in `normal` too, not only `versions`: otherwise a device identified as a PC would get the `-O` shape on its next scan and lose its build to the fingerprint guess. **Not chosen**: `smb-os-discovery` (it opens an anonymous, then a guest, SMB session, which is a logon attempt that shows up in the device's security log, and it needs SMBv1, which Windows 10 and 11 turn off); `smb-protocols`/`smb2-capabilities`/`smb2-time` (they give only dialects, capabilities or the clock, never the OS or its build; the Windows answer on 135/445 is already in `-sV`'s banner); `ms-sql-ntlm-info`, `smtp-ntlm-info` and the other NTLM scripts (they work the same way but for services rare on a small office's devices; add one when a walk needs it). **Version skew**: a job carries the shape name, not the argv (D-111 (3)), so a worker from an older release builds its own line for `normal`/`versions`, without the scripts. Core and the scan worker ship in one release, so this lasts only during an update. The probe log then lists scripts that were not sent, never the other way round, and identification works as in D-501. No proto bump and no new shape: a new shape would make the older worker refuse every discovery scan (`invalid_job`). (2) **The NTLM answer is untrusted** (INV-7): only `<elem>` of those two script ids on an open port is read; `Product_Version` must be `major.minor.build` (no revision, e.g. `10.0.22631`), names `^[A-Za-z0-9][A-Za-z0-9._-]{0,99}$`, each at most 256 bytes and printable, the first value wins; anything else is dropped, and the XML limits of the parser still fail the whole batch. (3) **What it records**, only when something else on the device says Windows (review M1): `-sV` read a Microsoft product on the port that answered (Microsoft Terminal Services, Microsoft IIS httpd, Microsoft HTTPAPI), or 135 and 445 are open; and no sure non-Windows fingerprint and no non-Microsoft OS CPE of a service (OpenSSH's Ubuntu banner) says otherwise. FreeRDP-based RDP servers on Linux (gnome-remote-desktop) answer 6.1.7601, and proxies pass IIS's NTLM through: without this check a Linux box became "Windows 7". Then: the OS at the top nmap confidence (0.95; it outranks the `-O` guess), its computer name when nmap has none, and one software row (`microsoft`/`windows`, `windows server` for a server). A build only a client has gives that release and type pc (`Microsoft Windows 11 23H2 (build 22631)`); a build only Windows Server has (20348) gives that release and type server; a build both share (14393, 17763, 26100, and the 6.x ones) **names both and gives no type** (`Microsoft Windows 10 1809 / Server 2019 (build 17763)`, review M2: in a small office 14393 and 17763 are mostly Server 2016/2019), unless 88 and 389 are open (a domain controller, so Windows Server); an unknown build is "Windows" with the build, no type ("Windows Server" on a domain controller). Builds map to releases by Microsoft's release tables. **The row has its version but no KEV match keys** (`Guess`, as D-501 does with a fingerprint): the device names its release but not its monthly update revision (UBR), and NVD ends Windows ranges at a revision (`10.0.22631.4317`), so with keys it would mark every Windows flaw fixed since that release as affected: the false-CVE flood of D-501 (3). The identification reason is the new `os_no_patch_level`, whose note says to add the system it runs, Windows or Windows Server (winver shows which), with its full version on the device page, or install the osquery agent. (4) **Port rule**: with no type from NTLM or a sure fingerprint, RPC 135 and SMB 445 open together set the type pc (server with 88 and 389) at 0.4, never an OS or a version, and **only after the versions scan** (review H1). The inventory ranks a value by source before confidence and `nmap` outranks `passive`, so after a gentle or normal scan this 0.4 would beat any passive type: a printer, PLC or camera that passive data typed (Windows-embedded HMIs and print servers have 135 and 445) would become a pc, lose "fragile" and get the full scan. The versions scan is only for a device whose type is still unknown, with no passive, agent or manual type (`pickedPlan`), so there the rule replaces nothing. 445 alone gives nothing: Samba NAS boxes have it. `-O` stays off for unknown devices (`versions`), and fragile types (printer, camera, PLC…) still get only the gentle scan (D-45). (5) **W3-5: an OS banner is not software.** A service whose only CPE is an OS one (`cpe:/o:`) or that has no CPE gives a software row only when `-sV` read its version: "Microsoft Windows RPC" (`cpe:/o:microsoft:windows`) and other versionless banners stay under open services only. An application or device CPE (`cpe:/a:`, `cpe:/h:`) stays a software row even without a version (review M3): a product match on an edge appliance (an SSL VPN or OWA banner) is what the KEV list is about, and dropping it would be a silent false negative; the W3-5 complaint came from OS-type banners. (6) **W3-6: the first scheduled scan of a box runs in the next allowed window**: while no scheduled run has ever started (no `scan_run` with trigger `schedule`; W3-9 below), every window day's slot at the schedule time counts, whatever the weekday of a weekly schedule, and next run says so (Friday 14:40 with the weekly Sunday 23:00 default and 22:00–05:00 every day: "tonight 23:00", not "15 Nov"). Such an extra slot that closed or had nothing to scan is not recorded (no "missed" audit), so the first run is the first window that scans something; from then on the weekday counts. An extra slot counts only when the schedule was saved and the scope confirmed **before** it (review M4, the rule `missSlot` uses for "due"): a box set up at 23:30 inside an open window waits for the next night instead of starting at once. A first run on the night before the weekday is followed by the weekday's run the next night (Saturday, then Sunday): accepted, the first check is what was late.
