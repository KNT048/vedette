# Ids Contract

> Tier: optional (off by default, Preview) · Story: S-IDS-1 · Last verified: 2026-11-21 (every claim checked against the code)
> Source of the actual behaviour: `web/src/features/detection/{contract,mocks}.ts`.

## Invariants (always true)
- **INV-1** A log line is untrusted data (SYS-6): `Parse(kind, line)` is total and bounded: a line over 4 KiB, broken UTF-8, or a line cut by the logs module (`" ...[cut]"`) yields no event; a required field written twice, a stray quote, an address that is not an address (it has a zone), a port outside 0..65535, or an unreadable priority yields no event (fail closed, no guessing). A signature is at most 300 characters and a group at most 120; control and formatting characters (bidi) become spaces; at most 8 CVE ids per event, in the form `CVE-YYYY-N{4,7}`, sorted by year and then number. Go regexps run in linear time, and every quantifier is bounded. Tests: `FuzzParse`, `TestParseRefusesWhatIsNotSafeToRead`.
- **INV-1b** A syslog source over UDP (and TCP) is identified only by the sender's IP (logs FORBID-5): a machine on the LAN can spoof the firewall's IP and send forged IPS lines, creating alerts, `intrusion` incidents and a false "under attack" status. A TLS source with a pinned client certificate (logs POST-1) cannot be spoofed. For that reason notifications have an hourly cap (POST-1) and the page states the source of every alert; customers should use TLS for firewalls that send IPS events.
- **INV-2** Readable formats, by log source kind (`profileKinds`): FortiGate (`type=utm subtype=ips`: `attack`, `attackid`, `severity`, `srcip`, `dstip`, `dstport`, numeric `proto`, `cve` when FortiOS writes it), Suricata/Snort (the alert line `[gid:sid:rev] msg [Classification: …] [Priority: n] {PROTO} src -> dst` of `alert-syslog`/`fast.log`, IPv6 without brackets with the port after the last `:`, ICMP without a port; only when the syslog program is `suricata`/`snort`) and Suricata EVE JSON (`event_type=alert`, `alert.metadata.cve` in the form `CVE_YYYY_N`), Sophos (`log_type="IDP"`), SonicWall (`m=608|609`), Palo Alto (THREAT `vulnerability|spyware`, field positions 4, 5, 8, 9, 26, 30, 33 `name(id)`, 35), Meraki (`security_event ids_alerted`). Priority 1..4: Snort/Suricata keep it as is (greater than 4 becomes 4); textual levels critical/high/medium/low(info) map to 1/2/3/4. CVE ids come from the CVE field and from the signature name. Counted per profile: `TestCountIPSLinesPerProfile` (N IPS lines → N alerts, M with a CVE; a line that is not IPS → 0).
- **INV-3** One alert per (`log` source, profile, signature, sid, the CVE ids the event names, source address, destination address, UTC hour) (`dedupe_key`; the CVEs are part of the key, so the CVE set of an alert never changes and the incident key recomputed at read time matches the key at open time; `ids_alert_cve` is capped at `MaxCVEs` = 8 rows per alert); a repeated event only raises `count` and widens `first_ts`/`last_ts`. `source` is an open vocabulary (`log` today; an on-box engine later adds a value without changing the table). `TestOneAlertPerSignatureSourceDestinationAndHour`.
- **INV-4** `Offer` (called by the logs module after the batch has committed) never writes the database and never waits for the core writer (logs INV-12): it only reads and merges in memory, with at most `MaxPending` = 2,000 pending alerts (the events of the 2,001st alert are dropped and counted, with one WARN per flush round). The `flush` job (5 s) writes one transaction per round; a failed write returns the alerts to the buffer (merged with newly arrived ones, still within the `MaxPending` cap, with the overflow counted as dropped) so the next round writes them again. Stopping the process loses at most 5 seconds of unwritten events (accepted: the raw line stays in `logs_events`). Module off: `Offer` does nothing, and lines received while it is off are never read back. `TestNothingIsReadWhileTheModuleIsOffAndTheBufferIsBounded`.
- **INV-5** The device (`src_asset_id`, `dst_asset_id`) is the only device that has that address at the moment the event arrives (an IP in the list, or an SNMP-read address typed by the user, like the log source); two devices with the same address → no device. The name is read at answer time. Merging devices → moved inside the inventory transaction (`DeviceMerged`); deleting a device → the foreign key is set to NULL and the alert keeps the address. `TestMergeMovesAndRetentionDeletes`.
- **INV-6** Retention: `RetentionDays` = 90 days after the last event, at most `MaxAlerts` = 50,000 rows (oldest deleted); the `purge` job (Housekeeping) and every flush round.
- **INV-7** The severity of an alert is computed at read time: priority 1/2/3/4 → high/medium/low/info; **critical** when the targeted device is affected (an open finding) by a CVE the alert names. The alert's `findings` are the findings of `dst_device` for those CVEs, with the findings' status (`Findings.Linked`). A device a person ignored lists no findings, so an alert at it is rated by its priority alone.

## Postconditions
- **POST-1** After every flush, the alerts written are announced with `ids.alert.detected` (`AlertEvent`: `alert_id, source, target, title, what, action, severity, link, at, devices`); notify opens, counts or **raises** an incident of kind `intrusion` keyed by (`source` = the attacking address, `target` = `cve:<the CVEs>` or `rule:<sid>:<signature>`): one incident per (CVE or rule, source) while it repeats; critical when the targeted device is affected. `link` = `/detection/alerts/<id>`. Fixed order: most severe first (critical first), then newest, then the incident's source and destination addresses. An incident key already announced in this clock hour at an equal or higher severity is not announced again (the alert row still counts events); a higher severity is announced again, and notify raises the open incident to that severity with a separate message (`<id>-raised-<severity>`). The cap `AlertEventsPerHour` = 100 announcements per clock hour (like `IocEventsPerHour` in logs): beyond the cap the alert is still stored and shown, and **one** summary incident per hour is announced (`source=ids`, `target=more intrusion alerts <hour>`, `link=/detection`, the highest severity among the part not announced, at least medium); when the part not announced in a later round of the same hour has a higher severity than the summary already announced (an attack on an affected device after the cap ran out), the summary is announced again with the same key, the new severity and the current count, so notify raises it and sends a raise message (a few messages per hour at most). `TestACriticalAlertAfterTheBudgetRaisesTheHoursSummary`. `TestAFloodOfForgedSourcesIsAnnouncedWithinTheHourlyBudgetMostSevereFirst`, `TestARepeatAtAnAffectedDeviceRaisesTheIncident`, `TestAFailedFlushKeepsItsAlertsAndFindingsAreReadOncePerPage`.
- **POST-2** `GET /detection/alerts` (viewer): window `24h|7d|30d` by last event (anything else → 400 `bad_window`), `cve` (wrong form → 400 `invalid_cve`), `device` (source or destination), `q` over signature, group, addresses, device name, CVE; sorted by `last` (default) or `count`, ties by id; `offset`/`limit` ≤ 200; `total` is the number of matches across all pages. `GET /detection/alerts/{id}` → 404 `not_found` when absent. `incident` = the newest intrusion incident of the key that was open before or at the last event (notify `IncidentOf`), `null` when notify is off.
- **POST-3** The "attacked CVE" port: `Attacked(ctx, since)` → for each (CVE, destination address): the device, first/last time, event count, newest alert. The findings module does not read this port yet; the only reader is the `idsFindings` adapter (`cmd/vedette/ids.go`): an open finding of a device for which an alert within `AttackWindow` = 14 days names the CVE (at any destination address) has the status `under_attack` in the alert's `findings`, and other open findings are `exploited`. `TestAttackedPortRaisesAnAffectedFindingToUnderAttack` (fake consumer), `cmd/vedette` `TestWiringFirewallIPSEventRaisesAnIntrusionIncidentAndTheFindingIsUnderAttack`.

## Forbidden
- **FORBID-1** Blocking or modifying traffic (detection never blocks); opening ports, running processes, calling out.
- **FORBID-2** Interpreting the content of a line as a command; branching on the `what`/`title` text (display only).
- **FORBID-3** Reading another module's tables: inventory, findings and notify only through the ports (`Inventory`, `Findings`, `Incidents`) wired by `cmd/vedette/ids.go` (address → device through `logsInventory` in `cmd/vedette/logs.go`, so this includes SNMP-read addresses taken from sensor-active `ReadAddresses`).

`GET /detection/overview` belongs to core (`cmd/vedette/detection.go`): it answers even when this module is off, reading its `Summarize`.

## Tables owned
`ids_alert`, `ids_alert_cve` (main database). Foreign key to `inv_asset` (`ON DELETE SET NULL`).

## Events
- **Emits**: `ids.alert.detected` (POST-1).
- **Receives**: none (log lines arrive through `logs.Config.Received`).

## When the module is off (SYS-5)
No `/detection/alerts*` routes (404), no `flush` job, `Offer` does nothing; the `purge` job (Housekeeping) still deletes expired alerts. Data is kept. The overview reports the `ips_events` watcher as off.

## Dependencies
- **DEPENDS ON**: `core`, `inventory` (the device of an address), `logs` (received lines). Soft: `notify` (incidents), `findings` (related findings).
- **DEPENDED ON BY**: core (the Intrusion detection overview: `Summarize`, `NativeIPS`, `cmd/vedette/detection.go`). The findings module does not import ids (see POST-3).
