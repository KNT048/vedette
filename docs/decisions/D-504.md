Each sends one NTLM NEGOTIATE (type 1) with no credentials and reads the CHALLENGE (type 2), which carries the device's Windows version and build and its names; neither ever sends an AUTHENTICATE (type 3), so nothing logs in. rdp-ntlm-info runs only on an open RDP port, http-ntlm-info only on an open HTTP port (one GET of `/`). The probe log's `flags` column (INV-9) holds the line with the scripts. They are in `normal` too, not only `versions`: otherwise a device identified as a PC would get the `-O` shape on its next scan and lose its build to the fingerprint guess. **Not chosen**: `smb-os-discovery` (it opens an anonymous, then a guest, SMB session, which is a logon attempt that shows up in the device's security log, and it needs SMBv1, which Windows 10 and 11 turn off); `smb-protocols`/`smb2-capabilities`/`smb2-time` (they give only dialects, capabilities or the clock, never the OS or its build; the Windows answer on 135/445 is already in `-sV`'s banner); `ms-sql-ntlm-info`, `smtp-ntlm-info` and the other NTLM scripts (they work the same way but for services rare on a small office's devices; add one when a walk needs it). **Version skew**: a job carries the shape name, not the argv (D-111 (3)), so a worker from an older release builds its own line for `normal`/`versions`, without the scripts. Core and the scan worker ship in one release, so this lasts only during an update. The probe log then lists scripts that were not sent, never the other way round, and identification works as in D-501. No proto bump and no new shape: a new shape would make the older worker refuse every discovery scan (`invalid_job`). (5) **W3-5: a service banner is not software.** A service gives a software row only when `-sV` read its version (from the service or its CPE).
