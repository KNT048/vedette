# Legal and compliance: clear and transparent

Everything related to law, licences and cookies must be clear, transparent and compliant. This file is the only place that collects it; the data detail is in `PRIVACY.md`, component licences in `THIRD_PARTY_NOTICES.md`.

## 1. Licences

- Vedette code: **Apache-2.0** (`LICENSE`). `NOTICE` records the project name and copyright; anyone who redistributes must keep `LICENSE` + `NOTICE`.
- Third-party components: listed in `THIRD_PARTY_NOTICES.md` (name, version, licence, how it is used: embedded / a separate process / data). CI runs a licence check (`go-licenses`, `license-checker` for npm); GPL/AGPL must not be embedded in the binary, only a separate process/container.
- Data redistributed from the central side: each feed file carries `license` and `attribution` in `index.json`; the UI shows the source on every data row. A source that forbids redistribution never enters the central side.
- nmap: not distributed; it is not in any image of the project; it is installed from the OS package repository into the `scan` image that `vedette-host` builds on the box (`deploy/containers/scan/Containerfile.onbox`, code in `host/ops/scanbuild.go`); the nmap name/logo is not used in marketing. Spamhaus: its name is not used in marketing; waiting for confirmation of the embedding terms.
- Trademarks: "Vedette" is the project name; the names/logos of other vendors (Fortinet, Synology, CISA...) are not used except to indicate compatible products.

## 2. Personal data (Law 91/2025, Decree 356/2025, Decree 330/2026)

- Vedette runs **at the customer**; the customer is the data controller. Vedette processes: device IP/MAC/hostname, network logs (which may contain user names and emails in the logs). All of it is on the customer's box.
- The Vedette project receives **no data from the box**: the anonymous signal is not sent and the project runs no server that could receive it (`PRIVACY.md` §2). The only connections the box makes are the ones listed in `PRIVACY.md`.
- The customer can: choose which outbound connections are on (Settings → Privacy); set log retention; turn on PII redaction before sending to the AI; export or delete all data (Settings → Data).
- When the customer turns on BYOK AI: data goes to the **customer's** provider under their contract with that provider; Vedette says this plainly at the configuration step and lets the customer choose redaction.
- The PDPL report Vedette generates (S-REP-2) is an **assessment aid**, not legal advice; the report says so. Apache-2.0 §7-8: no warranty, the authors are not liable.

## 3. Scanning and inventory (Cybersecurity Law 116/2025, Penal Code Article 289)

- Active scanning only on **verified** assets: the LAN ranges the user declares + a ticked commitment; a domain through DNS TXT (re-checked before every scan); a public IP is only the IP the box itself uses to reach the Internet, which the box detects and renews by itself, valid for 30 days from the last sighting. There is no consent text; it is replaced by a commitment + the sentence "Vedette is provided as is under Apache-2.0; the authors are not responsible for how you use it". There are also general terms of use (`TERMS.md`, §5) accepted once at the first install or restore; the commitment by range and by target here stays as it is. **External domains and IPs:** there is no separate confirmation step any more; an admin's first Scan now with two-step sign-in records the scan commitment (who, when, the target, exactly the sentence shown next to the button and its version) in `exp_target` and `core_audit` in one transaction. An operator cannot scan a target that has no commitment. The current sentence also states the scope ("...including identifying its services and versions, safe checks for known exploited vulnerabilities and a passive web scan"); a commitment recorded under the old sentence is asked for again once, at the admin's first Scan now after the upgrade.
- **Addresses of names under a verified domain (LEGAL-2):** besides the box's own IP, active scanning and deep scanning also reach the addresses that a name under a verified domain resolves to **at scan time**, under the accepted test terms of that domain: all ports, OpenVAS, nuclei and active web scanning (ZAP), at the same depth for every name, no matter who serves the name (the customer's machine, third-party hosting, a CDN, a proxy or similar). The domain's terms say plainly that the scan touches third-party infrastructure standing in front of the customer's names; **the customer is responsible for having that third party's permission**; Vedette **does not check** who owns those addresses. Domain verification stays the same (DNS TXT, re-checked before every scan); right before each step core re-checks that the domain is still verified, the terms are still in force and the name still resolves to that address; an address that is not the box's also needs the domain guard of vedette-host (a token bound to the box in the TXT record) before anything beyond a name-based check is sent. With no tick box, a deep scan still includes checks that confirm a flaw with the exploit request itself in a harmless form (reading a file, running a harmless command), OpenVAS checks that may write a harmless test file or record and then try to delete it, authentication-bypass checks and public anonymous logins (like FTP anonymous), and the terms say exactly that; disruptive checks (denial of service, password guessing, signing in with default passwords, nuclei exploit checks and nmap that send more than one harmless read such as exploit POST requests and SQL injection probes) run only with a separate tick box, and never on an address reachable only through a name that points (CNAME) outside the domain, because the owner of that other name chooses the address (right before each step the box looks the CNAME up again; if it cannot be confirmed it counts as outside); the terms remind that the provider's testing policy (Cloudflare, AWS forbid denial-of-service tests) applies to the customer. Private addresses and IPv6 are never probed.
- A log of every probe (target, time, template) is kept ≥90 days to prove the scope. Passive web scanning with ZAP: the unit recorded is one line per page with the scope (`ip:port`, URL, the tool and options, the time), written before the run; each spider request is not recorded individually but is held to exactly that scope by the host's network barrier.
- There is no mode that scans an IP outside the scope. Without a target's accepted testing terms, nuclei runs only the read-only safe checks of the exploited vulnerabilities matched there; with them, the deep checks described above, and the disruptive ones only with their own tick. Intrusive, fuzzing and out-of-band templates, and templates that leave a lasting change, are never run (PRIVACY.md flow 9).
- The honeypot only listens, does not counter-attack, and does not interact with outside systems.

## 4. Cookies and web

- The Vedette SPA uses **three cookies, all the box's own and needed for sign-in**: the session cookie (`__Host-vedette_session`, HttpOnly, Secure, SameSite=Strict), the CSRF cookie (`__Host-vedette_csrf`, readable by the SPA) and the trusted-device cookie (`__Secure-vedette_device`, HttpOnly, sent only to the sign-in endpoints), and `localStorage` for UI preferences (language, theme). No tracking cookies, no third-party analytics, no external fonts/CDN (fonts are embedded). Because there are only necessary cookies, no banner is needed; it is still stated in `PRIVACY.md` §4 and on the Settings → Privacy page.
- The project runs no website or server of its own besides the GitHub repository and its releases.

## 5. Transparency to the customer (required in the UI)

- **Terms of use:** `TERMS.md` at the repo root is the only text (Apache-2.0 as is, no warranty; Vedette is a security testing appliance, it tests like an attacker with nmap, nuclei, ZAP, OpenVAS: after the target's test terms are accepted, every scan is a deep scan (all ports, version detection, read-only verification, active web scanning that submits forms); destructive checks (DoS, password guessing, signing in with default passwords, verification by exploit or by sending data that acts on the target) are off by default, run only with a separate tick, and can bring a service down or lock accounts; a verified name is deep scanned on every IP it points to, and verification proves only DNS rights, not the right to test the machine behind it; shared hosting, cloud, CDN and proxies may serve other people's systems, the operator must have the provider's permission, Vedette does not check who owns an IP; scan only what you own or are allowed to, an unauthorised scan may break the law and get the box's IP reported or blocked; data stays on the box except the flows in `PRIVACY.md`; the test terms of each target are accepted separately before the first deep scan). The first step of the first-time setup wizard shows the text and the box "I have read, understood and agree to the terms of use"; without the tick it does not go on, and `POST /core/setup` and `POST /core/setup/restore` refuse (400 `terms_not_accepted`), so a restore from a backup onto a new box needs it too. The box stores who accepted, when, which version (the date + SHA-256 of `TERMS.md`) and an audit line; Settings → General shows the whole text again. This adds to, and does not replace, the scan-scope commitment of §3. **From 2026-11-15:** `TERMS.md` adds the section "What Vedette tells you, and what it does not" (version 2026-11-15): tier 1 alerts at any age, a KEV CVE published and added to the list more than 12 months ago that matches only a product name is not reported; tiers 2-3 only list, do not alert, only the last 12 months and exactly the version the device reports/the person entered/the device states itself, never a version guessed from a banner; an old CVE outside the exploited list only when a scan finds it; public data has flaws, and an empty list does not mean safe. The invitation to accept again is TERMS-2.
- The Settings → Privacy page: every data flow leaving the box, each with a switch or the reason it cannot be turned off (feed pulls), the last send, a sample payload.
- Every AI result has the label "AI generated, needs a person to confirm".
- Every data row has a source and a time.
- A public `CHANGELOG`; the product's own security advisories are public (`SECURITY.md`).

## 6. Export / encryption

Vedette uses standard TLS and AES-GCM (the Go stdlib). There is no home-made key/algorithm. Global distribution through GitHub under GitHub's terms.

## 7. Rules for contributors

Adding a dependency/feed/outbound data flow = update `THIRD_PARTY_NOTICES.md` or `PRIVACY.md` in the **same commit**; CI blocks a dependency without an allowed licence.
