# Feeds Contract

> Tier: standard · Story: S-FEED-1…5, S-TIER-1…4 (data) · Last verified: 2026-11-21 (every sentence checked against the code)

Source of behaviour: `web/src/features/feeds/{contract,defaults,parsers,sourcesMock}.ts`. Source of data: `PRIVACY.md` flow 1, `docs/DATA_PIPELINE.md` §0, §3.

## Invariants
- **INV-1**: The box only pulls from declared sources: built-in feeds (on) and custom feeds (on); each pull is an HTTPS GET to exactly `Feed.url`, sending no customer data (SYS-7). No feed-data request goes to the project's GitHub. `TestContract_INV1_OnlyDeclaredSources`
- **INV-2**: Feed URL: `https`; `http` only for internal hosts (10/8, 172.16/12, 192.168/16, 127/8, `localhost`, `.local`, `.lan`, `.internal`, `.localhost`); anything else is 400 `invalid_url`. At save time (`CheckDest`): a host that is a literal IP that the pull refuses (INV-17: link-local, cloud metadata, unspecified, multicast, every transition form; and Vedette itself: loopback, core's container address on every port, Vedette's own ports on the machine's address) or `localhost`/`*.localhost` → 400 `blocked_host` with the pull's sentence (`ownText` for Vedette itself, `blockedText` for the rest), on `POST /feeds/custom`, `PUT /feeds/custom/{id}` and the mirror `PUT /feeds/sources/{id}`; other names are not resolved at save time (the dialer blocks at pull time). So `http://localhost`, `127.x` pass INV-2 but cannot be saved. Default caps for every pull and every custom feed: 5,000,000 bytes (over → 413 `too_large` at `parse-test`), 50,000 rows (`truncated:true`) and a time cap (60 s). The only exception is the per-source row cap of a built-in source (`Source.MaxRows`): `hagezi-tif` (`wildcard/tif.mini-onlydomains.txt`, 186,000 rows today, 3.4 MB) 250,000 rows; every other built-in source keeps 50,000 rows (`ipsum` uses `levels/3.txt`). The 5,000,000-byte cap applies to all. Real files measured on 2026-11-12 (the box's parser, no row rejected because of a cap): `hagezi-tif` 3,363,829 bytes, 185,999 rows = 12 comment rows `# ` + 185,987 bare names one per row (the `wildcard/` folder: one name covers its subdomains, the file has no `*.`; 50 names have international TLDs in `xn--` form, accepted) → 185,987 accepted, 0 rejected; `ipsum` (`levels/3.txt`) 251,501 bytes, 17,596 rows, each row a bare IPv4 (no header, no count column) → 17,596 accepted; `nuclei-templates` (`cves.json`) 2,312,968 bytes, 4,606 JSON Lines rows `{"ID":"CVE-…","Info":{…},"file_path":…}`, longest row 3,352 bytes → 4,606 CVEs, 0 rejected. EPSS does not download one large file: it is fetched from `api.first.org` in batches of ≤ 100 CVEs (each answer ≤ 50,000 rows). A cell longer than 4096 bytes does not run the customer's regex; a regex that compiles to over 1000 instructions is refused at save time. Redirects only follow the same host (a different host is refused), no downgrade https→http, at most 5 hops. At connect time: always refuse link-local (169.254/16, fe80::/10) and cloud metadata addresses; `http` only to private/loopback IPs (against DNS rebinding).
- **INV-3**: The parser fails closed (SYS-6): an invalid row is dropped, counted by reason (`rejected`, `reasons[]`, `rejects[]` first 20 rows); no row that is rejected gets into `feeds_*`; feed content is never interpreted as a command/HTML. The parser is fuzzed for 60 s in CI. `rejects[]` keeps the first 20 rows (the SPA must follow); `reasons[]` groups by message pattern, at most 50 groups + `other`. `rejects[].row` is the line number of the sample for a plain list (`lines`, counting `#` lines and blank lines too), the record number for other formats; `rejects[].reason` shows the value (cut to 40 characters, non-printable characters turned into spaces, quoted Go-style) and is only returned through `parse-test` (INV-7: the caller's sample or a built-in one); `reasons[]` always masks the value (`"…"`) (S-FEED-5); the status sentence of a pull ("Most often: …", "All N rows were rejected: …") shows the first row of the most common reason with the value passing through the same `quoteVal` (`Reason.Example`, not in the JSON), and the "other" group keeps the masked pattern. The reason for a URL names the class of the host: a private/reserved IP → "points at a private, reserved or special-purpose address", test names `.example`/`.test`/`.invalid`/`*.localhost` and `example.com|net|org` together with names under them (RFC 2606 §3) → "points at a reserved example or test name" (a bare name of the same class: "is a reserved example or test name"), a local or invalid name → "points at a local or private host". Feed text is untrusted plain text: control characters, C1 and Unicode format characters (bidi, zero-width) are removed from identifiers/keys and dropped from free text; consumers (notify, reports, ai, SPA) must escape according to their own environment.
- **INV-4**: A built-in feed cannot be deleted (only turned on/off, `url` mirror; the pull schedule is a `core_schedule` row `feeds.source:<id>`, interval only, 1 hour to 168 hours; `url:""` resets to the default). A custom feed: add/edit/enable/disable/delete; deleting a custom feed also deletes the records it loaded and its schedule (`core_schedule`).
- **INV-5**: the source's schedule is an interval of 1…168 hours (the limit of the owner `feeds.source`, the reason shown in the schedule editor; `interval_hours` in the API is read-only, derived from the schedule); feed name 1…60 characters, unique case-insensitively; a custom feed's address does not equal the current address of another feed (built-in or custom; scheme/host case-insensitive, default port and fragment dropped) → 400 `duplicate_url` naming the other feed, checked after every other error of the request body; the format must fit the kind: `vulnerabilities ⊂ {json,csv,rss}`, `ioc ⊂ {json,csv,rss,stix,lines}`.
- **INV-6**: Feed authentication secrets (`bearer|header|basic`) go through `core/secrets`, the API only returns `secret_last4`; a secret is ≥ 8 characters, no whitespace; editing a feed and leaving the secret empty keeps the old secret (SYS-4).
- **INV-7**: `POST /feeds/parse-test` does not write `feeds_*` and does not call the network (it uses the caller's `sample` or the built-in sample by format).
- **INV-8**: `POST /feeds/sources/{id}/fetch` on a feed that is off → 409 `feed_disabled`. One pull at a time per feed (`lockFeed`): `Fetch` called while the feed is pulling waits for that pull to finish and returns its result, without pulling a second time; `POST …/fetch` while the feed is pulling returns 200 at once with the feed as currently seen (the progress line of INV-19), and the job and the `nvd-kev`/`cve-org` pulls that follow the CISA or VulnCheck list skip a feed that is pulling. A failed pull: writes `status:error`, `error`, backs off the retry time, does not bring the job down; shown in Settings → Feeds.
- **INV-9**: Data is never more than 60 minutes overdue for a pull (age ≤ `interval_hours` + 60 minutes) when the source is on and reachable; `FeedStatus.generated_at` and `sources[].fetched_at` are always displayed (S-FEED-1). Tested with a fake clock. Stale means older than `interval_hours` + 60 minutes; a timestamp in the future (wrong clock) counts as due and stale. Default schedule: `cisa-kev` 1 hour (conditional `If-None-Match`/`If-Modified-Since`, 304 is a successful pull that does not download again; the default schedule of each feed is its `IntervalHours` in `builtinSources`: `cve-org` 1 hour; `vulncheck-kev`, `msrc`, `cisco-psirt`, `fortinet-psirt`, `chrome-releases`, `android-bulletin`, `rapid7-blog`, `gti-blog` and every IOC feed 6 hours; the other built-in feeds 24 hours; a new custom feed `DefaultCustomHours` = 6 hours); `FeedStatus.generated_at` = `last_success` of `cisa-kev` (the "Data updated" line of the home page).
- **INV-10**: Works without other modules: `inventory` off ⇒ `HotRow.you_have=null`, `matched_assets=[]`, `FeedStatus.inventory_on=false`; no error.
- **INV-11**: `you_have`: `yes` if there is an asset with a firm match (`how=yes`); `maybe` if it only matches by vendor for a "Multiple products" product; otherwise `no`. A CVE page (`GET /feeds/cve/{id}`): when `Inventory` additionally installs a `PlatformChecker`, a device that the platform rule of findings proves is not affected is dropped from `matched` and counted in `not_affected`; a failed check → returned by product (INV-10). `TestCVEPage_PlatformRulesAgreeWithFindings`.
- **INV-12**: IOC: `verdict=block` when ≥ 2 independent sources or 1 source of type DROP/CC0; `alert` when 1 source; except the whitelist by domain (not by CDN IP); never expand an IP to /24 (DATA_PIPELINE §3). Private/loopback/link-local/multicast/CGNAT/documentation/reserved IPs (including IPv4-mapped forms) and local names (`.local`, `.lan`, `.internal`, `.arpa`, `.test`, `.example`…) or documentation names (`example.com|net|org` and names under them), single-label names, and common public suffixes never become an IOC (both the parser and `Judge` check). Aggregated sources (IPsum, hagezi) do not `block` on their own and do not count as a second source of the same origin as theirs; Tor exits are informational only, not counted toward `block`. A domain from a built-in source with `Source.Subdomains` (currently only `hagezi-tif`, the file "Domains (without subdomains)") stands for itself **and every subdomain**; `IOCLookup` returns `IOCSighting.Subdomains` for those listings, while a custom feed always matches the exact name. Storage is unchanged: only the listed name is in `feeds_ioc`; looking up the parent name is the reader's job (`logs`). Test: `TestWiringLogsIocHitsFromTheFeedsModule`.
- **INV-13**: Every source host (built-in and custom feed) appears in `PRIVACY.md` flow 1 (legal.md), in Settings → Privacy (the flow 1 row: the built-in sources, hard-coded, and "any custom feed you add") and, read from the API, in Settings → Feeds → "Where this box connects" (every configured host, `FeedsSettings.tsx`, vitest `lists every host the box pulls from`); Settings → Privacy does not yet list the hosts of custom feeds (left for later); `raw.githubusercontent.com` is also the fallback address of the CISA list (INV-15).
- **INV-15**: the CISA list (`cisa-kev`, still using the built-in address) **asks both copies on every check**: `KEVPrimary` (cisa.gov) and `KEVMirrorURL` (the `cisagov/kev-data` repository), with the same parser, the same caps, a plain unauthenticated GET, each copy with its own validator (`etag`/`last_modified` of cisa.gov, `mirror_etag`/`mirror_last_modified` of the GitHub copy; one copy's validator is never sent to the other), only sent when the box knows the `catalogVersion` that copy gave last time (304 means that copy is still at that version). Keep the newer catalog (`kevKey`): a **plausible** `catalogVersion` (a real date, not more than 2 days after the clock of the server that answered, the `Date` header, using the box's clock only when there is none; not off its own `dateReleased` by more than a day), then `dateReleased` (also not more than 2 days ahead); a version that cannot be read goes by `dateReleased`. Within one check: the newer copy, then for the same catalog the copy with more entries, then the one from cisa.gov; the catalog being held is only replaced by a newer copy, or the same catalog with more entries, or the cisa.gov copy of the same size. There is no rule comparing with the number of entries stored (it freezes; the applied rule is additive). Not going back, not freezing: a held version that is not plausible counts as none; a copy with neither a version nor a plausible date is not used (noted, counted as one failed copy, still asked conditionally); a 304 is re-judged from what the box knows about that body (`version`, `released`, `count` in `kev_copies`) under the current rule, and read in full again within the same check when it would now be accepted. Turning the feed off and on, or changing the address, clears the version, `catalog_released`, `records`, `kev_copies` and every validator; changing the address sets `failures` to 0. When the box clock is off by more than an hour from the server, the note and warning say so (`clock_skew_s`). `Feed.answered_by` (column `answered_by`) is the copy that the catalog being held came from ("newest from": "CISA" or "CISA GitHub mirror"; null for other feeds). `feeds_source.kev_copies` (JSON) holds the result of the last check of each copy (`version`, `released`, `checked_at`, `error`), `catalog_released` is the `dateReleased` of the catalog being held. A failed copy (any kind of failure: 403, 404, 5xx, timeout, no connection, name not resolving, unreadable) is a **note** on an `ok` pull ("cisa.gov refused this box (HTTP 403); the other copy answered."); both failing is a failed pull, one sentence naming both causes, no address ("cisa.gov refused this box (HTTP 403), and CISA's GitHub copy answered HTTP 502."). A feed that has been changed to the admin's own address only asks that address. The tests in `kevfallback_test.go`, `TestKEVCopies_*`.
- **INV-14**: The "This week, in short" sentence is produced from a template on the box, needing no customer AI, with the source label on each line; `answer=have` creates exactly one manually declared device through `inventory`; `not_relevant` only stores the answer. The meaning of "have" is "tell me about this product" for exactly the device it declares: the first "have" writes `have_since` = the date of the entry that was clicked minus `HaveWindow` (7 days) and `AddManualDevice` returns the device id into `device_id`; later answers do not move these two columns. `Store.HaveSince` only returns answers that are currently "have" with a `device_id`, by device id (INV-11 of findings).
- **INV-16**: A built-in `feeds_source` row that the code no longer lists is deleted at startup (`Seed`, `retireBuiltins`), together with its pull history and its listings; an IOC listed only by that source is deleted, an IOC still listed by other sources is kept. A custom feed is never touched. `FeedStatus.kev` = `{state, error, interval_hours, checked_at, last_success, answered_by, copies}` for the home page: `off` when the admin turns off `cisa-kev`; otherwise `loaded` when there has been any `ok` pull (even if a later one failed), else `never_loaded`; `error` is the error of the last pull cleaned into one line ≤200 characters, when the last pull failed and the feed is on, in both `never_loaded` and `loaded` (an old list must say how long it has been old), null when the last pull was `ok`, there was none yet, or `off`. `interval_hours` = `feeds_source.interval_hours` of `cisa-kev` (the pull schedule), `checked_at` = `last_fetch` (the last ask, successful or not), `last_success` = the last `ok` pull; both timestamps are null when there is none. `answered_by` as in `Feed` (INV-15, "newest from"); `copies[]` = `{name, url, checked_at, error, catalog_version}` of each copy that was asked (empty for the admin's own address or before the first check); `sources[].url` of `cisa-kev` is `KEVMirrorURL` when the catalog being held came from the GitHub copy. The home page says "Checked every hour at cisa.gov and at CISA's GitHub copy, last at …; the newest list came from …" with a light note for a failed copy and for CISA's last addition, or a failed pull with the last good pull. The GUI never says "0 newly exploited" when `state != loaded`; the same for an empty "Newly exploited" table: replace the sentence "No newly exploited …" with the same sentence and link as the home page, while a table that has rows stays as is.
- **INV-17**: No pull (custom or built-in) ever connects to Vedette itself: loopback (127/8, ::1: inside a container, loopback is Vedette itself), the interface address of core's container and the honeypot decoy addresses (`Fetcher.Self`) on **every port**; the address of the machine running Vedette (`Fetcher.BoxAddrs` = `machineAddrs` of cmd/vedette: vedette-host, the container's gateway, the IPs in `-hosts`, `VEDETTE_BIND_IP`, host-alias names) is only refused on **Vedette's own ports** 8443, 8444, 8765, 514, 6514 (`vedettePorts`): another program on the machine, at the machine's address and its own port, is a normal source. Never the whole LAN subnet, where an internal feed such as MISP may sit. Checked on the resolved address, right before `connect` (against DNS rebinding); every redirect step goes through the same guard; no proxy. `BoxAddrs` reporting "not known" (vedette-host has not answered since startup) ⇒ only global unicast addresses (not RFC 1918, loopback, link-local, CGNAT, ULA, special ranges) are allowed in the meantime (built-in feeds still run, LAN feeds wait), and a pull refused only because the address is not yet known writes no error, no back-off, and the feed is still due on the next run. Transition addresses (NAT64 `64:ff9b::/96`, `64:ff9b:1::/48` read by every RFC 6052 layout /48 /56 /64 /96, unless the prefix length of the network has been learned (RFC 7050, AAAA `ipv4only.arpa` through the system resolver, at most 2 s, remembered 6 hours / 10 minutes if it could not be learned) and overrides the address: then only that layout (`TestLearnNAT64`, `TestAddrFormsNAT64LocalLearnedLength`), 6to4 `2002::/16`, `::a.b.c.d`) are checked in their embedded IPv4 form too; the container's default gateway is also the box. At save time, the literal IP part and the loopback names of this rule are already refused early (INV-2); the pull-time layer stays (a name that resolves to a forbidden address, a box address that changes after saving). The WARN line "feed pull failed" records `feed` (id) and `name`. Vedette itself (loopback, container interface, Vedette's ports on the machine address) is `ErrOwnAddress` (wrapping `ErrBlockedAddress`), the sentence `ownText` "That address is Vedette itself: …" both at save and at pull time, identical to notify, logs, ai; `TestOwnAddress_*`. A value extracted from a feed only shows in a row error as a short fragment: ≤ 40 UTF-16 units, non-printable characters turned into spaces, put in quotes. `TestDialGuard_*`.

## Preconditions / Postconditions
- **PRE-1** (`Fetch(feedID)`): the feed is on, the URL passes INV-2. **POST-1**: `feeds_source.last_fetch/records/status/error` are updated (the `error` of a good pull is a note **of that pull itself**; for a built-in feed whose count may be 0 on a healthy box or which counts something other than its name says (`heldNotes`: `nvd-kev`, `cve-org`, the four distribution feeds, `windows-releases`, `poc-in-github`), the row with `status = ok` shows a sentence saying what the feed is holding **counted from the stored data when the row is read** (`Service.live`: `GET /feeds/sources`, the answer of Fetch now and of `PUT /feeds/sources/{id}`) and then the note of the last pull, so the sentence is right immediately after an update (before the next pull) and as soon as another feed changes what it counts (the CISA list adds a CVE, NVD gets a version). Counted once and then cached by `last_fetch`/`rev` of the feeds that write that data (`heldFrom`; that data is only written in the transaction that writes a pull or when a feed is edited); a distribution feed with no devices: the what-it-holds sentence and then the waiting sentence; NVD while loading: the what-it-holds sentence and then the progress; a failed row only shows the error; a failed count is logged and the holding row keeps the pull's note. Every other built-in feed is recorded as "self-describing number" in `TestHeldNotes_EveryBuiltinFeedIsDecided`; `TestHeldNotes_EmptyAndFilled`, `TestHeldNotes_ShownRightAfterAnUpdate`, `TestHeldNotes_FollowTheData`); the event `feeds.vuln.new_kev` is only emitted for a CVE that has never existed before.
- **PRE-2** (`GET /feeds/hot`): `window ∈ {24h,7d}` (400 `bad_window`). **POST-2**: rows sorted with `you_have=yes` first, then the number of CVEs, then `max_epss`.
- **PRE-3** (`GET /feeds/cve/{id}`): the catalogue holds the CVE (`feeds_cve`); otherwise 404 `not_in_data`. **POST-3**: the CVE's brief (`Store.Brief`, section "CVE brief") plus `matched` (devices whose product matches the owner exploited-list entry, INV-11; null when `inventory` is off or the CVE is on no exploited list) and `not_affected`.
- **PRE-4** (`GET /feeds/search`): `q` 1…200 characters (400 `empty_query`). **POST-4**: one of `cve|ioc|text`; returned from the local DB, no network call. An indicator is only stated as listed by a feed that is **on** (`IOCSighting.Enabled`; the listing of a feed that is off stays in `feeds_ioc_source` but is old); no feed that is on lists it → `hit: null`. The same rule for `lookup_ioc` of the AI and MCP.
- **PRE-5** (`POST /feeds/custom`, `PUT /feeds/custom/{id}`): `admin`, through INV-2/5/6/17 (order: name, address, `blocked_host`, schedule, format, authentication, parsing rule, `duplicate_url`). **POST-5**: the feed is stored with its `parser`; `core_audit` writes (no secret written).

## Forbidden
- **FORBID-1**: Distributing data through GitHub/Cloudflare, a central builder.
- **FORBID-2**: Sending customer data (assets, logs) to a feed source. Only the box's IP is exposed in the source's logs.
- **FORBID-3**: Pulling an undeclared source or a source that is turned off.
- **FORBID-4**: Reading/writing `inv_*` tables directly; matching assets goes through the `inventory` interface.

## Dependencies
- **DEPENDS ON**: `core` (jobs, secrets, audit). Optional: `inventory` (`you_have`, "I have it").
- **DEPENDED ON BY**: `inventory` (KEV catalogue, matching, `feeds.ranges.updated`), `findings` (KevInfo, version ranges, signals, CVSS scores, tier records; `mitigation` only through `findings`), `scan` (`has_template`, new KEV, `NewKEVSince`), `notify` (events `feeds.vuln.new_kev`, `feeds.sync.baseline`; the CISA list warning goes through `notify.Publish`), `logs` (`IOCLookup`, `IOCListed`, `IOCSubdomainsOn`), `reports` (`NewlyExploited`, the KEV section), `ai` (slot `cve.panels`, `VulnByCVE`, `lookup_ioc`), `mcp-server` (`lookup_cve`, `lookup_ioc`, the hot table), `core/winrel` (Windows releases and monthly patches), `core/schedule` (owner `feeds.source`), `scripts/release` (signal seed). `honeypot` and `response` do not read feeds.

- **INV-19**: the built-in feed `nvd-kev` ("NVD affected versions", `services.nvd.nist.gov` CVE API 2.0, `?hasKev`) only asks for CVEs that are in KEV, `NVDPageSize` (100) per request, spaced `nvdPause` (6 s, NVD's no-key limit) apart; the first time (empty table, or the last good pull older than 100 days) it pulls everything and drops CVEs that NVD no longer returns; after that only CVEs changed since one day before the last good pull (`lastModStartDate/EndDate`). Nothing is written until all pages are in, so a pull that is not finished never deletes or half-updates (INV-3). Resilient to a slow/busy NVD: each request waits for headers up to `nvdHeaderTimeout` (2 minutes, `Request.HeaderTimeout` on the copy of the transport that has the address guard), a whole page up to `nvdPageTimeout` (3 minutes); a page that returns 408/425/429/5xx, times out or loses the connection is retried after `nvdRetryWaits` 6 s, 30 s, 2 minutes (or NVD's `Retry-After` if longer, capped at 15 minutes); out of retries or out of `pullBudget` when ≥ 1 page is already in ⇒ the pull **pauses** (`errNVDPaused`): the pages are kept in memory (`Service.nvd`), no error is written, no back-off; the job continues from the next page at `retryAt` (≥ 5 minutes after NVD was busy, gradually longer if there is no new page; at the very next run if only the budget ran out); pages held more than 24 hours with no new page, a changed address, a windowed pull whose window has passed `nvdIncrementalStale` (12 hours, left for the next pull, asking from one day before this pull finished, missing nothing) or the feed being **turned off** ⇒ dropped (the feed row stops reporting progress), pulled again from the start; the `running` flag is cleared with `defer` (even on a panic); a process restart also drops them (the new process pulls again from the start, 18 pages). No page obtained ⇒ a failed pull as before, with a sentence saying what NVD did ("NVD was busy (HTTP 503) for the first page, after every try. …"). An empty page while `startIndex < totalResults` ⇒ an error, not counted as done. While pulling or paused, `GET /feeds/sources` and `POST …/fetch` replace `error` with a progress line ("Loading version ranges from NVD: page 8 of 18. NVD was busy (HTTP 503); trying page 8 again in 30 s." / "…: 7 of 18 pages done. … Vedette goes on in 5 min."; "Updating" for a windowed pull) and a feed that has never been full returns `status:never` (`Service.live`). `TestNVDPull_*`. `ParseNVD` is closed: only the `vulnerable` entries of a non-`negate` node; a CVE with one bad entry (criteria not CPE 2.3, a version over 100 characters or non-printable) is dropped whole. A pull that changes data emits `feeds.ranges.updated {cves, first}`; a CVE that a full pull deletes (NVD no longer returns it) is also in `cves`, so that a device that was closed by an old range is matched again. Pulling the CISA list with new CVEs pulls `nvd-kev` right after (then `cve-org`, INV-20), unless the NVD pull is paused and has not reached `retryAt` (NVD busy/`Retry-After`). `TestNVDPull_ReviewLows`, `TestNVDPull_StaleUpdateStartsAgain`. The licence line carries the sentence NVD requires. `TestContract_NVDRangesPull`, `TestParseNVD_*`.
- **INV-20**: the built-in feed `cve-org` ("CVE records", on by default, checked every hour, address `github.com/CVEProject/cvelistV5`; another mirror puts the same layout under its own address) reads the CVE JSON 5 records of the CVE Program for every CVE the catalogue holds (`recordKeep`: CVEs in `feeds_cve`, CVEs with a list entry/a qualifying signal/a pinned finding, CVEs published within a 365-day window). Three paths, no request carrying customer data: (1) **the whole list**: the daily file `releases/download/cve_<date>_2300Z/<date>_all_CVEs_at_midnight.zip.zip` (669 MB, 2026-11-20), downloaded into a working file in `Deps.DataDir` (`feeds-cve-records/`), resumed from the last byte (`Range`) on the next run, limited by `recordRate` (4 MB/s), leaving `recordReadReserve` of `pullBudget` for reading; read as a stream entry by entry (`walkDailyArchive`/`walkZipStream`: CRC of each entry, caps on the number of entries/name/size, an entry with a data descriptor or encryption ⇒ error), writing `recordBatch` records per transaction, deleting the file when done; the cursor is in the `cve_record` row of `feeds_nvd_cursor` (`fill`: `next_index`/`total` bytes; `done`: `until` = data complete up to, `win_to` = the last reading of the change log). Before downloading: less free disk space than the remainder + 512 MB ⇒ a failed pull "Not enough free disk space …"; a disk write error is an error of the pull ("could not write … to this box's disk"), never a source error, and deletes what was downloaded; resuming the download only when the size of the source file is unchanged (`WantTotal`, different ⇒ download again from the start); turning the feed off ⇒ delete the working folder. Rereading the whole list does not overwrite a record read after the midnight of that file. ## Implementation (WP-20)
- **The owner entry of each CVE**: a CVE can be in several lists; pages, findings and inventory read the owner entry (`ownerOrder`: CISA, then VulnCheck, then a custom feed). The CISA list does not delete entries; VulnCheck and custom feeds replace their own entries on every pull (together with their signals); a missing vendor/product is written as `Unknown`, a missing date takes the date first seen.
- **IOC**: `verdict`, `score` (= the highest confidence that a feed gives; 0.5 for a feed that gives none) and `category` (by source, at most 2, "Custom feed" for a custom feed) are computed on read from `feeds_ioc_source` through `Judge`; not stored. An indicator that no feed lists any more is deleted after 30 days. Each pull of an IOC feed is a full snapshot: an entry that disappears from the feed disappears from `feeds_ioc_source`; a pull with no valid row is an error and deletes nothing. The domain whitelist has no configured source yet (no operation, no story): `Judge` receives an empty list.
- **`Service.NewlyExploited(ctx) (cves, productsInUse int, err error)`** (caller: `reports` through `cmd/vedette/reports.go`): the home page's first sentence as numbers, from the same table as `GET /feeds/hot?window=7d` (`Service.hot`): the number of CVEs newly exploited within 7 days and the number of product groups with `you_have = yes` (0 when inventory is off). The weekly report and the home page read the same function so they never differ. An entry dated after today (the box clock was moved back after a pull; a future feed date that became the pull date at save time) is not counted (`TestNewlyExploitedWindowIsHomes`).
- **Pull**: the `pull` job runs every 5 minutes, and each feed that is on and due by `State.Due` (the feed's schedule is its `core_schedule` row, plus a back-off of 5 minutes…6 hours after errors) is pulled in turn, vulnerability feeds first. Each successful pull of the CISA or VulnCheck list (job or "Fetch now") immediately pulls `nvd-kev` after it (only with the CISA list) and then `cve-org` if that feed is on, not pulling and has new CVEs or no record at all (`Service.pull`); their errors are only recorded on their own feeds. EPSS scores do not follow the list: `epss-all` has its own schedule. The result of each pull is written in **one** transaction (data + status + `feeds_fetch_log`); an error or corrupt data only writes the status, and the old data stays. A conditional pull (`If-None-Match`/`If-Modified-Since`) only after one successful pull and only for the current address. Only a manual pull (`POST …/fetch`) writes `core_audit` (`feeds.fetch`).
- **Events** (through `feeds.Publisher`, nil = dropped): `feeds.vuln.new_kev` for each new entry of the CISA or VulnCheck list, **except the first pull of that list into an empty table: that is the baseline, and only one `feeds.sync.baseline {source, count}` is emitted**; "empty" means there is no `cisa-kev` (or `vulncheck-kev`) row yet, so a custom feed that existed earlier does not lose the baseline; a failed pull followed by a pull again is still the baseline; `feeds.vuln.updated` when a KEV field changes or `has_template` changes. Payload types: `NewKEVEvent`, `SyncBaselineEvent`, `VulnUpdatedEvent`. **Record of what was announced**: the bus is best-effort, so every entry of the CISA list or of VulnCheck KEV that gets `new_kev` is also recorded in `feeds_kev.announced_at` of that list's row (the pull's time) **in the pull's own transaction**, exactly that set of CVEs: never for a first fill (baseline) or a custom feed's CVEs; the first announcement of an entry is kept. The events go out only after the pulls the list brings next (NVD, CVE records), so a stop in between (shutdown, module turned off, power cut) loses the events but not the record: a subscriber that missed them (scan's catch-up) reads them back with `Store.NewKEVSince`, and findings' reconcile (run at every start, then hourly) matches the devices again and announces an entry added within its recent window. A CVE that VulnCheck announced and the CISA list names later is announced, and recorded, once per list.
- **Reads for other modules** (`Store`, the entries of the CISA and VulnCheck lists in `feeds_kev`): `KevProducts` (vendor/product pairs + CVE count + a version of the row set, for `inventory.KEV.Products`), `KevIndex` (the CVEs by `vendor|product` key, for `inventory.KEV.CVEIndex`: a vendor's "Multiple products" entry matches every key of that vendor; kept in memory until `kevStamp` moves, so a device page or an agent report costs one small stamp query) and `KevCVEsByKeys` (one lookup in it), `KevVulns` and `KevVulnsByCVE` (for `findings.Feeds`), `NewKEVSince(at, cve, limit)` (the entries of the CISA list and VulnCheck KEV announced as `new_kev` after the point `(at, cve)`, oldest first, ordered by `(kev_announced_at, cve)`, `limit` 1…`MaxNewKEVPage`=500, an error outside that range; `HasTemplate` is the current value; for `scan.KEVFeed`, the catch-up part of the rescan job). `cmd/vedette/wiring.go` converts to the types of each port. The CISA list has no NVD affected ranges yet, so `findings` matches it by product only.
- **Inventory**: `feeds.Inventory` (`MatchProducts`, `AddManualDevice(ctx, tx, …)`) is installed by `inventory` through `cmd/vedette/wiring.go` (`feedsInventory`); `nil` or module off ⇒ INV-10. `answer=have` calls `AddManualDevice` within feeds' transaction, exactly once per product (pressing a second time creates nothing more). `Inventory` may additionally install `TxSettler.Settle(ctx, tx, committed)`: feeds calls it after the transaction ends (commit or rollback) so that `inventory` emits the device's events only once committed (`writeDeclaring`).
- **Differences from `contract.ts`/the mock** (deliberate): an empty secret on edit = keep the old secret (the mock reports an error); `window`, `answer`, a malformed body and a lowercase CVE id are blocked before the handler by the server generated from OpenAPI so they return `400 invalid` instead of `bad_window`/`bad_answer`/`invalid_body` (the handler still keeps its own checks); "This week" does not specially exclude `CVE-2022-27593` (that is a detail of the mock); the date in the sentence uses `2 Jan` (the mock uses `toLocaleDateString('en-GB')`, which can give `Sept`).
- **Custom feeds are not KEV**: `feeds.vuln.new_kev` and `feeds.vuln.updated` are only emitted for rows of `cisa-kev` and `vulncheck-kev` (including when `cisa-kev` lists for the first time a CVE that a custom feed had earlier: that is the first KEV sighting); a custom feed emits no event. The "This week" sentence only uses `cisa-kev` rows (a custom feed's CVE is never described as "added to the CISA list"; no CVE goes to the EPSS source: the daily file is a plain GET); hot, search and CVE still show the rows of custom feeds too.
- **Race protection**: `feeds_source.rev` increases on every edit/enable/disable; in the write transaction of a pull, the row is read again: deleted midway → `ErrNotFound` (404 at `POST …/fetch`), edited or turned off midway → the result is dropped, nothing is written. Turning a feed on again clears the back-off. The per-feed pull lock receives the ctx and is cleaned up when nobody holds/waits for it.
- **Storage errors**: if the transaction that writes an error result fails (not ctx), a second small transaction writes `status:error` + the sentence "The result could not be stored…" so there is a back-off and it shows in Settings.
- **Transactions**: each pull result is one transaction (all or nothing), except IOC lists. An IOC list (hagezi at 250,000 rows would hold the only writer for ~20 seconds if done as one transaction, blocking every other write of the box) goes in batches of 2,000 rows, one transaction per batch; between two batches a waiting write can get the connection. Each batch rereads the feed row itself (`Rev`, `Enabled`, existence) so a feed that is edited/turned off/deleted midway stops the pull at once: the next batch writes nothing, the result is not written (as before), and the rows of batches already committed stay as the data of the previous pull. Every upsert stamps `last_seen` with the timestamp of the pull (batch 0 raises the stamp by 1 ms until the feed has no listing with that stamp, so a clock that goes back or stands still does not break deletion); the last (small) transaction deletes (2,000 listings per transaction, each transaction rechecking the feed) the listings of the feed whose `last_seen` differs from that stamp, then in the last delete transaction counts again, then writes `feeds_source` + `feeds_fetch_log` + `core_audit`, so the `added/removed/records` numbers do not change. A reader during the pull sees the old and new lists merged, never fewer listings; a pull cut off midway (ctx, a storage error, the feed edited) leaves surplus listings, and the next pull cleans them (`maintain` does not touch `feeds_ioc_source`). A feed that is turned off midway keeps the batches already committed until its next pull (the listings of a feed that is off are still kept as usual). The column `feeds_ioc_source.seen` is no longer read or written (it remains in the table and in the export policy). Other results (KEV, templates; a custom vulnerability list of at most 50,000 rows, about 3 seconds) are still one transaction, with ctx checked every 256 rows (`ctxEvery`; an IOC list checks every 1,024 rows within a batch), and old data read once before the loop.
- **Ingest**: a vendor/product longer than 200 characters (or a key over 500) has its row dropped with a reason; a date in the future of a vulnerability feed becomes today (like the `first_seen` of an IOC). `answer=have` writes `device_added` (one device per product, no later answer creates more); a `have` answer while `inventory` is off makes the pull job create the device when `inventory` is on again (the actor is recorded as `system`). An error from `Inventory.MatchProducts` becomes `you_have:null` (INV-10). `GET /feeds/status` that has never pulled returns `generated_at` = 1970-01-01 (not pretending to be fresh); `parse-test` with `sample:""` gives 0 records; a text search returns at most 200 rows, matching ASCII lowercase.
- **Limits**: the request body is at most 1 MiB by default (`core/server`) but `parse-test` is raised to 8 MiB through `feeds.BodyLimits` (wired in `cmd/vedette/modules.go`) to accept the contract's 5 MB sample; a sample over 5,000,000 characters is blocked by the server generated from OpenAPI (400 `invalid`), and a body over 8 MiB is 413 `too_large`. `Vuln.links` is a string matching `^https?://` (not `format: uri`: ogen decodes `url.URL` with `ParseRequestURI`, which turns `#neo` into `%23neo`); the SPA only draws http(s) hrefs; KEV links taken from `notes` only keep `https://` (the finding page presents them as the vendor's advisory), and `http://` is dropped at load. Each part of `notes` is additionally split at a `,` standing right before `http://`/`https://` (`splitJoined`: links joined only by a comma; other commas in a URL stay) and then cleaned (`cleanLink`): drop a leading `(`, `<`, `[`, quote; drop trailing punctuation `. , ; : ! ?`, quote, `>`, and a trailing `)`/`]` only when there is no matching opener in the link (including the `%28`/`%5B` forms); `https:/host` becomes `https://host`. `cleanLinks` (split, clean, at most 10) applies to the links of every feed both at write time (`applyVulns`) and at read time (`scanVuln`), so a row stored before the rule reads back clean and an unchanged pull of a list sees no difference to write. `TestCleanLink`, `TestKevLinks_EveryLinkOfTheCatalogIsClean` (`KEV_FILE=` runs on the whole catalogue), `TestStoredLinksReadClean`. A lowercase `GET /feeds/cve/{id}` is 400 `invalid` (the GUI uppercases before calling). The lists `GET /feeds/sources` and `/feeds/status` return `url` unchanged for the viewer role: a custom feed should not put a token in the query string (use `auth`).

## Events
- **Emits**: `feeds.ranges.updated {cves, first}` (a `windows-releases` run changes `feeds_winrel`, `cves` = every CVE that has a Windows row: an `nvd-kev`, `nvd-recent` or `cve-org` run changes entries of these CVEs; a `ubuntu-osv`/`ubuntu-vex`/`debian-tracker` run changes rows of these CVEs, or that feed is turned on/off, `first` = the first time that feed has rows; `first` when the table was empty before; `cmd/vedette` makes inventory match every device again, the first time as a baseline), `feeds.sync.baseline {source, count}` (once, the first pull into an empty table; instead of the individual `new_kev` of that run), `feeds.vuln.new_kev {cve, vendor, product, has_template, date_added}`, `feeds.vuln.updated {cves[]}`.

- **Alerts** (INV-29): not a bus event; `Deps.Alert(ctx, id, title, text, critical)` is wired by `cmd/vedette/feeds.go` into `notify.Publish` (an incident-type message; `critical` for the warning, `high` for the "up to date again" message), like the AI budget warning.

## Behaviour when off (SYS-5)
No `/feeds/*` routes, no pull jobs, data kept. The home page "Hot" shows "Feeds is off". `inventory` stops new matching; `scan` stops rescanning by itself; `honeypot`/`logs` lose new IOCs.

## CVE brief (`Store.Brief`, `GET /feeds/cve/{id}`)
- **BRIEF-1**: `Store.Brief(ctx, cve)` is the one read model of a CVE (DB-DESIGN rule 10): text and title, CWE ids with MITRE's names (`content/catalog/cwe-names.json`, embedded; an id the list does not hold has no name), every stored CVSS score and the one `PickCVSS` picks with its band (`Severity`) and its vector read into words (`ReadVector`: attack vector, complexity, requirements, privileges, user interaction, scope, impact, a one-sentence summary; nil for a vector it cannot read whole), the exploited-list entries in the list's words (owner first), every `feeds_signal` row as stored with its feed's name (a new kind or source appears without a code change), every range with `counts` (`rangeOrigin`) and its versions in words, the origin that counts and `ranges_complete`, the references grouped (`refGroup`: the first of vendor-advisory, patch, mitigation, release-notes, exploit, government-resource, third-party-advisory, technical-description, issue-tracking, mailing-list, vdb-entry, media-coverage that a tag names, else other), solution, workaround, SSVC, EPSS with its day, the score of a week before and the kept days, and the NVD and CVE.org page addresses. Nothing is fetched to answer it. `TestBrief_CVE2025_22225`, `TestBriefRoute`.
- **BRIEF-2** (one writer rule per column, whichever pull came first): NVD's weaknesses (`ParseNVD` reads `weaknesses`, NVD's own and those it carries from the CNA and CISA's ADP; `NVD-CWE-*` placeholders dropped) replace `feeds_cve.cwe` when NVD lists any; the CVE record writes `cwe` only while NVD has not answered or `cwe` is empty. Known limit: a CVE-record CWE update after NVD answered with no CWE is not applied (nothing records who wrote `cwe`; rare, since NVD carries the CNA's CWEs; `TestBrief_WeaknessesDoNotDependOnWriteOrder` asserts it). NVD's references (`references`, NVD's tags read into the CVE record's words by `nvdTag`: "Vendor Advisory" is `vendor-advisory`, "US Government Resource" `government-resource`) replace a CVE's `feeds_cve_ref` rows (source `nvd`) once NVD has tagged any, for every CVE the catalogue stores; the CVE record's references (source cna/adp, the CNA's tags) stand until then and never replace NVD's after. A rejected record drops every reference. `TestBrief_ReferencePrecedence`.

## Vendor notations (`statedRows`, `Range.Generic`, `RangeScheme`, `core/versionscheme`)
- **VN-1** (rows kept as the vendor states them): a product of a CVE record that the generic rules of INV-20 refuse is no longer dropped whole: its affected versions are stored as written (`statedRows`: bounds as written; `fixed` = the `lessThan` end when a change at the end or `defaultStatus` unaffected says the versions from there are unaffected; a range with `changes` split into its affected stretches, each ending at its fix; an "affected except" entry as one range per fixed release, from the one affected version it names), beside NVD's rows, with `version_type` = `vendor:` + the entry's versionType (`vendor:custom`; `vendor:text` when none). Left out: git commits, entries limited to some operating systems or models, a bound that is not printable ASCII, holds a quote, backslash or semicolon, or is longer than the column. At most `recordMaxStatedProduct` (500) rows per product and `recordMaxStated` (2 000) per record, deduplicated with a map: a product over either keeps no row, counted in `CVERecord.StatedDropped` (a record of 60 000 hotfix changes makes no row). `Skipped` still counts the product. No column or table is added: precedence (NVD > CNA/ADP) is applied when read, as before.
- **VN-2** (matching unchanged): every reader that matches reads only rows the generic comparison orders (`Range.Generic`, SQL `genericRowSQL`): `rangeOrigin` (so `Store.Ranges` and the brief's `counts`), `kevRecordView`/`KEVRecordRows` (so `KevAffected`, `RangesFromCVEOrg`), `Catalogue` (`RangesFrom`, `RangesComplete`), the held note. A change of display-only vendor rows bumps `feeds_cve.updated_at` but is not `feeds.ranges.updated` news (`replaceRecordRanges` reports apart the change of the rows a matcher reads: generic rows, and the rows of a product with a version scheme). The record rows of a product with a version scheme never reach the generic views (`recordSkipped`): the scheme reads them (`SchemeRangesOf`, VN-5). `recordSkipVendors` keeps Juniper (products without a scheme) and Microsoft; Citrix left it when NetScaler got its scheme.
- **VN-3** (version schemes): a product's scheme is declared in the product catalogue (`content/catalog/products`, `scheme`; CVE record names of the product in `record`) and implemented in `core/versionscheme` (`vmware-esxi`, `citrix-netscaler`, `linux-kernel`, `java`). `RangeScheme(r)` finds the range's product (`productid.ByRangeName`: its CPE, or its record key) and reads the row in the scheme: a `versionscheme.Span` and its fixed release; `versionscheme.Judge` compares an installed version inside its release train first (a range whose end is in that train decides alone), then by release order; a version or bound the scheme cannot place is not comparable, never guessed; a train two of a product's ranges end in at different releases (`versionscheme.Conflicts`: NetScaler's FIPS build written without the word, CVE-2026-88779) is not comparable and named as no fix; an NVD row that names one release in its CPE without bounds is not read by a scheme (`pinnedInCPE`), never "every version". The ESXi build table (`content/catalog/esxi-builds.json`) is read through `versionscheme.ESXiBuild`.
- **VN-5** (scheme readers for the match pass): `SchemeRangesOf(cves)` returns the rows a version scheme reads (vendor-notation rows, and every CVE record row of a product with a scheme, `SchemeProduct`); `SchemeCVEs(keys)` the CVEs whose record rows name those products (a CVE only the vendor's rows describe reaches the match pass before NVD analyses it); `DistroCVEs(pkgs)` the CVEs an enabled distribution feed has a word on for those (distribution, release, source package) triples. A
  pull of NVD or CVE records that changes the matched rows of a CVE on no exploited list sends `feeds.ranges.updated` with
  `Catalogue` (and `CVEs` empty when no listed CVE changed): findings' match pass runs then. `TestNVDPull_CatalogueChangeIsNews`. Schemes: `vmware-esxi`, `citrix-netscaler`, `linux-kernel`, `java`, `juniper-junos`.
- **VN-4** (reader revision): the record cursor's address carries the range reader's revision (`recordReader`, `recordCursorURL`: `<feed>#ranges-2`). A box whose cursor carries an older one (or none) reads the whole list again, once, resumable like any whole read (`recordRereadMark` on the cursor while it downloads): every stored record is replaced, one read after the archive's midnight too, and the cursor goes back to that midnight so the changes since are read again. `TestCVERecords_ReaderChangeReadsTheWholeListOnce`.
- **BRIEF-3**: each `BriefRange` carries `Train` and `FixedRelease` as its product's scheme reads it (none for a train in conflict, `schemeWords`), `Versions` in the scheme's words ("from 8.0 before 8.0 U3d (build 24585383)"); `Brief.Fixes` is the fixed release of each product and train, the vendor's (CNA, ADP) first. A vendor row never counts. CVE-2025-22225: NVD's 55 rows count; VMware's 8.0 U3d (24585383), 8.0 U2d (24585300), 7.0 U3s (24585291) per train. `TestBrief_CVE2025_22225`, `TestBriefRoute`, `TestParseCVERecord_VendorRows`, `TestCount_VendorNotations` (the class audit), `core/versionscheme` table tests.
