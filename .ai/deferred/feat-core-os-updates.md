# Deferred: feat/core-os-updates (WP-07b part 2: core side of OS updates and backups)

- [ ] Software updates `/core/updates*` (not the OS ones): `container.pull|start|stop|rollback`, signed manifests/index (`update-manifest.md`), `UpdateHistory`, advisories; the OS endpoints ship now, these stay 501.
- [x] `/core/logs/export` registry (INV-13): done in feat/logs-export (D-132) for the 8 categories. The host's platform logs (`logs.export`, `GET /v1/exports/{id}/content`) are not one of them: see `.ai/deferred/feat-logs-export.md`.
- [ ] `/core/data/export` (my data as JSON) and `/core/data/purge` (type the organization name): not started.
- [ ] Restore from the GUI: the contract has no endpoint for `backup.restore` yet (only the download). When a restore story exists: core writes a snapshot of its CURRENT state (with key), calls `backup.restore {backup_id, snapshot}`, and expects to be stopped by the host and to read the run result after it comes back (`GET /v1/runs/{id}`); the upload of a user file is a separate flow (host-api 6.12).
- [ ] GUI states for what the backend now answers and the mock never does: `409 not_appliance` (container-only install: Settings → Updates should say the OS part is not available and hide the buttons), `409 no_check_yet` on `GET /core/updates/os` (show "Check now" instead of the page), `503 host_unreachable`, `409 dpkg_locked` with `retry_after`, `409 low_disk`, `502 snapshot_rejected|apt_failed|health_check_failed|host_error`. Needs a story criterion under S-CORE-7 and a mock case, GUI-first (`rules/gui-first.md`); `contract.ts` stays as it is.
- [ ] First check: nothing runs `os.check` by itself, so a fresh box answers `no_check_yet` until someone clicks Check now. A daily job (when update checks are on under Privacy and `host` is reachable) would fix it; decide with the software-update job.
- [ ] `core.os.install_finished` event (CONTRACT "Events"): published nowhere; add with its first subscriber (notify "reboot needed"?).
- [ ] `OsPackage.cves` is always `[]` (the host does not know CVEs): fill from the KEV/NVD data of `feeds` through a port in `cmd/vedette` when that data has package-level matching.
- [ ] Privacy write: `PATCH /core/privacy` is not implemented in Go yet. When it is, it must store `update_check` in core_setting key `core_privacy` (that is what `OSHandlers.updateCheckOn` reads; absent row = on). `GET /core/privacy` and `PATCH /core/privacy` must use `keyPrivacy` and `privacySetting` (handlers_os.go); `TestPrivacySettingShapeIsPinned` fails when the shape moves.
- [ ] The backup download keeps a `manual` backup on the host for every download (host keeps at most 10, no `backup.delete`, D-85) and core allows one download a minute: the page may want to say so, and show the 429 `retry_after`.
- [ ] GUI after a change on a never-checked box (settings, reboot): the answer carries an empty host part (distro "", `last_check` at the zero time); `setOs` in `api.ts` caches it, so the page needs a "not checked yet" state for it (same story criterion as `no_check_yet`).
- [ ] Linux-only behaviour of the host paths (peer check, `SO_PEERPIDFD`, rootless `core` under Quadlet, `core_cgroup`) is still untested on a real machine (host-api 15, 16); core only needs the socket to be reachable by the `core` uid.
