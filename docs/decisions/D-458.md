| D-458 | **Every Vedette container runs under Vedette's own AppArmor profile `vedette-container`, a copy of Podman's `containers-default` whose signal and ptrace rules also match the stacked label crun gives a container under `NoNewPrivileges` (host, S-CORE-7; units of core, sensor, scan, honeypot; follows D-105, D-316 (10), #599).** (1) **What broke** (lab, fresh Ubuntu 24.04.5, kernel 6.8, Podman 4.9.3, profile `containers-default-0.57.4-apparmor1`, rootful Quadlet units with `NoNewPrivileges=true`): every process of `vedette-scan` and `vedette-honeypot` carried the label `containers-default-0.57.4-apparmor1//&crun (mixed)`, and the kernel denied `operation="signal"` from `containers-default-0.57.4-apparmor1` to the peer `containers-default-0.57.4-apparmor1//&crun`: podman-init (`RunInit=true`) could not forward SIGTERM to the worker, so `systemctl stop vedette-scan` took 10 s, ended in SIGKILL (status 137) and left the unit failed; init.py's SIGTERM to its children got EACCES (#599 made init exit anyway); and the SIGURG of Go's goroutine preemption was denied in core (`vedette`), the sensor and nuclei. (2) **Root cause, three parts.** (a) AppArmor 4.0 (Ubuntu 24.04, also 26.04 and Debian 13's `apparmor` package) ships `/etc/apparmor.d/crun`, `profile crun /usr/bin/crun flags=(unconfined) { userns, }`, so crun is no longer "unconfined" but a named profile. (b) crun, when the OCI spec has `noNewPrivileges` and crun itself is confined, writes `stack <profile>` instead of `exec <profile>` ("if confined only way for apparmor to allow change of profile with NNP is with stacking", `set_apparmor_profile` in crun 1.14.1 and main): under no_new_privs the kernel allows leaving a named profile only as a stack. The container's label becomes the stack of both. (c) The kernel keeps a stack sorted by profile name and matches a peer rule first against the whole label (`A//&B`), then against each part with the permissions intersected (`aa_label_match`, `label_compound_match`, `label_components_match` in `security/apparmor/label.c`). `containers-default` allows `signal (send,receive) peer=<its own name>` only; the whole label does not match that, and the part `crun` has only `signal (receive) peer=…crun*` there, no `send`: every signal between two processes of a container, and to a thread of the same process, is refused. Upstream fixed the template on 2026-11-06 (`signal (send,receive) peer={{.Name}}//&*` and the same for ptrace, container-libs PR 919, commit 6506a4c7f388) for the same stack seen on Ubuntu 25.10+/26.04 and CRI-O; it is in no release yet (backports to Podman 5.8/6.2 "might take a few more weeks"), so Ubuntu 24.04 (Podman 4.9.3, common 0.57.4+ds1-2ubuntu0.2), Ubuntu 26.04 (Podman 5.7.0, common 0.66.0; this machine's `/usr/bin/podman` carries only `peer={{.Name}}`) and Debian 13 (Podman 5.4.2; its `apparmor` package ships `/etc/apparmor.d/crun` too) all have the bug, and no noble SRU is filed. Ubuntu 26.04 kernels from 7.0.0-41 also force a `//&unconfined` stack on exec'd processes even without no_new_privs (Launchpad #2172640, containerd #12886 on 6.17), so the stacked peer is not only a crun/NNP matter. (3) **What ships**: `deploy/deb/vedette-container.apparmor`, installed by the `vedette-host` .deb as `/etc/apparmor.d/vedette-container` (a conffile, as Debian ships every profile; apt runs with `--force-confold`): Podman's template at 6506a4c7f388 with a fixed name, the parser-version checks dropped (every supported parser is ≥ 2.8.96), and the peer of its own rules written `{,**//&}vedette-container{,//&**}` for `signal (send,receive)` and `ptrace (trace,read)`, i.e. this profile alone or stacked with anything in any position (upstream's `{{.Name}}//&*` works for `containers-default` only because "co" sorts before "crun" and "unconfined"; "vedette-container" sorts after them, so its stack is `crun//&vedette-container`). Every other rule (network, capability, file, umount, the /proc and /sys denials, `deny mount`, the receive rules for unconfined, runc, crun, podman) is Podman's. A containers.conf module `/usr/lib/vedette/apparmor-containers.conf` (`[containers] apparmor_profile = "vedette-container"`) in the same package, and one `ContainersConfModule=` line in each of the four unit templates (honeypot: before its own module). Legacy templates `core-4`, `sensor-1`, `honeypot-2`, `scan-1` (D-316 (10)): units migrate at the next host start and take effect at the next restart; no host port is added (D-455 does not defer it). The postinst, only where `aa-enabled --quiet` (Debian's dh_apparmor gate; off, or not manageable as in a container: skipped), compiles the profile before it creates anything (`apparmor_parser --skip-kernel-load --skip-cache`), loads it (`--replace --skip-cache`, which also gives running containers the new rules) and checks the effect (`vedette-container (enforce)` in `/sys/kernel/security/apparmor/profiles`); any failure stops the package (a self-update is then reverted, the box keeps working as before). At boot `apparmor.service` (`Before=sysinit.target`) loads it from `/etc/apparmor.d`, the only directory it reads, before any unit. Podman refuses a container whose named profile is not loaded ("specified but not loaded") but ignores a containers.conf `apparmor_profile` where AppArmor is off or `apparmor_parser` is missing (`setupApparmor`, `apparmor.IsEnabled`), which is why the name goes through a module and not `--security-opt` (that one refuses to start without AppArmor). `NoNewPrivileges=true` and `RunInit=true` stay. The effect (labels, denials gone, a 2 s stop) is a lab line on 24.04, 26.04 and Debian 13 (`.ai/deferred/fix-apparmor-signals-nnp.md`). | Why: the other ways out. **Drop `NoNewPrivileges`** (crun then uses `exec`, no stack, on 24.04 GA): rejected, it is the one setting that keeps a setuid binary from raising privilege inside the container (the scan image is Debian slim with its setuid tools; `allowPrivilegeEscalation: false` is required by the Kubernetes "restricted" Pod Security Standard, https://kubernetes.io/docs/concepts/security/pod-security-standards/), and it would not help on 26.04 kernels that stack `unconfined` anyway (LP #2172640). **Worker as PID 1 without `RunInit`** (Go reaps): fixes only the scan stop; SIGURG and every other in-container signal stay denied. **Wait for upstream**: the fix is days old and unreleased; Ubuntu 24.04's Podman 4.9.3 would need an SRU nobody filed, so a supported box would keep the 10 s SIGKILL stop and degraded Go preemption for its whole life. **JIM's way** (one line `signal peer=@{profile_name}//&{crun,podman},` in `/etc/apparmor.d/abstractions/base.d/`, https://github.com/TetronIO/JIM/pull/1975): rejected, it changes every profile on the machine that includes `abstractions/base`, the administrator's too, and needs the cached `containers-default` unloaded. **`apparmor=unconfined`** or disabling the `crun` profile: drops confinement or breaks unprivileged user namespaces for every user (and 26.04 stacks regardless). A named, package-shipped profile per workload is how the top-tier platforms do it: Kubernetes `appArmorProfile.type: Localhost` with profiles loaded on the node (https://kubernetes.io/docs/tutorials/security/apparmor/), Docker/Podman `--security-opt apparmor=<name>` with containers.conf `apparmor_profile` as the default name (https://github.com/containers/common/blob/main/docs/containers.conf.5.md), Debian's dh_apparmor for loading at install. Cost: our copy can drift from Podman's later fixes; the header names the upstream commit, and when every supported distribution ships a Podman whose default handles stacks the units can go back to it (deferred line). Go impact without the fix: Go 1.14+ preempts a goroutine with SIGURG via `tgkill`; when that is refused the runtime falls back to cooperative preemption at function calls, so it keeps working, but a loop without calls cannot be stopped for a GC stop-the-world or the scheduler, and every attempt writes an audit line (https://go.dev/doc/go1.14#runtime, https://github.com/golang/go/issues/24543).
