| D-435 | **A TLS log source may pin its sender's client certificate by SHA-256 fingerprint (RFC 5425 section 4.2.1 mutual authentication, optional per source; closes the deferred line "mutual TLS is not built").** Before: a TLS source was known by its IP like TCP (D-214 (2)). Decision: `SourceInput.client_cert_sha256` (optional, 64 lowercase hex characters, only for `proto: tls`, else 400 `bad_client_cert`; over HTTP a malformed fingerprint is refused first by the generated validator as 400 `invalid` with `field: client_cert_sha256`, the GUI normalises before sending so it never meets it); stored in `logs_sources.client_cert_sha256` (config migration 0004, `''` = none, every existing row), returned as `LogSource.client_cert_sha256` (null = none). The listener asks for a client certificate only from a sender whose source pins one (`GetConfigForClient` by the remote IP, `RequestClientCert`, session resumption off for that handshake), then requires the first presented certificate's SHA-256 to equal the pin (constant-time compare); no certificate or another one closes the connection and is counted in `Stats.CertRejected` with one Warn per 10 s. A pin is a pin, not a chain check: whoever holds that certificate's private key is the sender (like rsyslog's x509/fingerprint mode), so no CA, revocation or expiry logic is built and a device may rotate its certificate by editing the pin. Changing or removing the pin, or removing the source, ends the live connection (the connection remembers the pin it was accepted with). The IP check stays: the pin is in addition to it, never instead. A device with no certificate configured is unaffected (the request is made only for a pinned source). The GUI field is optional, shown for TLS only, and accepts a fingerprint as tools print it (`AB:CD:...`, spaces, upper case), normalising before sending. Rejected: requiring client certificates for every TLS source (FortiGate and others send one only when configured; the default would break every existing TLS source), a CA-based mode with name matching (a certificate authority UI and revocation for a LAN syslog port; ponytail), and a global trusted-CA setting. | rsyslog's gtls driver offers per-peer modes anon (no peer authentication, advised against), x509/fingerprint ("The fingerprint must be provided as the SHA1 or the SHA256 hex string of the certificate"), x509/certvalid and x509/name (opened: https://docs.rsyslog.com/doc/concepts/ns_gtls.html); the mode is chosen per input (https://docs.rsyslog.com/doc/reference/parameters/imtcp-streamdriver-authmode.html, default none); syslog-ng makes it a per-source `peer-verify()` choice (default required-trusted, `optional-untrusted` turns client authentication off: https://syslog-ng.github.io/admin-guide/100_TLS-encrypted_message_transfer/004_TLS_options, from a search summary, page not opened); FortiGate sends a client certificate only when one is configured and the server asks for it (Fortinet community tip on mutually authenticated TLS syslog: https://community.fortinet.com/t5/Support-Forum/Configuring-Syslog-for-Mutually-Authenticated-TLS-Transport/td-p/97555, from a search summary, page not opened). All three make client authentication optional and per receiver or source; fingerprint pinning is the lightest mode that needs no CA. RFC 5425 section 4.2.1 and 5.3 (D-214). | 2026-11-13 |
