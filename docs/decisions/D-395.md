| D-395 | **MCP server reachable on the machine's own 127.0.0.1 on both install kinds: in the container it listens on the unspecified address of the container's own network, and the unit publishes `127.0.0.1:8765` only (mcp-server, S-MCP-1, S-CORE-9; replaces D-234 (3) and the MCP part of D-420 (4); closes `.ai/deferred/feat-mcp-server.md:3`, v1-readiness T9).** (1) **Why it did not work**: core listened on `127.0.0.1:8765` of its container and nothing published 8765. A publish cannot fix that alone: Podman (netavark, rootful and rootless) and Docker forward a published port to the container's own address, never to its loopback. Checked on the Mac's Podman 5 (rootful and rootless, `distroless/static-debian13` read-only, uid 65532): a listener on `127.0.0.1:8765` behind `-p 127.0.0.1:18766:8765` answered nothing (reset / empty reply); a listener on `0.0.0.0:8765` behind `-p 127.0.0.1:18765:8765` answered, and `/run/.containerenv` was present. (2) **What ships**: the core Quadlet unit gets `PublishPort=127.0.0.1:8765:8765` (template change with its legacy entry `core-3`, so boxes migrate at the next core restart, D-316 (10)); `deploy/compose/container-only/compose.yaml` gets `127.0.0.1:8765:8765`. Neither passes `-mcp-listen`: its default (empty) is `0.0.0.0:8765` in a container and `127.0.0.1:8765` elsewhere. Passing the flag was the first draft; the Opus review found that a core image from before this decision refuses `0.0.0.0` and exits, so a migrated unit started on the old image (a reboot or crash before the image step, a rollback rendering the current template with the previous digest, a compose file newer than its image) would have taken 8443 down with it. With the default, an older image under the new unit simply leaves MCP unreachable, as before. Same pattern as the sensor link 8444 (D-113, D-147 (5)). Never a LAN address: both files and their tests (`host/ops` golden units, `deploy/compose/compose_test.go`) pin the `127.0.0.1` host side; core's network stays its own bridge (no host network, which the compose test already enforces). (3) **INV-5 keeps its guard**: an explicit `-mcp-listen` and `mcpserver.New` still refuse every address off loopback, with one exception: the unspecified address (`0.0.0.0`, `[::]`) when the process runs in a container (cmd/vedette sees Podman's `/run/.containerenv` or Docker's `/.dockerenv`; `Config.InContainer`). A named address (a LAN or container IP) is always refused; on a machine without a container the unspecified address is refused, so a bare binary never opens MCP to the LAN. Known limit: a container on the host network (an operator's `network_mode: host`, a toolbox/distrobox) has the marker, so its default is the host's 0.0.0.0, still behind the token; no shipped file does that (compose test, golden units), and the sensor link 8444 has the same property. `GET /core/mcp` reports `127.0.0.1:<port>` and `http://127.0.0.1:<port>/mcp` (the host side of the publish, same port), never `0.0.0.0`. (4) **Who else can reach it**: the host itself (as on loopback) and peers on the container network (Vedette's own containers on `vedette-int` / the compose network), always behind the bearer token, the Origin refusal and the rate limits (D-230..D-232); the class "a container on the machine reaches unpublished Vedette ports" is T10's (`fix-docker-forward-drop.md:12`). Docker ≥ 28 drops direct-routed packets to ports published on loopback (INSTALL-CONTAINER already names Docker < 28). (5) **Port held on the host**: the runtime reserves `127.0.0.1:8765` while core runs, whether the module is on or off (off: a connection is refused or reset, POST-1 holds inside the container); a program already on 8765 would stop core starting, so `install.sh` preflight now checks 8443, 8444 **and 8765**, README names it. A box upgraded in place is not re-checked (accepted: the appliance is a dedicated machine, install.sh refuses one with other services). (6) **Page text** (Mlee's mcp-server feature, minimal edit): the appliance text was already true ("this machine only", SSH tunnel or reverse proxy); the container-only text now says the port is on 127.0.0.1 of the machine that runs Docker or Podman, never on the LAN, another machine uses an SSH tunnel to that machine, and an older `compose.yaml` must be updated; INSTALL-CONTAINER section 5 says a release may change the compose files and how to check them. Not chosen: **MCP through the 8443 listener at `/mcp`** (Home Assistant serves `/api/mcp` on its main port with OAuth; GitLab likewise) — it opens MCP to the LAN, against D-234 (2) and the MCP transport's advice to bind local servers to localhost, a product-direction change for kien; **host network for core** (exposes every core listener, 8444 and the syslog ports, on the host's interfaces and drops the container isolation of D-55); **a proxy on the host** (systemd-socket-proxyd or socat into the container namespace: another unit and process for one port); **a flag instead of container detection** (would also open the LAN on a bare binary).
