| D-383 | **Trap and decoy state come from what the box did, and the decoy IP is cleared only while every trap is off (S-HP-1, real-install QA 2026-11-12).** (1) Clearing the decoy IP (`PUT /honeypot/config` with an empty `secondary_ip`) is refused with 409 `traps_on` while any trap is on; the box never turns traps off behind the owner's back, and a trap cannot be switched on with no IP (re-checked inside the write transaction). Chosen over "clearing turns the traps off" because the big clouds make the owner release first: an AWS Elastic IP to release must not be associated with a resource, and Azure deletes a public IP only when it is not associated to any IP configuration or network interface, so an explicit order beats an implicit state change. (2) `Trap.state` and `Decoy.state` are `off`, `listening`, `conflict`, `starting`, `stopping`, `failed`: reported from the host (the container runs with the service on and the host holds the address), never inferred from the switch; only the owner's changes (and the module turning on) make a trap `starting`, inventory events do not; `failed` carries the host's plain reason. (3) A refused address is asked again three times, then every 10 minutes, and again when the wanted set changes or the module is turned off, so ten failing decoys cannot use the host's 10 writes a minute. (4) While the inventory has no device in the network the spare-IP hint says "not checked", not "unused".
