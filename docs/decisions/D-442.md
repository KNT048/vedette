| D-442 | **The NAT64 guard learns the network's own prefix length (RFC 7050) and judges only that layout; when it cannot, it keeps judging every layout.** `nat64Local` (modules/notify/channel/webhook.go, modules/logs/siem_send.go, modules/feeds/dial.go; three identical copies) read an address of 64:ff9b:1::/48 (RFC 8215) in every RFC 6052 layout (/48 /56 /64 /96) and refused it if any reading was forbidden, so a legitimate operator prefix such as `64:ff9b:1:a00::/64` (reads as 10.0.x.x in the /48 layout) or a /64 starting 0x7f (reads as 127.x) was refused for every address. (1) **Learning**: the first time a 64:ff9b:1::/48 address is judged, the box asks the system resolver for the AAAA of `ipv4only.arpa` (2 s limit). An answer inside 64:ff9b:1::/48 whose u octet (byte 8) is zero and that carries 192.0.0.170 or 192.0.0.171 in exactly one layout gives a prefix and its length (`learnNAT64`); answers that are IPv4, outside the /48, ambiguous or without the well-known address are ignored. (2) **Judging**: an address covered by a learned prefix is read in that layout only; an address outside every learned prefix, or nothing learned (no DNS64, lookup failed or timed out), is read in all layouts exactly as before, so the forbidden-IPv4 check is never weaker than the fail-closed reading for any address the learned prefix does not cover. A reading inside 0.0.0.0/8 is dropped as before. (3) **Cache**: 6 hours when something was learned, 10 minutes when not (one lookup per 10 minutes at most, only while 64:ff9b:1::/48 addresses are being judged; the common path never queries). The three copies each keep their own cache. (4) **Data flow**: this is one DNS query for the fixed public name `ipv4only.arpa` to the resolver the box already uses for every host name it resolves (feed, webhook and SIEM names); it carries no customer data, no box identity and no configured name, goes to no new party, and is not a new outgoing data flow, so `PRIVACY.md` and `rules/legal.md` ask for no row and no Settings text. (5) **Trust**: the answer is not authenticated (RFC 7050 section 3.1 says to validate with DNSSEC; the system resolver gives no such guarantee here) and RFC 7050 section 7 warns a forged answer can steer the host, so a forged answer is treated as hostile. IP-literal URLs never touch DNS, so DNS must not be able to weaken the guard: the classes a guard never allows (loopback, link-local, multicast, unspecified, broadcast, cloud metadata) are judged in every layout, learned or not; the learned layout (all learned prefixes that cover the address) only narrows the network-dependent checks (private ranges, the box's own addresses); a learned reading inside 0.0.0.0/8 falls back to every layout. The review's example, a forged `64:ff9b:1:a9fe:a9:fe00:c000:aa` teaching a /96 so that `...:0:1` reads 0.0.0.1, is still refused (metadata reading in the /48 layout). Accepted cost: a legitimate operator prefix whose first byte after the /32 is 0x7f (or another always-forbidden first octet) still reads as loopback in the /48 layout and stays refused. A forger can still make the guard stricter, never looser. (6) **Lookup**: one at a time, not under the cache mutex; a caller that finds a lookup running gets what is known (nothing at first, meaning every layout). Tests inject the learned prefixes (no real DNS): `TestLearnNAT64`, `TestAddrFormsNAT64LocalLearnedLength`, `TestNAT64CacheAsksRarely` in each package. | Why: Android, iOS and systemd-resolved (and clatd) learn the NAT64 prefix and its length from `ipv4only.arpa` instead of assuming one (RFC 7050 https://datatracker.ietf.org/doc/html/rfc7050 section 3: the well-known IPv4 addresses 192.0.0.170 and 192.0.0.171 are found in the synthesized AAAA to get prefix and length; RFC 6052 https://datatracker.ietf.org/doc/html/rfc6052 section 2.2 gives the layouts and the zero u octet; RFC 8781 https://datatracker.ietf.org/doc/html/rfc8781 PREF64 in router advertisements is the other source).
