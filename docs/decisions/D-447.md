(1) **QR sign-in**: Sign in with a QR code runs the Zalo web client's QR flow, re-implemented in Go from zca-js v2.2.0 `loginQR` (login page version, `logininfo`, `verify-client`, `authen/qr/generate`, the `waiting-scan` and `waiting-confirm` long polls, `checksession`, `jr.chat.zalo.me/jr/userinfo`, the device id `uuid-md5(userAgent)`), then one `getLoginInfo` with the new session; only then does the dialog say "Signed in as <account>". The session (cookies, imei, user agent) is the channel secret through `core/secrets`, saved by Save with `zalo_login`; the "I scanned it" button is gone. The QR image is decoded on the box and redrawn as an SVG path (no `data:` image under the page's CSP, and the browser never decodes Zalo's bytes). One sign-in per box at a time, in memory, 100 s for the code and 10 minutes for Save; at most one start per 30 s and five per hour. (2) **Recipient**: picked from the account's groups and friends (`getAllGroups` + `getGroupInfo`, `getAllFriends`), or found from a `zalo.me/g/…` invite link (`getGroupLinkInfo`; a group the account is not in is flagged) or a phone number (`findUser`); 20 look-ups per 10 minutes. Stored as before (numeric ID + group flag) plus the shown name. (3) **Approvers (option A, chosen by kien/supervisor after the Opus review found that a reply proves control of a Zalo account but not who the person is: a wrongly picked "Minh" would have become Bob's approver, breaking response INV-24)**: the administrator picks each approver's Zalo (a friend, or by phone number); on Save the box's account sends that Zalo a single-use confirm link `<BaseURL>/link/zalo?c=<token>` that names the Vedette user ("open this link and sign in to Vedette as Bob to link this Zalo account"). The token is made and kept by `response` (`ChatLinkToken`: an 8-hex hint of the person plus 128 random bits, stored hashed with (user, channel, Zalo ID), 10 minutes, single use, constant-time compare, five wrong tries, one a minute and five an hour per person, a new one replaces the old). Only the person, signed in to Vedette as themself, links it by pressing Confirm on `/link/zalo` (POST with CSRF to `/response/me/identities/zalo-personal/confirm`); opening the page never links; another signed-in user gets 403 `other_account` before anything is read, so the link stays good; a reply from the Zalo account links nothing (the reply-code link path of D-243, `LinkFromChat`/`Decisions.LinkChat`, is removed). An administrator's own row skips the message only when its address is the box's own signed-in Zalo account (the uid the saved session signs in as, which the QR sign-in proved): "Link my Zalo now" returns the same link and they confirm it in their session; any other Zalo of theirs gets the link by message like everyone's, so a wrongly picked friend can never become their identity (review round 2). Deleting the channel drops its approvers' proofs too. The confirm page shows the Zalo ID first and prominently, the admin-typed name only as "named … by your administrator". The dialog shows Sending → Waiting → Linked with Send again; audit `notify.zalo_link_code` (never the token), `response.identity_link`, and `notify.zalo_unlink` + `response.identity_unlink` when a linked approver is removed or given another Zalo (`response.DropChatLink`, so A→B→A needs a new confirmation); at most 10 link messages per 10 minutes per box. INV-24 holds: no administrator path marks a link for someone else. My account only shows Linked / Not linked for Zalo. zca-js has no sign-out call, so a cancelled, replaced or unsaved QR sign-in stays live on Zalo's side; the dialog says so.
