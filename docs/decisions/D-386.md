| D-386 | **A revoked running release and stale update information are shown, not only logged (S-CORE-2, update-manifest §4.1, §8, §13 (d)).** (1) `UpdatesState.running_revoked` (null or `{version, reason, since, action}`) names a revocation in the newest stored index that hits the release this box runs: kind `release` with the running version, or kind `image_digest` with a digest of the running release's manifest (when that manifest is known). A `key` revocation is not a running-release revocation: the box keeps the software and only stops trusting new documents signed by that key (§8); `advisory_only` stays an advisory. With several hits the one with a warning action wins. (2) Where it shows follows the maintainer's `action`: `block_install_and_warn` and `rollback_if_possible` are a critical banner on **every page** for every signed-in role, linking to Settings → Updates; `block_install` only blocks new installs (for example a build whose upgrade fails on some boxes while boxes already on it are fine), so it is a warning on the Updates page only. This settles §8's "banner on every page" against the action names, which would otherwise make `block_install_and_warn` mean nothing. (3) `UpdatesState.stale_since` is the stored index's `expires_at` once it has passed, null otherwise (no index yet, or current). It is a warning on the Updates page, not on every page, and it never blocks Apply or a bundle (§4.1, D-104): the usual cause is a box that cannot reach GitHub or has the check off, and the page then says which; the freeze-attack case (§13 (d)) looks the same to the box, so the words say newer and withdrawn releases may be missing. Both fields are computed on read from the stored, re-verified index (no new request; the clock decides staleness, so a box whose checks keep failing turns stale by itself). Not in this decision: the admin-channel notice of §8 and the automatic rollback of `rollback_if_possible` (deferred). Top-tier: TUF makes an expired timestamp/snapshot/targets file abort the update and "report the potential freeze attack" rather than fail silently (spec §5.3–5.6); Home Assistant Repairs keeps issue severities and reserves the highest one for real emergencies, the rest stay in the Repairs list; Chrome and Firefox show "can't update" in their own menu or About page, not over every tab.
