| D-473 | **Exposure: an administrator's Scan now is the authorization (kien 2026-11-13 via the supervisor; beta item 15; amends D-26, keeps D-5's record).** The separate confirm step (a tick box and `POST /exposure/targets/{id}/commitment`) is gone. The first **Scan now** on a verified target by an **admin whose account has two-step sign-in** records the D-26 commitment in the same transaction as its audit row: who, when, which target, and the exact sentence shown next to the button, with that sentence's version (`exp_target.commitment_by/at/version/sentence`; audit action `exposure.commitment` carries the sentence). The sentence has one source, `modules/exposure/notice.go`: the API sends `commitment_notice {version, text}` on a target without a commitment, the page shows what it received, the scan request echoes `notice_version`, and the backend stores the sentence of that version; a missing version is 400 `commitment_required`, an old one 409 `notice_changed`, and nothing is recorded. The mock's copy in `contract.ts` is held equal by a test (`TestNoticeMatchesTheContractOfTheGUI`). An administrator without two-step sign-in is refused (403 `twofa_required`, the page shows a link to turn it on); an operator on an unconfirmed target gets 400 `commitment_required` ("an administrator must run the first scan"); a confirmed target is scanned by an operator as before and later scans record nothing. Refused attempts keep their `exposure.scan` "not done" audit row. Commitments recorded before this change keep `version/sentence = NULL` and show the old "as is" line. **An SSO sign-in counts as two-step for this purpose** (the identity provider owns MFA; Vedette two-step cannot be turned on for an SSO account, D-195; GitHub and Microsoft treat IdP-enforced MFA the same way): `TwoStep` returns the method, `app`/`email` or `sso`, and the commitment stores it with the user id (`commitment_user_id`, `commitment_method`) next to the email; the audit line names both. Because the page cannot tell an SSO sign-in from no two-step, the button stays enabled for an admin and the server's 403 `twofa_required` is shown on the page with the link. The notice text of each version is pinned by a hash test. Two-step is checked as "the account has it on" (no code asked at each press: the press happens in a signed-in session, and the per-press code of D-357 is kept for high-risk response approvals); the check is `Config.TwoStep`, wired in `cmd/vedette` from `core/auth` (`GetUser`), so core/auth is untouched. Not done: a scan that is refused after the commitment was recorded (for example the IP is no longer current) leaves the commitment in place, since the administrator did confirm. Sources (named in the beta plan 2026-11-13 §3, not re-fetched here): Detectify, Qualys and Tenable authorize a scan through proof of ownership plus the user's permissions on the target, not through a step at scan time. | 2026-11-13 |
