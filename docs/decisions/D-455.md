| D-455 | **vedette-host adds a host port to a unit only at a restart it checks, and refuses one that is busy before it touches the running release (host, S-CORE-2, S-CORE-7; follows D-395 and D-214, D-316 (10)).** (1) **Gap**: D-395 adds `PublishPort=127.0.0.1:8765:8765` to core's unit, D-214 added `6514`. `install.sh` refuses a busy port on a fresh box, but an update in place never runs it: if another program listens on 8765, the new core unit cannot reserve the port, core does not start, and 8443 is gone until the revert. (2) **A change that only takes effect at a later restart never adds a host port** (same port and protocol as the unit on disk, any address): the unit migration at host start (D-316 (10)) runs at boot, before the programs that may hold the port have bound it, and its text would take effect at the next restart with no check and no health revert behind it; so it keeps the earlier unit whenever the current template adds a port, busy or not, with one `container.start unit_migration_deferred` audit line (`service`, `digest`, `ports`) per host start. A `container.start` without `restart` of a running, healthy service keeps its unit's template too (only `[Install]` may come back, from that same template), succeeds and audits the same line with `run_id`; `container.stop persist` drops `[Install]` from the unit's own template. (3) **The restart checks**: `container.start` with `restart` or another digest, and `container.rollback`, refuse **`412 port_in_use`** at `Check` when a new port is busy, again in `Run` right before the transition journal, and for a version switch once more right before the unit is written (after the `pre_update` backup, which can take minutes; the journal is dropped, the backup stays). A stopped service (`inactive`, `failed`) holds no port, so in `Run` every port of its unit is looked at; a running one, only the new ports (its container holds the others). The message names each port and the process (`8765/tcp (python3, pid 4242)`); the restart keeps its health revert. A `container.start` without `restart` and without a new digest is judged in `Run`, once the host knows whether it restarts. (4) **How it looks**: the kernel's socket tables `/proc/net/{tcp,tcp6,udp,udp6}` (TCP in LISTEN, every bound UDP socket; a clash is the same address, or either side unspecified, `::` counting for IPv4 because the table does not show `IPV6_V6ONLY`), and, only for a clashing socket, `/proc/<pid>/fd` links `socket:[inode]` with the holder's `comm` (printable ASCII, 15 characters) and `cgroup`. A socket held by a process of the service's own systemd unit (`/system.slice/vedette-<service>.service` or below: its conmon, its container) is not a conflict. `PublishPort=` is read only in the forms the host writes (`[ip:]host:container[/tcp|/udp]`); a range, a missing host port or another protocol is skipped, and a test pins that every line of every template is read. No program runs, no socket is opened, no probe bind. A table that cannot be read (also a read error half way) is logged and refuses nothing: the revert path stays the safety net, and the check never blocks an update on its own misreading. (5) **Consequence**: a template with a new port reaches a box only through core's restart of the service (the image step of a software run), never through a reboot. Core's update run gets the code as a final refusal of the step; its user-facing sentence is core's (deferred). | Why: the failure mode is the one Docker Compose shows when it recreates a container whose port was taken ("port is already allocated" after the old container is gone): the old release is down before the conflict is known. Top-tier installers and orchestrators check host ports **before** they act: kubeadm's preflight refuses `init`/`join`/`upgrade` when a control-plane port is in use (https://kubernetes.io/docs/reference/setup-tools/kubeadm/implementation-details/#preflight-checks), and the Kubernetes scheduler's `NodePorts` filter does not place a pod whose `hostPort` is taken on that node (https://kubernetes.io/docs/reference/scheduling/config/#scheduling-plugins). systemd and Podman have no such preflight: a `PublishPort=` that cannot bind makes the Quadlet unit fail at start (https://docs.podman.io/en/latest/markdown/podman-systemd.unit.5.html), so the host has to look itself, and only at the moment it acts, which is why a change that acts later (boot) does not get a port at all. Reading `/proc/net/tcp` and `/proc/<pid>/fd` is what `ss -p`, `netstat -p` and `lsof` do (https://www.kernel.org/doc/html/latest/networking/proc_net_tcp.html, https://man7.org/linux/man-pages/man5/proc_pid_fd.5.html). Not chosen: checking the port in the migration at boot (first draft; the Opus review found it races the programs that bind later, and a failure then has no revert); a probe bind (`net.Listen`, kubeadm's way): the host may not open a network socket (FORBID-2), and a bind on 127.0.0.1 says nothing about a listener on another address; running `ss` (an external program for what two file reads give); checking every port of a running service with the owner rule only (a cgroup layout we did not foresee for conmon would refuse every update); refusing on an unreadable table (one odd `/proc` would block updates for good). | 2026-11-12 |
