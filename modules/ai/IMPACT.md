# AI — Change Impact Map

> Go code in `modules/ai` and `modules/ai/provider`; the gates to other modules are in `cmd/vedette` (`ai.go`, `aipath.go`, `ai_plan.go`, `ailogdigest.go`, `reports.go`). The signatures below are the real signatures.

## Modifying: `RunJob(ctx, spec JobSpec) (JobResult, error)` — callers: `Brief`, `ExplainCVE`, `NewsCVE`, `Ask`, `LogDigest` (inside the module), `reportsAI.Summarize`, `responsePlanner` (`cmd/vedette`)
- **`/ai/*` handlers** (`handlers.go`: `/ai/cve/{id}/explain|news`, `/ai/ask`, `/ai/logs/digest`): changing the `ai_unavailable` error → every AI button shows the wrong state.
- **reports** (`weekly-report`, `pdpl-assessment`): changing `JobResult` → the AI comments in reports break.
- **response** (`response-plan`, through the `Planner` gate of `response`): changing the plan structure → `/response/plans` and the action-proposal step break. Action proposals go through the Go gate `response.Service.Propose` with the actor `ai:response`, not through HTTP; the `plan` job of `response` calls it after storing the plan, so changing the `response_plan` schema (adding `confidence`, `evidence`) or the "reads the box made" block of `cmd/vedette/ai_plan.go` changes what `Propose` receives. **`ConfigRead`/`RecentReads`/`RecordProposals`**: `response.Config.Evidence.ConfigRead` reads `ai_read`; changing the 24-hour limit, the id format or the row writing in `connectionTools` (ask_tools.go) changes the `config_read` evidence that `Propose` receives (`TestWiringConfigReadIsTheAIRecordOfAReadThroughTheConnection`). The `ai_read` table has an export policy row (`modules/core/export_policy.go`).
- **mitigation** (`mitigation-config`, "Ask my AI"), **logs** (`log-digest`): changing the "AI-generated" label → violates S-AI-6.
- Adding a new job: add it to `AiJob`, the assignment table, write `data: internal|public` (the INV-3 decision), update the GUI.

## Modifying: error codes of an AI job call, the output token cap, `ai_activity.stop` (POST-6)
- **mitigation** (`POST /findings/{id}/ai`, through `cmd/vedette` `aiMitigation.Run`): returns the `*apierr.Error` of `ai` unchanged; changing a code or message = changing what the finding page shows (`web/src/features/findings/findings.test.tsx` "Ask my AI failing with …").
- **response** (`planError` in `cmd/vedette/ai_plan.go`): only `budget_reached` (the monthly budget is used up), `rate_limited` (the loop fuse) and "not usable yet" stop the plan loop; any other new code only sets that finding back. `response` no longer has its own cap of 20 per day. A scheduled job (`Actor "system"`) receives 429 `budget_reached` once 80 % of the monthly budget has been spent (`scheduledPausePct`) with no `ai_activity` row, so the plan loop stops quietly; a temporarily reserved budget is 429 `rate_limited` (also stops the run, and the run 5 minutes later tries again). `Config.Alert` of `cmd/vedette` wraps `notify.ErrModuleOff` with `ai.ErrAlertOff`.
- **monthly token budget** (shared and per profile): `monthly_budget` at `/ai/config` and `/ai/profiles`, `used_month`, `month_used`/`renews_on`, the error code `budget_reached`; stops at 100 %, does not lower the level; the `budget-watch` job (80 % medium, 100 % high through `Config.Alert(ctx, id, title, text, high)`); a fuse of 30 calls/minute/job (`rate_limited`, audit `ai.fuse`). Callers of `RunJob` (explain, mitigation, reports, response-plan) read these error codes; `reports` and `mitigation` pass the error on unchanged. This part lives in the meter/budget (`meter.go`, `budget.go`, its notice sentences).
- **reports** (`reportsAI.Summarize`): the error goes straight to `POST /reports/*/ai-summary`.
- **GUI**: the page only shows `message`; `docs/API_CONVENTIONS.md` §3.3 keeps the codes (`TestConnections_ErrorCodesAreCatalogued` counts rows per entry). The cap of each job lives with the caller of `RunJob` (`brief.go`, `explain.go`, `news.go`, `ask.go`, `logdigest.go`, `cmd/vedette/reports.go`, `cmd/vedette/ai_plan.go`); `MaxAnswerTokens` bounds the retry. `estimateTokens` (the reservation while calling) adds this cap, so a large cap only holds the reservation longer, it costs nothing.
- `ai_activity.stop` and `retried` are not in the hash: changing them does not make the old chain wrong; the data export carries them like `outcome` (`modules/core/export_policy.go`).

## Modifying: `AskHook.step` / `notIDForms` (POST-7, INV-12a)
- **GUI** `AssistantPage.tsx` reads `hooks[].step`: only `question` is "The AI was not asked", `answer` is "the answer was held back"; changing a value = changing `contract.ts` (`AskHookHit`), `api/openapi.json`, `core/api/oas`, the mock.
- `notIDForms` loosens the ID-number finder for every call (question, data, tool result, memory, knowledge base): adding a form = a run of ID-number digits that can slip through; keep `TestContract_INV12_IDNumbersInEveryFormAreBlocked`, `TestIDNumbersAndTheFormsTheyAreNot` and `TestPersonalDataNextToVersionsIsStillFound` (every ID-number string placed next to each form) green; a new form needs a word in `formNeeds` so that 1 MiB of text still finishes well under `HookTimeout`.

## Modifying: `Router.Candidates(job) ([]Profile, []string)` (choosing primary/fallback, INV-3)
- Every `RunJob`. Changing the logic that excludes cloud profiles → may leak internal data; the INV-3 tests must stay green.

## Modifying: the tool loop of `ask-my-data` (`ask_loop.go`, `ask_tools.go`, INV-22)
- Adding a read tool = adding a surface of data leaving the box to the AI provider: write it in `toolImpl` (closed-schema arguments, row/byte caps, `Cite`), update PRIVACY.md flow 3 and `privacy.flow.3.what` in `web/src/locales/en/core.json` in the same commit; `log-investigate` shares this list (the `Jobs` of each tool).
- Changing `Config.Data` (cmd/vedette `aiAsk`) or `Config.Conns` (`core/conn/read`): changes the data the AI sees; changing `ConnReader` = changing the INV-14 surface. `RunJob` additionally has `JobSpec.tools`/`AnswerWhenBlocked` and `JobResult.Hits/Blocked` (other callers are not affected).
- The assistant's findings tools (cmd/vedette `aiAsk.Findings`, `aiAsk.Finding`) leave out the findings of devices a person ignored (`findings.Views`; one finding: not found when `View.Device.Ignored`), as `AffectedAssets` already did.
- GUI: `AskResult` matches `web/src/features/ai/contract.ts`; changing the shape = changing the mock, `api/openapi.json` and `core/api/oas` too.
- Changing the shape of the results of `search_assets`/`list_findings`/`lookup_cve` or the loop's caps: every turn resends the whole conversation, so the input tokens of a question grow with the size of the result times the number of turns after it; run `TestAskBetaBoxQuestionStaysInBudget` (≤ 8,000 / ≤ 20,000) and keep the totals clear (`matching_*`, `note`) so the model does not read one page as the whole.
- `ai_result` kind `ask` is written by `insertAsk`, keeping 100 rows; `GET /ai/asks` reads 10 rows. Exported through core's `ai_result` policy (the payload is JSON).

## Modifying: `device_updates` (`ask_updates.go`, `Config.Updates`, `Updates`/`DeviceUpdates`/`UpdateRow`; INV-22c)
- The data comes from the By device fix blocks of `findings.Service.ByDevice` through `aiAsk.DeviceUpdates` (cmd/vedette/ai.go); when the block shape changes in findings, change the adapter. The `status` words (confirmed, detected, suspected) come from each finding's verification; do not invent a rule here. `Ransomware`, `Likely`, `Reported`, `NVDLag`, `PlanRan` and `PlanCompared` were removed because nothing sets them any more.
- The description and schema travel in every turn: making them longer breaks `TestAskBetaBoxQuestionStaysInBudget` (≤ 8,000) first.
- The result is data leaving the box to the AI provider: PRIVACY.md flow 3 "Ask your data" and `privacy.flow.3.items` of `core.json` mention "the updates of one device"; when adding a field, change both in the same commit.

## Modifying: `ForModel(job, tools) []provider.ToolDef` / `Offered` (INV-14)
- **mcp-server**: not used. **ask-my-data / log-investigate**: adding a new read-only tool = changing the data surface the AI sees; a `write` tool never enters the list.

## Modifying: connections (`core/conn`, `Config.Conns`)
- Connections do not belong to `ai`: `response` reads the list, the fingerprint and the write tools from `core/conn`. `ai` is a **user** of the read-only reader `core/conn/read` for `read` tools; changing that reader = changing the data surface the AI sees (INV-14).

## Modifying: `Seal(prev, entry)` / `VerifyChain` / `VerifyActivity`
- **core/logs export** (`ai_activity`), **GUI Activity panel**: changing the hash formula → old chains can no longer be verified; a migration step is needed (write `version` into the entry).
- **`activity-verify`**: calls `VerifyActivity` every 24 hours and `Config.Alert` → `notify.Publish` (kind incident) when broken; if `VerifyResult` or the `Alert` signature changes, fix `cmd/vedette/ai.go` and `verify_alert_test.go`.

## Modifying: `HookRunner.Run(ctx, when, text)`
- Every `RunJob`, `Ask`. Changing the order (block before mask) or adding a built-in hook → changes the data leaving the box (PRIVACY flow 3).

## Disabling this module
- The AI buttons disappear (Findings/CVE, Logs digest, reports, Assistant); `response` loses the AI's plans and proposals but **keeps connections and actions on devices** (connections belong to `core`); `mitigation` only shows "No confirmed recommendation yet" + KEV requiredAction.
- No call goes out to a provider. `ai_*` and the log chain stay as they are.

## Library — the real signatures

- `New(Config) (Provider, error)`, `Provider.Complete(ctx, Request) (Response, error)`, `Probe(ctx, p, now) (ProbeResult, error)`, `StyleForKind`, `DefaultBaseURL`, `ParseBaseURL`, `Secret` (`NewSecret`, `Reveal`, `Last4`, `IsSet`).

## Running a job: `RunJob`, CVE explanation, usage, runs — the real signatures
- `RunJob(ctx, JobSpec) (JobResult, error)`: one call = the `before_ai` hook on the question and each data block (block/hold/error → not sent, a `blocked_by_hook` log row), `PromptBuilder` (built-in rules, untrusted data only in the fenced `JobSpec.Data`), `Router.Call` (primary → fallback, `Meter`), the `after_ai` hook on the answer, `JobSpec.Check` (wrong schema → `ErrBadOutput`, the answer is dropped), and then **one** `ai_activity` row + the result (`JobSpec.Store`) in one write transaction. The error the user sees is an `*apierr.Error`: 409 `ai_unavailable` (including a hook block, a bad answer), 429 `budget_reached`. A job with no allowed profile has **no** log row (nothing was tried). `connection-test` also writes one row.
- `ExplainCVE`, `CachedCVE` (`/ai/cve/{id}/explain|cached`): cache by `(CVE, hash of the feed entry + the matching devices)` in `ai_result`; `affected` is decided by the box (no match → no, a confirmed finding → yes, otherwise unknown), citation sources built by the box from the feed's links. `Config.Facts` (`ai.Facts`: `CVE`, `AffectedAssets`) is connected by `cmd/vedette` to feeds, findings, inventory; adding a field to `CVEFacts`/`AssetFact` = changing the data sent to the provider (PRIVACY flow 3).
- `Brief`, `Available`, `Configured`: the gate of `mitigation.AI` (`cmd/vedette/ai.go` `aiMitigation`) and of the Privacy page (`privacyFacts.AIConfigured`). Changing `BriefAnswer`/`JobSpec` → `mitigation` (`/findings/{id}/ai`) and `cmd/vedette/ai.go`.
- `Usage`, `Runs`: views over `ai_activity` (`status`: ok / schema_error if it cost tokens but was unusable / capped when the `outcome` column = `capped` (the shared cap or the profile's own cap blocked it before sending, or blocked a later turn of a question that had already spent tokens; checked before "cost tokens") / failed for every remaining case that cost nothing, including `outcome` = `not_sent`; the `outcome` column is outside the hash like `profile_id`); `New` rebuilds the meter from this month's `ai_activity` (`seedMeter`), so the level in force and each profile's cap do not change on restart.
- `ai_activity` has a trigger forbidding edits and forbidding an `INSERT OR REPLACE` overwrite; deletion by retention (`PruneActivity`) is in the same transaction as `core_chain_anchor` and lowers `core_chain_head.count`.
- `GET /ai/cve/{id}/cached`: the mock does not simulate the cache becoming invalid after a device changes (mock does not model cache invalidation after a device change); the backend only returns a row whose inputs hash matches the current feed and devices, and otherwise returns "nothing in the cache yet" as if it had never been explained (the backend serves only a row whose inputs hash matches). `contract.ts` is unchanged.

## Activity log: list, verify, retention, export — the real signatures
- `ListActivity(ctx, ActivityFilter)`, `VerifyActivity(ctx)`, `RetentionDays`, `SetRetention(ctx, who, days)`: `GET /ai/activity` (the 1000 newest rows after the filter, `total` is the whole log), `GET /ai/activity/verify`, `GET/PUT /ai/activity/settings`. Verify reads the anchor, the head and the rows in **one** read transaction (a row written midway does not look like a broken chain). Changing a column of `ai_activity` → change `activityCols`, `exportCols` and `entryMap` as well (the same set of columns as the hashed part).
- `ExportActivity(ctx, from, to, w)`: the `ai_activity` source of `GET /core/logs/export` (registered in `cmd/vedette/logexport.go`); exactly the hashed columns, no `seq`, no `profile_id`, so the exported file can be verified outside the box. Changing a column → old export files cannot be verified.
- `PruneActivity(ctx)` and `Jobs()` (the `activity-prune` job, 6 hours): deletes the run of old rows **consecutive from the start** whose `ts` is past retention (stops at the first row that is not past retention, so a clock moving backwards does not make younger rows get deleted early); **the newest row always stays** (the chain's head names it, `chainhead.Prune` does not delete it). One transaction with `ChainPruner.Prune`; `cmd/vedette` connects `ChainPruner` with `chainhead.Prune` and registers `Jobs()`. This job is `Housekeeping`: it still runs on schedule when the `ai` module is off, so do not let it do anything beyond deleting rows past retention (sending, calling a provider, writing new data) without dropping the flag. The module does **not** write `core_chain_anchor` or `core_chain_head`; without a `ChainPruner`, `PruneActivity` returns `ErrNoPruner` and `Jobs()` is empty.
- `VerifyActivity` reads `core_chain_anchor` (read-only, through `coredb.GetChainAnchor`): the first row after a prune continues from the hash of the last deleted row.
- The log row of a call cancelled midway records the profile (name, id, model) of the last attempt that sent a request.

## Rules and hooks (`/ai/rules*`, `/ai/hooks*`) — the real signatures
- `RulesView()`, `AddRule/EditRule/DeleteRule(ctx, who, …)`, `HooksView()`, `AddHook/EditHook/DeleteHook(ctx, who, …)`, `SetBuiltinHook(ctx, who, id, enabled)`, `TestHook(ctx, HookTestInput)`; `Hooks()` (the hook runner currently in effect) and `Rules()`. Handlers: `AiGetAiRules … AiPostAiHooksTest` in `handlers.go` (10 operations, admin role from the route table).
- State lives in `Service.harness` (`atomic.Pointer`, immutable: rules, built-in switches, custom hooks and the `HookRunner` built from them). Every change runs under `Service.mu`: build the next generation (recompile every hook) → write one transaction together with the `core_audit` row → swap the pointer. `RunJob` takes **one** generation at the start of the call (the hooks before and after, and the prompt's rules). **Callers of `RunJob`/`guard`/`PromptInput.Rules`**: do not hold a `HookRunner` longer than one call, use `Service.Hooks()`.
- `SetConfig` also writes `ai_hook_state.block-pii` and swaps `harness` (in the same transaction as `ai_setting`); `Config().RedactPII` reads from `harness`. Renaming/changing the meaning of `block-pii` → `redact_pii` changes with it; adding a built-in hook → add a pre-loaded `ai_hook_state` row (the `ai` migration), `builtinInfo`, the GUI (`harness.ts`) and PRIVACY flow 3.
- Changing `PromptBuilder` (the company-rules heading) → test `TestContract_INV7_RulesReachThePromptAsRulesBelowTheBuiltInOnes`. Memory and skills are **not** in `harness`: memory is read from the table on every call (not cached), the skill switch is in `Service.skillsOff` (a pointer to the map of skills that are off, replaced after the transaction commits). The knowledge base is not in `harness` either, for the same reason.
- Emits no events. **Data flow 3 (PRIVACY.md)**, no new flow: (a) the `Block personal data` hook can be turned off; when off, email, phone numbers and names next to an account are not masked and ID numbers do not block the call; (b) the company's rules written by the admin (at most 30, each at most 300 characters) are sent to the provider in the system prompt on every call. PRIVACY.md flow 3, `privacy.flow.3.what` (core.json) and the text in AI Settings must agree.
- The `after_ai` hook runs on each string of a structured answer (`afterHooks`, `harness_after.go`), with its own deadline (`Config.HookTimeout`); whoever writes a new job with a schema: `JobSpec.Check` runs twice: on the original answer and then on the masked one, and **the last call is on the masked text**; the existing Checks (`parseExplain`, `parseBrief`) store the parse result in a closure and rely on that, so a new Check must do the same or have no side effects.

## Memory and skills (`/ai/memory*`, `/ai/skills*`) — the real signatures
- `MemoryView(ctx)`, `AddMemory/EditMemory/DeleteMemory(ctx, who, …)`, `SetSuggest(ctx, who, on)`, `AcceptSuggestion/RejectSuggestion(ctx, who, id)`, `SuggestMemory(ctx, text, evidence)` (callers inside the module: log digest, and "Ask your data"), `Skills()`, `SetSkill(ctx, who, id, enabled)`. Handlers: `handlers_memory.go` (9 operations, admin role from the route table). Tables `ai_memory`, `ai_memory_suggestion`, `ai_memory_rejected`, `ai_skill_state`; the export policy rows of the tables are in `modules/core/export_policy.go`; the audit labels `ai.memory.*`, `ai.skill` are in `core.json`.
