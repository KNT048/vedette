| D-396 | **Docker coexistence, two fixes to the DOCKER-USER rules of D-267 (`host/ops/dockerfwd.go`). (a) The bridges of the box itself:** the `-i vedette0 -o br-+ -j RETURN` of D-267 also matched a bridge of the box named `br-…` (an uplink `br-lan`, `br-ex`): those packets went on to Docker's chains, nothing accepted them, and the containers silently lost the internet. iptables matches an interface only exactly or by a `+` prefix, so Docker's own bridges (`br-` + the first 12 hex digits of the network ID) cannot be matched by a pattern. Decision: keep `br-+` (it covers a Docker network from the moment Docker makes it) and add above the RETURNs one `-s <subnet> -i vedette0 -o <name> -m comment --comment vedette-int -j ACCEPT` for every bridge in `/sys/class/net` named `br-` + 1–12 of `[A-Za-z0-9_.-]`, not of Docker's form (`^br-[0-9a-f]{12}$`), that holds a port which is not a container's veth: a network card (`<port>/device`), a bond (`<port>/bonding`) or a link on top of another (`<port>/lower_*`: a VLAN); Docker's bridges, custom-named ones too (`com.docker.network.bridge.name: br-app`), hold only veths and stay behind `br-+` (review r2 M1); no `+` or `!` ever reaches a rule; at most 32 (past that nothing is changed, one log line). Fail closed: a new uplink bridge has no internet for at most one look (30 s); a new Docker network is never open to Vedette's containers. The host still only checks (`-C`) and inserts (`-I`), never deletes: the ACCEPT of a bridge that is gone matches nothing and `install.sh --uninstall` removes it (its pattern already covers it). **(b) Customer containers to Vedette's unpublished ports: block.** Docker's own accept for traffic leaving its bridges let a customer's Docker container open any port of a Vedette container on `vedette-int` (not only the published 8443, 514, 6514). Decision: a last rule `! -i vedette0 -o vedette0 -m comment --comment vedette-int -j DROP`, below the conntrack `DNAT,ESTABLISHED,RELATED` ACCEPT, so published ports through the box's address and replies still pass; traffic inside `vedette0` (`br_netfilter`) is excluded by `! -i`. It mirrors Docker 28's own default for its networks (a port that is not published is not reachable from outside the network). It changes the outcome only for packets Docker (or a later FORWARD rule) would have accepted; an administrator who wants a direct route puts an ACCEPT above our block, as for every other rule of ours. Also: inserts are refused (state `unexpected`, logged once) when a rule of someone else stands inside our block, since positions are counted inside the block and a DROP above the ACCEPT of replies would cut the GUI (review M2). Order kept: ACCEPTs of the box's bridges, `docker0` RETURN, `br-+` RETURN, conntrack ACCEPT, outbound ACCEPT, DROP. Not covered: a Docker network with a custom bridge name that does not start with `br-` is not protected from Vedette's containers (deferred N2); a bridge of the box named `br-…` whose ports are only taps or veths (a VM bridge) is treated like Docker's (no ACCEPT); IPv6 (`vedette-int` has none); a box without Docker (no FORWARD drop; netavark's own isolation, deferred). Rejected: one RETURN per Docker bridge read from `/sys/class/net` (first draft: a Docker network made by compose is open to Vedette's containers until the next look, and every network churns a rule and a delete; review M1), reading Docker's internal chains (`DOCKER-ISOLATION-STAGE-*` are gone from Docker 28's documented chains), calling the Docker CLI or socket (root-equivalent access the host does not need), documenting instead of blocking (Docker itself blocks the same flow for its own containers since 28.0). | Sources: Docker, [Packet filtering and firewalls](https://docs.docker.com/engine/network/packet-filtering-firewalls/) and [Docker with iptables](https://docs.docker.com/engine/network/firewall-iptables/) (DOCKER-USER is the chain for the administrator; rules match interfaces; firewalld zone `docker` lists every Docker bridge by name); Docker, [Engine v28: hardening container networking by default](https://www.docker.com/blog/docker-engine-28-hardening-container-networking-by-default/) (unpublished ports dropped from outside the network); Docker, [Bridge network driver](https://docs.docker.com/engine/network/drivers/bridge/) (containers on different bridge networks only through published ports; `com.docker.network.bridge.name`); moby, [bridge driver](https://github.com/moby/moby/blob/master/daemon/libnetwork/drivers/bridge/bridge_linux.go) (`"br-" + id[:12]`). | 2026-11-13 |
