| D-459 | **A software update crosses a sensor protocol bump: core switches first, core takes protocol N and N-1 (S-CORE-2, v1 blocker from lab T5).** (1) **Order**: Apply = [helper,] pull every image, **core's switch first** (step `restart`, with the snapshot), then `container.start` of the sensor, scan worker and honeypot (step `start`), sent by the NEW core after it restarted; steps `[host,] download, restart, start`. The host judges a sensor or scan worker healthy only when core takes its heartbeat (`cmd/vedette-sensor/health.go`), so they are judged only once core runs the new release. Before each of those calls the follower reads the host's state: a core that does not run the target (a rollback that put the database back resumed the run from the copy made before core's switch) stops the run there and the rollback is rebuilt from the host's record. Rollback keeps its order, the reverse: the others first (back to a protocol the running core takes), core last. (2) **Skew**: `core/sensorlink` takes `X-Vedette-Proto` = `ProtoVersion` or `ProtoPrevious` (= ProtoVersion − 1, a test keeps it so); a sensor or worker newer than core, or two behind, stays 426. A bump keeps core able to serve the old peer: new request fields optional (proto 3 has no `capture_error` = none); a bump that changes a reply must first pass the request's protocol to the handler and answer the old shape. A release that bumps the protocol to N sets `min_upgrade_from` no lower than the first release with N-1. (3) **A failure after core's switch** no longer rolls anything back (D-342 (3) chose all-or-nothing because skew was untested; it is now supported): core and the services already switched stay on the new release, the failed one went back by itself (or did not move) and keeps working with core; the run is `failed` and says so ("Vedette itself runs X. It keeps working with the services still on Y, which move with the next update. To put the whole box back on Y, use Rollback."), with a history entry (`moved`); the 6-hour rule after core's switch also writes it and says that core runs X and points to Rollback. A failure up to core's switch has changed nothing else (no undo). (4) **Limit**: the plan is made by the release being left, so only updates FROM a release with D-459 use this order; a box on 0.0.1-test.16 still reverts on a protocol bump and is reinstalled with `install.sh` (no release is tagged stable yet). | Kubernetes version skew policy: the control plane is upgraded first and a kubelet must never be newer than kube-apiserver, it may be older (https://kubernetes.io/releases/version-skew-policy/); Elastic: Elasticsearch, Kibana and Fleet Server are upgraded before the Elastic Agents they serve, and an agent may not be newer than Fleet Server (https://www.elastic.co/guide/en/elastic-stack/current/upgrading-elastic-stack.html, https://www.elastic.co/guide/en/fleet/current/upgrade-elastic-agent.html). Neither rolls the control plane back when a node or agent upgrade fails: the older node keeps working inside the supported skew and is retried. Not chosen: the sensor falling back to the old protocol on 426 (a newer agent than its server is the case both products refuse, and it would hide a wrong order); rolling core back automatically after a later service fails (core's rollback may put the database back, which needs the administrator's confirmation, D-342 (8)).
