| D-385 | **Without `vedette-host` (container-only, D-168) the sensor's fresh heartbeat is the authority for the box's own cards; with a host it never is (D-118 unchanged).** (1) `sensor-passive` refuses observations about the box (`boxAddresses`, INV-6) by `Host.HostCards`, the same source as `SetInterface`: with a host, its list. A configured host that gives no list (socket path set but absent, or a helper that has not answered since core started) holds the batch; before this change it fell back to the core container's own interfaces. (2) Only when core runs with `-host-socket=""` (`HostCards` ok=false) the box's cards are those of the passive sensor's last heartbeat **younger than 90 s**, the same rule as `online` (`onlineWithin`); without such a heartbeat the batch is held too, never filtered by the core container's cards (on the bridge it sees only its own link, so the real host cards were not excluded and the box could appear as a device of its own network). (3) A held batch is answered **503 `not_ready`** (new code of the closed sensorlink set, `Retry-After` 5 s), not `store_busy`: the capture splits batches and blames lone items only on `store_busy` while a heartbeat succeeds, so a long `store_busy` here would have dropped observations one by one; `not_ready` is retried whole and never blamed on an item. (4) `SetInterface` without a host accepts only a heartbeat younger than 90 s; an older one is "not reported in the last 90 seconds" (`bad_interface`), so an offline sensor's stale list cannot be chosen from. (5) `netHost.Interfaces` in `cmd/vedette` no longer reads the operating system's interfaces (`osInterfaces` removed); it is `HostCards` for `Service.Run`, which production never starts (D-141). Accepted: a sensor older than this core treats `not_ready` like any 503 (it may split), but the sensor and core images ship in one release; a vedette-host restart that briefly removes its socket holds batches for those seconds (the sensor's queue keeps them, 5000 max). Accepted risk: a compromised sensor (mTLS, passive role) can list extra MACs/addresses as the box's and so hide those devices from passive discovery; it can already do that by not reporting them, and the list stays bounded and validated by `sensorlink` (≤ 32 cards). | Same pattern as D-263 and the container installs it cites: Home Assistant Container (https://www.home-assistant.io/installation/linux/) and the Wazuh Docker agent (https://documentation.wazuh.com/current/deployment-options/docker/wazuh-container.html) report only what the process on the host network sees, not what an isolated container guesses. The 90 s freshness reuses the protocol's own liveness window (`docs/specs/sensor-protocol.md` §6.3), as Prometheus marks a target down after failed scrapes rather than trusting its last sample (https://prometheus.io/docs/concepts/jobs_instances/). A retryable "not yet" kept apart from "this item is bad" follows OTLP, which retries 503 whole and only drops data the server marks as rejected (https://opentelemetry.io/docs/specs/otlp/#failures).
