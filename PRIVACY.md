# Privacy — what Vedette sends out, and how to turn it off

Vedette runs on your own machine. Your devices, logs, findings and AI keys **never leave it**. Below is the **complete** list of data that goes out to the Internet. The same list is shown in the app under Settings → Privacy.

| # | Flow | What is sent | Where to | Can you turn it off? |
|---|---|---|---|---|
| 1 | Feed pulls (D-36) | The box fetches each feed **directly from its source**, with plain HTTPS requests for public files. None of your data is sent; only your IP address appears in the source's logs. Sources: CISA KEV (`www.cisa.gov`; if that address answers 403, an error or nothing in time, CISA's own GitHub mirror of the same file, `raw.githubusercontent.com/cisagov/kev-data`, D-91), FIRST EPSS (`api.first.org`), the nuclei-templates CVE list, IPsum and hagezi TIF (public data files on `raw.githubusercontent.com`), ET Open (`rules.emergingthreats.net`), abuse.ch Feodo Tracker (`feodotracker.abuse.ch`), the Tor exit list (`check.torproject.org`), and any **custom feed you add** in Settings → Feeds. Vedette's own GitHub repository is used only for software updates (flow 6); some public sources above happen to host their files on GitHub | Each source above, directly | No (the product needs feeds); you can remove a custom feed, or switch to offline bundles |
| 2 | **Anonymous signal: not sent.** | The box sends nothing to the Vedette project. The project runs no server that could receive it (D-81), and this version has no code that sends it | Nowhere | Not sent. Settings → Privacy says the same |
| 3 | AI (only if you configure it) | The data you choose to send (findings, aggregated logs) to **your** provider with **your** key. When you press **Test** on a profile, the box sends three tiny fixed requests (a one-word prompt, then the same with a dummy tool and with a JSON format, to learn what the model supports) with that profile's key to its address; no data of yours is in them, and each test is written to the audit log (never the key). A profile marked as inside your network must use a private address or a name that resolves to one; this is checked at every connection | The provider(s) you choose, or a model inside your network | Yes — nothing is sent without a configured AI profile; you can restrict log and device data to internal profiles |
| 4 | Lookups that need your key (only if you configure them) | IP/domain/hash lookups to the services whose keys you enter | Those services | Yes |
| 5 | Notifications (only if you configure them) | Alert content, and the 6-digit sign-in code if a user turns on two-step email codes (D-35). Email goes through **your own SMTP server**; no third party is involved. **Slack** (D-38) only if you add an Incoming Webhook; if you also turn on approvals in chat, the box opens a Socket Mode connection **outward** to Slack and sends approval requests and the result of each button press (no inbound port). Telegram approvals use long polling to Telegram. **Zalo personal** (unofficial, like the n8n Zalo community node; Zalo may lock the account, so use a separate one) only if you save a Zalo session for it: the box signs in to **Zalo's servers** with that account's session and sends alerts and approval codes through it. The hosts it contacts are exactly `wpa.chat.zalo.me` (sign-in and server info) and the `*.chat.zalo.me` chat or group service that Zalo names in its sign-in answer (names that do not match are refused before anything is sent), and, for reply-code approvals, an outward WebSocket to a `*.chat.zalo.me` address Zalo names. What is sent there: the session cookies you saved, the user agent you saved, the session's device ID (inside the encrypted sign-in and message parameters), the recipient's Zalo ID and the alert text. Nothing is sent to any other host. **Email approvals** (if you turn them on) add a single-use link to the message, valid 30 minutes, which opens a confirmation page on this box | The Telegram / Slack / Zalo OA / Zalo personal / webhook you set, or your own SMTP server for email | Yes — remove the channel (people using email codes are warned first and need an administrator reset); turn off "Approve actions from this channel" to stop the Slack connection, Telegram polling and email links; remove the Zalo personal channel to delete its session |
| 6 | Update checks (D-36, D-53) | Your current Vedette version (in the request to GitHub). For the operating system (D-53) the box runs `apt` through the privileged helper `vedette-host`, and the request carries what any apt client sends: the release and architecture of this machine and the package names it asks about. To install an update, the same helper pulls the container images of the Vedette release by digest, and the request carries what any container client sends: the image name and digest and the architecture of this machine. `vedette-host` also builds the `scan` image on the box from the signed base image (D-113 (7), D-147), **at install on every box (whether or not active scanning is turned on) and again whenever the `scan` image is pulled or updated**: a build container, run with the network, installs **nmap** from the Debian package repository, and that request carries what any apt client sends (the release and architecture of the base image and the package name `nmap`). No Vedette data, no inventory, no findings | **GitHub releases** (signed software updates; confirmed recommendation packs ship inside them; a release file download is redirected to a GitHub-owned file host, `objects.githubusercontent.com` or `release-assets.githubusercontent.com`), **ghcr.io** (the signed container images of a release, pulled by digest) with the host it redirects to for the image layers, **pkg-containers.githubusercontent.com**, and the distribution's **package mirrors**: Ubuntu `archive.ubuntu.com` and `security.ubuntu.com`, Debian `deb.debian.org` and `security.debian.org`. You can point apt at **a local mirror** inside your network (edit the apt sources on the box; the mirror host list in Settings → Updates follows), so nothing leaves the network. The `scan` image build is the exception: it contacts Debian's `deb.debian.org` **from inside the build container**, also on an Ubuntu box, and the local mirror you gave apt on the box does not apply to it (the container has its own apt configuration) | Yes — switch update checks off to update by hand or by bundle only. Operating system updates that you start yourself, or that unattended-upgrades installs, still contact the mirrors unless apt points at a local mirror, and an update you install by hand from the registry (not from a bundle) still contacts `ghcr.io`. There is no setting that skips the `scan` image build at install or when the image is pulled. A box that cannot reach `deb.debian.org` installs without active scanning (core, sensor and honeypot still install) and tries the build again the next time the `scan` image is pulled; switching update checks off stops the later updates, not the build at install |
| 7 | SIEM forwarding (only if you configure it) | Vedette events (alerts, trap touches, aggregated logs) as syslog/CEF/JSON | The SIEM/webhook address you enter | Yes — off unless configured |
| 8 | CVE news (only when you click it) | The CVE ID in lookup requests | Vendor advisory pages, GitHub, public RSS feeds | Yes — nothing is sent unless you click |
| 9 | External exposure (only if you turn it on) | Your verified domain names, to find subdomains in public certificate-transparency logs; and HTTPS requests to public "what is my IP" services so the box can see its own public IP (D-81): each request is a plain HTTPS GET with the default Go User-Agent and nothing else of ours (no product name, no identifier, no data of yours); the service sees the box's public IP. An IP counts only when at least two of the three services, run by three different operators, agree. How often: the first check after install is a full check (5 rounds on new connections, 3 requests each: 15 requests, to find every IP behind a load balancer). After that, auto-detect (on by default) asks each service once every recheck interval (default 60 minutes, you can set 1 minute to 24 hours): 3 requests per check. A full check also runs at most once an hour by itself, when you select Detect now, when you turn auto-detect on, when you verify a public IP again, and just before a scan of a public IP (at most one such check every 5 minutes), to confirm the box still goes out through that IP | Certificate-transparency search services; `checkip.amazonaws.com` (AWS), `icanhazip.com` (Cloudflare), `https://ifconfig.me/ip` (Google Cloud). No Vedette-run server | Yes — turn off auto-detect (then it is sent only when you select Detect now), or turn off the External exposure module |
| 10 | Time sync (NTP, D-56) | A standard NTP request (UDP port 123) so the box clock stays right. It contains no Vedette data; the server sees the box's IP address | `pool.ntp.org` by default, or the NTP servers you enter in Settings → Box network (they can be inside your network) | Yes — enter an NTP server inside your network and nothing goes out |
| 11 | Single sign-on, OIDC (only if you configure it) | The box reads the discovery document and the signing keys from the issuer address you enter, and exchanges the one-time sign-in code for a token (authorization code with PKCE). It sends your client ID, client secret and the one-time code; the identity provider sees the box's IP address and its redirect address. No devices, findings, logs or AI data | The identity provider whose issuer address you enter (it can be inside your network) | Yes — turn off the SSO module (auth-oidc); password sign-in keeps working |
| 12 | Connections you add (D-93, only if you add one) | The requests and actions you set up are sent to the connection's own address, which you typed (a public address is allowed; you type it on purpose). The credentials you entered (token, or user name and password) go there too; an SSH key is used to sign in but not sent. Nothing else is added, nothing goes to any other host, and the device sees the box's IP address. Sent when you press Test on a connection that is on, when an approved action or its undo runs, and when the AI uses an allowed read tool. The AI can use only read tools on the allow-list; a write tool runs only through an action a person approves. The box checks the certificate of the address, or pins its certificate or SSH host key at the first test (you can forget the pin); it never follows a redirect | Only the address you typed for each connection | Yes — delete the connection, or turn it off, in Settings → Connections; nothing is sent to a connection that is off |

**Bug report (D-42) is not a flow.** The box sends nothing when you report a problem. The form builds a filtered diagnostic file (version, module states, recent errors; no devices, logs, findings, keys, emails or IPs) that you download, and "Open GitHub issue" opens GitHub in **your own browser** with your text filled in. You decide what to post. Nothing leaves the box unless you do it.

Cookies: only the three that signing in needs, all first-party and never sent anywhere but your box: the session cookie (`__Host-vedette_session`), its anti-forgery companion (`__Host-vedette_csrf`) and a trusted-device cookie (`__Secure-vedette_device`, D-77) that keeps someone else's failed guesses from locking you out. No tracking, no analytics, no third-party fonts or scripts.

Export or delete all your data: Settings → Data.
