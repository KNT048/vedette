# Reports Contract

> Tier: optional (off by default) · Story: S-REP-1, S-REP-2 · Last verified: 2026-11-21 (every sentence checked against the code)
> Source of the actual behaviour: `web/src/features/reports/{contract,types,mocks,weekly,pdpl}.ts`. Legal content checked 2026-11-06: Law 91/2025/QH15, Decree 356/2025/ND-CP.

## Invariants (always true)
- **INV-1** The weekly report's figures are **computed when it is opened** from `inventory`, findings and KEV; `sources[]` states the source and time of each group of figures. The figures are not generated by AI. A device a person has ignored, and a finding closed because its device was ignored, do not enter any report; the KEV count takes only the CISA list (VulnCheck KEV stays on the box, and is named in `sources` only when a finding of the report comes from it).
- **INV-13** Every figure of the weekly report has the same source and definition as on another page: `kev_new`/`kev_matched` = `KEV.NewlyExploited` (the first sentence of the home page: CVEs newly exploited in 7 days and the number of products in use among them, the same table as `GET /feeds/hot?window=7d`); `devices` = the figure on the Devices page (including the Vedette box: `Device.Box`; the PDPL report drops the box as before); product name = `feeds.DisplayOf` as on the Findings page (`KEVEntry.Display`). `resolved` is a finding closed by a person within 7 days, and each row has `by` (the person who closed it); a finding with risk accepted within 7 days is not in `resolved` but is counted separately as `accepted` + `accepted_until` (the earliest expiry date), over the **same set of findings** the other rows use (a manually added product with no device is counted too, and the `noDevice` flag only changes the wording; a finding whose `first_seen` is after the time of generation is counted in no row; `TestWeeklyAcceptedRiskIsNotResolved`, `TestWeeklyAcceptedCountsWhatTheRowsShow`). `top_risks` (≤ `TopRiskCount` = 3) groups open findings by product (`severity` is the most severe level of the group, `cve`/`finding_id` is the finding confirmed by a scan if there is one): one with confirmation first, then the highest severity, then more findings, then name; the fix/verify `actions` are one item per such risk (`product`, `count`), then `review_devices`, `plan_os`. The first page is the figures, the Top 3 risks, Done this week (≤ 5 rows), To do next week; the full lists are an appendix. A report stored in the old form (without `top_risks`) can still be read (INV-2). The AI prompt carries Top risks by device count, with no device names. A `patched` finding that Vedette closed because the device was updated (`resolution_reason = fixed_by_update`, `resolved_by = system`; findings INV-2) is `resolved` in the week like every `patched` (only `not_relevant` is subtracted when the "Include not relevant" switch is off) and its row records `by` = "Vedette" instead of the `system` account (`weekly.go`: `ResolvedBy == "system"`). `TestWeeklyPatchedByAnUpdateIsResolvedByVedette`.
- **INV-14** `top_risks` groups by device + product and then merges groups that need the same action (the same product, the same fix); `top_risks[].action` and `actions[].text` (fix/verify) are the same sentence, naming the device and, only when NVD says so (`findings.FixedInForAll` through the `Remedies` port): the nearest version, taken from every end bound above the device's version, lying outside the affected range of EVERY finding of the same installed software on the device (one group = one software row, not by CISA's product name) (not the highest version of each finding); "fixes N of M" counts only the findings that version really closes; when there is no such version, "NVD names no single release that fixes all N: check the vendor advisory" (N = 1: "NVD names no release that fixes the exploited vulnerability of …"); for a Windows release Microsoft no longer updates (`feature_update`), "Move … to a Windows release Microsoft still services (a feature update) …"; for a fix available only through Extended Security Updates (`esu`), "Install the Extended Security Update … or move it to a Windows release Microsoft still services"; these two kinds are a class of their own (`class()`: kind + version), count as a "fix" task, and are never merged with a device that needs another version or has no patch data (`TestTopRisksWindowsStepsAreNotMerged`); the distribution's reminder comes with it; ranked by product like `top_risks` (one product in one place, devices that need another step say "N more devices need another step"), and the fix is read only for the products the page names; when there is none, a real fallback (vendor advisory / check the version). Mail: the subject "N things to do this week", `What` opens with the incident sentence, `Action` is the first task, `Items` are the remaining tasks (INV-12). A report stored in the old form (without `action`/`text`/`happened`) can still be read.
- **INV-15** A finding row of the weekly and PDPL reports (`FindingRow`) has `agent` (true when the version compared is the version the device's own agent reported, `findings` `evidence.agent`, through `Finding.Agent` of the `Findings` port): the status shows "Detected by the agent" in place of "Suspected", like the Findings page. A report stored earlier without this field can still be read (INV-2). `TestWeeklyOpenRowSaysTheAgentDetectedIt`.
- **INV-16** Two switches on the Reports page, shared by the weekly and PDPL reports, remembered per browser (`localStorage` `vedette.reports.include`, wrapped in try/catch): "Include devices not in the Devices list" (on by default) and "Include not relevant" (off by default; only in the weekly report, because the PDPL `risks` are only open findings). They apply to both the totals and the lists, on the page, on the print page (`/reports/print/*`, which has the same switches) and on a sent report that is reopened; each printed document has one line saying which choice was used (`FiltersUsed`). The server supplies the data, the browser filters: `FindingRow.device_approved` (false = the device is not yet approved, "To review"; a device inventory does not know counts as approved); `Counts.not_relevant` / `not_relevant_new` / `not_relevant_resolved` ("not relevant" findings within the figures, to be subtracted); the `not_relevant*` figures are omitted when zero (`omitempty`) so a report read back from history still lacks them (`TestHistoryEntryKeepsTheNotRelevantCountsAsSent`); `WeeklyReport.approved_only` = `counts`, `top_risks`, `actions` recomputed over approved devices only and their findings (no `review_devices`; `kev_matched` drops KEV products that are new only on unapproved devices, `kev_new` stays the same); `PdplReport.approved_only` = `inventory`, `measures`, `risks` in the same way, but the `unapproved` measure keeps the full version's value (dropping devices from the view does not mean they are approved). A report stored earlier lacks these fields: devices are always counted, and "not relevant" is subtracted per row as before. Email and the AI commentary use the full figures. `TestWeeklyApprovedOnlyView`, `TestWeeklyCountsNotRelevant`, `TestPdplApprovedOnlyView`, `web/src/features/reports/includeToggles.test.tsx`.
- **INV-17** Periodic reports (contract `contract.ts`: `ReportDefinition`, `ReportDocument`, `SentReport`; the server does not have them yet, and the endpoints below return 501 `not_implemented` through `server.Fallback` until it does): **one** definition (one template, a switch per section `options.sections`, a period `last_7_days | last_30_days | calendar_month` = the most recent whole month, a grouping `device | cve`, `include_not_added` on by default, `include_not_relevant` off by default, `charts`, ≤ 20 recipients). The send schedule is **not** part of the definition: it is a shared schedule keyed by the owner `schedule_key = reports.def:<id>` (`GET/PUT /schedules/{owner_key}`). The document has the sections Summary, Handled (who and how, from stored fields: `status`, `via`, `by`, `from_version → to_version`), Still open, New, External exposure, Detections, Coverage; a switched-off section is absent; statuses use exactly the findings' shared code set (`under_attack`, `exploited`, `public_exploit`, `critical_edge`, `update_recommended`, `patched`, `mitigated`, `accepted`, `not_relevant`, `false_positive`). A sent report stores the whole document (`SentReport.document`) and reopens exactly as sent. Check: `web/src/features/reports/conformance.test.ts`.
- **INV-2** A send-history entry (`rep_history`) keeps **the figures of that week as they were** (`HistoryEntry.report`); reopening/reprinting does not recompute.
- **INV-3** Schedule: `day` ∈ 1..7 (1=Monday), `hour` 0..23, `recipients` ≤ 20 emails, each address ≤ 120 characters and valid (checked at the edge, SYS-2); `next_run` is computed from the schedule, `null` when off. `day`/`hour` are read in the organisation's time zone (`Config.Zone`, cmd/vedette `orgZone`; the `zone` column of `rep_schedule` records the zone used): when the time zone changes, the job resets the mark from that moment instead of sending a second time in the week. This weekly schedule is the module's own (table `rep_schedule`, job `weekly-send`) and does not go through `core/schedule`. Send status ∈ {sent, failed}, `trigger` ∈ {manual, scheduled}, and the error is recorded explicitly (`error`).
- **INV-4** Email is sent only through the `notify` email channel (the customer's SMTP, PRIVACY flow 5); the module has no SMTP of its own.
- **INV-5** The AI commentary (`AiSummary`) is produced only by the `ai` module (`weekly-report`, `pdpl-assessment`), always shown in an "AI generated" block, and **does not change the figures**; it obeys the internal-data rules because the report contains device data. Without AI → the report is still complete, `ai_available=false`.
- **INV-6** PDPL report: the obligation regime (`Obligation.regime`: required/optional/exempt) for `dpia`, `dpo` is **computed deterministically** from the organisation's size (`size`, per Article 38 of Law 91/2025/QH15 and Article 41 of Decree 356/2025/ND-CP), not decided by AI; the other obligations are always required. The information-system level (`level` 1..5 or empty) is a separate regime, not part of the Personal Data Protection Law.
- **INV-7** Every PDPL report carries the disclaimer "supports assessment, is not legal advice" and states the legal sources; this sentence cannot be removed (`LEGAL.md`).
- **INV-8** `PdplOrg` is checked field by field when saved (`PUT /reports/pdpl/org`); `measures` (firewall, patching, eol, unapproved, remote, logging, honeypot, scan, backup) carry `status ∈ {ok, attention, unknown}` — missing data because a module is off is `unknown`, **never `ok`**; `coverage[]` states which modules are on.
- **INV-9** The weekly report has `happened` (incidents of the 7 days: trap touches, failed logins, a login accepted after failures, bad connections, other anomalies; `summary` + at most 3 rows) read through the `Incidents` port from `notify` (a login accepted before the old threshold also carries the title "was ACCEPTED", `modules/logs/authfail.go`) (it does not read the `notify_*` tables); `notify` off → `happened` is null and `sources` has no `incidents`. New-device incidents are not counted (the Devices page already says so). `sources[].at` of `kev` is the most recent successful CISA KEV pull (feeds off: the time the report was built, with no KEV figures).
- **INV-11** Bounded size: each list of the weekly report ≤ 100 rows per view (INV-16; the list that is sent keeps the first 100 rows of each view — all, approved devices only, without "not relevant", both — so ≤ 400 rows, `capViews`; the browser cuts back to 100 after filtering; PDPL risks ≤ 100), PDPL critical systems ≤ 50, send history 52 entries; counts are always of the whole. Strings from the network (device names, products) are sanitised (control/bidi characters, one line, length limit) before they enter the report.
- **INV-12** The server does not build HTML/PDF: the mail is a plain-text summary through `notify.SendReport` with a link to `/reports`. The PDPL AI prompt contains no name, tax code, address or contact person.
- **INV-10** Every mutation (schedule, organisation information, send) writes `core_audit` (SYS-3). PDF is not generated on the server: the print pages `/reports/print/weekly[/:id]`, `/reports/print/pdpl` are SPA routes.

## Preconditions (before calling)
- **PRE-1** `PUT /reports/schedule`: admin role. `POST /reports/weekly/send`: operator role, with ≥ 1 recipient (400 `no_recipients`) and the `notify` email channel on (409 `email_not_ready`); if missing → a clear error, nothing is sent, no history is written.
- **PRE-2** `POST /reports/*/ai-summary`: the `ai` module is on and the corresponding task has an allowed profile (409 `ai_unavailable`).
- **PRE-3** `POST /reports/pdpl/generate`: valid organisation information has been saved (409 `org_required`). `POST /reports/pdpl/ai-summary` needs a generated report (409 `report_required`); if the report is regenerated while the AI is writing, 409 `report_changed` and the commentary is not saved.

## Postconditions (after completion)
- **POST-1** After sending: one `rep_history` entry (`sent`/`failed`), and the email goes to exactly the recipient list at the time of sending.
- **POST-2** Schedule on: at `next_run` it is generated and sent automatically, recording `trigger=scheduled`; each hour slot is handled at most once (marked before sending); a miss caused by the box/module being off → exactly one catch-up send if it is ≤ 24 hours late, beyond that the slot is dropped; saving the schedule resets the mark, and a slot already past is not caught up.
- **POST-3** PDPL `generate`: produces a `PdplReport` from the device store, findings and module state; it has `generated_at`; the entries "key_systems", "by_kind", "sources" match the store at generation time.
- **POST-4** The AI commentary is stored in `rep_weekly_ai`/`rep_pdpl`, and one `ai_activity` entry is written through the `ai` module.

## Forbidden (never)
- **FORBID-1** AI changing figures or legal conclusions; AI commentary without the "AI generated" label.
- **FORBID-2** Sending a report to an address that is not in the saved `recipients`.
- **FORBID-3** Stating "compliant/meets the standard" while `measures` still has `unknown` or `attention`.
- **FORBID-4** Reading another module's tables directly (use the interface, IMPACT).
- **FORBID-5** An external PDF library/service or resources from a CDN in the print page (legal.md).

## Tables owned
`rep_schedule`, `rep_history`, `rep_weekly_ai`, `rep_pdpl`.

## Events
- **Emits**: no bus events; every change and every send writes `core_audit` (`report.schedule`, `report.send`, `report.pdpl_org`, `report.pdpl_generate`, `report.ai_summary`). `notify` has not registered `reports.report.ready` (nobody needs it yet).
- **Receives**: the job `weekly-send` (once a minute) from `core/jobs`. It receives no events from other modules.

## When the module is off (SYS-5)
No `/reports/*` routes, no scheduled-send job. The Reports page shows "module is off". `rep_*` (schedule, history, organisation information, generated reports) are kept; when it is turned back on the schedule resumes, with no bulk catch-up send.

## Ports (cmd/vedette/reports.go)
`Inventory.Devices` (including the box, `Device.Box`; `Device.NoDevice` = a manually added product with no device, so the to-do sentence does not name it twice), `Findings.All` (+ `ResolvedBy`), `KEV.Entries` (+ pull time, `Display`), `KEV.NewlyExploited` (feeds), `Remedies.Fixes` (findings.FixedInForAll + inventory.MatchInput), `Incidents.Week` (notify.IncidentsSince: counts the whole week in SQL), `Mailer.Ready/Send` (notify), `AI.Available/Summarize` (ai: `ai.Service.RunJob`, the tasks `weekly-report`, `pdpl-assessment`), `Modules.Enabled`. Reports does not read other modules' tables.

## Dependencies
- **DEPENDS ON**: `core` (jobs, audit, the organisation time zone through `Config.Zone`), `inventory` (devices, inventory sources), `feeds` (KEV), `notify` (sending; soft but needed to send), `ai` (commentary, soft), `scan`/`logs`/`honeypot` (soft, extend the figures).
- **DEPENDED ON BY**: no module reads `reports` data; `ai` declares two tasks `weekly-report`, `pdpl-assessment` (`modules/ai/jobs.go`, `skills.go`), and `core/server/modules.go` routes `/reports/*` by this module. `core/logs export` does not use it.
