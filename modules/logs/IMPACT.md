# Logs — Change Impact Map

> The public surface (connection IOC matching: `iochits.go`, `logs.Feeds`, `logs_ioc_hits`, `IocHit`/`IocHits`, `ExportKnownBad`, `signature/conn.go`; the syslog listener: the `listen` package, the `syslog` job; signatures: the `signature` package, signature counters, digest, the `anomaly` job, `Counts`; #338: `TopAddresses`, `SourceNames`): `Service` (sources, events, retention, `Ingest`, `Purge`, `ExportDeviceLogs`), `LogsHandlers`, `Jobs`.

## Modifying: `logs.Service.Ingest(ctx, []Line) (IngestResult, error)` — callers: the listener; later `sensorlink`
- The only entrance for log lines. Each line also goes through `signature.Of` (by the source's `kind`, read once per batch together with `sourceKinds`) and is added to `logs_signature_daily` / `logs_signature_buckets` in the **same** transaction (one statement per key; separate quotas for bounded signatures and pattern-finder signatures): adding work to the hot path means measuring again with `-race` (the per-batch cache makes a flood of identical lines cost only one signature). It writes **one** transaction on `logs.db` per batch (≤ `MaxBatch`), never writing the main database (INV-12): switching to writing the main database brings back the risk of writer starvation (#159/#160). A line from an undeclared source is dropped and counted (FORBID-5). When the total bytes exceed `MaxEventBytes`, `Ingest` wakes the `purge` job (the `kick` channel buffered at 1, merged, not waiting): that run writes audit to the main database (core's writer) so it is shared with everything else; changing the cap or the 90% level changes the box's maximum disk usage. A `Line.At` outside [now − retention, now] becomes now: the listener cannot write a line older than retention. The cleanup only runs inside the `Run` of the `purge` job (a long-lived loop, `Housekeeping`: running even when the module is off, stopping on shutdown): changing `Jobs` or `kick` changes when the cleanup runs, and the job history only has one row for the whole time the process runs. The counter recomputation at the first cleanup after startup uses a read snapshot and does not hold the writer; when there is a flood at startup, the WAL grows during the scan. `Ingest` also looks up IOCs **before** the transaction (`matchIOC`, reading the feed table of `feeds` through `logs.Feeds`, at most 5 seconds per batch) and writes `logs_ioc_hits` **inside** the batch transaction, then emits two events **after** commit (synchronously, in the listener's goroutine: the bus calls notify's handler, so keep the number of hits per batch and events per hour small); raising `MaxIocHitsPerBatch`/`IocEventsPerHour` raises the work of the hot path. Changing `Line`/`IngestResult` = fixing the listener. Changing `sanitizeLine` changes the stored and exported content (`device_logs`).

The last sentence of `bad_address` ("Seen on the mirror port: …") reaches `notify` and SIEM.

## Modifying: `logs.Feeds` (port, `Config.Feeds`), adapter `logsFeeds` in `cmd/vedette/logsioc.go`
- **feeds**: the adapter uses `feeds.IOCKey` (the canonical key: an IP as the exact address, a lowercase domain), `Store.IOCListed` (the digest `ioc_matching`) and `Store.IOCLookup` (the feed's `Sightings`: name + confidence; an indicator that no feed lists any more is not a hit). Changing `IOCKey`, `IOCRecord` or a feed name → changes what `bad_connections` shows (`feeds`, `confidence`). The `feeds` module off → the adapter returns `logs.ErrFeedsOff` (PRE-3): no hits.
- **cmd/vedette** (`logs.go`: one line `cfg.Feeds = logsFeeds{&d}`; `logsioc.go`: the adapter and `logsIocEvidence`). The `feeds` service is looked up on every call because it is built after `logs`.
- **The `Lookup` signature** (or adding a method such as `Subdomains`) changing = changing the adapter and `fakeFeeds` in `iochits_test.go`.
- **Subdomains**: `Listing.SubFeeds`/`SubConfidence` = the feeds that list a name together with all subdomains (`IOCSighting.Subdomains` of feeds, currently only hagezi TIF). A domain destination that is not listed under its exact name makes `matchIOC` (`listing`) look up the nearest parent name first, at most `maxIocParents` = 10 shortest parent names, never a single label (TLD); a two-label public suffix (`co.uk`) is refused by `feeds.IOCKey` in the adapter. Each name once per batch (the batch cache), so an unknown destination costs up to 11 lookups within the batch's 5-second budget: raising `maxIocParents` or dropping the cache raises the work of the hot path. A hit keeps `dest` = the name the device asked for; the event `logs.bad_address.detected` says "(listed as <parent name>, with all of its subdomains)" and `target` = `ioc:<parent name>` (several subdomains of one listed name = one incident in notify). The parent name is stored in the column `listed_as` of `logs_ioc_hits` and is in `IocHit.listed_as` (digest, `IocHit`, `IocHits`, the event `logs.ioc_hit.detected`, the `known_bad` export); the Logs page says "listed as …" and Look up goes to it. `Subdomains(ctx)` (adapter: `feeds.Store.IOCSubdomainsOn`, false when feeds is off) false → `listing` does not look up parent names: turning off hagezi TIF turns the lookup off; an error → look up as before (a hit is never lost because of this question).

## Modifying: the table `logs_ioc_hits` (`logs.db`; columns `blocked`, `listed_as`), the events `logs.ioc_hit.detected` and `logs.bad_address.detected`
- **logs** (`iocpairs.go`: `IocPairs` reads the table grouped by pair for `GET /logs/bad-connections`, when adding a column review the statement `iocPairsSQL`; `iochits.go`: `storeIOC`, `iocHits`; `purge.go` `dropStale` deletes hits past `retention_days`; `anomaly.go`/digest do not read this table through a snapshot). Migrations are additive. The table has no `asset_id` (INV-7): adding a device column would store old data when a device is renamed. The caps `MaxIocRows`, `MaxIocHitsPerBatch`, `IocEventsPerHour`, `IocDedupe` are what the user sees (many or few hits) and are work of the hot path. `blocked` comes from the profile's `conn_blocked` (`signature.Conn.Blocked`): changing the values in `fortigate.json` changes the incident wording ("tried to reach … (blocked by …)" instead of "connected to") and the **Blocked** mark on the page; the 24-hour dedupe key (`recentHitSQL`) so that a blocked attempt does not hide a connection that went through afterwards; `blocked` defaults to 0 ("connected to"). The dedupe key is (device, listed name) (two `EXISTS`, `dest = ?2` through `logs_ioc_hits_pair` and `listed_as = ?2` through `logs_ioc_hits_listed`; a recent row only hides a hit whose confidence is ≤ its own): changing the key changes the number of rows on the page when a machine asks many random subdomains (DGA). `listed_as` has no CHECK; `''` means duplicate by `dest`.
- **notify** (`logs.bad_address.detected` → `logEvent`, kind `bad_address`; merge key (kind, `source` = "logs", `target` = `ioc:<destination>`)): renaming a field or `target` changes how incidents merge; a `title` > 200 characters causes the whole incident to be refused. **response** (`logs.ioc_hit.detected` → the `ioc_connection` trigger in `modules/response/events.go` `iocEvent`; response does not yet read the fields `blocked` and `listed_as`, the decoder ignores unknown fields; the subdomains after the first hit of a listed name do not become events, so a rule "block {{trigger.dest_domain}}" only blocks the first subdomain until response reads `listed_as` (a deferred item); and the `ioc_hit` evidence of an AI proposal through `logsIocEvidence` wired in `cmd/vedette/response.go`: renaming a field of the event or of `IocHit` changes the trigger and the evidence). **The SIEM of logs** (`siem_run.go`): `bad_conn` reads `id, src_ip, dest, dest_kind, seen_via, asset_id, blocked` (CEF `act=blocked` when true, no `act` when false; syslog/JSON `blocked="true|false"`, an event missing the key = `false`); the `alerts` layer drops the `bad_address` incident when `bad_conn` is on (renaming the incident kind in notify → the record being sent twice comes back). A hit over the hourly budget reaches notify through `logs.anomaly.detected` (`source` "logs", `target` `ioc:more bad connections <hour>`, kind `log_anomaly`), not through `bad_address`.
- **`modules/core/export_policy.go`**: no new row (the table is in `logs.db`, not in the main database, like `logs_events`).

## Modifying: signature profiles (`modules/logs/data/profiles/*.json`) and `modules/logs/signature`
- **Connection matching**: profiles additionally have `local_field`/`dest_ip_field`/`dest_host_fields` (kv) and `conn_pattern` (template), `Result.Conn`; changing a destination field changes what is looked up in feeds: a field is only read when it appears exactly once outside double quotes (`strictFields`); do **not** add a free-text reader and do not loosen the "exactly once" rule (against planting an address to frame a device). A profile's samples declare `local`/`dests`; `FuzzConn` and `TestConn*` keep the rule.
- **`conn_patterns` (anchored with `^`, a tight character class, no user text before the address field) and `apps` are where a new template profile is protected against planting; loosening a pattern to be unanchored, adding `.*` before `local`/`dest`, or dropping the `apps` of the `iptables` profile lets text in a URL/user name/User-Agent become a fake connection. `TestFirewallProfilesInjection` keeps that. Changing the `kinds` of a profile changes `reads` in `content/logs/kinds.json` and `web/src/features/logs/catalog.ts` (`TestCatalogReadsMatchProfiles`). `MaxPatternBytes` 768. Linux gets the `iptables` profile: lines not sent by the kernel behave as before.
- **The signature is the key of everything downstream**: the digest, `Counts` (response `log_threshold` stores the signature in the rule), `logs_anomaly_sent`. Changing the rules of a profile or of the pattern finder makes **every signature of that kind change once**: the digest sees every line as "new" (fine after 7-8 days), a `log_threshold` rule that has stored an old signature stops matching, and events are sent again. Changing the rules = write it in the CONTRACT and tell `response`.
- Adding a profile for a kind: a JSON file with `samples` (and `vocab`/an id table if the signature is to be treated as bounded: without a vocabulary the line goes into the pattern finder's quota) (the loader runs them), the `reads` of that kind in `content/logs/kinds.json` changes to `parsed` and `catalog.ts` matches (`TestCatalogReadsMatchProfiles`, `kinds.parity.test.ts`); no need to add a fuzz seed of its own (a profile's samples are already seeds of `FuzzSignature`).
- **The vocabulary is data**: adding a FortiGate log id to `data/profiles/fortigate.json` changes the signature of that id from the pattern finder's text to `logid=… action=…` once (a `log_threshold` rule that has stored the old signature stops matching).
- The `signature` package must not import `database/sql` or `core/store` (it will move to the sensor together with `listen`). It imports `core/localnet` (only `net/netip` + `slices`) for `LocalOK`: changing the internal-network rule there changes which devices have connections looked up for IOCs, and also the `src_ip` check of response `iocEvent` (the same function).

## Modifying: `Counts(ctx, source, signature, window) (int, error)` — 1 caller: response `PollLogs`
- **response** (`PollLogs`, `log_threshold`; wiring `responseLogCounts` in cmd/vedette): the read gate into the per-line signature counters. Window [5 minutes, 24 hours], rounded out to 5-minute buckets (covering the whole window and at most 5 minutes before it: a threshold "≥ N in 5 minutes" can see up to 10 minutes of lines). Changing the bucket width (`bucketSeconds`, shared with `logs_source_buckets`) or the retention (24 hours and one bucket) changes every answer. With the module off there are no new lines so `Counts` only returns old numbers.

## Modifying: `TopAddresses(ctx, source, signature, window, n) ([]AddressCount, error)` — 1 caller: response `PollLogs`
- **response**: the gate for the address-based blocking templates `tpl-vpn-ban` and `tpl-ssh-acl`: `log_threshold` fills the event's `source_ip` from here. Wired through `cmd/vedette` (`responseLogCounts`). The count is a lower bound when the bucket quota is full (50 addresses per signature, 500 rows per source): a threshold is still correct in the safe direction (never blocking because of a line whose address was not sent), but a slow attacker in the middle of a flood of fake addresses may be missing. Changing the quota or the bucket width changes the answer and the disk cap (28.6 MiB per source). The addresses of the box, the gateway, and the decoys (`Config.NeverCount`, wiring `logsNeverCount`) are never in the list: dropping that source reopens the possibility that a fake line makes response target the box (response still checks never-touch).
- **Changing the `remote_fields`/`remote_patterns` rules of a profile or the shared reader** (`signature/remote.go`) changes which address is counted for every line of that kind, not the signature. The rule "exactly one address position, outside text the client controls; with a second position, even a `-` value, there is no address" is what keeps text written by an attacker from framing an innocent address (the output leads to automatic blocking): loosening it reopens the fail2ban bug CVE-2007-4321; a new pattern must anchor to the right label and have a hostile line in `TestShippedProfilesRemote`.
- **The address of the sending device (`sender_ip`)** is excluded in `tally`, so changing a source's `sender_ip` changes what is counted at once.
- **`SourceNames`** (a narrow read of `logs_sources`): `response` every minute; changing a field changes response's adapter.

## Modifying: the `anomaly` job and the event `logs.anomaly.detected`
- **notify** (`logEvent`): reads `source`, `target`, `title` (≤ 200 characters), `what`, `action`, `severity`, `devices[{id,name}]`; `source` + `target` is the incident merge key. Changing a field name or the meaning of `target` changes how notify merges. At most 20 events per hour per source: raising the cap raises the customer's notification volume.
- Two rooms of 20 events per hour per source (bounded; pattern finder), one summary per hour when the pattern finder has more groups than the room (only covering items not yet covered: the `covered` row), and one backlog summary per hour when bounded signatures wait for more than the room; the summary's `target` has the UTC hour so notify opens a new incident, the hourly limit is a 60-minute sliding window; the `target` of a bounded event is `sig:<signature>` (a separate namespace, never equal to the destination of a pattern-finder incident). Changing how `target` is set or dropping the hour from it makes notify accumulate quietly (notify's merge key is kind + source + target, `modules/notify/incidents.go` `dedupeKey`).
- Not `Housekeeping`: making it housekeeping means sending events when the module is off (SYS-5); `TestContract_SYS5_NoEventsWhileTheModuleIsOff` blocks that.
- **Editing a source** (`UpdateSource`): changing `kind` or `sender_ip` sets `logs_sources.signatures_since` and restarts the source's 24 hours; a new way to edit a source (bulk import) must do the same.
- **cmd/vedette** (`logs.go`): `Config.Events` is `d.Bus`; when missing the job does nothing.

## Modifying: `modules/logs/listen` — a package with no database, will run in `vedette-sensor` at L6
- **logs** (`listener.go`): `listen.Server`, `Config`, `Limits`, `Source`, `Line`, `Status`, `Stats`. The package **must not import `database/sql` or `core/store`** (it must move to the sensor with no code change, like `sensor-passive/capture`); all storage goes through `Sink` → `Service.Ingest`. Changing `Line` changes `Service.sink`. A batch of at most 500 lines matches `MaxBatch` of `Ingest`: raising one side without the other causes `ErrBatchTooLarge` and a lost batch.
- **Limits** (`Limits`): changing them changes the box's memory and flood tolerance: 1,000 connections × a 4 KiB buffer, a queue of 4,096 lines × at most 8 KiB. A line is cut at 8 KiB and then `Ingest` cuts at 2 KiB: lowering `MaxLine` below 2 KiB loses text that could have been stored.
- **The `syslog` job** (`Jobs`): not `Housekeeping`. Changing it to housekeeping opens the port when the module is off (SYS-5); `TestNoSocketWhileTheModuleIsOff` blocks that. Adding/editing/deleting a source calls `sourcesChanged`: a new way to edit a source (bulk import) must call it, otherwise the listener only learns of the new source (its lines are dropped like an unknown sender) after another wake-up or when the job restarts (the job does not reread the sources by itself; it only retries failed sockets and failed source reads every 30 seconds).
- **cmd/vedette**: the flag `-syslog-port` and `deps.SyslogPort` (the Quadlet of `core`: port 514 needs bind permission or a published port; without it use 5514 and publish `5514/udp`, `5514/tcp`). `logsJobs` returns four jobs (`purge`, `syslog`, `anomaly`, `siem`).
- **TLS**: `listen.Config.TLS` (from `logs.SyslogConfig.TLS`, `deps.SyslogTLS` in `cmd/vedette`); the TLS port is derived from the plain port (514 -> 6514, p -> p+1: core runs 5514 so 5515; changing `-syslog-port` changes the TLS port and the `PublishPort=6514:5515/tcp` of the `core` unit must follow). `Server.Addrs()` is unchanged, the TLS socket goes through `TLSAddr()`. `Status`/`Stats` additionally have `TLS`, `TLSPort`, `TLSErr`, `HandshakeFailed`; `normalize` takes `tlsOK`. Removing `tls_unavailable` for a box that has a TLS configuration changes every place that assumes "real refuses tls" (the e2e of a plain HTTP box still refuses).
- **Closing TLS connections**: `closeNow` (closing the raw socket), not `tls.Conn.Close`, in `applyLocked`/`closeLocked`/the shutdown watcher: a TLS sender that does not read makes `Close` hang under `s.mu`; `TestAStuckTLS*` blocks that. The idle/frame limits are set with `SetDeadline` (both directions).
- **The box**: one port for UDP and TCP, every IPv4 address. The box's firewall/NAT must let devices reach that port; the listener opens nothing besides the socket. The UDP/TCP sockets (and TLS when configured) are open the whole time the module is on, with or without sources: an install where port 514 is held by another process (the host's rsyslog on a non-container install) now sees the bind Warn and retries every 30 seconds as soon as the module is turned on, not only when the first source exists. Any test that assumes "no source means no socket" is wrong.
- **Accepted protocols**: `register` limits connections of a protocol other than the declared one at `MaxConnsIPOther` (8); the unknown-sender table is keyed by (IP, protocol) so `GET /logs/unknown-senders` can return the same IP twice and the page groups by IP (`LogsPage.tsx`); the sentence warning that UDP can be spoofed (`unknown.forged`) shows when there is a UDP sender. `listen.Accepts(declared, arrived)` is the only rule (lookup, `register`, cutting connections in `applyLocked`, `Service.UnknownSenders`, the filter of the mock `GET /logs/unknown-senders`); changing it changes the hint sentence of the Protocol field (`form.protoHint.*`) and the 409 `duplicate` message (Go + mock).
- **Unknown senders**: `Stats().UnknownSender` (the IP from the socket, the `Proto` of the last time) is the source of `Service.UnknownSenders` → `GET /logs/unknown-senders` → the suggestion on the Sources page. Changing `UnknownKept` (256) changes the number of senders remembered, not the number returned (`UnknownShown` = 10, `contract.ts` `max(10)`: returning more than 10 makes the decoder refuse). Dropping `Proto` means the hint "already declared with another protocol" no longer names the right protocol.
- **web/src/features/logs**: the Sources page tells the device to send to the source's port (default 514) while the box may listen on 5514: the GUI does not know the real port yet (a later item, needing a story criterion).
- `Config.SelfAddrs` (cmd/vedette `vedetteSelf`: the honeypot's decoys) is refused on every port at save and on the socket.
