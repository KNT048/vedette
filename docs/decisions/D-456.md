| D-456 | **Box without Docker: `vedette-int.network` gets no `isolate` option (neither `true` nor `strict`); nothing changes for new or installed boxes (closes the D-396 deferred line "netavark isolates only with `isolate`").** What the option does, from netavark's own firewall code (`src/firewall/nft.rs`, v1.14; the iptables driver of 1.4 has the same chains): FORWARD jumps to `NETAVARK-ISOLATION-1`, which matches only packets that **leave** an isolated bridge (`iifname <bridge> oifname != <bridge>`); with `isolate=true` they are dropped only when they go out to another bridge that is also isolated, with `strict` when they go out to any netavark bridge; every drop matches a netavark bridge by name, never a card or a bridge of the box (`br-lan`). (1) `isolate=true` closes nothing: a customer's Podman network made without the option (every network by default up to netavark 1.x, the `podman` default network included) is not isolated, so its packets to `vedette-int` never enter the isolation chains and the replies go back to a non-isolated bridge. (2) `strict` would block TCP from those networks in effect (the replies leaving `vedette0` hit the drop, which stands above netavark's `ct state established` accept), but not a one-way UDP packet; it is unknown to netavark 1.4 of Ubuntu 24.04 (`strict` came in 1.7; 26.04 ships 1.16, Debian 13 1.14), so the network file would differ per OS for a partial gain. (3) Netavark 2.0 makes `strict` the default for every bridge network ("to restore the previous behavior the network must set `isolate=false`"), so a supported OS that ships it isolates `vedette-int` with no change of ours. Vedette's own paths stay: on `vedette-int` stand only `core` (published 8443, 127.0.0.1:8444, 514, 6514) and the on-box scan build (`--network vedette-int`, needs the internet through the box's uplink, not another netavark bridge); `sensor` and `scan` use the host's network, the honeypot its own namespace `vedette-hp` (`Network=ns:`), the LAN comes in through a card and the box's uplink bridges are not netavark's, so no isolation chain matches them. **One path does break:** a customer's root Podman container on another netavark network can no longer reach core's published 8443, 514 or 6514 through the box's address. By 1.14's chains (if 2.0 keeps them), the FORWARD jump to `NETAVARK-ISOLATION-1` stands above every network's `ct state related,established accept`, so the DNAT'd packet that leaves a strict customer bridge for `vedette0` is dropped, and with the customer's `isolate=false` the replies leaving a strict `vedette0` are dropped. Only Vedette can set `isolate=false` on `vedette-int`, and even that leaves a strict customer network cut off (strict drops toward non-isolated bridges too). Whether that path matters, and whether `vedette-int` then needs `isolate=false`, is decided when a supported OS ships netavark ≥ 2.0 (deferred line, install-check on that OS). (4) An installed network cannot take the option in place: Quadlet makes it with `podman network create --ignore`, which leaves an existing network's configuration as it is, and `podman network update` changes only DNS servers; it would need core stopped, `podman network rm vedette-int` and a new create (a short outage of core, same subnet). Since nothing is added, no migration is needed. What stays open on a box without Docker: a customer's other root Podman containers (and any root process of the box, as before) can open a port of `core` on `vedette-int` that is not published to them, notably 8444 that is published only on 127.0.0.1; closing that needs a forward rule like D-396 (b) in a firewall that is not Docker's, which D-267 rules out, so it waits for netavark 2 (deferred line: install-check on the first supported OS with netavark ≥ 2.0). Rejected: `isolate=true` (closes nothing, see (1)); `strict` where netavark ≥ 1.7 (two forms of the network file, a recreate for installed boxes, partial, and the default anyway from netavark 2.0); our own nftables rule on boxes without Docker (a firewall Vedette does not own, D-267). | Sources: Podman, [podman-network-create(1), latest](https://docs.podman.io/en/latest/markdown/podman-network-create.1.html) (`strict`: block traffic to and from all other bridge networks, the default when the option is omitted; `true`: only between networks that both have isolation; `false` restores the pre-Podman 6 / Netavark 2 behaviour; `--ignore` does not change an existing network) and [v4.9.3](https://docs.podman.io/en/v4.9.3/markdown/podman-network-create.1.html) / [v5.4.2](https://docs.podman.io/en/v5.4.2/markdown/podman-network-create.1.html) (isolation only between networks that have the option); netavark, [firewall/nft.rs v1.14.0](https://github.com/containers/netavark/blob/v1.14.0/src/firewall/nft.rs) (ISOLATION-1/2/3 chains, the jump above the established accept); netavark [release notes](https://docs.rs/crate/netavark/1.10.3/source/RELEASE_NOTES.md) (isolate in v1.1.0, `isolate=strict` in v1.7.0) and [v2.0.0](https://newreleases.io/project/github/containers/netavark/release/v2.0.0) (strict isolation by default); [Ubuntu netavark](https://launchpad.net/ubuntu/+source/netavark) (noble 1.4.0, resolute 1.16.1), [Debian trixie netavark](https://packages.debian.org/trixie/netavark) (1.14.0); Quadlet dry run on Podman 5.7 (`ExecStart=… podman network create --ignore --subnet … --interface-name=vedette0 vedette-int`). | 2026-11-12 |
