# Core Contract

> Tier: core · Story: S-CORE-1…8 (S-CORE-3 in part: OIDC belongs to `auth-oidc`; S-CORE-8 is a route of the `host` module, with the handler here) · Last verified: 2026-11-21 (every sentence checked against the code)

Source of behaviour: `web/src/features/core/contract.ts` + `web/src/mocks/core.ts`. The paths below have no `/api/v1` prefix.

## General conventions (used by every module)
- **Events** (fixed in `core/events`): the name `<module>.<object>.<verb>` (the regex in `events.ValidName`), published in-process through `core/events` **after the transaction commits** (Outbox → Flush); there is no SSE endpoint that pushes events to the GUI yet. Sensor→server uses event batches that are idempotent by `seq` (ARCHITECTURE §3).
- **Module off** = `Registry.Enabled(id)==false`: its routes are not registered, its jobs do not run, its gates are closed, and its tables are kept (SYS-5). Other modules call an optional module only after checking `Enabled`; off = treated as absent. **Exception:** a module that is off may run the retry loop of `modreg.OffGuard` (only to stop something still alive outside the process, each attempt at most `OffAttempt` = 60 s, and `Teardown` must respect `ctx`) until the host confirms; that is not a job, a route or a gate. `OffGuard` also stops the `sensor` and `scan` containers when their modules are off; the `modreg.NewOnGuard` loop runs only when the module is **on** (it starts their containers) so it needs no exception.
- **Errors**: JSON `{error:{code,message}}`; 401 not logged in, 403 missing role, 409 state conflict.

## Invariants
- **INV-1**: A module with `tier: core` cannot be turned off (`PATCH /modules/core` → 400 `core_module`). `TestContract_INV1_CoreAlwaysOn`
- **INV-2**: Every write handler (POST/PUT/PATCH/DELETE) of every module goes through `core/audit.Append` (SYS-3); the test harness builds its list from the route table (`routes.Operations`, every non-GET operation with the tag `core` for which the module has a handler): an operation that lacks a trial step, or whose write step leaves no `core_audit` row, fails. `core_audit` is append-only, with no API to edit/delete; exceptions: `POST /core/data/purge` and the retention job `core/audit-prune` (INV-37, not an API).
- **INV-3**: Turning on a module with a missing dependency → 409 `missing_dependencies` with `missing[]`, and nothing is turned on; only with `with_dependencies:true` is the dependency turned on along. Never turned on implicitly.
- **INV-4**: Turning a module off does not delete tables and does not turn off the modules that depend on it; the response returns `affected[]` = the enabled modules that depend on it. Dependent modules run in degraded mode (see each module's IMPACT).
- **INV-5**: Roles `viewer < operator < admin` come from the endpoint table (`role`); an endpoint that does not declare a role makes the server refuse to start. `role: public` covers only `/setup`, `/core/setup*`, `/core/auth-options`, `/auth/*`, `/install/*`, `/intake/*`, and the endpoints that carry a one-time token in the request itself: `GET|POST /response/approve/{token}`, `GET /response/blocklist/{token}.txt`. Checked by `core/api/routes_test.go` (code generation fails if an operation lacks a role).
- **INV-6**: Secrets (passwords, TOTP keys, channel/feed/OIDC secrets/tokens) go only through `core/secrets` (AES-256-GCM, a 0600 key file); the API returns only the last 4 characters; they do not enter logs, `/core/data/export`, `/core/data/backup`, `/core/logs/export` (SYS-4).
- **INV-7**: Users: you cannot disable yourself; you cannot remove the last active administrator **who uses a password** (an SSO administrator does not count, so a broken IdP does not lock the box owner out; 400 `last_admin`); an SSO account (`core_user.sso_issuer` set) cannot have its role changed by hand, cannot be reset a password, cannot change the password, cannot turn on 2-step, and does not go through any password confirmation step (409 `sso_user`); it can be disabled like any account; in the web an administrator does not reset their own 2FA (400); the only path outside the web is the console command `vedette reset-admin <email>` on the box: only for an active administrator who uses a password, in one transaction setting a temporary password, turning off 2-step, ending every session and writing the audit `user.console_reset` (actor `console`); the temporary password is returned exactly once (and must be changed at the first login, INV-27); resetting the password **and** resetting 2FA end every session of that person in the same transaction; a user changing their own password, turning 2FA on or off ends **every** session of theirs and in the same transaction creates a new session for exactly that browser (the same device and address, a new session token and CSRF; the handler resets both cookies): the user stays logged in while a copy of the old cookie (malware, an extension, a shared machine) does not (OWASP Session Management: change the session identifier after a privilege change / re-authentication); name and email have no control characters (Cc) or invisible format characters (Cf: bidi, zero-width, soft hyphen, tag), and the organisation name too; a duplicate email is always 409 `duplicate`. A login in progress whose password (`core_user.cred_version`, raised on a real password change/reset, not raised on rehashing), lock state or 2FA kind changes before it writes creates no session and does not overwrite the new password (a rehash writes only if `cred_version` is still the same). An administrator's action on another person (create, edit, reset password, reset 2FA, write general settings, export audit) checks the **actor** again in the write transaction: a locked account → 403 `disabled`, a revoked session → 401 `unauthenticated`, no longer an administrator → 403 `forbidden`; nothing is written. Changing one's own password, turning 2FA off and turning 2FA on check again in the write transaction: the account is not locked, the session in use is alive, and the password that was proved has not been changed (otherwise nothing is written and a newer password is not overwritten). The order of refusal is always: the caller (lock/session) first, then the old password (`cred_version`), then the state. Changing the password and turning 2-step on or off (starting TOTP, starting email codes) require re-entering the current password: wrong → 400 `wrong_password`, counted against the **per-account re-authentication counter** (key `account`, separate from the wrong-login counter per (IP, email): the same level of 10 times / 15 minutes and the same growth of waiting time, counted before checking, refunded when correct) and writes `auth.reauth_failed` (no password in `detail`), so that a stolen session guessing the old password also leaves a trace like a wrong login.
- **INV-8**: Once 2FA is on, a login with a missing/wrong code creates no session. The kind `email` when the email channel is unusable → 503 `twofa_email_unavailable`, never falling back to password only. Email code: 6 digits, 10 minutes, single use, 5 wrong tries cancel the code, resend after 60 s (429 `resend_too_soon`), at most 5 sends/hour (`too_many_codes`). TOTP: RFC 6238 SHA1, 6 digits, 30 s, ±1 step, a code of one step can be used once (`core_user_totp.last_step`). More than 10 wrong logins in 15 minutes per (IP, email) pair (IPv6 per address with cap 10 and per /64 with cap 100) → 429 `rate_limited` with a growing wait; attempts are counted before checking so parallel attempts cannot exceed the limit; the 2-step code is also limited separately per account (10 wrong / 15 minutes, not per IP), including the confirmation code when turning on TOTP (`POST /core/account/2fa/confirm`: counted before checking, refunded when correct) and a TOTP key waiting for confirmation is cancelled after 5 wrong codes (400 `too_many_tries`, like an email code). **Device cookie**: after a successful login the box sets `__Secure-vedette_device` (HMAC-signed, bound to the user + `cred_version`, with a **new nonce on every successful login**, never re-signing the nonce of the cookie that was sent, so a copy stolen earlier does not share a counter with the owner's current cookie); a login that carries a valid cookie of exactly that account is counted per cookie (10 times / 15 minutes) and exempt from the address and /64 counters, so someone in the same /64 cannot lock the account owner out; a missing/wrong/expired cookie, another person's cookie, or one after a password change is not exempt; a stolen cookie is still limited to 10 times / 15 minutes. An unknown email and a wrong password return the same `invalid_credentials`, with the same work at the writer (both write `auth.login_failed`). Password hashing/checking runs under a concurrency cap (`MaxHashing`); beyond the cap or the waiting time → 503 `server_busy` + `Retry-After`, not counted as a wrong guess. Email codes are stored as a keyed HMAC-SHA-256 (`core_email_code.hmac_key` in `core/secrets`), not a plain SHA-256. `preview_code` is never in a real response.
- **INV-9**: A session expires after **4 hours of inactivity or 7 days from login**. Only three cookies, all the box's own and needed for login: the session `__Host-vedette_session` (HttpOnly, Secure, SameSite=Strict, Path=/), CSRF `__Host-vedette_csrf` (Secure, SameSite=Strict, readable by the SPA) and the trusted device `__Secure-vedette_device` (HttpOnly, Secure, SameSite=Strict, `Path=/api/v1/auth/`, 90 days); no other cookie, no analytics, no external CDN resources (legal.md). A `Secure` cookie is always set; the prefixes `__Host-` (session, CSRF: Secure, Path=/, no Domain) and `__Secure-` (device) are enforced by the browser (GitHub uses `__Host-user_session_same_site`); browsers accept Secure cookies from `http://localhost` so `make dev` works normally; HSTS (`max-age=31536000`) only when the box owner supplies a certificate through `-tls-cert`, never with a self-made certificate (825 days, signed by the box's own CA; the CA is in `core_secret`, INV-33; if the CA cannot be used it is remade, and does not stop core from starting; the box remakes its own pair when less than 30 days remain, at startup and daily while running); plain HTTP only on loopback (a `-listen` other than loopback uses TLS). A `Host` header outside the allow-list (`-hosts`, by default loopback names and the names in the certificate) → 421 `misdirected_request` before routing (against DNS rebinding). `Retry-After` is on every 429 and on 503 `server_busy` that carries `retry_after`. `TestContract_INV9_HTTP*`.

## Preconditions / Postconditions
- **PRE-1** (`PATCH /modules/{id}` enable): the caller is `admin`. **POST-1**: `core_module.enabled=true`, `enabled_at` set, and `core_audit` has `module.enable` (in the same transaction); after the commit the module's routes answer (the module gate in `core/server`) and its jobs run (`core/jobs`), with no restart needed.
- **PRE-2** (disable): the module is not `tier:core`. **POST-2**: after the commit the module's routes return 404 like a route that does not exist, its jobs are cancelled, and the gate is closed — with no restart needed; `core_audit` has `module.disable` (with `affected`). `host` (`kind: component`) has no switch.
- **PRE-3** (`audit.Append`): has `user`, `action`, `target`. **POST-3**: the row is added in the same transaction as the change; an audit write error → the change is rolled back.
- **PRE-4** (`exec.Run`): the binary ∈ the allowlist, and argv is a validated array. **POST-4**: no shell; stdout/stderr are size-limited; a timeout is mandatory.
- **POST-4b** (`pdftext.PDFText`): a PDF is untrusted data and is **never parsed inside the core process**. `core/pdftext.PDFText(ctx, r) (string, error)` runs `vedette pdftext` (the same binary) through `exec.Run`, **only when the binary has registered itself as the child** (`pdftext.UseSelf()`, called only by `cmd/vedette`; not registered = `ErrNoChild`, no input is read, nothing runs), and the child prints `Marker` before the text and the parent requires it (missing = `ErrCrashed`): argv is exactly `["pdftext"]`, the file on stdin (≤ 10 MiB, `ErrTooLarge`), UTF-8 text on stdout (≤ 4 MiB, if cut then `ErrTruncated` with the text), a clean environment, the child process sets its own RLIMIT_AS (address space at start + 512 MiB) / RLIMIT_CPU 60 s / CORE 0 before reading the first byte (if it cannot set them it exits 13 without reading), a kill clock of 60 s, at most 2 child processes at once, and stderr is never logged or returned. Typed errors: `ErrNotPDF`, `ErrEncrypted`, `ErrTooLarge`, `ErrLimit` (timeout, killed by the kernel), `ErrCrashed` (a Go fatal error, stack overflow, out of memory under the limit). A malicious file kills only the child process, never core. Tests: `core/pdftext/pdftext_test.go` (`TestHostilePDFs` including a `/Size 40000000` sample that only RLIMIT_AS can block, `TestCPULimitStopsAnEndlessLoop` with a child built with RLIMIT_CPU 2 s, `TestNoRegisteredChildStartsNothing`, `TestOutputWithoutTheMarkerIsACrash`, `TestOutputIsCappedAtMaxText`, `TestNotAPDFAndEncryptedAndInputCap`); the assertions about limits run only on Linux.
- **PRE-5** (`updates/apply|rollback`): `admin`, the component exists; automatic mode starts an Apply with the user `system` without a route (INV-35 "Automatic mode"). **POST-5**: see INV-35 (one run over every service: Apply changes `core` first, Rollback returns `core` last; a failure before `core` changes means nothing else has changed, a failure after that means `core` is on the new version; a failed rollback returns the other services).
- **PRE-7** (`data/restore`): `admin`, `confirm_data_loss: true`, the current password (and two-step code when on), backup in the host's list, no install/update/restore running, a `vedette-host`. **POST-7**: a `pre_restore` backup of the data as it was exists on the box before anything is replaced (INV-36); the run ends `done`, `reverted` (data from before put back) or `failed`, and its end is audited once in the database core then runs on.
- **PRE-8** (`setup/restore`): setup not done, the setup code, a `vedette-host`, an upload younger than an hour, a 32-byte key that opens the backup's secrets or `confirm_without_key`. **POST-8**: the box's data is the backup's (or, when it did not start, the fresh box's again: INV-36), the upload is gone from `snapshots/`, and the host keeps it as a `manual` backup "Uploaded backup of <date>".
- **PRE-6** (`updates/os/install`): `admin`, no run in progress, `scope ∈ {security, all}`, there are pending packages, and there is a `vedette-host`. **POST-6**: a snapshot with the key was written (INV-18), an `OsRun` is created, apt lines appear gradually at `GET /core/updates/os/run`, at the end there is a `result`, the snapshot is deleted and `os.install_done` is written exactly once.

## Forbidden
- **FORBID-1**: A shell command string anywhere (SYS-1); `eval`.
- **FORBID-2**: `core` importing a package of another module (the dependency direction: module → core). Interaction the other way (sending a 2FA email code, checking the email channel) goes through an interface that `notify` implements.
- **FORBID-3**: Logging or returning a secret; returning `preview_code`.
- **FORBID-4**: Sending data outside beyond the 12 flows of PRIVACY.md (flow 12: only to exactly the address the admin typed for each connection); "Report a problem" (S-CORE-5) sends nothing: the diagnostic bundle is built and downloaded in the browser.
- **FORBID-5**: Another module writing to the `core_*` tables (go through the interface of `core/*`).
- **POST (reading the time zone)**: `(*APIHandlers).OrgTimeZone(ctx) (string, error)` returns the IANA name of `core_org.timezone` (no org row yet: `Asia/Ho_Chi_Minh`, the column's default); no other module reads `core_org`. Times that a reader sees (a page, a notification, an email, text for the AI, the summary line of the approval step) are written through `core/orgtime` (`orgtime.Source` reads the time zone each time it is used, so a change in Settings › General takes effect at once; if it cannot be read, UTC): `cmd/vedette` gives `OrgTimeZone` to notify, ai, reports (`Config.Zone`), sensor-active, scan, honeypot, exposure (`Config.Location`) and `OSConfig.Zone`; test `TestWiringScanWindowFollowsTheOrganizationTimeZone`. cmd test: `TestWiringQuietHoursFollowTheOrganizationTimeZone`.

`core_module`, `core_audit`, `core_chain_anchor`, `core_chain_head`, `core_user`, `core_session`, `core_user_totp`, `core_email_code`, `core_email_code_send`, `core_org`, `core_setting` (organisation, general, privacy, the update channel), `core_secret`, `core_job_run`, `core_connection`, `core_connection_tool`, `core_sensor_cert`, `core_run`, `core_run_step`, `core_run_item`, `core_run_log`, `core_schedule` (INV-41); plus the version-ledger tables `core_migration_<module>` and `core_schema_epoch` kept by `core/store`. `core_setting` keys: `os.settings` `{window, auto_security, applied_at}`, `os.run` `{run_id, scope, user, snapshot, audited}`; `core_privacy` `{update_check, telemetry}` (read/written by `GET`/`PATCH /core/privacy`; the OS code reads `update_check`); `core_updates` `{channel, follow_release?, mode, last_check, last_check_error?}` and `core_update_release` `{index, index_sig, carried, offer, running}` (INV-34); `core_update_run` (the software run and its plan) and `core_update_history` (≤ 100 entries) (INV-35).

## Events
- **Emits**: `core` emits no event through `core/events`. Enabling/disabling a module and deleting data go through `modreg.Registry.Publish(Change)` after the commit (`Change.Enabled`, `Change.Affected` = INV-4); other modules listen with `Registry.OnChange(fn)` or ask `Enabled`.
- **Receives**: none (schedules go through `core/jobs`).

## Behaviour when off
Not applicable (tier core). With `notify` alone off: email 2FA reports `reason:module_off`, and a user of the email kind cannot log in until an administrator resets it.
