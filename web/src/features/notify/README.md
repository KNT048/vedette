# features/notify

Stories: S-ALERT-3: the Incidents page `/incidents` (trap hits, connections to bad addresses, anomalous logs, unknown devices; repeats are merged, acknowledge/close, a Respond button → `/response?incident=<id>`, a delivery badge). S-ALERT-1: vulnerability messages show on the finding page through the slot `finding.panels`; the full send history + resend are on the page `/settings/channels/history` (the History link of Settings → Alert channels), with filters by channel, result and kind. `/alerts` redirects. S-NOT-1 (Settings, the `channels` section, tabs Channels and Settings (`?tab=settings`: quiet hours and grouping, `AlertSettings.tsx`): Telegram, Slack (Incoming Webhook; Socket Mode for approving actions in chat), Zalo OA, email SMTP, webhook; send a test; a minimum level per channel; a quiet schedule across midnight; merged messages).
Multi-site/MSP is not supported (a product decision): there are no messages that combine several customers.
Slot registered: `finding.panels`. Secrets are kept only on the mock side and never returned (only the last 4 characters). The number of KEV vulnerabilities that do not match a device shows in History.
Mock tables: `notify_channels`, `notify_rules`, `notify_incidents`, `notify_alerts` (vulnerability messages), `notify_approval_sends`. A clean install: no channel, no incident. Data flow leaving the box: PRIVACY.md flow 5.
The Zalo channel needs an OA ID, a recipient ID (user_id) and an access token (a Zalo token lives only about 25 hours).
S-NOT-2 / S-RESP-2: the Slack channel, personal Zalo (unofficial), and the switch "Approve actions from this channel" in each channel (Slack, Telegram, email, personal Zalo) with a list of approvers. Other modules read it with `peek('notify_channels')`: each channel has `approvals?: boolean` and `approvers?: {user_id, address}[]` (a clean install: none).
