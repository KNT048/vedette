# Mitigation Contract

> Tier: standard · Story: S-MIT-1 (the "What to do" part), S-MIT-3, S-MIT-4, S-AI-2 · Last verified: 2026-11-21 (every sentence checked against the code)

Mitigation is the **"What to do"** part of a finding: the confirmed mitigation pack, "Applied", the "Have I been hit?" signs, and the AI explanation. The finding (match, status, lifecycle) belongs to the `findings` module; `mitigation` depends on `findings`, and turning `mitigation` off loses no detection or alert. GUI: `web/src/features/findings/{Recommendation.tsx,WhatToDo.tsx,packs.ts}` and the `pack`/`ai`/`applied` parts of the finding page. Source of behaviour: `findings/{contract,mocks,packs}.ts`.

## Invariants
- **INV-1**: "Applied" is recorded only for a CVE that has a confirmed pack (400 `no_pack`), adds an `AppliedEntry {item, ts, user}` (once per item), and does **not** change the finding's `status`. (the test needs a DB)
- **INV-2**: A trustworthy pack: "Vedette confirmed" is shown only when the pack has `status: confirmed`, `confirmed_by`, `confirmed_at`, `drafted_with`, `sources[]` and a valid signature of the update; the loader rejects a `draft` or unsigned pack. A CVE without a pack → `pack:null` and the UI shows "no confirmed recommendation yet" + the original KEV information + an "Ask my AI" button only when AI is usable.
- **INV-3**: An AI result always carries the label "AI generated" and records `model`, `profile`, `tokens`, `citations`; it is never shown as a confirmed recommendation (S-AI-6). `POST /findings/{id}/ai` when no AI profile is assigned to that task or `ai` is off → 409 `ai_unavailable`; errors of the AI call itself (`ai_cut_off`, `ai_bad_format`, `blocked_by_hook`, `provider_error`, `unreachable`, `ai_timeout`, `budget_reached`) are returned exactly as the `ai` module reports them. `mitigation` has no write tool for the AI (SYS-8).
- **INV-4**: Every `CodeStep` that has a `side_effect` must show it before the user copies the command; `{IP}`/`{HOST}` are replaced with the device's values, escaped (device values are untrusted data).
- **INV-5**: `firewall[].detected=true` when `inventory` has a device of that vendor.
- **INV-6**: The "Have I been hit?" signs and the check commands are only text from the signed content; Vedette never runs them.
- **INV-7**: `recheck` when there is no pack (`genericRecheck`) for a finding with `evidence.agent`: "Nothing to look up: the agent on <device> reports the installed version of <software> …", then install the update (the agent reports the new version by itself, usually within two hours; Vedette closes the finding itself), adding the line "Rescan this device" when the CVE has a template and the device has an IP; never "About screen". `TestGenericRecheck_AgentVersionIsNotAskedFor`. **No agent reports the device any more** (`Provider.SetAgents` = `findings.AgentReports`, cmd/vedette `agentReports`, the same check as Updates to plan and the "No agent reports" line of the finding page): a finding with `evidence.agent`, `evidence.agent_row` or `known_version.source = agent` says "an agent last reported …" and never says the agent reports or will report the new version by itself; the next step is to reinstall the agent or "Mark as handled" → Patched. `TestGenericRecheck_NoAgentReportsTheDeviceNow`. A finding that only matches a product with `evidence.agent_row` (the agent reported a version, which cannot be compared against NVD): the first step is "Nothing to look up on <device>: its agent reports the installed version of <software> …, but Vedette cannot compare it …", not "About screen". `TestGenericRecheck_AgentRowProductMatchDoesNotAskForTheVersion`. A finding with `Row.Known` (the version of the matching software row, from **every** source: agent, SNMP, LLDP, scan, typed by a person; findings sets it on GET) and no `evidence.agent`: `knownRecheck` states the version and who supplied it ("Nothing to look up: Vedette read <software> <version> from <device> over SNMP. …"), step two says how the new version reaches Vedette ("Read with SNMP now", stated by itself through LLDP, "Rescan this device", "I updated <software>", the agent reports by itself), step three covers the scan template; never "About screen"/"Check which version". It does not promise to close by itself, only "closes the findings it can prove that version fixes. If this one stays open, press "Mark as handled" and choose Patched." (Junos after the last version NVD lists has no evidence, findings INV-4c); a finding with `evidence.agent_row` keeps the agent row's own sentence. With no version: "Check which version of <software> runs on <device> …" (without gluing the software name to the device name). `TestGenericRecheck_M23_KnownVersionFromEverySource`.
- **INV-8**: **general hardening** (`findings.Guide.Hardening`, `hardening.go`) is now only the **general "Have I been hit?" signs** per software family read from the KEV vendor/product, or for a finding on no exploited list from the name of its software line (`Row.Known`, which also names the software) (Windows, IIS, Linux, OpenSSH, web server, VMware ESXi, Synology DSM, Junos, FortiOS, RouterOS, Cisco IOS, network device, generic), containing no device values, when the confirmed pack is absent or has no signs of its own (a pack with signs → `hardening:null`). `Hardening = {software, family, checks}`. It says nothing specific about the CVE: the GUI writes "Not a Vedette recommendation for this CVE", never "Vedette confirmed" (FORBID-2), never "Applied" (INV-1); it is only text (FORBID-1). Firewall configuration comes only from a confirmed pack (INV-5) and from "Ask my AI"; without a pack the page's firewall step says no configuration is published, names the firewalls in the inventory and offers "Ask my AI" and adding a firewall in place (`web/src/features/findings/WhatToDo.tsx`). Tests: `TestContract_INV8_ChecksArePerFamilyAndClaimNothingAboutTheCVE`, `TestContract_INV8_TheConfirmedPackWinsWhereItHasItsOwn`, `TestContract_INV8_FindingWithoutPackShowsGeneralChecksOnly`, `TestSummaryForNamesTheFamilyOnce`, `TestHardeningCount_EveryWalkedFindingNamesItsSoftware`; GUI `web/src/features/findings/hardening.test.tsx`.
- **INV-9** (device merge; `devicelifecycle.go` `FindingFolded`, core/lifecycle): when a merge of two device rows folds two findings of one CVE into one, the "Applied" marks and AI results of the finding that goes become the kept finding's, inside the inventory's write and before the FK cascade would delete them: an item marked on both keeps the earlier mark, of two AI results of one skill the newer stays.

## Preconditions / Postconditions
- **PRE-1** (`Guidance(finding)`, the source of the "What to do" part of `GET /findings/{id}`): the finding exists (checked by `findings`). **POST-1**: returns `pack`, `compromise`, `recheck`, `ai`, `ai_available {explain, config}`, `applied`, `hardening` (INV-8: general signs only); the device is substituted for `{IP}`/`{HOST}` per INV-4. The general `recheck` (when there is no pack) refers to the device by `AssetView.Name` (never the id), assumes no admin page, and mentions "Rescan this device" only when the device has an IP.
- **PRE-2** (`POST /findings/{id}/applied`, `…/ai`): `operator`. **POST-2**: returns the new `FindingDetail`; a failure changes nothing.

## Forbidden
- **FORBID-1**: Running commands or writing configuration on a customer's device/firewall: only text (commands, configuration) is shown for the user to paste. Executing actions belongs to `response`. (Kept in `findings` too, because the two modules touch the device in two ways: detection and the guidance content.)
- **FORBID-2**: Showing AI content as "Vedette confirmed" or merging it into a confirmed pack.
- **FORBID-3**: Loading a pack that is not `confirmed` or not signed.
- **FORBID-4**: Suricata/CRS/CrowdSec/nftables "virtual patch" rule packs (S-MIT-2).
- **FORBID-5**: Changing a finding's `status` itself (the job of `findings`); only `findings` writes `fnd_*`.

## Dependencies
- **DEPENDS ON**: `core`, `findings` (finding, KevInfo), `inventory` (`firewall[].detected` through `Vendors.HasFirewallVendor`). Optional: `ai` (explanation).
- **DEPENDED ON BY**: the SPA finding page (the "What to do" panel), `ai` (asking the AI when there is no confirmed recommendation). `findings` does not depend on `mitigation`.

## Endpoints owned (minimum role)
| Route | Vai |
|---|---|
| `POST /findings/{id}/applied`, `/findings/{id}/ai` | operator |

`GET /findings/{id}` is served by `findings`; its "What to do" part is supplied by `mitigation` (PRE-1) by registering a "What to do" provider (an interface in `core`) through the `core` module registry; `findings` does not depend on `mitigation`. `POST /findings/{id}/applied|ai` is routed by `mitigation` under the `/findings` prefix and disappears when `mitigation` is off (the provider is absent, and the "What to do" fields are `null`/empty).

## Tables owned (`mit_`)
`mit_applied`, `mit_ai_output`, `mit_pack` (packs loaded from an update; the content is a signed file, not customer data), `mit_pack_state` (one row: the version of the update that was loaded, to prevent loading an older one again). `mit_applied` and `mit_ai_output` have an FK to `fnd_finding` (cascade).

## Events
- **Emits**: none.
- **Receives**: none (packs are reloaded by the `load-packs` job).

## Behaviour when off
No `POST /findings/{id}/applied|ai` route; the finding page loses the "What to do" panel (`pack`, `compromise`, `recheck`, `ai`, `applied`, `hardening` are empty). Findings, status and `notify` alerts keep working normally. Tables are kept.

## Stories and decisions
S-MIT-1 (the "What to do" part), S-MIT-3, S-MIT-4, S-AI-2. No traffic blocking; packs are confirmed through a PR; AI profile per task; no virtual patching; `findings` is a separate module.

## Implementation
- Pack file format: JSON (`status`, `cve`, `confirmed_by`, `confirmed_at`, `drafted_with`, `sources[]`, `patch`, `workaround`, `firewall[]`, `checklist`, optional `recheck{steps,code}` and `compromise`); unknown fields are rejected. A per-pack `recheck` replaces the CVE-2022-27593-specific branch in the mock; when missing, the generic text is used. `firewall[].detected` in the file is ignored.
- **Signed packs in the image:** confirmed packs live in the signed `core` image, directory `/opt/vedette/content/mitigation` (from `content/mitigation/packs/`): the `*.json` files, `VERSION`, `packs.minisig` (a minisign signature by the release key over the `Statement`), `packs.list` (a copy for people checking by hand). `Statement(version, docs)` = `vedette mitigation packs v1`, `version <v>`, then `<sha256> <name>` per file, sorted by name: it binds `Update.Version`, every byte of every `Docs[].Data`, and the set of documents; names must be plain `*.json` file names, with no duplicates (`ErrBadPackSet`). `ReadPackDir(dir)` reads with bounds (regular files only, no links, ≤ 1000 packs, 256 KiB per pack, 32 MiB total; an unknown file → the whole directory is rejected; no directory or only a README → `ErrNoPackDir`). The box's `Verifier` is built by `cmd/vedette` (`packVerifier`: `Statement` + `internal/release.VerifyContent` with the embedded key, the current or the backup key; the key revocation list is not read yet). The job `mitigation/load-packs` (at startup, when the module is enabled, and daily) calls `Install`; `ErrReplay` (same or older) is silent, a bad signature makes the run fail and changes nothing. Tests: `packsig_test.go`, `cmd/vedette/mitigation_packs_test.go`. The shipped packs (`content/mitigation/packs/`) are checked by `shippedpacks_test.go`: the box parser accepts each, every command line (firewall step, verify, undo, "Have I been hit?" command, recheck command) carries the link of its source and every link a pack names is in its `sources`, each pack fills the four steps, and the finding page of CVE-2026-123890 shows them (`TestShippedPacks_FindingPageShowsTheFourSteps`); `scripts/release` `TestSignPacksSignsTheShippedPacks` signs them through the release path with a test key.
- `Loader.Install(ctx, Update)`: an absent `Verifier` or a bad signature → the whole update is rejected and nothing changes (fail closed). Each file that fails INV-2 is excluded separately and listed; a pack missing from the new update is withdrawn. All of `mit_pack` is replaced in one transaction + `core_audit`.
- INV-4: `{IP}`/`{HOST}` accept only a parseable IP (no zone) and a host name matching `^[a-zA-Z0-9][a-zA-Z0-9_.-]{0,63}$`; any other value is replaced with `<IP>`/`<HOST>`, not escaped into the text, and substitution is done in a single pass.
- Update: no valid pack (no documents, or all excluded) → `ErrNoValidPack`, the packs already loaded are not deleted, and the result still returns the reason for each document; a version no newer than the installed one, or not comparable → `ErrReplay` (table `mit_pack_state`, one row). A rejected update does not use up its version. The `Verifier` must sign a statement that binds `Version` and the bytes of every `Docs[].Data`.
- AI result: bounded in length and number of items (the `ai` module has cut at the end of a sentence, never in the middle of one, `ai` POST-8), only `http(s)` links are kept; stored in `mit_ai_output` (label "AI generated"). A `mitigation-config` answer carries `configs[]` (`CodeStep`: `title`, `code` to paste as is, `note` "Based on: …", `side_effect`), at most 10 blocks, and a block over 40,000 characters is dropped whole; `shortened=true` when part was cut or dropped, and the page says so; `no_config_reason` when the AI says why no configuration helps, and the page shows it in place of a configuration block. Block title: "Configuration to review before pasting"; every AI block always carries a fixed reminder ("AI-generated: read every line before pasting…") and, when present, `CodeStep.check` (an address that is not the device's or the firewall's that was sent) shows "Check these addresses" above the block (a warning, not a filter). The software sent: the software row the finding matched (`Row.SoftwareID`, not counting a row marked as not installed), otherwise the row that the Evidence names exactly as "<name> <version>" or whose product equals the KEV product (`aiMatched`). `AIRequest.FixedIn` is the page's `fixed_in`: the AI receives the same facts the page has. The `aiMitigation` gate (`cmd/vedette/ai.go`, `aiFindingData`) sends each inventory/feed value on its own line, without control characters and with a length cap (`aiVal`; the host name follows the INV-4 regex, the IP must be parseable): the KEV entry + CVSS + attack vector (`aiAttack`); the device (name, IP, type, vendor, model, OS, the software of the finding with its version (only that row, not the whole list), open ports with product, ), and for `mitigation-config` also the ports of the vulnerable product (`aiVulnPorts`, computed in Go; a finding on the device's platform (both the KEV product name, with the vendor's word dropped, appearing in the OS as whole words, or a device of that very vendor where the product is an OS/firmware by word: Junos, IOS XE, FortiOS, Windows; not "Sophos Firewall", "Windows Server Update Service") lists every port named by service, with plain and TLS variants in one group, and never says "runs it"/"write no rule" from a banner; an application finding: a port whose product/page that the scan read has every word of the product runs it; only a port of the **same service** as that port can be ruled out ("another product", with a note about reverse proxies), a port of a different service is always "not known which product" (Exchange: SMTP names Exchange, OWA on 443 names IIS); a port of the same service (plain/TLS, "ssl/https", "https-alt" in the same web group as "http") whose product could not be read is "most likely the same server" when that service has no other product, the page title (if any) names the product, and the page/certificate names no other product of the device (with only a certificate it is still the same server); banners turn `()` into `[]` and drop `;:,` so they cannot forge the line structure; when no port matches it lists candidates by service together with the product, and a TLS port that was not identified ("ssl/unknown") is still a candidate), the Evidence sentence (installed version, affected range), the fix (`fixed_in`), basis/confidence; for `mitigation-config` also a network block: the firewalls/routers in inventory (the same kinds `Vendors` reads) that sit on the device's path (`aiPickWalls`, `cmd/vedette/aipath.go`: the device's network gateway, a firewall on the same subnet, or the box's gateway; at most 6; when the path is not known it is an assumption and the firewall's configuration block carries "(assumed)"; when the device is a network gateway there is no firewall; each entry has vendor, model, OS, IP), and for the device and for each firewall the platform's self-reverting way to apply (`aiSafeApply`, with the vendor documentation source in the code: Junos `commit confirmed`, IOS XR `commit confirmed`, IOS/IOS XE `configure terminal revert timer` when an archive exists, otherwise `reload in` as a separate step with a restart warning, FortiOS `cfg-save revert`, Arista `commit timer`, VyOS and EdgeOS `commit-confirm` then `confirm` + `save`, RouterOS Safe Mode; IOS and Arista save with `write memory` / `copy running-config startup-config`; recognised by OS/model, not only vendor (FortiWeb, FortiAP, Arista APs, SwOS have none); other platforms such as NX-OS, ASA, AOS-CX, Linux have no such line). Device data is the customer's network data as before (it carries internal data, goes through the privacy rules and the `before_ai` hook). `TestAIFindingData_M2_2_TheAIGetsThePageFacts`, `TestAIVulnPorts_TheVulnerableProductsPortsOnly`, `TestAISafeApply_OnlyPlatformsThatHaveOne`, `TestContract_INV3_M2_2_ConfigAnswerKeepsItsConfigBlocks`.

## Mismatches / open questions
- S-MIT-1 lists 8 firewall vendors; the pack format has only `fortigate`, `mikrotik`, `generic`. The shipped packs put the other families (Cisco IOS, Cisco ASA, pfSense, OPNsense, Sophos Firewall, and Windows Firewall or the Synology firewall where the device runs them) as titled blocks inside the `generic` guide: a vendor of its own would widen `FirewallVendor`/`ApplyItem` and the `mit_applied.item` CHECK, a table rebuild.
- When `mitigation` is off, `pack:null` cannot be told apart from "no confirmed recommendation yet" (see the open questions of `findings`).
