| D-210 | **Per-address counters and `TopAddresses` for `logs` (#338, WP-24 L3 follow-up, Emily).** (1) **Which address**: the remote peer the line is about (the client of a failed login, the source of a blocked connection), never the log sender (`sender_ip`). It is data, not Go per vendor (D-58): profiles gain `remote_fields` (kv, in order of preference: FortiGate `remip`, `srcip`) and `remote_patterns` (a named group `addr`: FortiGate `ui="https(addr)"`, Windows `Source Network Address` / `Client Address` / `IpAddress` as text, JSON and XML for 4625/4771/4768, MikroTik `src:port->`); every line a profile does not settle, and every line of a kind without a profile, goes through one generic reader without regular expressions (`key=value` with `rhost`, `rip`, `client`, `src`, `srcip`, `remote_*` ..., the word after `from` or `by`, postfix `host[addr]`, openvpn `name/addr:port` and `[AF_INET]addr:port`), **Guarantee (round 2): a line yields a remote address only when exactly one address site exists in it and it is not inside text the client controls (quoted spans, for the generic reader); any second site, even with an unparseable value like `-`, means no address** (the line still counts in `Counts`). Patterns count SITES, not parsed addresses (all matches of every pattern; one site with a value of 1 to 64 characters, so a `-` is a site; two sites give none, which closes the Windows 4625 case with `Source Network Address: -` and a workstation or account name that carries a label, and the JSON `Message` case); a key written twice with two values (`kvFind` reports it) is none; the generic reader skips every candidate inside a double-quoted span (nginx and apache request, referer and agent) and an odd number of unescaped quotes gives none (an injected quote could hide the real address), a bare word that is itself an address is a candidate too, so the client address that starts an access-log line is read and one injected anywhere else makes the line ambiguous (none); different candidates give none. Cost: a line with a bare second address that is not the peer (`from <peer> to <box>`) gives none (fail-safe); missing data is better than a framed address; a kind whose profile has rules for the address gets no generic reader at all, Windows patterns are anchored on the exact label, MikroTik's on firewall lines, FortiGate reads only `remip`, `ui` and `srcip` (never `msg`). Trade-off: an attacker can hide itself by adding an address of its own to the line (`from <box> from <real>` gives none, where before it gave the box address that was then dropped) but cannot frame an innocent one, which for automatic bans is the worse failure; fail2ban CVE-2007-4321 and DenyHosts CVE-2007-4323 were the first-match-from-the-left bug (and CrowdSec parses fixed fields, not text). Read with `net/netip` only (port, brackets, zone, `name(addr)` removed, IPv4-mapped unmapped); text that does not parse is no address and the line still counts in `Counts`. (2) **Never counted**: unspecified, loopback, multicast, link-local, IPv4 broadcast, the log sender itself (the source's `sender_ip`, per source in `tally`: a FortiGate local-out line names it as `srcip`), and the box, its LAN gateway and the honeypot decoys through `Config.NeverCount` (wired in cmd/vedette from the sources core/conn and response already use: vedette-host addresses, decoys via `DecoyIPsRead`, container addresses, the container's bridge gateway, the host's `default_route.gateway`, `-hosts` literals; single addresses, not subnets, because a container interface may sit on the LAN); asked at most every 30 s once a whole answer has been had, at every batch before that, an error keeps the last set; `TopAddresses` applies the set again when reading, so lines stored before the box was known are not returned. A container-only install (no vedette-host) does not know the LAN address, gateway or decoys: fail-open, stated, and response still checks never-touch. Private LAN addresses do count (an internal brute-forcer is real). (3) **Storage**: volume migration 0004 `logs_signature_addrs(bucket, source_id, sig_hash, addr BLOB 4|16, count)`, same 5-minute bucket, same transaction and same housekeeping purge as `logs_signature_buckets` (24 h + one bucket), no second writer pass; at most 50 addresses per signature and 500 rows per source and bucket. At a quota a new address replaces the row with the fewest lines only if it has more lines (ties: the old row stays), where the lines are exact: the batch plus the earlier lines of the same bucket and signature that got no row, kept in memory (4,096 entries, applied after the batch is stored, a restart loses one bucket at most; past the limit entries go from the largest (source, signature) group first, lowest count first and among equal counts the least recently updated, never by hash or address: a flood only starves its own signature. Measured on the first version: ~4,200 one-line addresses early in a bucket then one line per 10 s of a slow attacker on a signature with a lower hash than the flood's gave 0 of 30 lines kept (by hash order the eviction was arbitrary); now 20 of 20 for both hash orders, `TestPendingFloodStarvesOnlyItsSignature`); so an attacker that sends one line per batch (batches close every 2 s, so one line every 10 s is one per batch) behind 50 one-line addresses gets its row at its second line with its true count (first version: 90 lines, 0 returned). Rows are never inflated (space-saving was rejected: its `min+1` would make one-line spoofs look like attackers and trigger a ban); counts are lower bounds. Limits: an address pushed out starts again; a flood of more than 4,096 no-row addresses spread over many signatures of one source can still push out the entries of the signatures it floods (upgrade path: count-min sketch). fail2ban, CrowdSec and Wazuh keep exact per-IP state; this keeps it for the addresses that matter. Measured ceiling (`TestMeasureAddressCeilings`, every quota full, IPv6, index included): 199 bytes/row x 150,500 rows (301 buckets x 500) = about 28.6 MiB per source, on top of the 61 MiB of D-206; `TopAddresses` 24 h on a full source 47 ms. Rejected: 1,000 rows per bucket with text addresses (260 bytes/row, 71.8 MiB per source).
