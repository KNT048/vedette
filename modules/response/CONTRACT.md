# Response Contract

> Tier: optional, **high risk**, off by default · Story: S-RESP-1..4, S-AI-8 · Last verified: 2026-11-21 (every sentence checked against the code)
> Source of the actual behaviour: `web/src/features/response/{contract,state,engine,ai,logic,data,mocks}.ts` (the mock already has tests for the blocking gates).
> This module is the **only exception** to SYS-8: the only place where Vedette's code executes write tools against other devices, and only after a request has been approved.
> Model: a user's rule **WHEN** (a trigger with data fields) **IF** (conditions) **THEN** (a chain of actions with typed parameters), or an AI proposal. The server holds the command templates; the client never sends a command.

## Invariants (always true)

### Approval
- **INV-1** **By default every request needs a person to approve.** An action on another device (`connector_id ≠ null`) only runs when `status = approved` or under INV-5. A "box's own" action (`blocklist_add`, `msg_send`, `webhook_call`: `connector_id = null`) also needs approval under the default rule but is not blocked by the execution switch (INV-9).
- **INV-2** **High risk needs 2 different approvers**: `requires_approvals = 2` when there is an item with `risk=high`, or an item whose `targets` > `multi_target_max`, or the total `targets` > `multi_target_max` (`two_because` states the reason). The second person must approve **exactly the same set of actions** as the first (409 `selection_differs`); the same `user_id` approving twice is refused (409 `same_approver`); the second person's selection drops duplicate ids before comparing (`[a, a]` does not replace `[a, b]`). **An automatic approval (`via=auto`) never counts as one of the two people**. One request = one bundle; one approval covers the whole bundle. Right before computing `final`, every earlier approver is read again (`Users.Lookup`: still exists, not disabled, still operator/admin); a person who no longer qualifies is dropped from `approvals` (with a log row) and not counted. Test `TestWP31_L1_*`.
- **INV-3** The approver must be a Vedette user with the **operator role or higher**, with a channel identity that is in that channel's approver list (configured right in the channel). Approving from chat only counts when `external_id` is in that list. Buttons: Slack (Socket Mode), Telegram (bot, long polling). Personal Zalo (an unofficial API, with a clear warning): reply with a code. Email and Zalo OA: a link (INV-4). **Division of work**: `notify` sends, authenticates the platform and creates the token/code; `response` maps the identity and holds every gate. **Email link:** `DecideByLink` (`via=email`). **Chat:** `DecideFromChat` (`via=slack|telegram|zalo-personal`). Checked in this order (first a limit of 20 decisions/minute per `channel|ExternalID`, 429 `rate_limited`, writing one `refused` row per window): the channel is in `approval_channels` and ready (otherwise 403 `channel_not_allowed`) → `ExternalID` matches **exactly** one `Approvers` entry of the channel (otherwise 403 `approver_not_listed`, writing `refused`) → the user is still enabled, role operator+ → the risk policy below (every chat channel refuses with 403 `channel_not_allowed`, both approving and rejecting, when the request is high risk or the whole approval message text does not fit one message, that is `approvalMessageText` sets `noButtons`; an old button or callback gets the same answer; only a low/medium request that is short enough can be decided from chat; Zalo still has its own sentence for high risk) → (personal Zalo) the reply code matches the request, the person, the decision, is unused, not expired and is burned in the decision transaction (`approval-tokens.md` §7). The actor in the log: "<name> via <channel> (<ExternalID>)" (`resp_log` and `core_audit`; an unknown sender: "<id> via <channel>"). **Implementation details:** (a) the Zalo code lookup runs before the policy (the request is in the record) but "already used/expired" (409 `used`/`expired`) is said after the policy; a wrong, unknown code, another person's code or a code for the wrong decision (the prefix `A-`/`R-` must match `Approve`) → 400 `invalid_code`, a fixed message, the code does not go into the log; every record of `(zalo-personal, ExternalID)` is compared by a constant-time hash and the record must belong to exactly the person of `ExternalID`; (b) the code is burned in the decision transaction together with that person's other A/R code for that request, a decision refused by a gate does not burn, a rejection does burn (`linkOpt.kind = "code"`); (c) the policy applies to both approving and rejecting; (d) the person and the channel are checked again under `s.mu`; (e) **two people**: chat is not counted in the "one email link" limit of INV-4 (g): chat is the second person after a link and vice versa; one person through app + chat or two chats is still `409 same_approver`; (f) the `Status` of `ChatOutcome`: `approved` (the approval completes), `pending` (still waiting for the second person), `rejected`; a refusal is an `*apierr.Error` (the adapter turns it into `DecisionResult.Status` = the error code); (g) `response.decision.made` is emitted after commit (`final=false` for the first approval of two). (h) a rate table of its own for chat, an identity that is in the list can always get in when the table is full, one line "chat rate table full" per minute; an id/channel that cannot be real uses one key and a fixed name "(invalid id)"; (i) a refusal of a stranger (`approver_not_listed`, `channel_not_allowed`, 429) one line per window per identity with the number held back, at most 60 lines per minute for all strangers; (j) a completed approval from chat answers at once, the item runs in the background (`runDetached`, tracked by `sendWG`, `Close` stops it); an approval in the app is still synchronous; (k) the check again under the lock binds the same `user_id`; (l) `RecordReplyCode` refuses a high-risk/`in_app_only` request; (m) an unused code is compared first, trimming only ASCII whitespace. **Policy by channel and risk**: in the app — low/medium 1 person, high 2 people (INV-2), high by AI per INV-16; Slack/Telegram buttons — low/medium/high (high 2 people), an `in_app_only` request → 403 `in_app_required`; email link (Zalo OA left for later) — only low/medium, high → 403 `in_app_required`; personal Zalo code — low/medium, high → 403 `channel_not_allowed` (`in_app_only` → 403 `in_app_required`, checked first); `via=auto` only per INV-5.
- **INV-4** **Approval link by email** (`/response/approve/{token}`; Zalo OA has no way to send a link yet): a signed token, single use, expiring in 30 minutes, tied to exactly one request and one recipient; `GET` is read-only (never approves), a `POST` with `decision` is required so that a link scanner does not approve on someone's behalf; no approving by reply email. View status: `ready | expired | used | decided | unknown`. A `v1.` token is signed by `notify`; the record is in `resp_tokens` (`kind=link`); the MAC is checked through `notify.VerifyApprovalLink` by the record's `key_id`. `GET` writes nothing; a status other than `ready` → every content field `null`. `POST` in this order: a limit (10 POSTs and 20 wrong tokens per minute per IP, 429 `rate_limited`) → an unknown token 404 `unknown` → expired/used/decided 409 `expired|used|decided` → the approver is still valid (enabled, operator+, `address` = the login email, still in the channel's list, the channel ready and in `approval_channels`) otherwise 403 `approver_not_listed` → the risk policy (high → 403 `in_app_required`) → the decision with `via=email`. The token is **burned in the decision transaction** (`UPDATE … WHERE used_at IS NULL`, 0 rows → 409 `used`; two concurrent POSTs: one wins); **a decision refused by a gate does not burn the token**, pressing Reject does burn it. The handler refuses `Sec-Fetch-Site` other than `same-origin`/`none` (403 `csrf_invalid`, for both GET and POST; no header means curl or an old browser, and the server has already refused a foreign `Origin` on POST); no session is used, the token is the only credential. **Implementation details:** (g) two people: at most **one** approval by email link on a request that needs two (a second one → 403 `in_app_required`, the token is not burned); (h) `RecordLink` refuses a high-risk/`in_app_only` request; (i) an approver who is no longer valid → `GET` returns `unknown` with no content; checked again under `s.mu`; (j) a known link's 409 writes `refused`; `decided` rereads `used_at`; (k) a limit of its own, keyed on the address too; (l) the `notify` module off → a link cannot decide. (a) the `resp_tokens` record (`kind=link`, SHA-256 hash of `token_id`) is created by `RecordLink` (from `notify.TokenRecorder`) **before** the email goes out, only accepting the `email` channel, a request that is still `pending`, an expiry ≤ 30 minutes and not beyond the request's expiry; (b) `LinkView`/`DecideByLink` look up the record by hash and then call `LinkTokens.Verify` (= `notify.VerifyApprovalLink`) with constraints **read from the record**: a record whose person/request/channel/expiry was changed makes the MAC not match → 404 `unknown`; a key that cannot be read is an error (no decision), not `unknown`; (c) in the decision transaction, `tokenGate` runs **first** (already used → 409 `used`, expired → 409 `expired`) so the loser of two concurrent POSTs always sees `used`, and `burnToken` runs **right before** the decision is written (after every gate); (d) the risk policy applies to both approve and reject: a risk other than low/medium or an AI request `in_app_only` → 403 `in_app_required`, the token is not burned; (e) the limit by `sourceKey` of the peer address (not reading forwarding headers): POST 10/minute, wrong tokens 20/minute, **GET also counts wrong tokens** (429 `rate_limited`, `Retry-After`); (f) an unknown token writes no log row (a stranger cannot fill the log chain); a refusal for a known link (`approver_not_listed`, `in_app_required`, the gates of `approve`) writes `refused` without the token; a 409 carries `request_id`.
- **INV-5** **"Pre-approved"**, a field of the rule: OFF by default; only an **admin** can set it (the minimum role of `POST/PUT /response/rules` is admin); `pre_approved = true` is refused unless **every** action of the rule has `risk = low`, is **reversible** (has a rollback step) and `ttl_min ≤ 1440` (not `null`); checked again when it runs (not only when saved). **A rule cannot be pre-approved if its request needs two people** (INV-2): refused at save time (400 `invalid`) and at run time (the request becomes an ordinary `pending` request, `resp_log` says "pre-approval not used"). Editing the template, tool or risk of a custom action **turns off pre-approval** of every rule that uses it (logged; the admin saves again to confirm). A generated request carries `pre_approved = true`, `via = auto`, writes `resp_log`. Every other gate still applies (INV-9). An AI request is not a rule so it is never pre-approved (INV-15, INV-16).
- **INV-6** A request expires after `expiry_min` ∈ [15, 30] minutes: `status = expired`, every item `skipped`, **nothing is changed**, a notification is sent; approving after expiry → 409 `expired`. A request that is no longer `pending` being approved/rejected → 409 `not_pending`.
- **INV-7** The execution switch (`Settings.execution`) is **OFF by default**. Turning it on needs: an admin, two-step login already enabled, and typing exactly `I ACCEPT THE RISK`; it writes `accepted_by/accepted_at`. Turning it off: an admin. When off: every action on a device is refused for both approval and undo (409 `execution_off`). `PUT /response/settings` does **not** change this switch.
- **INV-8** Emergency stop (`/response/emergency-stop`, operator role): turns execution off at once and cancels every `pending` request in the same operation; returns the number cancelled; writes the log. **The emergency stop also opens the shared breaker** (INV-12), so pre-approved rules, the box's own actions (`blocklist_add`, `webhook_call`, `msg_send`) and every item not yet run stop until an admin `POST /response/breaker/reset` (`fire` and `runItem` read the breaker per rule/item). Only an admin can reopen the shared breaker. After commit, the emergency stop also **cancels the context of every device step being sent** (`trackStep`/`stopInFlight`; not an undo), and `core/conn/write` sends no more SSH lines once the context is cancelled; the item ends `failed`, `state_unknown`, "Stopped by the emergency stop while the step was being sent"; **an undo already being sent runs to the end** (the safe direction); `recheck` refuses with `step_cancelled` a step whose context has ended (a read-only step in flight is refused with `emergency_stop`). Test `TestWP31_L5_*`. Settings has `stopped_at` (set at the emergency stop, cleared when an admin does `breaker/reset`): GET/PUT settings still return 200 during the stop; the GUI says clearly it is an emergency stop, not "more than N actions/hour".

### Safety envelope
- **INV-9** The blocking gates, in order, apply to **every** source (approver, pre-approval, AI) and are checked again right before running: the execution switch (only actions on devices); the status (`pending`); expiry; a valid item selection; two different people; (high-risk AI) approval in the app + two-step code; the action is still enabled in the catalogue (403 `tool_not_allowed`); the connection unchanged since the request was created (409 `connection_changed`: compare the fingerprint including id, kind, address, the `UpdatedAt` version; it is `core/conn.Fingerprint`, `updated_at` only changes when a security field of the connection changes, not with `status`/`last_test`; the writer `core/conn/write` rereads the connection right before sending and refuses when the fingerprint differs from the step's `ConnFP`, the connection is disabled, it is missing an enabled write tool, the URL is outside `target`/`allow`, a runtime-value placeholder remains, a forbidden header); the write tool and the undo tool still exist and have not been edited since the request was created (409 `tool_unavailable`: the item stores the run tool and the undo tool, and the step that is sent uses exactly the stored tool); the quota `max_per_hour` ∈ [1,20] approved device actions/hour (429 `rate_limited`); the item still has the **action fingerprint** (`actionFP`: the run/undo/read-back templates **with `expect`**, the `precheck` template, the `precheck_refuse` strings, and the risk) as when the request was created (409 `tool_unavailable`: editing a custom action, even editing only the pre-check, the refusal strings or `expect`, also **cancels** every pending request of it and turns off pre-approval of the rules that use it; an edit outside `ChangeAction` makes the next approval or run be refused). The execution switch, the breaker and the maintenance window are **read again in the transaction that claims the item** (`claimItem`, a compare-and-set together with marking it running): an emergency stop, the switch turned off or the breaker opened after `runItem` read still blocks a step not yet sent, including a box action; an item that was swept/cancelled cannot be claimed and nothing is sent. That transaction also rereads the connection and the catalogue and reruns `gateItem` (including `connectionGate`): a connection edited or deleted after `runItem` read still blocks the step (no "Running:" row), and the writer is the second layer (compare `ConnFP` right before sending). The `max_per_hour` limit counts device items that have run **or may have run** (`sent_at` set at `claim`, together with `executed_at`, `state_unknown` or `running_at`), not only `executed_at`. Test `TestWP31_L2_*`.
- **INV-10** **The never-touch list** (gateway, DNS, domain controller, the box itself, the admin IP, services the customer declares: an IP, CIDR, or domain): a matching target → the action is refused `never_touch`, not run, logged. An entry can be declared as an IP, CIDR, domain (protecting the parent domain too: blocking `corp.example.com` is refused when `login.corp.example.com` is declared), a **MAC address** and a **port name** (`Gi1/0/48`, `1/1/52`; a port name protects that port on every device, on the safe side). **The subject of the event** (the fields `ip`/`src_ip`/`source_ip` and `mac`) is counted for every trigger and every action that **names a port, MAC, VLAN or network port (even when there is an additional address)** or names no address at all; an action that only names an address only affects that address. The subject of an AI proposal is the finding's asset (looked up in the directory; a lookup error → refused), not an `asset_id` the AI wrote. **The gateway is taken automatically**: the box's address and every inventory device of kind `router`/`firewall`, **with no limit on the number of rows** (`inventory.DevicesOfKind`; read at planning time and at run time). A MAC entry recognises `aa:bb:..`, `aa-bb-..`, Cisco `aabb.ccdd.eeff` and 12 contiguous hex digits, stored in canonical form. When the list cannot be built (reading the box address or the inventory fails) → the action is refused `never_touch` (fail closed), the blocklist returns 503. Checked at planning time **and** at run time. The blocklist (INV-17) never contains an entry that matches this list. `Config.BoxAddrs` is wired by `cmd/vedette/response.go` with the address vedette-host reports and the honeypot decoy IPs (`DecoyIPs`), so a decoy IP is also "the box itself"; **when not known, fail closed** (`BoxAddrs` returns an error → `errNeverTouchUnread`), and `Config.BoxMACs` adds the NIC's MACs on the MAC side. Test `TestResponseBoxAddrsHoldTheDecoysAndTheHost` (`cmd/vedette`). **Pre-seeded**: besides the declared list, the box's own address and every router/firewall in the inventory, the list also has the **box's default gateway and DNS** reported by `vedette-host` (`Config.HostInfra`: the gateway of the kernel's default route, the gateway and DNS stored for the management NIC); when it cannot be read (the host is configured but has not answered) → refused as with the box's address (fail closed). It adds every IPv6 gateway (`default_routes6`), the DNS in use (`resolvers`: including DNS handed out by DHCP), and the **gateway's MAC** (`HostInfra.MAC`, from the kernel's neighbour table; the label "Default gateway of this box") so an action that only names a MAC (isolating a switch port by MAC, an event with no IP) aimed at the gateway is refused even when the gateway is not a router in the inventory; an IPv6 link-local gateway is only protected by MAC (the IP kind never accepts link-local). **Only seed what has stood still** (against fake RA/DHCP and ARP/ND spoofing; `hostMACs.vet`, `cmd/vedette`): the gateway and DNS in the **first** `state/net` answer after core starts are trusted at once; a gateway/DNS address **first seen after that** is a candidate, neither the IP nor the MAC is seeded until it has been present in at least 3 consecutive answers spanning at least 10 minutes (absent once and the count starts again), writing a WARN + `core_audit` `network.gateway_new`/`network.dns_new` when it appears and `network.gateway_adopted`/`network.dns_adopted` when accepted; the first MAC of a trusted gateway is pinned, another MAC is a candidate under the same rule (`network.gateway_mac_changed` on change, at most once per 10 minutes per gateway; `network.gateway_mac_adopted` each time accepted), at most 4 MACs per gateway and **the first pinned MAC is never dropped**. A gateway/DNS that the admin stored in netplan is trusted at once. So someone faking the gateway/MAC can still be isolated in the first 10 minutes; a legitimate change of gateway/DNS through DHCP/RA is only protected after 10 minutes. An address family with no trusted gateway in one answer keeps the previous gateway (`keepGateways`); a gateway missing its neighbour entry keeps the pinned MAC. GET shows each value on one line (a self-seeded entry that duplicates a declared entry is not repeated); PUT does not store a self-seeded entry when it returns exactly the value and the label that GET showed, the same value under a label the admin wrote themselves is a declared entry and is kept. Tests `TestTheBoxGatewayAndDNSAreNeverTouch`, `TestSavingTheShownListDoesNotStoreTheSeededEntries`, `TestResponseHostInfraHoldsTheGatewayAndDNS`, `TestTheBoxGatewayMACIsNeverTouch`, `TestResponseHostInfraHoldsTheIPv6GatewayTheGatewayMACsAndTheLeaseDNS`, `TestGatewayMACIsPinnedAgainstSpoofing`, `TestGatewayMACRotationNeverEvictsTheFirstPin`, `TestNewGatewaysAndResolversAreCandidates`, `TestInfraReportWritesAnAuditRow`.
- **INV-11** Deduplication: the same (target, action) that is open (`pending/approved`) or currently in effect → merge, creating no new request, writing `deduped`. One rule run = **one** merged request.
- **INV-12** A per-rule limit `max_per_hour` ∈ [1,100]; a **shared breaker** `breaker_max_per_hour` ∈ [1,200] (counting actions of rules and the AI): exceeded → `breaker_tripped_at` is set, **every rule and AI proposal pauses**, `breaker_notified` is sent; only an admin can `POST /response/breaker/reset`. An action touching more targets than `multi_target_max` needs a second approver (INV-2). Maintenance window: inside the window no rule or AI request is created.
- **INV-13** Every action has an **undo**, a `ttl_min` (self-removal, 5..43200 minutes, or `null` = keep until removed by hand) and a **check after running** (`verified {ok, detail}`; empty when the action cannot be read back). **The pre-check and the read-back are data**: the `precheck` step (read-only) runs right before `run`; if the output contains one of the `precheck_refuse` strings → the item is `failed` "Refused by the check before: …", **no write step is sent**. `verified` is only judged when `verify.expect` is present: after `run` the read-back output must contain the filled-in `expect`, after undo it must not; with no `expect` → `verified = null`; a 2xx or a command with no error is never counted as checked. A device action that has `{interface}` but no `precheck` with ≥ 1 refusal string is unavailable. Undo: operator; refused when execution is off; **still allowed when the action has been disabled in the catalogue** (removing a change is the safe direction) but not when the connection or the undo tool has changed (`connection_changed`/`tool_unavailable`). A device step runs in a goroutine and `runItem`/undo stop waiting at the item's deadline even if `Executor` does not respect the context (writing "State unknown", releasing the step lock); a real result that arrives late replaces the sweep's "State unknown" (a correcting log row). Only the `sweep` job undoes by itself when the TTL ends; GET never sends a step to a device. An expired TTL → undo by itself and writes `ttl_removed`.

### Typed parameters (SYS-1, SYS-2)
- **INV-14a** The agent's data (trigger fields: source IP, device name, domain, log content…) is **controlled by the attacker**: every value that goes into a template must pass through a **typed placeholder** (`ip, cidr, domain, port, mac, vlan, interface, text`) and be checked by type before use; the wrong type → refused, writing `refused`, **nothing runs**. `text` only consists of letters, digits, spaces and `. , : @ # / _ -`; no quotes, no shell characters, no newlines.
- **INV-14b** **Escaping by transport** is the second layer (after the type check): `json` → escape as a JSON string; `url` → percent-encode; `header` → drop CR/LF; `cli` → only values that passed the type check. The shell characters `; | & $ \` < > ( ) \ ! ~ ^` are **never** allowed, even in the fixed part of a template (SYS-1). The command template is held by the server; a `POST` from the client/AI only consists of the action name and the parameter values; the fields `cli/method/path/body/headers` in an AI request → refused.
- **INV-14c** The action catalogue: a built-in action only allows changing `enabled`, `ai_may_propose`, `connection_id`; a custom action (add/edit/delete) declares: name, description, connection, the `run/rollback/verify` templates, risk. The template fields must fit the connection kind (API: `method/path/body`, HTTP additionally `headers`; SSH: `cli`; MCP: a write tool + `body` is the JSON arguments). A read-only connection is refused (409 `read_only`). Delete only when no rule uses it. An action `available=false` has `unavailable_reason`. A template additionally has `precheck`, `precheck_refuse`, `verify.expect` (type-checked like the other steps); `tool`/`rollback_tool` are only used with an MCP connection, a built-in action over HTTP/SSH has `tool = null`. `available=false` also has reasons: a runtime value remains, `{interface}` has no pre-check, the connection is not ready (`NotReady`), `tool` set for a non-MCP connection. `GET /response/catalog` (viewer role) only lets an admin see the **values** of the `headers` lines in a template; other roles see the header name and `(hidden)`. **Details:** (1) **The pre-check and the read-back are read-only.** A read-back over HTTP is only a `GET` with no body (anything else is 400 at save time, and built-in data fails to load); a read-back and pre-check over SSH must not contain a command that changes configuration (the banned-command list is **data** `core/conn/cliban/cli-ban.json` (package `core/conn/cliban`), the section "read_only_steps": `configure`, `copy`, `write`, `shutdown`…) and **must not share any line with `run` or `rollback`**, except the first line being identical in both (the line that turns off paging/sets up the terminal). The shared list of spec §9.3 (the section "everywhere": `reload`, `erase`, `delete`, `no username`, `copy … tftp:`…) applies to **every command line of a custom action** and to the pre-check/read-back of every action; built-in templates are approved data so their `run`/`rollback` lines are not compared (FortiOS `delete` of its own object). An MCP connection has no named read tool in the catalogue yet, so an MCP action with a pre-check or read-back is "unavailable" (saving an MCP action with either is 400). (2) **The network-port gate cannot be bypassed with another placeholder.** The parameter kinds have no "port name" kind (`{port}` is a TCP/UDP port number, `{id}` is an integer, `{name}` is a free name), so it cannot be told apart by declared kind. The choosing rule: an action that has `{interface}` in any template always needs a pre-check + ≥ 1 refusal string; a **custom** action also needs it when `{port}`, `{id}` or `{name}` is in the **command or API path** of `run`/`rollback` (not in a JSON body or header), because `interface GigabitEthernet1/0/{port}`, `interface Port-channel{id}`, `interface {name}` all name a port. The 400 error says the reason and points the way (use `{interface}`, or declare a pre-check). Built-in templates are reviewed data so they are only subject to the `{interface}` rule (`fgt_vip_disable` uses `{name}` for the VIP object, not a port). (3) **A pre-check that asserts enough.** `precheck_expect` (a string the output must contain) plus `precheck_refuse`; an output that is empty after normalisation is refused (fail closed); matched through `normalizeOutput`. (4) **Approval shows the pre-check and the read-back**: `Change` has `precheck`, `precheck_rules`, `verify_rule` together with `verify`; `verify` records exactly the stored method, with no default "GET". (5) The header values of the pre-check are also hidden from non-admins like `run`/`rollback`/`verify`. (6) Additional forbidden headers: `Via`, `X-Forwarded` (prefix), `X-HTTP-Method-Override`, `X-HTTP-Method`, `X-Method-Override`, `X-Real-IP`, `X-Original-URL`, `X-Rewrite-URL`. (7) A step with only headers is no longer considered empty: it is checked (and refused if it has no command or API call). (8) The undo tool (`rollback_tool`) is checked before running as at undo time (409 `tool_unavailable`). (9) Built-in templates: ArubaOS-Switch is **not** a built-in template (spec 6.2), `fgt_policy_disable` has a pre-check that refuses a `deny` policy, the two port-shutdown actions refuse a port that is already down (`administratively down`, `Admin state is down`). (10) An action whose pre-check cannot run on its connection kind (a pre-check that only has a command on an API connection, or only has an API call on SSH) is "unavailable" with a reason.
- **INV-14e** A proposal in an AI plan (`resp_plans`) only stores `action_id` and typed parameter values, never a command/path/body. `RequestProposal` rebuilds the change through the same planner as a rule (type check, escaping, connection address, never-touch), checks the switch, the maintenance window, the breaker, deduplication (`pending/approved/executed` counts as already requested); the generated request carries `ai ≠ null` so the AI gate applies. **Writing the plan**: the `plan` job (5 minutes) only runs when the module is on, `Planner.Available` is true (the `ai` module is on, with a profile for the `response-plan` job) and `Critical` exists; each AI run asks for at most 3 open critical findings that have no plan yet (there is no separate per-day cap: the overall limit is the monthly token budget of the `ai` module; `Planner.Plan` returns `ErrPlanUnavailable` when the budget is used up, the `ai` breaker is open or no usable profile is left, then the whole run stops and findings are not set back); a finding that fails/is refused waits 1 hour, 6 hours, 24 hours and then is given up (in memory, counted again on restart); it does not run when the AI is paused (`ai_paused`). The AI has **no tools at all**, it only returns JSON of steps; `savePlan` stores the whole plan or nothing: `action_id` must be a catalogue action that is on and `ai_may_propose`, parameter names exactly equal to the names the action accepts, values going through `planProposal` (type, escaping, the device's never-touch, connection) and `aboutTheDevice` (**every** value must equal exactly the IP of the finding's device, each value on its own; no names, CIDR, interface, MAC, VLAN, port, id; an action that only has free text is refused; checked again in `RequestProposal` by `Directory.Device`; only actions whose every value is `ip` are given to the AI; `blocklist_add` is only given when the device IP is an address the list can publish (`offeredFor`), so the plan for a LAN device is not refused as a whole because of it; a stored proposal refused for this reason shows the status `not_publishable`, not `tool_unavailable`). `RequestProposal` is one person's click and does not call the AI, so it is not subject to `st.AI.Triggers`, `BudgetHour`, `BudgetDay` (which measure AI proposals through `Propose`); every other gate still applies, only the `contain` step carries proposals (≤ 3), the undo time is set by the server; what is stored is the checked value. Refused → not stored, writing `resp_log` (`refused`, `plan_invalid`) and `core_audit` (`response.plan_refused`); stored → `proposal` + `response.plan` (actor `ai:response`, "AI-generated"). Creating a plan creates no request and touches no device, **except** when the execution switch is on **and** `finding` is in `ai.triggers`, the job sends each proposal of the plan that was **just stored** through `Propose` (actor `ai:response`, trigger `finding`, evidence = the finding + the reads the AI cites, the AI's `confidence`; `checkDraft` refuses `confidence` outside 0..1, > 3 read ids, malformed ids, evidence on a step that has no action), every INV-15 gate applies, once, no resending; the result is reported to `Planner.Proposed` (an AI log row with `links`). `AIAction.ConnectionID` (not in the JSON) says the connection of a device action. Test: `plan_send_test.go`. `ai_available` of `GET /response/plans` = module on ∧ `Planner.Available`; with the AI off an existing plan still shows, and everything else runs. Test: `planner_test.go`.
- **INV-14d** A new rule **always starts in dry-run** (`live=false`): it writes `dry_run`, creates no request, runs nothing; a template creates a copy as a rule that is off + dry-run. `simulate` (a saved rule or not) builds exactly the command/request that would run with the latest event and `executed = 0` always. Limits: conditions ≤ 10, actions 1..6, `schedule_min` 15..10080. **A condition value matches its field:** a `number`/`port` field of the trigger catalogue has `min`/`max` (`GET /response/triggers`); "at least"/"at most" only on a field that has a range and the value is a plain decimal number within the range; "equals"/"is one of" on a field that has a range accept a number in the range, on a field with `choices` accept one of the choices (case-insensitive); wrong → 400 `invalid` with a sentence naming the field's label and the range. A catalogue or rule template that violates this makes `loadData` fail (the box does not start). A stored rule with a condition that violates the field's range matches no event (`storedCondsOK`) until it is saved again.

### The AI sends requests: the safeguards are on the server, not in the prompt
- **INV-15** An AI proposal (**the real build: the Go gate `Service.Propose` with the actor `ai:response`**; `POST /response/ai/proposals` only exists in the preview) only becomes a **request** when it passes all of these (**every gate runs inside one write transaction**; the proposal body has no command field, checked at the boundary: `confidence` finite 0..1, `why` ≤ 400 through `cleanLine`, ≤ 10 distinct evidence entries, parameters ≤ 200 characters; a request always waits for approval, never `via=auto`; the order of checks follows the mock `ai.ts`: maintenance → breaker → AI paused → trigger allowed + `ai_allowed` → `ai_may_propose` → a typed plan, never-touch, `not_publishable` (`blocklist_add` on an address the list never publishes, 409), available → evidence missing/wrong/not about the target → `confidence` < 0.8 → an open request exists → refused within 7 days with no new evidence → quota → a digest note → the second check for high risk (≥ 2 evidence entries, `confidence` ≥ 0.9) → request; every refusal/note goes to `resp_log`, notes ≤ 50): (1) the trigger is in `ai.triggers` and `ai_allowed`; (2) the action has the flag `ai_may_propose` (also checked when `RequestProposal` builds a request from a stored proposal: 403 `tool_not_allowed`); (3) **the evidence is real and about the target**: each `evidence.id` can be looked up (a finding that is **still open** through `Directory.Finding`, ioc_hit/config_read through the `Evidence{IocHit, ConfigRead}` gate; a nil gate → 422 `evidence_invalid`); at least one evidence entry of the right kind proves the trigger (`ai_evidence` of the trigger catalogue; a trigger that no kind can prove is not used by the AI: 403); at least one evidence entry speaks about the target by kind; a read only counts for a device action through exactly that connection; only relevant evidence counts for "new evidence" and "≥ 2"; an action that names a port/MAC/VLAN/no address needs a finding for the never-touch subject (409 `never_touch`); (4) `confidence ≥ 0.8` (`AI_MIN_CONFIDENCE`); (5) one open request per (target, action); (6) when refused, **7 days** without repeating (`AI_REPEAT_DAYS`); (7) the hourly/daily quota (default **2/hour, 5/day**; ranges 1..20 and 1..100); (8) the quality breaker: only counted when **at least 5 of the 10 latest proposals have been decided**; then **more than half of the decided ones being rejected** pauses the AI (`ai.paused_at`, a `breaker` log row, a notification) until an admin does `resume`; (9) **high risk**: the second deterministic check (`second_check`) must pass. When it does not pass → the result is a `suggestion`/`digest` (not a request), still logged.
- **INV-16** A high-risk AI request: `in_app_only = true` → only approved **in the app with a two-step code**, by **two different people** (INV-2); approving from chat/email → 403 `in_app_required`; a person who has not turned on two-step → 403 `twofa_required`; no code entered → 400 `code_required`. **Read it as both rules**: two different people, **each person** entering their own two-step code. Checked before the approval transaction: `in_app_only` needs `via=app` (otherwise 403 `in_app_required`) → **every read-only refusal of the transaction** (`approvalGate`, the same function, read once from the reader: `expired`, `not_pending`, the selection `invalid_items`, an approver demoted/locked `forbidden`, `execution_off`, `selection_differs`, `same_approver`, `in_app_required` (the second person also through email), `gateItem` without `run` — `tool_not_allowed`, `connection_changed`, `tool_unavailable` including a connection not ready — and the hourly limit `rate_limited`) → `TwoStep.Verify` = `core/auth.VerifyTwoStep(ctx, userID, code, purpose, summary)` with `purpose` = `response.approve.<request-id>` (the code is tied to exactly this request) and `summary` = one line built by the server saying what is being approved (OWASP Transaction Authorization): a TOTP code is accepted only once (a code already used to log in or used the previous time is refused), the email method with an empty `code` sends a code and returns 400 `code_required` (`sent_to`, `resend_after`). **An error from `VerifyTwoStep` is returned unchanged** (code, status, accompanying fields), not turned into another code: 400 `code_required`, `invalid_code`, `wrong_code`, `too_many_tries`, `code_expired`, `no_code`; 403 `twofa_required`; 429 `resend_too_soon`, `too_many_codes`, `rate_limited` (with `Retry-After`); 503 `twofa_email_unavailable`. A nil `TwoStep` gate → 403 `twofa_required`. **The transaction does not trust a nil result:** `aiStepUp` returns evidence that the code passed for exactly this request and this person; in the approval transaction, an `in_app_only` AI request without that evidence → 403 `twofa_required` (a chat/link path that does not go through this step is shut; a clock going back between two reads cannot open it either). **The summary line:** `<Risk>-risk AI request: "<the chosen action>" on "<the asset>"`: the risk first, names placed in double quotes (a `"` inside is changed to `'`), passed through `cleanLine` (dropping control, format, bidi characters, U+E0000 tags, variation selectors, empty Hangul/braille filler characters), only listing the chosen items, over 200 characters it writes `and N more`. **Hints and refusal notes** also go through `cleanLine`. **Rereading the account:** every approval in the app rereads the approver in the transaction (still exists, not locked, role ≥ operator), otherwise 403 `forbidden`. **A code is not spent on an approval that will be refused:** the same `approvalGate` runs before `Verify` (on the reader) and in the transaction (where it decides, on `tx`), so the state is the same for the same refusal (tests in `ai_approve_test.go`); that refusal does not call `Verify`. Only when the state changes between the two reads (execution turned off, catalogue/connection edited, demotion, expiry, someone else approving first) does the transaction refuse after the code has passed: keeping the error code and status, the message adds "Your two-step code was used by this attempt; ask for a new one to try again." The maintenance window, the breaker and the never-touch list do not block an approval (they only block at run time, `gateItem` with `run`), so they are not part of this check. There is no time window: one code per approval.
- **INV-17** The blocklist: a firewall **pulls** from an internal URL with a token (`/response/blocklist/{token}.txt`, plain text, one IP per line; **only public addresses**: RFC 1918, ULA, `100.64.0.0/10`, `0.0.0.0/8`, loopback, link-local, multicast, `240.0.0.0/4` and every IANA Special-Purpose block (IPv4/IPv6) not globally routed (`198.18.0.0/15`, `192.0.0.0/24`, `64:ff9b::/96`, `2001:db8::/32`, `fec0::/10`, `100::/64`, ... the table `notPublishable`; three IPv4 documentation blocks are an exception because of sample data) are dropped at publication; three comment lines only consisting of `# vedette blocklist`, `# generated <time>`, `# entries <count>`, no device/rule/event names; at most 10,000 entries, the 10,001st is refused `limit`; a store error → 503 `server_busy` with `Retry-After`, never an empty list; headers `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`; a pull limit by source address, by /64 for IPv6, a limit table of 10,000 keys); the token is the only credential; regenerating the token invalidates the old address at once; each entry has `source, reason, added_at, expires_at` (TTL self-removal). No write permission on the firewall is needed. A `blocklist_add` with an address that cannot be published (the same `publishable`/`notPublishable`) is refused **at planning time** with `not_publishable` (409; different from exposure's `not_public` 400) in `planAction` (right after the never-touch check, so the gateway/box still returns `never_touch`), and writes a `refused` row (`not_publishable: …`). **Rules** (`fire`, including manual runs): that is a "no effect" refusal, not a safety refusal, so **only that action is dropped** (one `refused` row), the other actions of the rule still go on (block the source + send a message → still sends the message); every other refusal (`never_touch`, `invalid_target`…) still refuses the whole run. A **fixed** value that cannot be published is refused at rule save/simulation time (400 `not_publishable`); a value from a trigger is only known at run time. An AI proposal (`Propose`) and a request from an AI plan (`RequestProposal`) are refused 409; an AI plan at save time (`savePlan` → `plan_invalid … (not_publishable)`), but the plan job does not give `blocklist_add` for a device whose IP cannot be published (INV-14e). The simulation shows the error at that step. An item created before this version is refused again at run time (`carryOut`, item `failed`, a `refused` row), never reporting "Added". An old entry for an address that cannot be published in `resp_block_entries` is deleted once when the module starts (`dropUnpublishable` in `ensureSeeded`, one `refused` row + audit `response.blocklist.cleanup` stating the number of entries). Filtering at publication stays as the last layer, silent (no row written on each pull). The full URL that the admin sees begins with `Config.BaseURL()` (a function, asked on every build; `cmd/vedette` gives the Box address of Settings → Box network, defaulting to the management IPv4, never a fixed name `vedette`); nil or empty → the URL from `/api/v1` onward.
- **INV-18** Learning from rejection: rejecting an AI request can save the reason as a rule or memory hint (`remember`) — only a **hint**, never applied by itself. The approval rate is measured (`/response/metrics`). `remember ∈ {none, rule, memory}` writes `resp_hints` (keeping at most the 50 newest rows); nothing reads `resp_hints` to change rules or the prompt. **Resume** only clears `ai.paused_at`, it does **not** clear the window of 10 decisions (the mock's `resume()` does the same): the next decision on an AI request evaluates the window again and may close the breaker at once.
- **INV-17a** **Responding from an incident (S-RESP-3).** `GET /response/incidents/{id}` (viewer) and `POST /response/incidents/{id}/request {action_id}` (operator). The source is read by the **server** through the gate `Config.Incidents` (`cmd/vedette` `responseIncidents`: the public `notify.IncidentDetail`, and for a decoy incident the `honeypot.HitDetail` of the hit in `link` `/honeypot/hits/<id>`; a test hit, another kind, a deleted hit → no source; notify off → 404); the browser only sends `action_id`. The address is parsed with `netip` at the boundary (with a zone → no source), `scope` = `public` when `publishable`, otherwise `lan`; the device is read again through `Directory.Device` and only accepted when the IP still matches. **What is offered** (`incidentOffers`): a device action that only has the parameter `{ip}` and is on **or** has a chosen connection, and `blocklist_add` only when the source is public; each entry goes through `planAction` (type, never-touch, connection, address) with `{ip}` = `{{trigger.source_ip}}` of an event built from the incident, together with the reason it is not ready (off in the catalogue, execution off for a device action, an open request already exists). Actions that block a split or an isolation VLAN are not offered (they need a switch port, which no source has yet). **Asking**: reread the incident and the source (outside the lock), then in one write transaction under `s.mu`: an action not in the offered list or turned off → 403 `tool_not_allowed`; a device action while execution is off → 409 `execution_off` (a box action is not blocked by the switch, INV-9); maintenance 409 `maintenance`; breaker 409 `circuit_open`; a never-touch list that cannot be built → as INV-10; `planAction` refuses → its code; deduplication 409 `already_requested`; `checkBreaker(1)`; then `createRequest` with `source = person`, actor `<email> (app)`, `proposal_id = incident:<id>`, `ttl_min = 1440`, sent to the approval channels like every request (POST-5). Never pre-approved, nothing runs in this call (FORBID-1); no source → 409 `no_source`; a `resolved` incident → the panel `note`, no choices, asking 409 `incident_resolved`; the source of a `scan` hit that has no `service` hit from the same source within ±1 hour (`honeypot.SourceConnected`; `IncidentInfo.Unconfirmed`, the source may be forged) → the panel `note`, every choice not ready, asking 409 `source_unconfirmed`; a confirmed scan → the request reason adds "(a scan; … not forged)". Maintenance and the breaker are reasons not ready in the panel. `Det.Fields.kind` is the hit kind. Metrics: `person` does not go into `ai` or `rules`. Every refusal writes `refused`. `resp_actions.source` accepts `ai`, `rule` or `person`; the blocklist entry of this request has the source "Asked from an incident". Tests in `incident_test.go` (`incident_test.go`), `TestResponseIncidentRespondReadsTheTrapSource` (`cmd/vedette`).

### Log
- **INV-19** `resp_log` is append-only, a hash chain: `hash = SHA-256_hex(prev_hash + "\n" + canon(entry without hash))`, the same formula as `core_audit` and `ai_activity`; the `prev_hash` of the first row = 64 `0` characters; returned **oldest first** to verify from the start. **There is no edit/delete endpoint.** Before a step is sent to a device (or webhook) the item is marked `running` with a log row (kind `approved`, "Running: …") in a transaction that has committed; the step runs on its own context with a time limit (not the approver's context); an item still `running` after a restart or past its deadline is marked `failed` "State unknown: check the device" by the `sweep` job and logged; an item of an `approved` request that has not started after 10 minutes is also `failed`. A log row reporting events dropped because the queue was full (`event_backlog: N …`) is **merged into one row per minute** with the count since the previous row (the `DroppedEvents` count is still complete), so that an event flood does not make the append-only log grow by one row per event. It records every event: `rule_fired, proposal, request, approved, rejected, executed, rolled_back, ttl_removed, refused, expired, failed, settings, emergency_stop, blocklist_token, dry_run, simulated, deduped, breaker, ai_note`. Every **refusal** is also recorded. **`GET /response/log` returns `ts` as the string exactly as stored and hashed** (`2026-11-11T14:16:30.000Z`), not `date-time` (ogen re-encodes it, dropping the milliseconds): the returned string can be verified with exactly the formula.
- **INV-20** Every mutation also writes `core_audit` (SYS-3). No secret in `detail` (SYS-4); connection secrets are in `core` (INV-21).

### Connections and the device executor
- **INV-21** **Connections and their secrets belong to `core`** (`core_connection`, `core_connection_tool`, `core_secret` purpose `core_connection`). `response` has no connection tables or secrets: the catalogue, items and log only hold `connection_id` and the fingerprint `conn.Fingerprint` (id, kind, address, `updated_at`), never credentials, pins or authentication headers. The catalogue reads connections through the gate `Connections` (installed with `core/conn`); device actions are available **when `ai` is off**. Deleting a connection while `response` still has a change in force on it → 409 `in_use` (`core/conn` asks `response.ChangesInForce`).
- **INV-22** **The executor gate:** each item stores the **exactly** filled-in version of `precheck`/`run`/`rollback`/`verify` at the time the request is created (`Exec`); the step that is sent has the form `Step{ConnectionID, ConnFP, Phase ∈ precheck|run|rollback|verify, Tool (MCP only), Lines (SSH), Method, URL, Body, Headers (HTTP), Args (MCP, typed JSON values)}` and returns `Result{Status, Output, Detail}`. `Output` (at most 1 MB) lives only in memory to compare `precheck_refuse`/`expect`, and is **never stored, logged or returned through the API**; the item only keeps `Detail`, one cleaned line of at most 200 characters. A device item with no `Exec` (created by an old version) → `failed` "made by an older version". Budget: HTTP and MCP **15 s per call** (connect 5 s), SSH **20 s per line and 60 s per session**, a whole item (pre-check + read before running + run + read-back) **90 s** (`stepTimeout`); expiry → "State unknown: check the device" as INV-13. An action that still has runtime-value placeholders (`{seq}`, `{previous_vlan}`, `{found_id}`, `{rules_before}`, `{timeout}`) is unavailable; `{expiry_s}` = `ttl_min` × 60. The `tool` field of the catalogue is only used for MCP connections; the HTTP and SSH kinds use the fixed tool of the kind (`send_request`, `run_approved_command`, `apply_config`, `launch_job`). (a) `Exec` is built by `buildExec` as soon as the request is created (`planAction`, at the same time and from the same template as the `Change` that the approver sees; not rebuilt at run time), consisting of four steps + `precheck_refuse`, `precheck_expect`, the filled-in `expect`; `{expiry_s}` is filled in there, and an action that uses `{expiry_s}` while the item has no `ttl_min` is `tool_unavailable` "needs an undo time". (b) `DeviceStep` additionally has `ConnFP`, `Lines`, `Method/URL/Body/Headers`, `Args`; `DeviceResult` has `Status` ∈ `ok | not_sent | connection_changed | failed | unknown` (an unknown status is treated as `unknown`: it may have been applied). `not_sent` (nothing reached the device: a broken dial or TLS, refused before sending), `failed` (HTTP 4xx for a write step; every failed read step) → item `failed` "Nothing was changed"; `unknown` (sent, **the result is not known**: a timeout after sending, HTTP 3xx or 5xx, an MCP write tool reporting `isError`, every SSH line refused or the session closing midway, the writer or executor **crashing** in the middle of a write step) → `failed` + `state_unknown` (counted as in force, `ChangesInForce`); **the wording of an error message never decides the result**; `connection_changed` → refused 409. A `precheck`/`verify` step is read-only so it never leaves "State unknown". (c) `carryOut`: `precheck` (rerun the read-only command check on the built lines: `data/cli-ban.json`, HTTP only `GET` with no body) → `precheckVerdict` on the output after `normalizeOutput` (the refusal strings, `precheck_expect` must be present, an empty output is refused: fail closed) → `run` → `verify` **only when there is `expect`** (`readBackHolds`); the output is dropped right after comparing. (d) `undoItem`: `rollback` and then `verify` where `expect` **must not** remain in the output; if it remains → the item keeps `executed` with a reason (sweep retries, logged once); a read-back that does not answer → still `rolled_back` with a note. (e) A device item with no `Exec` → `failed` "made by an older version"; its undo also fails with that reason. (f) `unavailable()`: adds `NotReady` (from `core/conn.NotReady`, through `ConnectionInfo.NotReady`) and "the write tool exists only for MCP". (g) The transaction that claims the item (`claimItem`) **rereads the connection and the catalogue** and reruns `gateItem` (including `connectionGate`); a connection that was deleted → 409 `connection_changed` "no longer exists"; it does not mark `running` when refused. (i) **Checked again right before each write step**: after the pre-check and before `run`, it rereads the emergency stop (`Settings.StoppedAt`, set by `EmergencyStop`, cleared by `ResetBreaker`), the execution switch, the breaker, the maintenance window and whether the action is still on; if any of them forbids, **nothing is sent** and the item is `failed` with a reason. Before each `rollback` it only rereads the **emergency stop**: the execution switch and the breaker do **not** block an undo (an undo is the safe direction), the emergency stop blocks every step that touches a device, undo included, until an admin continues. (j) **An undo keeps the identity, not the fingerprint**: `rollbackGate` and the writer (`Step.ByIdentity`) compare `conn.Identity` (id, kind, address; `itemRec.ConnIdent`), the connection must still be on and the pin/server key must still match; changing a token, pin, allow-list or the tool switch does not get an undo stuck, an undo ignores the write tool switch (written to the log); `run` still keeps the full fingerprint. The result text of a stuck item never says "Nothing was changed". (k) **An unclear result has a way out**: after an unclear `run`, if there is `expect` it is read back at once once and on every sweep run (`resolveUnknown`): the text is present **and before running the text was absent** → `executed` (with an auto-undo time), the device answers without the text → `failed` with no more state_unknown, unclear (no answer, or **printing empty**) → still unclear. **Reading before running:** an action with `expect` reads that text right before `run`: it uses the output of `precheck` when the pre-check step **is** the `verify` step (the same step as built), otherwise (after a recheck (i), so that an emergency stop/switch off/action turned off during the pre-check does not send even the read) it sends a read-only `verify` step. The item only stores a bool `present_before` (in the JSON `items`, no migration), **does not store the output**, and stores it **before the write step is sent**, in a small compare-and-set transaction on the `running_at` stamp of that claim (an item already swept or taken by another path → nothing is sent), so a restart between `run` and the result still leaves it for the sweep. A read before that does not answer or does not finish → no write step is sent, `failed` "The read before … Nothing was changed" (like the pre-check). **An empty answer counts as the text being absent**: a device that prints empty because of a glitch when the text was in fact present means that the later unclear run is counted as Vedette's and removed when the time runs out; chosen because `show` of an object that does not exist yet (the first ACL) prints empty, and a refusal would mean the first block never runs. A read-back after an unclear `run` (immediately or by sweep): the text present and `present_before = false` → `executed` with an auto-undo time; `true` (it was there before, possibly by someone else) → `failed`, no more state_unknown, not counted as in force, not auto-undone, the result says "State unknown … already there before this step … will not undo it. Check the device."; **missing** (the item has no record of the read before) → never denied: `executed`, in force, can be undone by hand, **no** auto-undo time, the result says the item has no record of a read before so the change may have existed beforehand. A `run` that **answers clearly** with `present_before = true` → `executed`, **does not** set `remove_at` (does not automatically remove a possible change of someone else), the result says "already there before this step, so it is not undone automatically"; a manual undo is still open. The hourly limit counts items (`SentAt`), not counting read steps. Tests in `readbefore_test.go`. A `state_unknown` item can be undone through the undo endpoint (`rollback` and then the read-back must no longer have `expect`) and becomes `rolled_back`. (l) **An unclear undo** (no answer, or a read-back printing empty/not answering — empty is not evidence) keeps the item `executed` with `undo_unclear`: the next attempt **reads first**: already gone → done, not sent again; still there → sent again; unclear → wait. (m) Before sending, `Exec` is **rebuilt** from the catalogue row (with `actionFP` checked) and the stored values and then compared with the stored `Exec`; if different nothing is sent. (n) The strings `precheck_refuse`, `precheck_expect`, `expect` are normalised like the output (`normalizePattern`: for JSON output, dropping whitespace outside strings in double quotes, like `json.Compact`; otherwise collapsing spaces) when compared, and a custom action for an API/MCP connection stores them in that form if they contain double quotes. (o) `RestCall` shows `headers` (filled in) and `{expiry_s}` is the number of seconds that will be sent: `Change.Rest` is the built step itself (`stepOf`). (p) When the request is created, the URL of every step must be under `target` and under an `allow` entry (the same rule `conn.AllowsURL`), otherwise the action is "unavailable" with a reason; `?query` is kept (it is inside the approved step, `under()` only looks at the path), a `#fragment` is refused by the writer. (h) A connection that disappears while a step is running: `finishItem` still records the result, sets `remove_at = null` (leaves the sweep) and writes **one** log row "no longer exists"; `undoItem` with a connection that is gone also drops `remove_at`, does not retry, logs once. ## Preconditions (before calling)
- **PRE-1** `POST /response/proposals/{id}/request` (from an AI plan): execution on, the action on, no open request for that proposal yet.
- **PRE-2** `POST /response/execution {enabled:true}`: admin + two-step on + exactly the phrase `I ACCEPT THE RISK` (INV-7).
- **PRE-3** Creating a rule: admin role; `trigger` ∈ {honeypot, ioc_connection, finding, unknown_device, log_threshold, new_port, schedule, manual}; the condition fields belong to the field catalogue of that trigger.
- **PRE-4** Adding a custom action: the connection has at least one write tool that is on (a connection of `core/conn`). A template must not set a forbidden header (`Authorization`, `Cookie`, `Host`, `Proxy-*`, hop-by-hop, `Forwarded`, `X-Forwarded-*`) → 400; `expect` ≤ 200 characters and only in `verify`; `precheck_refuse` ≤ 8 strings × 80 characters and `precheck_expect` ≤ 80 printable ASCII characters.

## Postconditions (after completion)
- **POST-1** When enough people have approved → each item is run through the connection, `status` becomes `executed` or `failed` (a connection that does not answer → `failed`, changing nothing), with `result` and `verified` (`null` when the template has no `expect`). The order of a device item: `precheck` (matching a refusal string → `failed`, writing nothing) → `run` → read back and compare with `expect`; undo: `rollback` → the read-back must not contain `expect`.
- **POST-2** Undo → the item is `rolled_back`, `rolled_back_at` is set; the TTL ends → automatically `rolled_back` (`ttl_removed`).
- **POST-3** Rejected/expired → no device is changed.
- **POST-4** `rules/{id}/manual` runs a rule with the `manual` trigger on the chosen device; still passing every gate.
- **POST-5** `sent_to` records the channels that received the approval request; a channel that is not "ready" (approval not on/no approver yet) does not receive. After the request-creating transaction commits (never inside the write transaction), `response` calls `Notifier.RequestApproval(ctx, ApprovalMessage{RequestID, Title, What ≤ 4 KiB, Risk, InAppOnly, Channels, Expires})` with a 60 s limit, `Channels` = the `approval_channels` that are still ready (empty → nothing is sent), then writes `sent_to` and one log row; a send failure does not cancel the request (it can still be approved in the app). `createRequest` registers `fx.later(queueSend)` (a background send, at most 2 at the same time, `Service.Close` stops it) (every creation path: rules, `RequestProposal`, `Propose`), running after commit and after releasing `s.mu`, with a 60 s budget counted from when it is queued; a **pre-approved** request (`Quiet`) is not sent; with no approval channel ready `notify` is not called; `sent_to` is the label of the channels that had at least one message go out; one log row `request` ("Approval request sent to …", with "still open in the app" on an error, "in the app only, no link" when `InAppOnly`) and the audit `response.request_sent`; `Sweep` deletes token records that expired more than 7 days ago.

- **FORBID-1** Executing any write tool outside the path: request → approval (or INV-5) → the INV-9 gates → execution. - **FORBID-2** A client or the AI sending a command string/template; a free shell string; replacing a placeholder without the type check and escaping (INV-14).
- **FORBID-3** The AI approving by itself; pre-approval for an AI request; a high-risk/irreversible/TTL > 24 hours action in "pre-approved" (INV-5).
- **FORBID-4** Returning the approval token, the approval URL or the whole blocklist token in a list/log/audit response (the preview has `email_links`, admin; it is **not** in the real build).
- **FORBID-5** Preview-only endpoints (`/response/rules/run`, `/response/actions/{id}/chat-decision`, `POST /response/ai/proposals`) exist in the real build: the real build returns 404 `not_found` like an unknown path. **A known limit**: this 404 is returned by the handler, after the authentication and role check of `core/server`, so an unauthenticated person gets 401 and a viewer gets 403 rather than 404 like an unknown path; marking "preview only" in the route table so that the real server does not register the route is the job of `core/server` + `apigen`.
- **FORBID-6** Editing/deleting a `resp_log` row; writing a log row without linking the chain.
- **FORBID-7** Blocking an entry on the never-touch list; blocking while inside the maintenance window; running while the breaker is open.

- **FORBID-9** Storing, logging or returning through the API the output of a device (only one cleaned `Detail` row, INV-22); sending credentials before the SSH host key or TLS pin matches; skipping certificate verification.

A `log_threshold` rule has exactly one condition `count_window` on `signature` (the value = a signature pasted from the digest, one line ≤ 200, comparison only; W 5..1440); when `Counts ≥ N`, `TopAddresses(…, 50)`: **each address that alone sent ≥ N lines** is its own event with `source_ip` = that address (IPv4-mapped turned into IPv4; with a zone or invalid → dropped), `count` = its line count; no address reaching N (lines spread over many addresses or naming no address) or a failed address read (a warning) → one event for the source, `source_ip` empty, `count` = the total. Each (log source, signature, W, N, address or none) gets one event and then stays quiet for W + 5 minutes (that burst is still in `Counts`' sliding window); the id ends with `<address>/` so keys are not prefixes of each other; Logs turned off between `Counts` and `TopAddresses` (`ErrLogsOff`) → no event. The window is rounded out to 5-minute buckets: N lines within at most W + 5 minutes. A packet's source address can be spoofed: blocking is on the line of a completed session. A rule with `match = all`, `{{trigger.signature}}` is not used in actions, the fields `source_device` = the log source name, `source_ip`, `count`, `window`, `threshold`; the condition matches exactly the event of its W and N. The address is never the log-sending machine, the box, the gateway or a decoy (logs CONTRACT `TopAddresses`), and response still applies its own never-block list when building the action. An action with `ip` = `{{trigger.source_ip}}` on an event with no address is refused `tool_unavailable` "Not available: no single address sent at least N lines…" (other triggers: an empty address is still `invalid_target`, INV-10). **`exposure.port.opened` → `new_port`**: exposure only emits `exposure.snapshot.created` (counts), so `cmd/vedette` (`exposurePortsOpened`, exposureports.go; running when `response` is on, reading nothing when `exposure` is off) compares that scan date with the previous scan date of the same target using exposure's public `Snapshots`/`Diff`/`SnapshotOf` and emits one `PortOpenedEvent {target_id, date, ip, port, service, label?, identified?}` for each newly opened port, at most 20 per scan (the remainder: one warning row in the machine log, still on the Exposure page); the first scan date is the baseline, nothing is emitted. `portEvent` checks at the boundary: `target_id` matches the name regex, `date` is `YYYY-MM-DD`, `ip` through `CheckValue(PIP)` and `publishable` (the blocklist's "public" rule: not private, CGNAT, 198.18/15, 6to4…; the IPv4 documentation block is still accepted), `port` 1..65535, `service` one line ≤ 60 through `cleanLine` (a banner); wrong → dropped, with a warning. A pre-approved rule does not run by itself an action whose address/range value covers the event's `ip` (`heldForAuto`, `actsOnAddr`): that is the customer's own public address or an address a name of the customer's points to (shared hosting, a dangling record), so it waits for an approver. The event id is `port:<target>:<date>:<ip>:<port>` so a rescan within the day (replacing the day's snapshot) does not run the rule a second time; `device` is empty (no source yet: a public NAT → device).

## When the module is off (SYS-5)
No `/response/*` routes (including `approve/{token}` and `blocklist/{token}.txt`), no rule jobs, **the customer's firewall that pulls the blocklist gets 404 and stays still with the block it has already loaded** (nothing is removed from a device). A `pending` request can no longer be approved. The `resp_*` data and the `resp_log` chain are kept. An action that was executed but has a TTL does **not** undo itself when the module is off (no job): the UI/notification must list the items still in force before turning it off. The GUI does this in two places: the **Turn off AI response** button of the Response/Settings page and the turn-off dialog in Settings → Modules through the slot `modules.disable` (`web/src/features/response/Leaving.tsx` `InForce`); changing the module turn-off dialog must keep that slot. The Respond button on Incidents/Findings says "the `response` module is off". Connections in Settings → Connections remain and can be edited (they belong to `core`); a decision from chat that `notify` forwards is refused because the module is off.
