# Sensor-passive Contract

> Tier: standard · Story: S-INV-1, S-INV-3, S-LOG-4 (the SPAN metadata extraction part) · Last verified: 2026-11-21 (every sentence checked against the code)

Source of behaviour: `web/src/features/inventory/{contract,SensorsSection}` (`/inventory/sensors*`) and Box network. Box network (`web/src/features/core/{NetworkSection,SpanCard}.tsx`, API in `modules/core/handlers_network.go`, applied through `vedette-host`) does not belong to this module: the module only provides the SPAN status and `SetInterface`.

## Invariants
- **INV-1**: Strictly passive: the sensor sends no frame onto the LAN (no ARP probe, no mDNS/SSDP query, no DHCP). Packet capture is opened read-only; the `tx_packets` counter of the listening card is not changed by Vedette. `TestContract_INV1_NeverTransmits`
- **INV-2**: Packet capture needs only `CAP_NET_RAW`; it opens no listening port (SYS-1 does not apply because nothing is spawned; ARCHITECTURE §6). **Where it runs**: the `capture` half runs **only** in the `sensor` container (`vedette-sensor passive`): host network, `User=<sensor_uid>:<sensor_gid>`, no `UserNS`, `DropCapability=ALL` + only `AddCapability=NET_RAW` (ambient; lab gate, fallback UID 0 + `NET_RAW`), no `NET_ADMIN`, no `NET_BIND_SERVICE`, read-only rootfs, no DB. The `core` half needs no capability (`core` keeps `DropCapability=ALL`). The `vedette-sensor` binary does not link `database/sql`, SQLite, the generated API, `core/store`, `core/audit`, `core/secrets`, `core/pki` or any module beyond the leaf packages in the test's list (`TestBinaryDependencies` of `cmd/vedette-sensor`). `TestContract_INV2_OnlyNetRawNoListener` (MANIFEST)
- **INV-3**: Packet content is not stored. With SPAN only DNS queries (name, qtype), TLS SNI, HTTP Host and IP flows (5-tuple + counts) are extracted. `MetaItem` has exactly the fields `Kind, At, SrcMAC, SrcIP, DstIP, Name, QType, Proto, SrcPort, DstPort, Packets, Bytes, First`, and none of them is a slice/map/pointer; `TestContract_INV3` locks the list and searches for the secret string of the HTTP fixture in every place data is stored. Free-text values are cut at 200 bytes (inventory rejects longer ones); a value that is empty after cutting (a name made only of dots/hyphens) is dropped and counted as `value_empty`, and does not enter the queue. A value that says nothing about the device (`capture.UsefulValue`) is also dropped and counted as `value_meaningless`: a hostname whose first label is only a UUID or 32 hex digits (a macOS mDNS service name, `6a3d1565-….local`; DHCP opt 12 likewise) and a model with no letter at all (TXT `model=0,1,2`); the backend rejects these from a remote sensor (`invalid_item`). `TestIdentifiersAndNumberListsAreNoNameOrModel`, `TestItemsAreCheckedAtTheEdge`. It contains no C0/C1 control characters, no bidi reversal characters, no line/paragraph separators, and no invisible formatting characters (Unicode Cf: zero-width, joiner, BOM, soft hyphen, tag). **The vendor from the OUI table** goes through the same `printable()` check before entering the queue (the table is also cleaned by `make oui`; `TestEveryVendorIsCleanText`).
- **INV-4**: Packets are untrusted data (SYS-6): the DHCP/mDNS/SSDP/LLDP/ARP/DNS/TLS parsers fail closed and have size limits; a malformed packet is dropped and counted, with no panic. Every parser has a `Fuzz*` (ARP, DHCP, DNS/mDNS, SSDP, LLDP, TLS SNI, HTTP Host, pcap reading, the whole pipeline); run locally for ≥ 30 s each, CI 60 s (not wired to CI yet). Dropped packets are counted by reason (`malformed_*`, `excluded`, …).
- **INV-5**: Every observation is written with `source=passive` and `confidence ∈ [0,1]` per protocol (hostname from DHCP/mDNS, vendor from OUI, model from SSDP…), sent through `inventory.RecordObservation`; it never writes `inv_*` directly.
- **INV-6**: A new MAC → an asset with `approved=false` (S-INV-3). Observations about the box itself do not create an asset duplicating the "This box" device. After the split, `capture` takes the box's own MAC/IP from the real card in the host's network namespace (the `sensor` container runs on the host network), not from `core` (the `core` container only sees `vedette-int`). In `core`, an entry about the box is rejected (`refused`) according to the host's cards (`Host.HostCards`); a host that is configured but cannot supply the list → the batch is not applied (503 `not_ready`, the sensor resends the whole batch, without splitting). **No host (container-only build)**: the box's card is the card in the passive heartbeat **younger than 90 s** (the same `online` rule), never the card of the `core` container itself; no such heartbeat → the batch is not applied (503 `not_ready`). `TestNoHostTheBoxIsWhatTheFreshHeartbeatReports`, `TestItemsAboutTheBoxAreRefused`.
- **INV-7**: Exclusion filters (ranges, machines, ports) are applied before extraction; excluded traffic leaves no row. They also apply to addresses inside DHCP (`ciaddr`, `yiaddr`, option 50). **Known gap**: a DHCP DISCOVER/REQUEST with no `ciaddr` and no option 50 has no address to which an exclusion rule can apply; the MAC (already matched to the Ethernet source MAC) and the hostname (option 12) are still recorded, because there is nothing to exclude by address. To remove a machine from every trace, use filtering by port/traffic on the SPAN, not an IP rule. A non-first IP fragment has no port: when a port rule exists it is skipped (fail closed, counted as `fragment_skipped`). **Limit**: LLDP carries no IP address, so IP/range/port rules cannot apply to LLDP (the filter model does not have MAC yet).
- **INV-8**: The sensor only calls out to `core`; `core` never calls into the sensor. Per `docs/specs/sensor-protocol.md`: the `capture` half talks to `core` **only** through the sensor protocol, `passive` role (mTLS, URI SAN `vedette:sensor:passive`): `GET /sensor/v1/config` (long-poll, ETag), `POST /sensor/v1/observations` (a batch idempotent by `(epoch, seq)`, `rejected[]` is not retried), `POST /sensor/v1/heartbeat` (30 s), `POST /sensor/v1/metadata` (see Configuration); any other route → `403 forbidden_route`; module off → `409 module_off`, stop at once and drop the queue (SYS-5). There is no in-process path in production (`core` has no `capture` job); tests use a real client over loopback mTLS.
- **INV-9**: `PATCH /inventory/sensors/{id}`: `interface` must be ∈ `Sensor.interfaces` (400 `bad_interface`; `Sensor.interfaces` are the cards in the newest passive heartbeat, and with no heartbeat yet → `bad_interface`), `span` boolean; a card marked SPAN has no IP. A warning "no mirrored traffic seen" when only the box's own MAC is seen. **Default card**: `sp_sensor.interface` NULL (nobody has chosen, or SPAN was turned off) → the sensor listens on `Host.ManagementCard` (the management card: configured, otherwise the default route; never loopback or `vedette0`); with no host (container-only) → the only wired card that is up and has a global IPv4 in the newest heartbeat, and if there is no wired card then the only such card, with two or more candidates → it does not listen. The default is **not stored**, it is computed at every `GET /config` and `GET /inventory/sensors` (`interface` = the card being listened on); a stored choice always wins; the name goes through `sensorlink.ValidIfaceName` before being sent. `Sensor.chosen` = `sp_sensor.interface` has a card (a stored choice), false when `interface` is the default or null; only an explicit choice overrides the default, and the default is never stored in its place. A link that is not a card (`sensorlink.VirtualIfaceName`: loopback, container bridges `docker0`/`br-…`/`podman0`, veth, VPN, VLAN, `vedette0`; the same rule as `cardsOf` of Box network) is never the default, is not in `Sensor.interfaces`, and `SetInterface` without a host rejects it (`bad_interface`): the sensor has already removed them from the heartbeat (`osInterfaces`), and core checks again because the heartbeat is untrusted (SYS-6). Known limit: a machine whose addresses are on `br0`/`bond0` has no listed card with an address; choose the physical port underneath, without SPAN. `TestDefaultCardIsTheManagementCard`, `TestWiringSensorDefaultCardIsTheDefaultRouteCard`.
- **INV-10**: Fingerbank (optional): off by default, BYOK key, every call is listed in PRIVACY.md. Not built yet; the embedded OUI table is not Fingerbank and makes no outbound call.

## Implementation
- **Packet source**: `Source{Next, Close}` has no write/send function. `FileSource` reads pcap/pcapng (pure Go, macOS development and every test); `OpenLive` (`afpacket_linux.go`) is a receive-only AF_PACKET socket, promiscuous (the card's receive filter, nothing transmitted), needing only CAP_NET_RAW. Outside Linux: `ErrNoLiveCapture`.
- **Flood limits (SYS-6)**, `book.go`. Every operation of `deviceBook` is O(1) under the lock, with no map scan on the hot path (it runs in `Engine.Handle`, the packet-capture goroutine). The book belongs to `Service` and survives every rebuild of the Engine (a settings change, reopening a card after an error); it lives in memory, so after a process restart it is empty (loading from the store would need a new interface in `core/observe`).
  - **First frame**: a FIFO ring of fixed capacity **20,000 slots** + a MAC→slot map. Inserting into a full ring **pushes the oldest first frame out and never refuses**. A MAC is "new" only when it is heard again in a second frame **≥ 2 seconds** after the first frame while the first frame is still in the ring (a random MAC seen in only one frame creates nothing; counted as `new_macs_unconfirmed`; a time that goes backwards does not count as a second frame). **TTL of the first frame: 2 hours** (a device that speaks in bursts tens of minutes apart, such as SSDP NOTIFY max-age 1800, DHCP renewal, mDNS announce, is still confirmed). **Bound for a real device**: a real device is confirmed as long as **fewer than 20,000 other new MACs** arrive between its two frames (at most 2 hours apart); a flooder needs > 20,000 different MACs between each real device's two frames to block it, and still cannot create any device (see the budget below).
  - **Devices already reported**: an LRU (`container/list` + map) of at most **50,000**; `admit` moves an entry to the front, and when full it drops the entry **not seen for the longest time**. A dropped device that comes back is a new device (two-frame rule + budget). A device already reported always passes, even when both budgets are exhausted and the ring is full.
  - **New-MAC budget**: **60 per minute and 200 per hour** (the window opens at the first use, and only forward time resets it; a time going backwards does not reset it); beyond that, only `new_macs_dropped` is counted. A flood can block new real devices for at most until the end of that hour. The GUI does not show "new-device budget exhausted" yet (needs a story).
  - **Value budget per MAC**: for each MAC already reported and each field, at most **4 new values per hour**; repeating a value already let through within the window is not a new value; beyond that it is dropped and counted as `values_dropped`. Values are stored as keyed hashes (8 bytes), so 50,000 devices x 6 fields is still only a few MB. The second layer is in inventory: each (device, field, source) keeps at most 32 `inv_observation` rows, and `Record` deletes old rows in the same transaction (inventory INV-16), which protects even when the source is another sensor.
  - **Vendor still owed**: the "vendor still owed" flag lives in the book alongside the device entry: it is set when the device is first reported, and cleared when the vendor row has reached inventory, was rejected outright by inventory, or the MAC has no vendor. A capture error midway or a failed final flush does not lose the vendor: the next frame of that MAC, even through a new Engine, queues the vendor row again.
  - The counters `new_macs_unconfirmed`, `new_macs_dropped`, `values_dropped` are part of the dropped-packet counters. A non-unicast IP (broadcast, multicast, loopback, 0.0.0.0/8, 240.0.0.0/4) never reaches the sink (the observation is kept, the IP dropped); DHCP: the client's `chaddr` must equal the Ethernet source MAC, and an ACK must be sent to that MAC or to broadcast; `other_macs` counts only unicast frames between two machines that are not the box (replies to the box and broadcast are not counted, INV-9). The dropped-packet counters are logged at INFO periodically (5 minutes, only when they change); `contract.ts` has no field to show them yet.
- **Confidence scale** (INV-5, `engine.go`): MAC↔IP from ARP/DHCP ACK/LLDP 0.9 · LLDP name 0.7 · DHCP opt 12 name and mDNS name (an A record with exactly the source IP) 0.6 · kind from LLDP capabilities 0.6 (Telephone → `iot`, read before Bridge because an IP phone bridges the PC port; AP → ap; Bridge → switch; Router → router) · OS from DHCP option 60 (vendor class) of a known client 0.4 (`dhcpOS`: `MSFT …` → Microsoft Windows, `android-dhcp-N` → Android N, dhcpcd → Linux/BSD, `udhcp` → Linux (BusyBox); no vendor, no version) · model from SSDP SERVER (only when the header matches a known pattern that names the device: AVM FRITZ! with the name repeated exactly twice, Sonos `(ZP…)`, the Philips Hue bridge `IpBridge`; ≤ 200 bytes, model ≤ 40; any other header, such as `Linux/5.4 UPnP/1.0 MiniUPnPd/2.2`, is UPnP software and not a device, becomes no value, and is never dumped verbatim; `ssdp.go`), mDNS TXT `model`/`md` 0.5 · model and OS read from the LLDP system description 0.5, only when the description matches a known vendor pattern (Juniper, Cisco IOS/IOS XE, HP/Aruba, MikroTik, lldpd on Linux; `sysdesc.go`; `ParseSysDesc` is the same function used for the SNMP sysDescr of sensor-active) or is a short model token (≤ 40 characters, no whitespace, containing a digit); lldpd only when the distribution name is in the known list; IOS XE only for the OS; any other description becomes no value and is never dumped verbatim · kind from the mDNS printer service / SSDP InternetGatewayDevice 0.5 · mDNS iot service 0.3. Vendor from the IEEE OUI table (`content/oui`) 0.4, once per new MAC (owed until it reaches inventory, see above); a locally administered (random) MAC and a group MAC have no vendor.
- **SPAN extraction** (`MetaItem`, closed type): DNS (name + qtype), TLS SNI, HTTP Host (port dropped), IPv4 5-tuple flows + counts (accumulated over 60 s). Enabled by `Extract`; the box itself (the MAC/IP of every card) creates no asset and no metadata, including traffic sent to the box (INV-6).
- **Limits**: each flush has at most 5,000 observations, 20,000 metadata items, 20,000 flows; an overflow is counted, never silent. A batch has ≤ 500 elements. A duplicate observation is resent only after 15 minutes.
- **Capture loop** (`capture.Runner`) runs inside `vedette-sensor passive`: only when the module is on; module off → `409 module_off` stops it at once with no final batch flush. `SetInterface` wakes the `config` long-poll to change the card immediately (see "Split in two").
- **API**: `GET /inventory/sensors` and `PATCH /inventory/sensors/{id}`. `status`: `online` (heartbeat within 90 s), `offline` (has reported before, then silent for 90 s), `never_connected` (never had a heartbeat: `last_seen` is empty; not called "lost contact"). `starting`: not online while `Config.Starting()` says the box is still starting the sensor container (cmd/vedette `startWatch`: the OnGuard start is still being retried, for at most 10 minutes, or the host confirmed the start less than 3 minutes ago); with `Starting` nil (container-only build, dev) it is never `starting`. `capture_error`: the reason from the newest heartbeat, **only when `online`**, `null` when capturing, with no card, or not online; the GUI shows "Reporting, not capturing" together with the reason (`TestCaptureErrorShowsWhileOnline`). `PATCH` `{interface, span}` serves only the container-only build (any card in a fresh heartbeat, with an address or not, SPAN or not; `null` → back to the default card): `Service.ChooseCard` calls `SetInterface` when `Host.HostCards` returns `ok=false` without an error; with a host (or a configured host that gives no list) → `ErrUseBoxNetwork` → 409 `set_in_box_network`, nothing changes (on the appliance, Box network calls `SetInterface` through `PUT /core/network/span`). `ErrBadInterface` → 400 `bad_interface` with `SetInterface`'s reason turned into a sentence (capital first letter, final period); `ErrNotFound` → 404 `not_found`. Returns `Sensor` as GET does. `TestPatchSensorChoosesTheSpanCardOnlyWithoutAHost`, `TestSensorsHandler`, `TestDefaultCardIsTheManagementCard`, `TestWiringContainerOnlyAdminChoosesAnAddressedCard` (cmd/vedette).
- **SPAN verdict**: `off` (SPAN off), `no_link` (the card lost its cable), `no_traffic` (no packets in 30 s or no capture), `own_only` (packets, but no MAC other than the box in 5 minutes), `ok`.

## Split in two (sensor protocol)
- **The `capture` half** (`modules/sensor-passive/capture`, running in the `sensor` container): `Source`, `Engine`, the device book (`book.go`), flushing and sending through `Link{Config, PostObservations, PassiveHeartbeat}`; it does **not** import `core/store` or any package under `core/` that touches the DB. The book's budgets (60/200 new MACs, 4 values per MAC per field per hour) still run here as the first layer. The queue is in memory only, with no WAL: a sensor restart loses at most one flush (≤ 5 s) and a new `epoch` begins.
- **The `core` half** (`modules/sensor-passive`, inside `core`): the `sp_*` tables, `Config`, `Observations`, `PassiveHeartbeat`, `Metadata`, `Status`, `SetInterface`, and the handlers of the four `passive` role routes. `SpanStats()` and `Status()` come from the **heartbeat** (they no longer read an in-process `Engine`): `online` when there is a heartbeat within 90 s, with `last_seen`/`version`/`devices_seen`/`interfaces` from the newest heartbeat; the SPAN verdict is computed in `core` (`off`, `no_link`, `no_traffic`, `own_only`, `ok`; a sensor that is `offline` → `no_traffic`).
- **Budgets on the `core` side**: the `observations` handler applies again at most 60 new MACs/minute and 200/hour, at most 4 new values per (MAC, field) per hour, with in-memory maps by MAC; an entry over the limit → `rejected[]` with `budget_exhausted` (a compromised sensor can bypass the first layer but not this one). `core` sets `source=passive` by role (a body with `source` → `400`) and clamps `confidence` to the cap of the passive scale for each field. The third layer is still inventory's cap of 32 rows (inventory INV-16).
- **Configuration** to the sensor: `{interface, span, extract, filters}` through the `config` long-poll; an unreadable filter → `interface: ""` (no capture). SPAN metadata goes through `POST /sensor/v1/metadata` (sensor-protocol §6.7): `capture.LinkMetadata` reduces each item to `{kind, at, src, dest}` (no port, no counter, no resolver address; a flow only in the direction in which the conversation started — SYN without ACK; SYN-ACK/RST is a reply — and only when the destination is a public address, so a LAN server answering a scan does not become a "connection to" the scanner), with each triple sent once per 10 minutes; the capture loop only queues (≤ 10,000 items), and a separate goroutine `LinkMetadata.Run` sends, spaced ≥ 2.5 s apart, following `Retry-After`; `Engine.Pending` counts only observations (metadata does not trigger an early flush); a failure is counted as `metadata_failed`. The `core` half (`Service.Metadata`, `sensorlink.MetadataReceiver`) **stores nothing**: it hands the batch to `Config.Mirror` (`MirrorMatcher`; `cmd/vedette` wires it to `logs.MatchMirror`), module off → `409 module_off`, matcher failure → `503 store_busy`.
- **Tests**: pcap replay → `capture` → real client → handler over loopback mTLS → temporary SQLite store; every existing `TestContract_*` runs on the split build.

## Code of the two halves
Code: `capture/` (the sensor half: `Runner`, `Engine`, device book, analysers, `Source`), `backend.go` (the `core` half: `Config`, `Observations`, `PassiveHeartbeat`), `metadata.go` (`Metadata`), `local.go` (`Service.Run`: in-process packet capture, used only by the test suite), `cmd/vedette-sensor passive`. Details:
- **API of the `capture` half**: `capture.New(Config{Link, Interfaces, Open, Meta, Clock, Log, Version, pacing…})` then `Runner.Run(ctx)`; `Link` is the three functions `Config(ctx, etag, wait)`, `PostObservations(ctx, req)` (one attempt, no backoff), `PassiveHeartbeat(ctx, hb)`: `*sensorlink.Client` is the remote version. `Run` sends a heartbeat immediately at startup and every 30 s, **even when no card has been chosen yet** (the admin chooses a card from the heartbeat's list), asks `config` with a long-poll, and follows it: `interface ""` stops capture at once with no final batch flush; a different card or filter flushes one last time and then reopens; a filter that does not compile means no capture and counts `filters_invalid`; `409 module_off` from any call stops at once, drops the queue, stops the heartbeat, and asks `config` again every 60 s. The queue is in memory only, at most 5,000 observations: when full it drops the **oldest** and counts `observations_dropped`.
- **API of the `core` half**: `Service.Config(ctx, wait, ifNoneMatch)` (long-poll by ETag; `SetInterface` and `ConfigChanged()` wake it; an unreadable filter gives `interface ""`), `Service.Observations(ctx, req)`, `Service.PassiveHeartbeat(ctx, hb)`, `Service.Drops()`; `Status`, `SpanStats` and `SetInterface` rely only on the heartbeat. PRE-3 is `Observations` (together with POST-3).
- **`Observations`** checks each item (a MAC in protocol form, not a group address or all zeros; a unicast IPv4 IP; has a MAC or an IP; `field` in `observe.Field`; `value` 1…200 bytes and clean per INV-3; `confidence` in [0,1]; `seen_at` from 24 hours before to 5 minutes after): wrong ones go to `rejected[]` with `invalid_item` or `out_of_window`. Then the budget (60 new MACs/minute, 200/hour, 4 new values per MAC and field per hour; `capture.FloodBudget`): beyond it → `budget_exhausted`, logged once per minute. Then inventory writes; an item it rejects at the edge is `refused`, and the rest are written in the same call. The budget is **charged first, written after**: a store failure gives `503 store_busy`, no item is written, no budget is spent, and `seq` is not stored. `confidence` is clamped to the field's cap (`capture.MaxConfidence`). A batch whose `seq` has been seen (in that epoch) gets `200` and is not written again. Core keeps the two newest epochs.
- **Heartbeat** of the `passive` role: `drops` carries the 35 keys of `sensorlink.DropKeys` (an unknown key is ignored and logged once; at most 64 unknown names are remembered and logged); `capture_error` (proto 4) is the reason capture is not running, in the closed set `sensorlink.CaptureErrors` (`no_permission`, `no_interface`, `filters_invalid`, `capture_failed`; an unknown name of the right form → `capture_failed`, a wrong form → 400): the `capture` half sets it in `captureLoop` (an error opening the card or a broken session; `errors.Is(err, os.ErrPermission)` → `no_permission`, `capture.ErrNoInterface` → `no_interface`) and clears it when the card opens or the session ends; `core` keeps it in memory with the newest heartbeat; `core` keeps the list of cards (in memory) and writes `last_seen`, `version`, `devices_seen` and the SPAN measurements into `sp_sensor`/`sp_span_stat`. `online` means a heartbeat within 90 s; the SPAN verdict is computed in `core` from those measurements (`off`, then `no_traffic` if the sensor is `offline`, `no_link`, `no_traffic`, `own_only`, `ok`).
- **`SetInterface`** checks the card against the **host's cards** (`Host.HostCards`), not the heartbeat: it can be chosen before the first beat and while the module is off (the choice is stored; capture uses it when the module is on); a SPAN card has no IPv4 in the host's list. The heartbeat is for display only (`interfaces`). A heartbeat naming a different card does not change the configuration. **The only exception (container-only build)**: when core runs without `-host-socket` (`HostCards` returns `ok=false`; a configured host that cannot supply the list is an error, fail closed), the card must be in the newest passive heartbeat's list **younger than 90 s** (already blocked and checked by `sensorlink`; the name goes through `ValidIfaceName`), and a SPAN card has no IPv4 in that list; no heartbeat, or a heartbeat 90 s or older → `bad_interface` with the sentence "the sensor has not reported its network cards in the last 90 seconds"; `iface=""` needs no heartbeat. `TestNoHostTheCardIsChosenAgainstTheHeartbeat`, `TestTheCardIsChosenAgainstTheHostNotTheSensor`. The HTTP path when there is no host: `PATCH /inventory/sensors/{id}` (GUI Devices › Setup › Sensor › Configure); `PUT /core/network/span` still returns 409 `not_appliance`.
- **Abuse protection**: an entry carrying the box's MAC/IP (per the host) is `refused`, and `modules/inventory` does not let a source other than `agent` set the MAC of `is_box`, move the IP of a `manual`/`is_box` device, or attach an observation to the box; a `mac` row must have `value == mac`; `kind` includes only the 5 kinds the parsers emit, each with its own cap; 4 new IPs per MAC per hour (both `capture` and `FloodBudget`); the duplicate filter of 15 minutes and the cap of 6,000 items/minute in `core`; splitting a batch only on `503 store_busy` with a heartbeat that just succeeded (never on `503 not_ready`); `batchMax` returns to 0 after each delivery; the vendor debt is kept on `budget_exhausted`; `core` checks the module switch under the lock, creates the sensor row once, and loads the budget from inventory; an unknown `drops` key is ignored and logged once; the heartbeat rejects a duplicated card name; `vedette-sensor passive` drops virtual links.
- **Tests** (none captures real packets, they only replay fixtures): the `TestContract_*` suite runs twice through `TestSuiteThroughTheLink` (in-process, and at the far end of the loopback mTLS link with `VEDETTE_SP_CAPTURE=remote`), and the remote version must pass exactly the in-process version's tests; `backend_test.go` (roles, budgets, clamping, item checks, epoch, fake cards, the view from the heartbeat, long-poll, 503 retry, poison-item hunting, `module_off`, filters); `capture/*_test.go` (poison, retry, queue, `Runner`); `FuzzCheckItem`, `FuzzFloodBudget`, and the older analyser fuzzers.
- **Wiring into `cmd/vedette`**: there is no `capture` job; the `core` half goes through `sensorBackend` on the `-sensor-listen` listener. `Service.Run`/`local.go` and the pacing parameters of `Config` remain in the module only because the `TestContract_*` suite uses them as a harness; `Host.Interfaces` is only for `Service.Run`; `SetInterface` and rejecting entries about the box use `Host.HostCards`. `netHost.Interfaces` of `cmd/vedette` never reads the cards of the `core` container.

## Preconditions / Postconditions
- **PRE-1** (`capture.Runner.Run(ctx)` in `vedette-sensor passive`, the card from the `config` long-poll; the card chosen by `SetInterface`): the card exists and `CAP_NET_RAW` is held. **POST-1**: capturing; `Sensor.status=online`, `last_seen` is updated by the heartbeat (`POST /sensor/v1/heartbeat`, 30 s) and the sensor shows `offline` after 90 s without a heartbeat. When opening the card fails it retries with a pause of 5 s, 10 s … up to 10 minutes; a session that had received frames before failing restarts its pause from 5 s.
- **PRE-2** (`SetInterface(id, iface, span)`): `admin`. **POST-2**: capture switches to the new card within the same request; `core_audit` records it.
- **PRE-3** (`Service.Observations`, see "Code of the two halves"): `seq` increases; every observation has `source=passive`. One `seq` sequence per sensor is shared by observation batches and metadata batches (as in sensor-protocol §5.2: one sequence per (sensor, epoch)); `sp_seq` keeps the highest number. When inventory rejects one item at the edge (`observe.ErrRejected{Index}`, wrapping `ErrInvalid`), the capture loop drops exactly that item (counted as `observation_rejected`; the rejected item is still held by the duplicate filter for 15 minutes so it is not resent at once) and sends the rest: one bad item does not blind the whole batch (sensor-protocol §5.5), and there is not one write transaction per item. Another error (store busy, I/O) says nothing about the items: the whole batch goes back to the Engine's queue and is resent whole after a pause that doubles on each failure (at most 1 minute); the final flush (end of records, settings change) tries only once and then forgets, counting `observation_failed`. A batch that fails 3 times in a row is split in half and each half tried (binary search); a lone item that still makes the batch fail while the store still accepts writes is dropped and counted as `observation_failed`, so the queue is never blocked forever. A flush interrupted by shutdown (ctx cancelled) is not a store failure and does not raise the failure counter or the pause. `ensureSensor` runs once per `deliver`, not once per retry. A batch that inventory has accepted is never written a second time, even when saving the batch number fails (`Observations` logs a Warn and still returns the ack). **POST-3**: resending the same `seq` does not create a second observation. `Observations` is called by the `POST /sensor/v1/observations` handler with the `epoch` of the sensor process (32 hex); `core` keeps the 2 newest epochs per sensor; a rejected item is returned in `rejected[]` (`invalid_item`, `out_of_window`, `budget_exhausted`, `refused`) and is never resent.
- **PRE-4** (`SpanStats()`): none. **POST-4**: `{pps, other_macs, last_packet_at}` are really measured, not inferred. The measurements are sent by `capture` in the heartbeat, `core` does not measure them itself; with no heartbeat in 90 s → verdict `no_traffic`.

## Forbidden
- **FORBID-1**: Sending any packet onto the network.
- **FORBID-2**: Storing payloads, cookies, HTTP/TLS content.
- **FORBID-3**: Writing `inv_*` directly.
- **FORBID-4**: Running Zeek/Suricata or another IDS inside this module. Intrusion detection belongs to the `ids` module (IPS/IDS events in received firewall logs); SPAN metadata goes only to the `logs` bad-address matching (logs POST-2c).
- **FORBID-5**: Sending device MACs/fingerprints out when Fingerbank is off.

## Dependencies

- **DEPENDED ON BY**: `logs` (receives SPAN metadata for IOC matching, S-LOG-4; group B), `honeypot` (no), SPA Devices › Setup › Sensor.

## Tables owned (`sp_`)
`sp_sensor` (id, name, interface, span, version, last_seen, devices_seen), `sp_span_stat` (SPAN measurements), `sp_seq` (seq received). The row key is `SensorID` (a constant); `name` is **for display only** (`Sensor.name` of GET), not an identity: the sensor link authenticates with the `passive` role's mTLS (`core/sensorlink`), not by name. `Config.Name` is a function asked again on every `ensureSensor`, so it must be cheap and non-blocking (#471: `core` passes the box name reported by vedette-host, read from memory `boxHostName.Cached`, `cmd/vedette/boxname.go`); a name different from the last write makes the same row be rewritten with the new name, changing nothing else; `nil` → the machine name of the process itself, empty → `vedette` (`TestSensorsHandler`).

## Behaviour when off
No packet capture, no job (the `passive` role routes return `409 module_off`, the sensor stops at once and drops its queue, the host stops the `sensor` container); **the `sensor` container runs exactly when the module is on (SYS-5)**, and only after the first installation (like `scan`: see `sensor-active/CONTRACT.md`): when `core` starts and after each enable, `modreg.OnGuard` calls `container.start` of `sensor` (retried with backoff until the host confirms); when it starts and after each disable, `OffGuard` calls `container.stop` with `persist` (the unit loses `[Install]` and a reboot does not bring it up; enabling again makes `container.start` set `[Install]` back); each function checks the module again under the lock before touching the host (`cmd/vedette/modulecontainer.go`; `TestModuleContainer*`, `TestOnGuard*`); before sending a write command, the function reads `GET /v1/state/containers` and skips when not needed (already running or coming up with `[Install]`, regardless of health; or already stopped and without `[Install]`); `container.start` goes out only when the host says clearly that the unit is wrong (stopped/broken, `[Install]` lost, not a host unit), and a WARN log (rate-limited) records which field caused the write; if the read fails (`rate_limited`, the host does not answer, the read times out) or `unit_state` = `unknown`, that is an error for the guard to read again later, not a write — starting a container that is running but that the host sees as not yet healthy will restart it, and `sensor` is unhealthy when `core` (which receives the heartbeat) is restarting during an update; the wait is bounded: when the state cannot be read continuously for 2 minutes (read errors, the host does not list the service, `unknown` forever) counted from the first time, `container.start` is still sent (WARN `state unreadable for …`), and one good read resets it; on the disable side, an unreadable state still sends the stop command; after a reboot when the stop was not yet confirmed, the unit still has `[Install]` so the container comes up until `core` stops it a few seconds later, with no route/job/port open (`core` returns `409 module_off`): do not "fix" this by removing `[Install]`; with no host (`-host-socket` empty) there is nothing to follow; new devices are found only by active scan/agent/manual entry; the passive "unknown device" S-INV-3 and S-LOG-4 (IOC matching from SPAN) are lost. The device list and old observations are kept.
