| D-524 | **osquery reports Windows's monthly update revision (UBR) and the device shows it ("Microsoft Windows 11 Pro 10.0.22631.4460"); using it in KEV matching is a follow-up owned by the findings owner (TUNE-5, tool-tuning plan §5; S-INV-4; amends D-169 (7) schedule; supervisor's split after review round 1, 2026-11-14).** (1) **Where the UBR comes from.** Not a new `registry` query: osquery 5.12 (the pinned 5.12.1) already reads `HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows NT\CurrentVersion\UBR` itself into `os_version.revision`, a Windows-only column. The schedule gains one Windows-only, read-only snapshot query `os_revision` = `SELECT name, version, revision, arch FROM os_version;` (3600 s, `platform: windows`). It is a query of its own because the column does not exist on Linux (adding it to `os_version` would fail that query there) and an osquery older than 5.12 then fails this query alone. D-169 (1) stands unchanged: snapshot-only, read-only tables, no `registry`, `exec`, `file`, `hash` or `curl` table. (2) **Intake.** The row is untrusted (INV-7): `version` must be `10.0.<5-digit build>` (Windows 10, 11, Server 2016 and later), `revision` a positive integer 1..999999 as osquery writes it (no sign, no leading zero; 0 or empty would place the machine at the first build of its release), the name 1..200 characters; anything else is dropped and the stored value stays. The node keeps the last good one (`intake_osquery_nodes.win_name`, `win_version` "10.0.22631.4460", `win_target` x64/x86/arm64/"" from WMI's OSArchitecture; migration 0006) because osquery's splay sends queries of one interval in different requests. The device OS reads the full version on an `os_version` report of the same build, and on the revision's own report (a feature update not yet reported keeps "… build 26100"). (3) **First report (D-503).** `os_revision` is an answer of its own (`reported` gains `os_revision`): within the first hour it is asked every minute until a usable revision arrived, even when `os_version` came first (review M3); with `--config_refresh=300` the full version shows within minutes of enrolment. A Windows osquery older than 5.12 is asked every minute for that hour only. (4) **Not in this decision: matching.** The UBR is collected and shown; KEV matching does not read it yet, so matching is exactly as before (Windows-OS entries "cannot check" unless a person adds Windows with its version, D-504). A first design (a Windows software row with the release's NVD CPE and a findings rule for entries naming only other releases, commit 662e9736) was reviewed (`tune5-review1.md`) and split off: the findings owner designs it, with the review as input — suppress only when the device's build is above every listed release's build (out-of-service releases are missing from new entries, H1); sibling releases on one build line (25H2/24H2, 23H2/22H2, 10 22H2/21H2) evaluated by revision, and only for releases NVD has named (H2); NVD product names checked against real data; Wazuh `os.arch` and target_hw (M1); feature upgrades and their open findings (M2); hand-added "Windows" rows next to the agent's (M4); target-only No not a proof (L1).
