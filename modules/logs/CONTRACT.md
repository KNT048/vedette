# Logs Contract

> Tier: optional (off by default) · Story: S-LOG-1, S-LOG-2, S-LOG-3, S-LOG-4 · Last verified: 2026-11-21 (every sentence checked against the code)
> Source of the actual behaviour: `web/src/features/logs/{contract,types,mocks,kinds,catalog}.ts`.

## Invariants (always true)
- **INV-1** Logs and metadata are untrusted data (SYS-6): the parser fails closed (a line that cannot be parsed is only stored raw, the whole batch is not dropped), there are limits on line/batch size, and bad lines are counted; line content is never interpreted as a command. Tests: parser fuzz per `SourceKind` (`FuzzSanitizeLine`, `listen` Fuzz*) and `FuzzSignature` (every bundled profile and the shared pattern finder).
- **INV-2** The logs module does not run an IDS/IPS and does not read IPS events: intrusion detection belongs to the `ids` module, which receives every stored batch of lines through `Config.Received` (POST-6). The sources of logs are only (1) SPAN metadata: DNS queries, TLS SNI, HTTP Host, IP flows; no payload is stored; (2) syslog. Values of `seen_via`: `span_dns | span_sni | span_http | span_flow | syslog:<device name>`.
- **INV-3** Log source: `name` matches `^[a-zA-Z0-9][a-zA-Z0-9_.-]{0,63}$`; `sender_ip` is a valid IPv4; `proto` ∈ {udp,tcp,tls}; `port` 1..65535 (default 514, tls 6514); `kind` belongs to `KIND_IDS` (a catalogue of 48 kinds, each with a configuration checked against the vendor's documentation). `state` ∈ {receiving, silent, never}; `asset_id` is the device in the inventory that has that address: an IP in its list, or an SNMP read address typed by the user for the device (`asset_via` = `snmp_read` when it is not an IP in the list; the default read address, that is the IP at save time, does not count). A read address typed by the user wins over a device found by a scan at the same address (the same machine seen twice); when a device that the user approved is there, both have the address: `asset_id`/`asset_name` = `null` and `asset_matches` lists both (never picking one at random). `asset_id` = `null` and `asset_matches` empty if no device has it.
- **INV-4** Retention (`retention_days`) ∈ {7, 30, 90, 180}; default 30. Expired → events are deleted. Deleting a source does **not** delete the logs already received (kept until retention ends).
- **INV-4b** `GET /logs/sources` additionally returns `logs_bytes` (the disk size of `logs.db` + WAL, `store.DB.Size`, two `stat` calls, no row scan) and `disk_free_bytes` (the free space of the file system holding the box's data directory, `store.DiskFree`, shared with exposure); each number is `null` when it cannot be read, and the page still answers. Test: `TestSourcesCarryLogsSizeAndFreeDisk`.
- **INV-5** `GET /logs/events` returns at most the 200 newest rows, `total` is the real number of matches; `q` ≤ 200 characters; window ∈ {1h, 24h, 7d} and not beyond `retention_days`. Each returned row has `host`, `app` (null when the header does not say) and `message`: the line read through `listen.ParseSyslog` when listing (RFC 5424 or 3164; with no header `message` is the whole line); a BSD line with no host name (`<34>Nov 11 08:30:15 sshd[1]: hi`: the parser reads the tag as the host name because RFC 3164 requires a host name) shows `app` as that tag, `host` null, `message` the part after it; `host`/`app` drop control and format characters (bidi); `line` is still the stored line, which search and evidence use. No extra column is stored.
- **INV-6** Digest: baseline = 7 days (`baseline_days = 7`); grouped by (signature, source, destination) in the count table `logs_signature_daily`, with no line scan. A signature is a short normalised text standing for one kind of line: a profile by device kind (JSON data in `data/profiles`: FortiGate, Sophos, Palo Alto, Cisco ASA, MikroTik, SonicWall, pfSense/OPNsense (`filterlog`), Linux/UniFi (`iptables`), Windows Security by event id) or the shared pattern finder that masks IPs, numbers, hex for every other kind and for lines the profile does not recognise. "new" = a signature first seen for the source **after** the source's 24-hour start-up and within the last 24 hours (not in the baseline days); "spike" = a 24-hour estimate ≥ max(20, 5 × `baseline_per_day`). Each source has a **24-hour start-up** counted from its first line: no "new", no spike, no event; a signature seen during start-up belongs to the baseline. Clean install: an empty digest (`new`, `spikes`, `bad_connections` = []). **`history_days`**: the number of whole days that have logs counted from the first line of the longest-listening source (or its last kind/sender-IP change), by the signature counter (`sourceRow.Started`, set in `anomalies`), at most `baseline_days`; below that the Logs page says it is learning what is normal ("Learning what is normal: N of 7 days"), and does not say "logs look normal". Tests: `TestDigestSaysHowManyDaysOfLogsItHas`, `TestDigestWithItemsOverHTTP`. `box.ip` = `null` when the LAN range has not been declared **or** the box has no address in that range (a container does not see the host's LAN address); the page tells the two cases apart through `box.lan`. The details of the computation are in the section "Signatures, baseline, digest".
- **INV-7b** `GET /logs/bad-connections` (`IocPairs`, `iocpairs.go`): the hits within the window `24h` or `7d` (anything else → 400 `bad_window`) grouped by SQL by (`src_ip`, `dest_kind`, the listed name = `coalesce(nullif(listed_as, ''), dest)`) on `logs_ioc_hits`, like the digest (several subdomains of one listed name are one row; the row carries the subdomain when there is only one, the listed name when there are several): `hits`, `first_seen`/`last_seen`, the union of `feeds` and `seen_via`, the highest `confidence`, the number of `blocked` hits, `other_devices` (a window function: other source addresses that have hits to the same listed name). The device is named at read time (like INV-7). Search `q` (≤ 200 characters, case-insensitive) on the device address and name, the destination, `listed_as`, the feed name, runs on every row before sorting (`sort=last`: the newest last hit first, `hits`: the most hits first) and paging (`offset`, `limit` ≤ `IocPairsPageMax` = 200); the device name lives in inventory so the filtering runs in Go after grouping. Feeds off → empty (PRE-3). `TestIocPairs*` (including `TestIocPairsGroupByListedName`).
- **INV-7** `IocHit`: `confidence` ∈ [0,1] (the highest among the feeds that list the destination); `dest_kind` ∈ {ip, domain}; `feeds` is the names of the feeds that list the destination when the line arrived (at most 8); `seen_via` ∈ `syslog:<source name>` or `span_dns|span_sni|span_http|span_flow` (from `MatchMirror`). The stored row `logs_ioc_hits = { id, ts, src_ip, dest, dest_kind, seen_via, feeds, confidence, source_id, blocked, listed_as }` in `logs.db`; `blocked` = the logging device blocked the connection, only when the profile says so explicitly (kv profile: `conn_blocked`, FortiGate `action` ∈ {deny, dropped, blocked, block, reset}, Sophos `status` ∈ {Deny, Drop} or `log_subtype` = Denied, exactly once like every connection field; template profile: the `blocked` flag of the `conn_patterns` entry; every line of the pair in the batch must be blocked); when it is not stated explicitly (MikroTik, other kinds) = `false` ("connected to"), never guessed; the event `logs.bad_address.detected` of a blocked hit says "tried to reach <destination> (blocked by <source name>)", a hit that went through says "connected to"; 24-hour dedupe: a blocked hit is a duplicate of every hit of the pair, a hit that went through is only a duplicate of a hit that went through (a blocked attempt does not hide a later connection); **`asset_id`/`asset_name` are not stored**: looked up from the source IP through `Inventory` **at read time** (digest, `IocHit`, `IocHits`, the event), so renaming or deleting a device is reflected at once; with no device they are `null`. The IOC list is taken from `feeds` through the interface `logs.Feeds` (an adapter over `feeds.Store.IOCLookup`, key normalised by `feeds.IOCKey`), it does not pull feeds itself. **Subdomains**: a domain destination that is not listed under its exact name is matched through the nearest parent name (`a.b.bad.example` → `b.bad.example` → `bad.example`) **only** for a feed that lists the name together with all subdomains (`Listing.SubFeeds`, currently hagezi TIF); a feed that lists the exact name (a custom feed, every other source) never matches a subdomain; a single label (TLD) is never looked up, a public suffix (`co.uk`) is never an IOC; at most 10 parent names (the shortest), each name once per batch. The hit stores `dest` = the name the device asked for and `listed_as` = the parent name (`''` when the feed lists exactly `dest`; API `IocHit.listed_as`, `null` then; the Logs page says "listed as <parent name>" and Look up goes to the parent name); `feeds`/`confidence` are those of the feeds that matched the parent name; the event says "(listed as <parent name>, with all of its subdomains)" and `target` = `ioc:<parent name>`. No subdomain feed is on (`Feeds.Subdomains`, asked once per batch, only when a name needs checking; an error = check as before) → no parent lookup. Tests: `TestIOCSubdomainOfANameListedWithItsSubdomains`, `TestIOCSubdomainOfAnExactListingOrATopLevelDomainIsNoHit`, `TestParentDomains`, `TestIOCSubdomainsOfOneListedNameAreOneHit`, `TestIOCNoParentWalkWithoutASubdomainFeed`. One row per (device, listed name) pair within 24 hours (the listed name = `listed_as` if present, otherwise `dest`; several random subdomains of one name, and the name itself, are one row — the row of the first subdomain, not counted more; a firmer hit than the recent row (higher confidence, e.g. an exact-name feed 0.9 after a subdomain hit 0.6) is not hidden; a repeat found in the table is remembered within the batch, looked up through two indexes `logs_ioc_hits_pair` and `logs_ioc_hits_listed`; a row with an empty `listed_as` is deduplicated by `dest`; tests `TestIOCListedNameDedupeKeepsAttemptsConfidenceAndOldRowsApart`, `TestIOCSubdomainsErrorStillWalks`); at most `MaxIocRows` = 10,000 rows (the oldest deleted), `MaxIocHitsPerBatch` = 50 new hits per batch; kept by `retention_days` (job `purge`, Housekeeping). **A destination read from a line**: only from a field that the device's profile names (`local_field`, `dest_ip_field`, `dest_host_fields`, or the `conn_pattern` of a template kind); a field only counts when it appears **exactly once** as `key=value` outside quoted text (twice, even with the same value, a stray quote, an unclosed quote, two `->` in a MikroTik line, two pattern matches = a line with no connection; FortiGate only reads lines with `type` = `traffic` or `utm` (`conn_when`), MikroTik only the first TCP `(SYN)` packet and not `connection-state:established|related|invalid|untracked` (`conn_refuse`): UDP, ICMP and other flags = no connection); a device with no profile and a line the profile does not recognise **never** has a destination (there is no free-text reader: missing data is better than a false hit); the device must be a private IPv4 (RFC 1918 or 100.64/10) and not the box, a port of the box or a decoy (`NeverCount`); a private, loopback, link-local, multicast, unspecified, broadcast, CGNAT, documentation, benchmarking or reserved destination is never looked up. Tests: `TestContract_POST2_*`, `TestContract_INV7_*`, `TestIOCBlockedLineIsAnAttempt`, `TestIOCAmbiguousLinesMakeNoHit`, `TestIOCOnlyPublicDestinationsFromLANDevices`, `signature` `TestConn*`, `FuzzConn`.
- **INV-8** SIEM: on only when configured; `events` ≥ 1 of {findings, alerts, honeypot, bad_conn}; the signing key `secret` ≥ 16 characters, stored through `core/secrets` (SYS-4), the API only returns `secret_last4`; leaving it empty on edit = keep the old key. Default off, sends nothing (PRIVACY flow 7).
- **INV-9** The SIEM destination is declared by the customer (`host:port` or a URL); every test send and real send goes only to that destination (SYS-7). Three formats: `syslog`, `cef`, `json` (a signed webhook). The destination is never Vedette itself (`siemOwn`, at save time and on the socket): loopback, core's container address and the honeypot decoy addresses (`Config.SelfAddrs`) on every port (`TestOwnAddress_SiemSelfOnEveryPort`); the machine's address (`Config.BoxAddrs` = `machineAddrs` of cmd/vedette) on ports 8443, 8444, 8765, 514, 6514 (the machine's 514/6514 would loop back to Vedette's own syslog listener); another SIEM on the machine at its own port is a normal destination. The sentence `ownText` is the same as feeds, notify, ai; link-local, cloud metadata, multicast, unspecified, broadcast are still refused (`siemForbidden`); `TestSiemForbiddenTable`, `TestSiemSaveValidation`.
- **INV-10** `GET /logs/siem` is admin only (it has the configuration); every mutation writes `core_audit` (SYS-3).
- **INV-11** Logs sent by a customer's devices do **not** go to the AI by themselves: only through the `ai` module with the hooks and the internal-data rule.

## Preconditions (before calling)
- **PRE-1** `POST /logs/sources` / `PUT /logs/sources/{id}`: admin role; input goes through the schema (SYS-2). The listener runs inside `core` and binds unprivileged ports (5514, TLS 5515), needing no capability.
- **PRE-2** `POST /logs/siem/test`: a stored configuration already exists.
- **PRE-3** Only when the `feeds` module is on is there IOC matching; if it is off, the adapter returns `logs.ErrFeedsOff` (`Feeds.On()` = false), looks nothing up, has no hits, logs no warning; the digest still runs with an empty `bad_connections` (stored hits are kept, not shown) and the Logs page says why (reading the state of the `feeds` module: `digest.bad.emptyFeedsOff`; when feeds is on, an empty list only says there was no connection to a listed address in the last 24 hours, unless `ioc_matching` = false). The digest has `ioc_matching`: true only when `feeds` is on and a feed that is on lists at least one indicator (`Feeds.Listed`, an adapter over `feeds.Store.IOCListed`); false when feeds is off, when every IOC feed is off or has never been loaded, or there is no `Feeds` gate; a read error → write a Warn and treat as true (the page keeps its usual sentence). The Logs page then says it cannot match (`digest.bad.emptyNoIoc`), and does not say "no device connected". Test: `TestDigestSaysWhetherConnectionsCanBeMatched`. A failed feed read never blocks `Ingest` or loses a line: one Warn is written for a run of identical errors.

## Postconditions (after completion)
- **POST-1** Adding a source → immediately after (the `syslog` job is woken, not waiting 30 seconds) the listener accepts packets from `sender_ip` over the declared protocol (`udp`, `tcp` or `tls`); `state = never` until the first line. **`tls`**: a box that has a TLS configuration (`deps.SyslogTLS`, a copy of the HTTPS configuration: the same `GetCertificate` so a certificate renewal takes effect at the next handshake, TLS ≥ 1.2, no client certificate required except for a source with a pin) accepts `proto: tls`, and the TLS socket (box port 6514, inside the container 5515) stays open while the module is on, whether or not a `tls` source exists, and closes when the module is off (SYS-5). A box with no TLS configuration (loopback/dev, serving plain HTTP): `proto: tls` is refused on create and on edit with 400 `tls_unavailable` ("Syslog over TLS needs the box's HTTPS certificate; this box serves plain HTTP. Choose UDP or TCP.") and nothing listens on 5515; a leftover `tls` row has nothing listening for it and a Warn log says so. A `tls` source is identified by the **sender IP** like TCP (RFC 5425 section 4.2.1 specifies mutual authentication; server-side authentication is done; client authentication is **optional per source** by pinning the SHA-256 fingerprint of the client certificate (`client_cert_sha256`): only a source with a pin is required to present a certificate, a connection that does not present the right certificate is closed and counted in `Stats.CertRejected`; with no pin, the policy of section 5.3 "Unauthenticated Transport Sender" applies); an unknown IP is cut **before** the handshake, the handshake has a 10-second limit, each declared sender may only start 20 TLS connections per second (burst 100, `Limits.HandshakeRate/HandshakeBurst`; the excess is closed before the handshake and counted in `ConnRejected`), a failed handshake is only counted (`Stats.HandshakeFailed`; a connection cut by `SetSources` is not counted) and a Warn log at most once every 10 seconds. **`GET /logs/sources` has `box.tls`**: what a device must trust — `kind` `box_ca` (a leaf signed by the box's CA; the PEM is the CA, the same certificate as `GET /intake/ca.pem`, obtained through `Config.TrustAnchor`), `self_signed` (the PEM is the leaf itself) or `issued` (issued by someone else: the PEM is the chain the box owner supplied, `issuer` names it); the same `port` that devices send to, the SHA-256 fingerprint, the subject, the expiry of the certificate in `pem` (only the CERTIFICATE block); `null` when the box has no TLS, and hidden when the box's CA cannot be given out at the moment (the leaf is being reissued); a source has `client_cert_sha256` (`null` = not pinned, only `tls` sources; a non-TLS source = 400 `bad_client_cert`; over HTTP, a badly formatted fingerprint is refused first by the generated validator as 400 `invalid` with `field: client_cert_sha256`, `bad_client_cert` is also the code of the service called directly). For now the listener runs **inside `core`** (not `sensor`); a source's port (`port`) is only a hint for the device, and the listener uses one port of the box.
- **POST-2** A connection from the LAN to an IP/domain that is in a malicious feed (a syslog line from a device that has a profile) → creates `logs_ioc_hits` (one row per device-destination pair per 24 hours, `IocDedupe`; a repeat inside it is held back only while the incident it would count on is open: once that incident was resolved after the pair's newest hit, by a person or by Vedette (`Config.Incidents`, notify `ResolvedSince`), the repeat is a new hit and is announced, within `IocEventsPerHour`; `TestIOCARepeatAfterTheIncidentWasResolvedIsANewHit`) and, **after the batch transaction has committed**, emits two events: `logs.ioc_hit.detected` (for the `ioc_connection` trigger of `response`) and then `logs.bad_address.detected` (for `notify` and SIEM), with the source device (S-LOG-2, S-LOG-4 syslog half). The feed lookup runs **before** the batch's write transaction (the writer of `logs.db` is not held while reading feeds).
- **POST-2c** (S-LOG-4 SPAN half) `MatchMirror(items)` (≤ `MaxMirrorBatch` = 1000 items; `cmd/vedette` calls it from `sensor-passive` `Config.Mirror` when the `logs` module is on): each item `{kind dns|sni|http|flow, at, src, dest}` is matched against the feeds **exactly as POST-2** (the same `matchIOC`, the same subdomain rule, the same 24-hour dedupe, the same two events); `src` must be a LAN address (`LocalOK`) and not the box/gateway/decoy (`NeverCount`); `dest` is a public address (`PublicDest`) or a clean name (`CleanDomain`); other items are dropped one by one; `at` outside [now − 1 hour, now] → now. A batch that was not fully judged (a feed lookup failed — not feeds being off — or `MaxIocHitsPerBatch` was reached) stores the hits it has and then returns `ErrMirrorIncomplete` (the sensor receives `503 store_busy` and sends again; pairs already stored are skipped like repeats). **Only hits are stored** (`seen_via` `span_*`, `source_id` = `span`): no log line, no counter, no name or flow that did not match (FORBID-1; `TestMirrorMetadataMatchesTheFeedsAndStoresOnlyHits` counts every other table). The `bad_address` event says "Seen on the mirror port: …" instead of "Seen in the log of …".
- **POST-2b** (S-LOG-1) From day one, with no baseline needed: **5 failed logins from one remote address within 10 minutes** on one source (sshd "Failed password"/"Invalid user"/"authentication failure", Windows 4625; one attempt is the largest number among the three kinds of lines, not the sum) → exactly **one** `logs.anomaly.detected` (target `auth:<address>`) **after the batch transaction has been written**; the same (source, address) is not reported again within 1 hour (`AuthDedupe`) while its incident is open: once the incident was resolved after it was announced (`Config.Incidents`, notify `ResolvedSince`), the next failure past the threshold is announced again as a new incident, within the hourly budget, and so is the next accepted login after its own incident was resolved (`TestAuthFail_ARepeatAfterTheIncidentWasResolvedOpensANewOne`); a successful login ("Accepted …", 4624) from that address after the failures → severity `high` (if it comes before the threshold the first incident is high, if it comes after then one more incident `auth:<address> accepted` is added). The remote address is the address the signature reader finds (not the log sender, not the box); a LAN address still counts. State is in memory, with caps: 2,048 pairs (a new pair is dropped when full), 32 hour marks per kind, 5 account names (≤ 32 characters), 20 medium-severity incidents per hour (an incident with a successful login is never cut). A line only counts when the syslog program is sshd/sshd-session (PAM: login/su/sudo too) and the phrase opens the message, or by the Windows event id present in the accompanying data; IPv6 counts by /64; an incident with a successful login always uses the target `auth:<address> accepted`. Tests: `TestAuthFail_*`.
- **POST-3** Retention changes → applied to the next cleanup run; returns the new `retention_days`.
- **POST-4** `POST /logs/siem/test` returns `{ok, at, detail}` and stores `last_test`.
- **POST-5** With SPAN: no real mirrored packets → the sensor status warns (the configuration is in Settings → Box network), and does not silently say "nothing".

- **POST-6** (S-IDS-1) After the batch transaction commits, `Ingest` calls `Config.Received(ctx, []StoredLine)` (if present) with every stored line: the cleaned text, the receive time, the id, the name and `kind` of the source. That function must not block or write the main database (INV-12); `cmd/vedette` connects it to `ids.Service.Offer` when the `ids` module is on. Logs does not know which line is an IPS event.
## Forbidden (never)
- **FORBID-1** Storing SPAN packet payload (metadata only, INV-2).
- **FORBID-2** Returning the SIEM signing key through the API/export; writing it to logs.
- **FORBID-3** Sending events to a SIEM when `enabled=false`.
- **FORBID-4** Giving raw logs to the AI other than through the `ai` module.
- **FORBID-5** Accepting syslog from an IP that has not been declared as a source and storing it as a valid source. (A proposal; see open question 2.) Assigning a source over UDP/TCP is best-effort only (a UDP sender IP can be spoofed, and any machine on the LAN can receive another IP); the TLS listener (port 6514) also only identifies the source by the sender's IP (no client certificate by default, an optional per-source pin: the policy of RFC 5425 section 5.3 "Unauthenticated Transport Sender", which the RFC calls "generally NOT RECOMMENDED"; accepted because the sender IP is checked, the port is LAN-only, and it has the same level of trust as UDP/TCP 514; mutual authentication per section 4.2.1 can be turned on per source).

## Tables owned
Two databases (INV-12). **The main database (`vedette.db`)**: `logs_sources`, `logs_retention`, `logs_siem` (configuration, audited in the same transaction, included in backups). **`logs.db`** (a separate file next to `vedette.db`, with its own writer): `logs_events`, `logs_volume`, `logs_source_buckets`, `logs_source_seen`, `logs_signature_daily`, `logs_signature_buckets`, `logs_signature_addrs`, `logs_anomaly_sent`, `logs_ioc_hits`. `response` reads `logs_ioc_hits` through an interface (`IocHit`, `IocHits`; IMPACT), not reading the table directly.

## Storage and the single writer (INV-12)
- **INV-12** The log volume (`logs_events` and the counters) is in `logs.db`, **not** in the main database: each `store.DB` has one writer, and 2,000 lines/second/source must not wait for or hold core's writer (findings events were lost because the writer was busy, #159/#160). The two databases do not reference each other: a line only names its source by id, and a line outlives its source (INV-4). `NewService` refuses when the two databases are the same one. `Ingest` writes at most one transaction on `logs.db` per batch (≤ `MaxBatch` = 500 lines) and never writes the main database. Test: `TestIngestNeverWaitsForTheCoreWriter` (hold core's writer, ingest still completes).
- **Sanitising (INV-1)**: every line goes through `sanitizeLine`: bad UTF-8 → U+FFFD, control characters except tab → space, cut at `MaxLineBytes` = 2,048 bytes on a character boundary and marked `...[cut]`. Fuzz: `FuzzSanitizeLine`, `FuzzNormalizeSource`.
- **Sanitising, the full version (review #186)**: every character of `unicode.Cc`, `Cf`, `Zl`, `Zp` except tab becomes a space (C0/C1 controls including NEL and DEL, bidirectional overrides and isolates, zero-width characters, BOM, soft hyphen, U+2028/2029): they make a line display backwards, escape search, or fake a second line in the page and the export file.
- **Search with caps**: at most `MaxSearches` = 2 searches at the same time on a box, each `SearchTimeout` = 5 seconds; no room → 503 `server_busy` (an existing code; the message says to narrow the time range or the keyword). **A keyword search scans from the newest back in steps of `scanChunk` = 20,000 rows of the `ts` index**: it stops when `EventsPage` = 200 matching rows are found, when the window ends, or when `SearchTimeout` runs out; in the latter two cases (window not yet exhausted) it returns 200 with `searched_back_to` + `next_cursor` (an opaque cursor `<ts>_<id>`; `null` = the window is exhausted), and `cursor=<next_cursor>` continues right below it, with no repeats and no gaps (`TestEventsKeywordSearchContinuesWhereItStopped`); a step still running when time runs out is dropped whole. Only when the first step cannot finish is it 503 `server_busy` (also when the driver reports "interrupted"). The cursor is untrusted input: exactly the form `2006-01-02T15:04:05.000Z_<id>` or 400 `bad_cursor` (`TestEventsCursorIsValidated`), going into the statement only as a parameter; a `cursor` with no keyword is also 400. A full page always has a cursor (read one extra row to know whether more exist): only a page that exactly equals the last matching rows of the window has none (`TestEventsFullPageOnTheLastStepStillHasACursor`). The cursor is **unsigned** (unlike the default of `API_CONVENTIONS` section 4): the viewer can already read every row, and the cursor is only a position put into SQL as a parameter. Each step carries only a lower bound on `ts` (two lower bounds make SQLite scan the whole window). The GUI shows API errors through `QueryState` (with a retry button), the mock is unchanged. **Case-insensitive only for ASCII letters** (`asciiLower` in Go matches `lower()` of SQLite); other characters must match exactly (Vietnamese typed exactly as in the line matches). Upgrade path: an FTS5 index (not built yet).
- **Audit of purge (SYS-3, the two databases do not share a transaction)**: a cleanup run that has anything to delete writes `logs.purge_started` (the cut-off, the byte cap) to the main database **first**; if that cannot be written nothing is deleted. Then, on every exit (done, error, ctx cancelled, even before the first chunk), it always writes `logs.purge` with the row count using `context.WithoutCancel`. A crash between the two rows leaves a "started" row with no closing row: meaning a cleanup was left unfinished.
- **Row id** is `AUTOINCREMENT`: `le-N` is never reused for another row, even after a purge.
- **Time**: `ts` is the receive time (the device's time drifts, RFC 3164 has no year), within [now − retention, now]; empty, in the future or older than retention = now (a row written exactly at the retention mark would be deleted by the next cleanup). A line longer than 4 × `MaxLineBytes` is cut **before** sanitising (the sanitiser scans the whole string; stepping back at most 3 bytes to cut on a character boundary) and always has the marker `...[cut]`.
- **Cleanup**: the `purge` job (a long-lived loop, running even when the module is off: one run at startup, then every hour or when woken) deletes rows past retention in chunks of 10,000 rows (one transaction per chunk, so the writer of `logs.db` is released between two chunks, respecting `ctx`), keeps the total **bytes of line text** at no more than `MaxEventBytes` = 4 GiB however retention is set (against a full disk; the real file is about 1.6 times larger because of indexes), drops counters older than 2 days and the "last received" marks of deleted sources. The byte count lives in the one-row table `logs_volume`: `Ingest` adds in the batch transaction, the cleanup subtracts in the delete transaction. **`Ingest` wakes the `purge` job** when the total exceeds the cap (`startPurge` only sends without waiting into the `kick` channel buffered at 1, so `Ingest` never waits and many batches share one wake-up; it never waits for core's writer, INV-12). The `Run` of the `purge` job is long-lived and **only ends when `ctx` ends**: it loops "one run (recompute the counter if not yet, then clean), wait for `ctx.Done` / `kick` / `PurgeEvery`"; a `kick` that arrives when the previous run started less than 1 minute ago is postponed to the end of that interval (not dropped). A failed run (a counter recomputation that fails because the disk is full, a cleanup error) only writes a Warn and loses exactly that run, and the next `kick`/timer tries again; a panic inside a run is caught (an Error is written with the stack) and also only loses that run, so that the flood guard does not stay off for a whole hour (`TestTheLoopSurvives*`). There is no separate goroutine any more: the job is `Housekeeping`, so it **stops on shutdown** (the context of `core/jobs` cancels a cleanup midway, the "started" row still gets a closing row, see above) and **still cleans rows past retention when the module is off**; turning the module off does not cancel it. The scheduler's `recover` wraps it. When the module is off nobody calls `Ingest` (the route and listener are off) so there is no `kick`; if there were, it would only fill the buffer. Test: `TestThePurgeJobRunsWhileTheModuleIsOff`. The job history (`core_job_run`) now records **one long run** for each process run (ending at shutdown, status `cancelled`), not one row per hour; `core/jobs` only writes when `Run` ends and there is no "running too long" alarm; the cleanup deletes the oldest rows down to 90% of the cap so that not every batch starts a run. When nothing has expired and the cap is not exceeded: no delete statement, no audit. When there is something to delete: one `logs.purge_started` row, and **always** a closing `logs.purge` row (even with a count of 0, even when cancelled before the first chunk). The over-cap step reads the counter inside each delete transaction and stops when it is ≤ 90% (the expiry delete chunk or another cleanup may already have been enough). The counter is only right when every writer is this binary (an old binary running on a new `logs.db` does not add to it): when there are no more rows to delete while the counter still exceeds the cap it is recomputed from the rows and a Warn is written; the first cleanup after each startup (the entry of the job loop) recomputes before deleting, so that a drifted counter does not delete real rows; the recomputation reads the total and the counter in one read transaction (a snapshot) and then briefly writes the difference, not holding the writer; when there is a flood at startup, the WAL grows during the scan.
- **`device_logs` export** (`ExportDeviceLogs`): has its own cap `ExportMaxBytes` = 32 MiB (an upper-bound estimate: each row counts as double the text bytes plus 128; the fixed part at most 118 bytes with a 29-character source id; going from the newest row and stopping at the first row that does not fit; only reading up to the newest id seen when measuring), so that this source never makes the whole `GET /core/logs/export` return 413 (core's shared cap of 128 MiB). Over the cap: keep the **newest** rows, in old → new order, and the last row is `{"id":"cut","ts","source_id":"","line":"[device_logs cut: ...]"}` saying that old rows were dropped; to get everything, export a shorter range of days.
- **Search** (`GET /logs/events`): window ≤ retention; `q` matches within the line and within the source name; the 200 newest rows; with no keyword: `total` counts exactly up to `CountCap` = 100,000; with a keyword: `total` = the number of matching rows found (≤ 200 per answer) (measured with 5 million rows: no separate SQLite file needed; writing 500 rows 10 ms; a keyword that does not match over 7 days: an empty 200 after 5 seconds, `searched_back_to` about 2.6 million rows, instead of 503).
- **Backup, restore, data deletion**: `logs.db` is **not** in the backup; restore and rolling back to an old version do not touch it; the text in the RUNBOOK and the backup screen is not part of this module; data deletion is done by `core` from the list of module data file names that `cmd/vedette` supplies (logs registers nothing). Because rolling back to an old version may run an **old binary on a new `logs.db`**, every migration of `logs.db` (`migrations/volume`) must be **additive only** (new tables, columns, indexes; no DROP, RENAME, DELETE, UPDATE, no change to the meaning of a column). The test that enforces it: `TestVolumeMigrationsAreAddOnly` (strings and comments are dropped in one left→right pass; `"name"`, `` `name` `` and `[name]` are accepted as quoted fragments; forbids REPLACE INTO, INSERT OR REPLACE, CREATE TRIGGER, CREATE UNIQUE INDEX, PRAGMA, CHECK in ALTER ADD COLUMN, and INSERT INTO a table not created by that very migration). An incompatible change = a new file `logs-v2.db` and a new decision.
- **Syslog listener (package `modules/logs/listen`)**: imports neither `database/sql` nor `core/store` (like `sensor-passive/capture`, so that moving it to `vedette-sensor` later needs no code change); the module gives it a `Sink` that calls `Ingest`. It runs as a `core/jobs` job named `syslog` (**not** `Housekeeping`: SYS-5, module off = context cancelled = every socket closed; on again = reopened) and **does not end** when a socket fails to open or when reading a source fails: a socket that opened is kept as it is (UDP does not go down because TCP is busy), `ListenStatus()` has `UDPErr`/`TCPErr` saying which protocol is down and why, a Warn is written once per new reason, and the job retries exactly the missing part every `SyslogRetry` = 30 seconds (inside the job, not rerunning the job). The last batch is stored before the job ends: the batcher outlives every producer, and an `Ingest` call running at shutdown is **not cancelled** (its context is not cancelled by `quit`; from the moment of shutdown each call takes at most `FlushOnClose` = 5 seconds, so a hung Sink does not hold up the whole shutdown). `ListenStatus().Conns` is the number of open TCP connections. **Sockets are open even with no sources**: while the job runs, the UDP and TCP sockets are always open (TLS when the box has a TLS configuration), so that an undeclared sender is counted instead of meeting a closed port that leaves no trace; sources only decide whose lines are kept. Adding, editing and deleting a source wakes the job (`Service.sourcesChanged`): the TCP/TLS connection of a deleted source, or one that no longer accepts that connection's protocol, or whose pin changed, is closed; the sockets do not change. Port: `-syslog-port`, default 514 and then 5514 **only when binding 514 is not permitted** (`fs.ErrPermission`; a port that is busy is an error, not a reason to switch ports); one port for both UDP and TCP, kept once chosen; switching ports writes a Warn. `Service.ListenStatus()` says which port is in use, whether it is the fallback port, and the counters; **the API does not return it yet** (the `box` block of `GET /logs/sources` has no port field, adding it needs a story criterion: the deferred item of L2).
- **Sender identification (FORBID-5)**: the source IP of the packet/connection (IPv4-mapped unwrapped), matched against a declared source **and the protocol that source accepts** (`listen.Accepts`: exactly the declared protocol, and a `udp` source also accepts `tcp` from its IP because TCP is no easier to spoof than UDP; a `tcp` source does not accept UDP; `tls` only accepts TLS and no other protocol accepts in its place; one device is one source, IPs do not overlap; a connection over a protocol other than the declared one, that is TCP of a `udp` source, at most `MaxConnsIPOther` = 8 per sender so that it does not take the share of TCP/TLS sources out of the 1,000 connections); when not matched it is dropped at once (TCP: closed before a goroutine is created) and counted in a table of 256 senders (LRU) (`Stats().UnknownSender`: the address **taken from the socket, never from the text of the line**, the protocol of the last time, the count, the last time). `Service.UnknownSenders` (S-LOG-1) returns the 10 most recent senders for `GET /logs/unknown-senders` (operator and above: the address of an unknown sender), dropping a sender that a source **now** accepts by the protocol it used (adding a source makes the suggestion disappear at once); with caps: an LRU of 256 entries by (IP, protocol) (a sender that uses two protocols is two entries, and the page merges them into one row that names both), returning the 10 most recent, each entry only has IP, protocol, count, last time, **no text of any line is stored** (untrusted and nobody asks for it); in memory only: empty when the listener is not running, counted again from 0 when the listener restarts. `TestAnUndeclaredSenderIsListedOverHTTP`. This is best-effort (UDP can spoof IPs).
- **Framing (INV-1)**: UDP one message per packet (the trailing `\r\n` dropped). TCP two styles on one connection (RFC 6587): octet counting (`123 <34>...`, only accepted when after the number and the space comes `<`, so a line that begins with a number is still a line) and newline-terminated (`\r\n` is fine); empty lines and an LF after an octet-counted frame are dropped **under a 5-minute idle limit counted once for the whole stretch containing only newline characters** (a line of nothing but CR/LF does not hold the connection forever) (not turning on the frame's 30-second limit: a silent sender is not a slow sender); the frame limit is absolute, so dripping one byte at a time is also cut after 30 seconds. A count above `MaxFrame`, a line with no newline longer than `MaxFrame`, or the stream ending in the middle of a frame → **close the connection** and count `BadFrames` (it cannot resynchronise). A message longer than `MaxLine` is cut and counted in `Truncated` (the connection stays alive). NUL and odd characters go on unchanged: `Ingest` sanitises (not twice).
- **Envelope (INV-1)**: `listen.Parse` reads RFC 5424 (strictly), RFC 3164 (including the form without a timestamp, like FortiGate `key=value`), and the CEF / LEEF 1.0 / 2.0 header inside the message. **Fail-closed**: a line that cannot be understood becomes `Format "raw"` (PRI −1, the whole line is `Msg`), is still stored and counted by format (`Stats().Formats`), never dropping the whole batch. Header fields have caps (host 255, app 48, procid 128, msgid 32, CEF field 512). The stored text is the **verbatim message** (including `<PRI>`); the envelope (`Line.Env`) only serves counting and the signatures, and `ts` is still the receive time.
- **Limits (SYS-6; a starting point to be measured)**: a message is kept up to 8 KiB (`MaxLine`; 2 KiB stored at `Ingest`), a UDP packet and a TCP frame up to 64 KiB (`MaxFrame`); TCP 1,000 connections in total and 256 per source (above that it is closed, counted in `ConnRejected`); idle for 5 minutes then closed (`Idle`); a frame that has begun must finish within 30 seconds (`FrameTimeout`, against slow-loris); 2,000 lines/second per source, burst 10,000 (a token bucket per source; the excess is dropped and counted in `RateDropped`); a queue of 4,096 lines (when UDP is full it drops and counts `QueueDropped`, when TCP is full it stops reading so that the sender's window closes); a batch of ≤ 500 lines, ≤ 1 MiB of text or 2 seconds (whichever comes first) goes into `Ingest`; when `Ingest` refuses a batch that batch is dropped and counted in `SinkLost` (Warn at most every 10 seconds); at shutdown it drains the queue within 5 seconds.
- **TLS 6514**: done. **It must be released together with two publish lines**: `PublishPort=6514:5515/tcp` of the `core` unit (host/ops) and `6514:5515/tcp` in `deploy/compose/container-only/compose.syslog.yaml`; otherwise, a `tls` source is accepted but no line ever arrives. A TLS sender that does not read (KeyUpdate, a corrupt record) must not hang the listener: the connection is cut on the raw socket, not with `tls.Conn.Close`. Devices must trust the box's certificate: with a self-signed box the certificate must be exported/pinned on the device (the Sources page shows the certificate to download: `box.tls`).
- **Signatures, baseline, digest**:
  - **A profile is data** (`modules/logs/data/profiles/*.json`, embedded in the binary; package `modules/logs/signature`, with no database so moving it to the sensor needs no code change). Three rule kinds: `kv` (preselected `key=value` keys, in order; `vocab` lists the allowed values of each key: a value outside the list is dropped from the signature, and for the first key alone, a value outside the list means the line does not belong to the profile; a key in `mined` has its value passed through the pattern finder), `event_id` (an RE2 pattern with a group `id`, a table of event names is the vocabulary; an id not in the table means the line does not belong to the profile; Windows, including Snare's tab form `MSWinEventLog\t…\t<id>\t`), `template` (a leading tag such as the RouterOS topic, `head_vocab` lists the allowed words, plus the rest passed through the pattern finder). **A signature is only "bounded" (`Result.Bounded`) when every part of it comes from the vocabulary of the bundled data**: FortiGate only uses `logid` and `action` from the list (a correctly formed 10-digit id that is not in the list is still read by the profile, keeping `logid=<id> action=<a>` and **not** bounded) (source: FortiOS Log Message Reference, docs.fortinet.com; the list is short and safe, an unknown id goes through the pattern finder; `msg` is not in the signature, only in `sample`), Windows only uses an event id in the table. MikroTik has a message part that is free text so it is **not** bounded. Everything else goes through the pattern finder and counts against the pattern finder's quota. The optional fields `src`/`dst` (a key or a pattern) give the source/destination address; an address only accepts letters, digits and `. : _ -` up to 64 characters, the rest is dropped. Each profile must come with 1..8 `samples` (a line, the expected signature, source, destination) and **the loader runs each sample**: a sample that does not produce exactly the signature causes the whole profile to be refused. **The loader is strict and fails closed**: an unknown field is refused (at all three levels), a file > 64 KiB, > 32 files, > 12 keys, > 8 RE2 patterns, a pattern > 256 bytes, a duplicate id or device kind, a rule kind containing a field of another kind, no profile found → `NewService` returns an error (the module does not start on a broken rule). Tests: `TestLoaderRejectsUnknownFields`, `TestLoaderRejectsBadProfiles`, `TestShippedProfiles`.
  - **The shared pattern finder** (`signature.Mine`): stateless (the same line gives the same signature on every box, after every restart). It masks: IPv4 (with port) → `<ip>`, host/domain name (≥ 2 dots, or 1 dot with a common domain suffix) → `<dom>`, email address → `<email>` (a hand scan around `@`, linear; no bounded regular expression), URL (`://`) → `<url>`, the value of an identity key (user, username, acct, account, login, name, host, hostname, rhost, src, dst, query, domain, url, email, set_id, suser, duser, shost, dhost, and every key that **ends** with user/username/name/host/login/account case-insensitively such as `client_user`, `targetUser`, `sasl_username`, `TargetUserName`; the forms `key = v`, `key := v`, `key=v`, `key:v`, `key: v`, `key="v"`, `key=<v>`, `"key":"v"`) → `<v>` even when it is a short word, PAM/Dovecot `(name,IP)` → `(<name>,ip)`, `name (ip)` (MikroTik hotspot), `name(uid=` (PAM) and `[name] FAIL LOGIN` (vsftpd) → `<name>`, `name/ip:port` (openvpn), the squid user column (the word before `HIER_…`), `name : user NOT in sudoers` and `name : TTY=` (sudo), `FAILED SU (to root) name` → `<name>`, a host name such as `DESKTOP-4K8R2QP` → `<host>`, sentences inside `msg=`/`logdesc=`/`message=` are **kept** (only the names in them are masked), a single-quoted string with no whitespace → `<s>`, hex ≥ 8 characters, MAC, IPv6, `0x…` → `<hex>`, digit runs → `<n>`, long identifier-like / random-looking words (≥ 16 bytes with both letters and digits, ≥ 20 bytes with a capital letter in the middle of the word, ≥ 24 bytes with digits or capitals) → `<tok>`, words starting with `/` → `<path>`, a double-quoted string → `<s>`, the value after `=` → `<v>` (except short words that are purely letters ≤ 16 bytes such as `action=deny`, addresses or numbers), and the name after `user`/`username`/`login`/`account`/`acct`/`for`, Vietnamese `tài khoản`/`người dùng` and Russian `пользователь(я)`/`логин` → `<name>` (dropping the characters `[] <> "" '' : (` around the name; the name may begin with a digit or be written in non-ASCII letters; the same after `->`) (skipping `of`, `invalid`…; a sentence word such as `failed`, `locked`, `from` blocks masking: "SSL user failed to logged in" is kept) ("Invalid user oracle" and "Invalid user postgres" are one signature; a list of user names does not become a list of signatures). Only the first 4 KiB of the line is looked at, the result is ≤ 240 bytes, valid UTF-8, no control characters. FortiGate does **not** put `dstport` or the destination in the signature (the deny log of a firewall facing the Internet is one signature, not one signature per port). The catalogue entry tells the truth (S-LOG-1): `reads: parsed` **only** for a kind that has a profile (`fortigate`, `sophos`, `paloalto`, `cisco-asa`, `mikrotik`, `pfsense`, `opnsense`, `sonicwall`, `ubiquiti`, `windows`, `linux-rsyslog`, `linux-journald`); a kind with no profile (such as `suricata`) is `stored` (the digest reads them with the shared pattern finder). The test `TestCatalogReadsMatchProfiles` keeps `content/logs/kinds.json` and the profiles in agreement.
  - **Counters** (`Ingest` adds in the same `logs.db` transaction as the batch, in one write): `logs_signature_daily(day, source_id, signature, dest, count, first_seen, sample, mined)` by UTC day, key `(day, source_id, signature)`: `dest` is only for display (the destination of the newest line), it is **not** in the key, `logs_signature_buckets(bucket, source_id, sig_hash, count, mined)` by 5 minutes (kept for 24 hours and one bucket, for `Counts`, the signature is stored as the first 64 bits of SHA-256 and not as text). A flood of identical lines is **one row** (`TestContract_INV1_FloodOfIdenticalLinesIsOneRow`: 1,000,000 lines). **Caps against an untrusted device, two separate quotas**: lines read by the shared pattern finder (`mined = 1`) at most `MaxMinedPerDay` = 1,000 rows per source per day, lines read by a profile at most `MaxBoundedPerDay` = 2,000, so a flood of dissimilar lines never pushes a profile signature out of the digest (`TestContract_INV1_MinerFloodCannotPushOutAProfileSignature`); the 5-minute bucket: 600 bounded + 200 per source (600 is not smaller than the largest bounded vocabulary, 540 FortiGate signatures: `TestBoundedVocabularyFitsTheQuotas`). The excess is counted into the signature `(other)` (the count is not lost) and **never shows as "new" or a spike**. The byte cap per source, **measured** with every quota full and every value at its maximum length (`TestMeasureCeilings`, indexes counted): the daily counter 1,147 bytes/row × 30,010 rows (10 days) = 32.8 MiB; buckets 124 bytes/row × 241,101 rows (301 buckets: 24 hours plus one bucket plus the delay of the hourly cleanup; 600 + 200 + 1 rows per bucket) = 28.5 MiB; about 61 MiB per source in total, outside `MaxEventBytes` (this cap was chosen to be written down instead of adding the sample bytes to `line_bytes`). `sample` is the first line of the row, cut at 300 bytes, written once when the row is created: it is the only copy of a line outside `logs_events`, and it follows retention (see below).
  - **Baseline by UTC day**: 24 hours is estimated like a sliding-window rate limiter: `count24 = today + yesterday × (1 − the fraction of the day that has passed)`. `baseline_per_day` = the average of the **complete** days the source has had within the 7 days before yesterday (the day the source started is a partial day and is dropped; with no complete day yet there is no spike); the source's start day is taken from the oldest day still kept (so an old source has all 7 days). The daily counter keeps the 9 complete days before today plus today (10 UTC days), reading back 9 days (the oldest day is only to know when the source started); **the 24-hour warm-up restarts when the source's kind or sender IP changes** (`logs_sources.signatures_since`, `TestContract_INV6_ChangingKindOrSenderRestartsTheWarmUp`); a signature last seen more than 8 days ago is "new" again. Cost (`TestMeasureDigestCost`): one read of all rows of 10 days (not scanning `logs_events`) and then one lookup by the index `(source_id, signature, day)` for each displayed item. **The digest and the events share one read** (a snapshot): the `anomaly` job stores the result after each run; the digest serves that when it is no older than `DetectEvery` (a clock going back counts as old), and if older it reads once and stores; any change to the sources clears the stored copy and raises the generation (`snapGen`), so a read that started before a change is not stored after it. **Order** (`rank`, used for the digest and events): bounded "new", bounded spike, then the pattern finder's "new" with the fewest lines first (a flood of user names is many signatures with the same line count, a real event has only one line), then the pattern finder's spike with the most lines first, finally by text. The digest lists at most `DigestMax` = 20 items per kind, **round-robin across sources** (the highest-ranked item of each source first, then the second item, by source id; within one source by `rank`: bounded first, the rarest "new" item first, ties by the newest first seen) (`TestContract_INV6_DigestIsRoundRobinAcrossSources`); there is no field yet counting the items not listed (`more`: needs an API contract change); `sample` is taken from the newest row of the signature; a deleted source does not appear.
  - **Retention**: the cleanup of `purge` (Housekeeping, running even when the module is off) deletes `logs_signature_daily` of the UTC days before (today − 9 days) whatever the retention is (9 complete days plus today) (the baseline only needs that much; a retention of 180 days does not make the counter any bigger), deletes `sample` of a row whose `first_seen` is older than retention (by time; looked up by a range of the primary key, not scanning; this only happens with a retention of 7 days), `logs_signature_buckets` and `logs_signature_addrs` older than the bucket containing (now − 24 hours) (deleted by range because the key starts with the bucket; in the same transaction, `TestPurgeDropsOldAddressCounters`), `logs_anomaly_sent` older than 3 days. This is cleanup of auxiliary counters so there is no separate audit row; `POST /core/data/purge` deletes all of `logs.db`. `TestPurgeDropsOldSignatureCounters`.
  - **`Counts(ctx, sourceID, signature, window) (int, error)`**: the read gate for the `log_threshold` of `response`. `window` ∈ [5 minutes, 24 hours] (outside that `ErrBadWindow`); reads `logs_signature_buckets` by the signature hash and 5-minute bucket, through the index `(source_id, sig_hash, bucket)` (not reading another source) so the window is rounded out: the result covers the window and at most 5 minutes before it. A signature not seen yet = 0. `sourceID` is the id (`ls-…`), `signature` is exactly the text in the digest. No other module reads the table directly.
  - **The remote address of a line**: the `signature` package additionally returns `Result.Remote` (`netip.Addr`): **the remote party the line is about** (the client of a failed login, the source of a blocked connection), **never** the device that sent the log (`sender_ip`). Profiles are data: `remote_fields` (kv, in priority order: FortiGate `remip`, `srcip`), `remote_patterns` (every kind, a group named `addr`: FortiGate `ui="https(addr)"`, Windows `Source Network Address` / `Client Address` / `IpAddress` in text form, JSON and XML of events 4625/4771/4768…, MikroTik `src:port->`); **no shared reader runs on a line of a kind that has address rules in its profile** (a line that the profile does not read, or reads but whose rules do not find an address, has no address); a kind with no profile, or a profile with no address rules, goes through the shared reader (not using regular expressions): `key=value` with the key `rhost`, `rip`, `remip`, `client`, `src`, `srcip`, `remote_*`, `client_ip`, `peer`, `ip` …, the word after `from` or `by` (sshd, postfix `from unknown[addr]`, openvpn `[AF_INET]addr:port`), `host[addr]` (postfix) and `name/addr:port` (openvpn); **Exactly one address position or none (round 2)**: a line gives a remote address only when it contains exactly one address position and that position is not inside text the client controls (a quoted double-quote segment, for the shared reader); with a second position, even one with a value that does not parse such as `-`, there is no address (missing data is better than a slandered address: `TopAddresses` leads to automatic blocking). A profile's patterns count POSITIONS (every match of every pattern, a value of 1 to 64 characters so `-` is also a position), not parsed addresses; the shared reader skips candidates inside a double-quote segment (the request line, referer, user agent of nginx/apache; an odd number of unescaped quotes means the line has no address, because an inserted quote can hide the real address and expose a ready-made one) **Round 3: the shared reader is an allow-list by position** (kinds with no profile): an address is only read at (a) the first word of the message (after the `tag:` word) when the line is an access-log line (`ADDR ident user [date`), (b) sshd `from ADDR port N`, `by ADDR port N`, `user NAME ADDR port N` (the address right before ` port <number>`), (c) apache `[client ADDR]` / `[client ADDR:port]`, (d) `key=value` with a remote key (`rhost`, `rip`, `client`, `src`…; a position even when empty or `-`); every position must be the same usable address; **every other word in address form** (inside quotes, JSON, after `user`, in the request) is not a candidate and makes the line ambiguous: no address, even when the line has no allowed position at all (`user 8.8.8.8 not found` no longer yields 8.8.8.8); a word inside or opening a quote segment is never a position. postfix `host[addr]`, openvpn and `from ADDR` without `port` are no longer read; the price: a line with a second address that is not the remote party (`from <peer> to <box>`, `X-Forwarded-For` in quotes) has no address: text that an attacker writes into a line (a user name, workstation name, URL, a `msg` field) is not allowed to point to a different address (the same class of bug as fail2ban CVE-2007-4321 and DenyHosts CVE-2007-4323: the first match from the left). Every match of every pattern (`FindAll`, counting positions), every `remote_fields` key written twice with two values (`kvFind` reports a duplicate) and every candidate of the shared reader is collected; if there are **two different usable addresses** the line has **no address** (still counted in `Counts`). The Windows patterns anchor to the correct label (`Source Network Address:` / `Client Address:` at the start of the field or line; JSON on a quoted key `[{,]\s*"IpAddress"\s*:\s*"`; XML `<Data Name="IpAddress">`), the MikroTik patterns only for firewall lines (`proto …, addr:port->`) and `from addr via`, FortiGate only uses the keys `remip`, `ui`, `srcip` (not reading `msg`), `by` only counts when followed by `addr port`. The cost: an attacker can **hide themselves** by adding another address to the line (`from <box address> from <real>` no longer yields the box address and is then dropped), but cannot **frame** an innocent address; chosen like fail2ban/CrowdSec (the output leads to automatic blocking: framing is the worst error). What remains: a line with exactly one position that an attacker can write and no other real position still gives that address (there is nothing to check against); with Windows 4625 and nginx/apache this no longer happens because the real position is always present (even `-`) or is the first word of the line. `TestGenericRemote`, `TestShippedProfilesRemote` (hostile lines). **Only read with `net/netip`** (`signature.ParseAddr`: drops quotes, port, square brackets, `name(addr)`, zone; IPv4-mapped becomes IPv4); anything that does not parse is not an address (the line is still counted in `Counts`). **Never counted** (`signature.Countable` and `Config.NeverCount`): unspecified, loopback, multicast, link-local, broadcast; **the address of the device that sent the log itself** (the source's `sender_ip`: a FortiGate `local-out` line records `srcip` as its own address), the address of the box itself, the LAN gateway (`default_route.gateway` of the host network state, not the container's bridge gateway) and the honeypot's decoy addresses (the gate `Config.NeverCount`, asked at most once every 30 seconds with a 2-second deadline **after one complete answer has been received**; before that (the host has not answered, the decoy profile cannot be read yet) it is asked again on **every batch**; on error it keeps the last known set, nil leaves only the special addresses above; wiring uses the same sources as core/conn and response). **`TopAddresses` filters that set again on read**: a row stored before the box address was known is not returned once it is known (`TestContract_TopAddresses_BoxAddressStoredBeforeItWasKnownIsNotReturned`). **Container-only install (no vedette-host)**: the box's LAN address, the LAN gateway and the decoys are not known, so only the container address, the bridge gateway and `-hosts` apply (fail-open, stated clearly; response still checks never-touch). A private LAN address **is** counted (an internal password guesser is real). `TestParseAddr`, `TestGenericRemote`, `TestShippedProfilesRemote`, `FuzzParseAddr`, `FuzzRemote`, `TestContract_TopAddresses_NeverTheBoxTheGatewayADecoyOrASpecialAddress`.
  - **Address counter** `logs_signature_addrs(bucket, source_id, sig_hash, addr, count)` (addr is 4 or 16 bytes), in the same 5-minute bucket and the same `Ingest` transaction as `logs_signature_buckets` (no extra write; one read of the source's whole bucket per batch). **Caps against a spoofer** (INV-1): per source per bucket at most `MaxAddrsPerSignature` = 50 addresses per signature and `MaxAddrRowsPerBucket` = 500 rows for the whole source. A new address when there is no room **replaces the row with the fewest lines only when it has more lines** (a tie: the old row stays); the "line count" is **exact**: this batch's lines plus the lines of earlier batches in the same bucket for an address that has no row yet, kept in **memory** (`MaxPendingAddrs` = 4,096 entries; when full it drops from the largest (source, signature) group first, within the group the lowest count, ties the entry updated longest ago, never by hash or address so a flood only starves its own signature: `TestPendingFloodStarvesOnlyItsSignature`; only applied after the batch has been stored; **a restart loses at most one bucket**); an address enters a row with the accumulated count (`TestContract_TopAddresses_SlowAttackerBehindAFullSignatureIsKept`, `…BehindAFullBucketIsKept`: 1 line every 10 seconds after 50 and 60 spoofed addresses, or after a bucket full of 500 rows, still comes back with the right count). A row is never higher than the number of lines that address sent (no inflating counts like the space-saving algorithm), so a spoofed 1-line address cannot look like an attacker, and a sender of 10 lines beats a flood of 1-line addresses (`TestContract_TopAddresses_SpoofedFloodIsBoundedAndTheRealAttackerWins`, `TestTopAddressesCountsAreNeverInflated`, `TestContract_TopAddresses_BucketQuotaCoversEverySignature`). **Stated limits**: an address that is pushed out and comes back starts counting again (the count is a lower bound); a sender that sends one line per batch among more than 4,096 addresses that have no row in one bucket can lose its memory; upgrade path: a count-min sketch; a mined line over the bucket's signature quota (going into `(other)`) still has an address row so `TopAddresses(S)` can list an address when `Counts(S)` is lower. **The byte cap per source, measured** (`TestMeasureAddressCeilings`, every quota full, 16-byte IPv6 addresses, indexes counted): 199 bytes/row × 150,500 rows (301 buckets × 500) = about 28.6 MiB per source, outside the 61 MiB of the signature counters and `MaxEventBytes`; `TopAddresses` over 24 hours on a full source 47 ms. The measured `Ingest` cost of a batch of 500 lines (negligible when the quotas are full; a new row is only written once per bucket).
  - **`TopAddresses(ctx, sourceID, signature, window, n) ([]AddressCount, error)`** (`AddressCount{Addr netip.Addr; Count int}`): the read gate of `response` for the question "which address" (the blocking templates `tpl-vpn-ban`, `tpl-ssh-acl`). `window` ∈ [5 minutes, 24 hours] like `Counts` (`ErrBadWindow`), rounded out to buckets; `n` < 1 is `ErrBadCount`, `n` > `MaxTopAddresses` = 50 is cut; most lines first, ties by address (`netip` order, deterministic). Read through the index `(source_id, sig_hash, bucket)`. A signature not seen, a source not seen or a line with no address = an empty list, no error. The count is a **lower bound** when the quota is full; an address outside the quota may be missing. Module off: the data is kept, reads still work, no new writes (only the `syslog` job calls `Ingest`, not Housekeeping; `TestContract_SYS5_AddressCountersAreWrittenOnlyByJobsThatStopWithTheModule`).

  - **The event `logs.anomaly.detected`** (job `anomaly`, every `DetectEvery` = 5 minutes; **not** Housekeeping so module off = no job = no event, SYS-5; `Config.Events` nil = nothing is sent): payload `AnomalyEvent{source, target, title, what, action, severity, devices[{id,name}]}` exactly as `notify.logEvent` reads it. `source` = the source name; `target` of a pattern-finder signature = its destination with the most lines, or the signature itself when there is no destination; several pattern-finder anomalies of the same source + `target` merge into **one** event; **two separate rooms per source per hour, each room `EventsPerHour` = 20 events**. (1) A **bounded** signature (vocabulary of the bundled data; at most 540 signatures exist) always has its own event with `target` = `sig:<signature>` (a separate namespace within notify's merge key: kind + source + target, so a pattern-finder incident to the same destination does not swallow it; the destination is in `what`), never in the pattern finder's summary and not crowded out by the pattern finder's signatures (bounded spikes share the bounded room: waiting at most 1 hour); if there are more than the room, room−1 events go separately (the most recently seen "new" signature first regardless of line count; the line count only breaks ties) and the last place of the hour is **one backlog summary** (`sig:waiting events <UTC hour>`, the exact total waiting) naming the items not yet named (from the end of the order, listing the rarest first; when there is a summary, one place of its own in the hour is reserved for the item that has been named for the longest while still waiting, first in first out); the remainder **still waits for the next hour and is sent separately** (not lost, not recorded as sent), so every bounded signature is either reported on its own or named before it stops being "new" (`TestContract_Events_BoundedOverflowIsNeverSilent`). This commitment applies to "new" items; a spike is best effort within the UTC day (the `ref` of a spike is the UTC day; a spike that continues is evaluated again the next day). The limit of 20 per hour is a 60-minute sliding window: two full batches exactly 60 minutes apart give 40 events within a window closed at both ends. (2) The rest (the pattern finder, including its spikes) is best effort: when the number of groups is no more than the room, each group is one event; when more (a brute force, a scan, or a device sending a different line each time) then **one summary event per source per hour**, whose title says exactly what it carries and the real time span ("<source> logged N new kinds of message since <date and time in the organisation's time zone (`core/orgtime`, `Config.Zone`), with the time zone's abbreviation, "UTC" when it cannot be read> [and K spikes in the last 24 hours] (possible brute force or scan)", or "K kinds of message spiked in the last 24 hours"), `target` = `new kinds of message`, `spiking kinds of message` or `new and spiking kinds of message` with `<UTC hour>` (by what it carries) **different every hour** so notify opens a new incident instead of quietly raising the count on the old incident, `what` lists the rarest items first (through `summaryEvent`, not through `eventFor`). **A summary only covers items not yet covered by any summary** (the `covered` row in `logs_anomaly_sent`; a one-time burst of 21 kinds is one summary, not one per hour: `TestContract_Events_OneOffBurstIsOneSummary`), and when that hour already has a summary the run does nothing. **The items a summary covers are not recorded as sent one by one** (only the `summary` and `covered` rows), so when the flood is over and there is room in the room, they are sent separately. What is beyond `MaxAnomaliesPerPass` = 200 is only counted into the summary. Every item sent separately is written to `logs_anomaly_sent` so it is not sent again (`TestContract_Events_MinedFloodIsOneSummaryAnHour`, `…RealBoundedEventSurvivesAFloodAndSpikes`, `…BoundedFloodWaitsForTheNextHour`). The device that sent the log is looked up in the store **once** per source per run (not at all when the run sends nothing). `severity`: `low` for "new", `medium` when the group has a spike. `devices`: the store device that has the IP of the log sender and, when the line's destination is IPv4, the device that has that IP. No resending: the table `logs_anomaly_sent` (key source + kind + signature + `ref` = first seen for "new", UTC day for "spike") remembers across restarts; written **after** emitting so a crash midway only causes a duplicate send (notify merges by source + destination), not a loss. Every string of the payload is cut to notify's limits (`what` and `action` ≤ 1,000 characters, `source`/`target`/`title` ≤ 200, device id ≤ 96 bytes, name ≤ 253): notify refuses a longer payload and `Bus.Publish` swallows the error, so not cutting would lose the incident while still marking it "sent" (`TestContract_Events_PayloadFitsWhatNotifyAccepts` mirrors the limits, because logs does not import notify). A spike that continues is reported again each UTC day (the key `ref` is the day): notify merges by source + destination so it only raises the count. The clock jumping backwards: counters never write backwards (`first_seen` takes the smallest value), a line whose receive time is outside [now − retention, now] already became "now" at `Ingest`; after a backward jump, "new" can be missed for up to a day and a row of a future day waits until the clock reaches it. Tests: `TestContract_Events_*`.

## Events
- **Emits**: **`logs.ioc_hit.detected`** (payload `IocHit`; `response` listens for the `ioc_connection` trigger); **`logs.anomaly.detected`** and **`logs.bad_address.detected`** for `notify` to open an incident (3-part names `<module>.<object>.<verb>` as `core/events` requires; the payload carries its content already described by logs, because only logs understands logs): `{source, target, title, what, action, severity, devices: [{id, name}]}`. `source` and `target` are the incident merge key (the same kind + source + destination while open only raises `count`), `title` ≤ 200 characters in English, one sentence "who did what", `severity ∈ critical|high|medium|low|info`, `devices` are the matching inventory devices (may be empty). Every string is data from logs (untrusted); notify cuts it and shows it as plain text. These two names replace `logs.anomaly` and `logs.bad_address` in the CONTRACT of `notify`. `logs.bad_address.detected` carries the SIEM fields too (`id, src_ip, dest, dest_kind, seen_via, asset_id`) beside the fields above; `target` = `ioc:<destination>`.
- **Receives**: `inventory` (the device store to look up IPs); the IOC list from `feeds`; (when on, the `siem` job runs and the configuration enables that layer) `findings.finding.created|status_changed|urgency_raised` (`finding.urgency_raised` only for a rise to layer 1 or 2, record level `critical` for layer 1 and `high` otherwise, fields `id`/`asset_id`/`cve`/`basis`/`from`/`to`; `finding.status_changed` adds the field `reason` when present), `notify.incident.created`, `honeypot.hit.created`, `logs.bad_address.detected` to forward to SIEM; `logs.anomaly.detected` is not listened to separately because it already becomes an incident.

## When the module is off (SYS-5)
No `/logs*` routes, no `anomaly` job so no `logs.anomaly.detected` event, and no `syslog` job so no `Ingest` so no IOC lookup, no hits, no `logs.ioc_hit.detected`/`logs.bad_address.detected` event (only `Ingest` creates hits; the `purge` job only deletes hits past retention and emits nothing: `TestIOCPurgeFollowsTheRetentionAndIsSilent`) (`TestContract_SYS5_NoEventsWhileTheModuleIsOff`), no listening on ports 514/5514/6514 (the `syslog` job is cancelled: every socket closes, open connections are cut; test `TestNoSocketWhileTheModuleIsOff`), no SPAN analysis, no SIEM push. `logs_*` is kept. The `ioc_connection` and `log_threshold` triggers of `response` no longer have events; the Logs page and the `logs.panels` panel say "the module is off".
