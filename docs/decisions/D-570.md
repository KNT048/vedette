| D-570 | **The three distribution feeds (`ubuntu-osv`, `ubuntu-vex`, `debian-tracker`, D-516) are each fetched once to fill them, then updated only while the inventory, the box included, has a device of that distribution whose deb packages an agent read (`findings.DeviceDistro`, the same rule the matcher uses for a distribution's word). Without one, a filled feed is not fetched and nothing is recorded; its stored rows stay; it stays due, so the first pull happens at the next check (every 5 minutes) after such a device appears; Settings → Feeds says "Not updated: no Debian device now…" (or Ubuntu). If the inventory cannot be read, or the inventory module is off, the feed is pulled as before. PRIVACY flow 1 now says that Canonical or Debian can tell that you run their distribution, but not which releases or packages (S-FEED-1, S-MIT-1 D-516 criterion; feeds INV-22; LEAN plan §4).** (1) Why: before this, `RunPull` fetched every enabled due feed whether any device needed it. These three are 63 + 79 + 90 MB a day, and the two xz archives unpack to 12.6 + 29.9 GB that `core` parses whenever Canonical changes them (numbers in `distro.go`, 2026-11-14). A box with only Ubuntu devices saves the Debian download and parse; a box with neither saves all three. The data was never used without such a device: findings reads a distribution's word only for an agent's packaged deb row on that distribution (D-516). (2) Privacy trade-off: a box that fetches only the Ubuntu files tells Canonical it has Ubuntu, which the always-fetch design hid. The release and the packages stay hidden, because each file still covers every release. kien's LEAN goal (tools run only what Vedette uses) outweighs hiding the distribution family from its own vendor; PRIVACY flow 1 and Settings → Privacy say it. (2b) Why the first fill always runs (Opus review r1, H1): if the Debian rows were missing when the first Debian device enrolled, NVD's upstream ranges would judge its backported packages, and findings and notify would alert on them until the tracker loaded minutes later. With the rows filled once, that device is judged on them at once. The cost: rows as old as the last pull until the next check (5 minutes) updates them. A distribution's "fixed in" and "not affected" do not change once published, so old rows are right; only a CVE CISA added since the last pull has no word for those minutes. (3) Fail-open: a read error pulls, because a missed "fixed in" closes no finding. Fetching too much costs bandwidth; fetching too little leaves real fixes unread. (4) Top-tier: Trivy and Grype ship one database for every distribution, so they are not the model; their DB is small and pre-built. Wazuh's vulnerability detector (4.x) is configured per provider (canonical, debian, redhat, msu…), with per-OS entries and an `<enabled>` flag each, so only what is configured is pulled. Vedette does the same from the inventory, with no setting to keep in step. ponytail: the inventory is asked on each tick while a distribution feed is due (every 5 minutes while no device needs it); the upgrade is an inventory event when a device's OS changes. | Sources: https://documentation.wazuh.com/4.7/user-manual/capabilities/vulnerability-detection/configuring-scans.html (sample `<vulnerability-detector>` with per-provider and per-OS entries, fetched 2026-11-14); `docs/plans/2026-11-14-lean-tools.md` §4; kien's LEAN goal (2026-11-14 17:1x, via the supervisor). | 2026-11-14 |
