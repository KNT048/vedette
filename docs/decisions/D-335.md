| D-335 | **The `ioc_connection` trigger is fed by `logs.ioc_hit.detected` (the `IocHit` of logs L4, D-213), by subscription, not by polling.** `response.Service.iocEvent` maps a hit to an event `ioc:<hit id>` with the trigger fields `src_ip`, `device`, `dest`, `dest_kind`, `dest_ip`/`dest_domain` (one of them, the other empty), `feeds` (≤ 10 names, joined), `confidence` (0..1, as logs and the trigger field both use, D-57 (13); not ×100) and `switch_port` (empty: nothing knows it yet). Every field is checked at the edge, like a honeypot hit: an id of ≤ 64 plain characters, a private source address (mapped IPv6 kept as IPv4), a destination valid for its kind (address or domain, canonical spelling), a finite confidence in 0..1; anything else is skipped with a warning and never reaches a rule. The device is named from the directory only when its address still matches; else from the hit's own name. | Logs already publishes the event once per device and destination per 24 h; a subscription keeps response free of logs' tables (rules/modules.md) and runs rules within seconds, like `honeypot.hit.created` (#304). Not chosen: polling `logs.Service.IocHits` (a second read path and a delay); multiplying confidence by 100 (the issue text predates D-57 (13), which made both 0..1). | 2026-11-12 |
