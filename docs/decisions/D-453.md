| D-453 | **vedette-host never reboots past a logind block inhibitor (apt installing); it refuses, waits or reports instead.** Measured on Debian 13.7 and Ubuntu 26.04.1: while apt installs, APT holds a logind lock ("APT is installing or removing packages", what `shutdown` / `shutdown:sleep`, mode `block`), and `systemctl reboot` from a system service fails with "Operation denied due to active block inhibitor"; before this the host only logged it while `os.reboot now` had already answered `succeeded`, and a scheduled reboot was dropped, so the box silently did not reboot. (1) **Reading the locks**: `busctl --system --json=short call org.freedesktop.login1 /org/freedesktop/login1 org.freedesktop.login1.Manager ListInhibitors`, one new exact argv in the exec allowlist (`/usr/bin/busctl`, systemd package, already a Depends); `--json` exists since systemd 240 (Ubuntu 24.04 has 255, Debian 13 257, Ubuntu 26.04 259). A lock blocks a reboot when its mode is exactly `block` and `shutdown` is one of its `what` words; `delay` (unattended-upgrades' shutdown hook) never refuses, and `block-weak` (systemd 257) is ignored by logind for root. The parser is fail-closed: exactly `{"type":"a(ssssuu)","data":[[[what,who,why,mode,uid,pid],...]]}`, no unknown field, no trailing data, at most 8192 locks and 1 MiB, otherwise the list is **unknown**, never partial. `who`/`why` come from any local program: printable ASCII only without quotes, angle brackets, ampersand, backquote or backslash (others become `?`), spaces collapsed, at most 64/120 bytes. (2) **`os.reboot now`**: `Check` refuses with a new `409 reboot_inhibited` whose message names who and why. **An unknown list allows**: the safety is logind's own refusal, which the host never overrides; refusing on unknown would make the box unrebootable whenever busctl breaks. (3) **Scheduled reboot**: a block lock postpones it like a running command (`rebootRetryBusy`, 1 minute), the schedule stays (`reboot_scheduled_at`), `reboot_waiting_inhibitor` is audited once per schedule, and the existing 24-hour expiry bounds the wait. (4) **The race** (lock taken between the check and `systemctl reboot`): on a failed `systemctl reboot` the host reads the list again (never systemctl's localized stderr); with a block lock it tries again every 30 s for up to 30 minutes from the start, raising the `rebooting` write gate again at every try so nothing new starts, audits the wait once, and then gives up with `reboot_failed` `{reason: inhibited, who, why}`, clears `Pending` and lowers the gate; any other failure is `reboot_failed` `{reason: systemctl_failed}` at once, as before. (5) **Never** `--check-inhibitors=no`, `--force` or `-i`. (6) **Core and GUI**: no change in this PR; they learn only from the host's audit and log today. Spec text (host-api §6.4) and a deferred line describe the follow-up: core maps `reboot_inhibited` to a 409 with the host's cleaned text, and `GET /v1/state/os` gains `reboot_wait` and `reboot_failed` for the Updates page. | Why: rebooting while dpkg configures can leave packages half-configured; the lead's lab showed `systemctl reboot --force` cutting dpkg mid-configure, which the self-update applier survived but other apt runs may not, and Ubuntu runs unattended-upgrades by default, so a night reboot can meet apt. Nobody in the reference set forces past the lock: systemd says a block lock "inhibits operations entirely until the lock is released" and only a privileged user may override it (https://systemd.io/INHIBITOR_LOCKS/); APT takes the lock precisely so that halts and reboots wait for package operations (Ubuntu bug 1820886, https://bugs.launchpad.net/ubuntu/+source/apt/+bug/1820886); unattended-upgrades' `Automatic-Reboot` runs `/sbin/shutdown -r <time>` after its own run with no flag to ignore inhibitors and only logs when it fails (https://github.com/mvo5/unattended-upgrades/blob/master/unattended-upgrade, `schedule_shutdown`). The lead's brief also names Synology DSM and pfSense/OPNsense refusing a reboot while their own update runs and needrestart, which restarts services and leaves reboots to the admin; not re-verified here, and none of them is cited as forcing. Not chosen: `systemd-inhibit --list` (no JSON even in systemd 259, free-text columns that cannot be split reliably); speaking D-Bus in Go (a new dependency for one read-only call); parsing systemctl's stderr (localized and not a contract); refusing on an unknown list (above); retrying a "now" reboot forever (the gate would block core's writes indefinitely). Limits: a host restart during the 30-minute wait drops the pending reboot as any reboot that did not come (startReboot), with no `reboot_failed` line; a lock held for more than 30 minutes after a "now" reboot ends in `reboot_failed`, and the operator reboots again; a scheduled reboot that waits longer than 24 hours expires (`reboot_schedule_expired`); `who`/`why` text that is not ASCII shows as `?`; the result depends on apt taking the lock (APT has done so since at least 1.6.11, per the bug above). | 2026-11-12 |
