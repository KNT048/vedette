| D-441 | **Log keyword search: a time-budgeted newest-first scan that answers with what it found, how far back it looked and a cursor to continue; no FTS5 index.** Measured once (2026-11-13, `TestMeasureFiveMillionLines`, `VEDETTE_MEASURE=1`, 5,000,000 rows of about 200 bytes over 6 days, Ubuntu box, through `~/vedette-wt/heavy`): before, a keyword that matches nothing was 106 ms (1 h), 2.3 s (24 h) and 503 `server_busy` past 5 s (7 d). After: 1 h 76 ms, 24 h 1.7 s (whole window, no match), **7 d: 5.0 s, answers 200 with an empty list, `searched_back_to` 2026-11-06 10:28 (about 2.6 of the 5 million lines) and a `next` cursor**; a common keyword fills the page of 200 in 8-9 ms with a `next`; no keyword 5-7 ms (unchanged); `Ingest` of 500 lines 10 ms per batch (unchanged, nothing was added to the write path). **How it works:** `GET /logs/events` with a keyword walks the `ts` index from the newest line back in steps of 20,000 rows, filters each step with the same `instr(lower(line), ?)` as before, and stops at 200 matches, at the start of the window, or when `SearchTimeout` (5 s) is spent. The last two cases that did not reach the window start answer 200 with `searched_back_to` (time) and `next` (an opaque `<ts>_<id>` cursor); `before=<next>` continues strictly below it, so no line is answered twice or missed. The GUI says "N matching lines found so far, searched back to <time>. Older lines are not searched yet." and shows **Search older lines**, which appends the next step. A search that could not finish even its first step is still 503 `server_busy`. `total` for a keyword search is the matches found so far (at most 200 per answer); the count to `CountCap` stays for a search with no keyword. The cursor is untrusted input: only the exact `2006-01-02T15:04:05.000Z_<id>` form is accepted (else 400 `bad_cursor`) and it is only ever a bound argument. One trap found while measuring: with two lower bounds on `ts` SQLite takes the first (the window start) and each step read the whole window (700 ms for a step of 18,000 rows); the step now carries only its own lower end (14-25 ms). **Why not FTS5 (now):** the trigram tokenizer is what gives substring search like today's `instr`, and its index is larger than the text it indexes; on a 5 million line table that is a second multi-GB structure on the largest table, an extra write on every `Ingest` (the writer is the part of logs that must not slow down, D-432), a migration that has to index existing rows, and the byte-cap purge (D-200) must delete from it row by row (for external-content tables a delete re-tokenizes the stored text and stale tokens stay if the text differs); substrings under 3 characters (a port, `10.`) fall back to a full scan anyway, so the slow case would remain for short keywords. The honest scan gives the person an answer and the means to go on with no storage cost; FTS5 stays the upgrade if a customer needs "all matches over weeks in under a second". | Why: a customer's log search must not end in an error on a normal-size box; leading log tools tell the person how much was searched instead of failing. Sources (pages opened 2026-11-13): SQLite FTS5 trigram tokenizer, index-size and LIKE fallback below 3 characters, external-content delete caveat (https://www.sqlite.org/fts5.html); Grafana Loki line filters are a "distributed grep" over the selected streams and the answer is to narrow the selector and range, not to index the text (https://grafana.com/docs/loki/latest/query/log_queries/); Elasticsearch returns partial results by default when shards time out, `allow_partial_search_results` (https://www.elastic.co/guide/en/elasticsearch/reference/current/search-search.html); Graylog scopes a search by a time frame the person can scroll (https://go2docs.graylog.org/current/making_sense_of_your_log_data/search_your_log_data.html). Not chosen: FTS5 now (above), raising `SearchTimeout` (holds a reader longer for the same wall), a background search job with polling (a new job type and screen for what a cursor does). | 2026-11-13 |
