The seven feed data images keep Greenbone's tag so the weekly feed update can pull new data; they are trusted only as upstream's own install trusts them (Greenbone's registry over TLS): they run their own entry point as root and write the tests ospd-openvas runs, and whether openvas checks the tests' signatures (with the key of the pinned gpg-data image) depends on `nasl_no_signature_check`, not yet read on a box (deferred). Every change of ours is in `compose.vedette.yaml`. Both ship in the vedette-host .deb at `/usr/lib/vedette/greenbone/`. (2) **Runs with** `podman compose` and docker-compose v2, fixed argv through vedette-host (`up -d`, `stop`, `ps`, `pull`/`up -d` of the seven feed services, `image inspect` of the seven feed images and `rmi <ID>`; never `down`, `-v`, `rm`, `prune`), one OpenVAS operation at a time, not under the global write lock. `greenbone.down` is a new generation: it cancels the operation that runs and every up or feed update already waiting gives up when its turn comes, so a turn-off never loses to a queued up. The provider package is installed on the first enable, not at install (OpenVAS is optional): `docker-compose-v2` on Ubuntu 24.04 and 26.04 (Ubuntu's `docker-compose` is the Python v1 on 24.04; 26.04 has docker-compose-v2 2.40.3, checked on .181 and the N100), `docker-compose` on Debian 13, always `--no-install-recommends` (docker-compose-v2 Recommends `docker.io`: no Docker daemon is ever pulled in). It is a version floor checked by its effect (`podman compose version` ≥ 2.24, the oldest shipped: Ubuntu 24.04's 2.24.6), not a pin: the package comes from the distribution's archive, whose security updates must flow in (as nmap, D-146). docker-compose talks to podman's API, so `podman.socket` is enabled when it was not, with a marker (`/var/lib/vedette-host/greenbone-podman-socket.enabled`) so that `install.sh --uninstall` disables it again only then; an enabled socket that is not active is started. (3) **Socket:** the override binds gvmd's `/run/gvmd` to the host directory `/run/vedette-greenbone/gvmd` (0755, uid:gid 1001 = the user gvmd of Greenbone's gvmd image, made by the host before every up; gvmd listens 666). Its parent `/run/vedette-greenbone` is **0750, root, core's group** (host.conf `core_gid`), made at the host's own start and checked before every up, and core's Quadlet unit mounts it read-only: only root and core can reach or replace the socket; gvmd does not need the parent (the runtime bind-mounts `gvmd/` straight onto `/run/gvmd`), and a host account that happens to have uid 1001 cannot reach `gvmd/` (review r1 M1; the first version's 0755 parent let any local user reach gvmd). Core never depends on a volume compose creates, starts normally while OpenVAS is off, and `Dial` says "starting" until the socket appears. (4) **GMP login:** the admin user's password is 24 random bytes in core/secrets (48 hex), made on the first up and set by the host on every up with gvmd's own documented command (`gvmd --user=admin --new-password=…` as the user gvmd), run through the image's `timeout -k 5 60` so each try ends inside the container, one try at a time, again every 10 s for up to 20 min while gvmd migrates; a wiped volume (W4-1) gets it back. When it never takes, the project is stopped again: it never runs on gvmd's default `admin/admin`. The password travels in the args of greenbone.up (redacted in the audit by its key) and its only exposure is that argv in the box's process list while a try runs (≤ 65 s each), to local users of the box: gvmd has no stdin or file option, and GMP's modify_user would need the old password, which a wiped or foreign database does not give. Never logged, never in an error. (5) **Down / uninstall:** Down = `compose stop`, volumes kept; turning OpenVAS off on the page, and switching the External exposure module off while OpenVAS is enabled, call Down (the module on again starts it). The weekly feed update never stops OpenVAS by itself: a pull that outlasts exposure's 60 minutes leaves the stack up (review r1 M2). After a successful update the host removes the feed images it replaced (by ID, the seven exact feed repositories only, without force, so podman refuses one still used; review r1 M4). `install.sh --uninstall` never touches the project, its containers, images, volumes, the provider package or the socket folder, podman stays with them (W4-1), and the uninstall no longer suggests `podman system reset`, which would delete OpenVAS's volumes. (6) **LEAN-1, only what Vedette uses:** off by `profiles: [disabled]` in the override, each safe because nothing that runs depends on it and Vedette's path (GMP to gvmd over the socket, ospd-openvas scanning, the feed services) never uses it: `gsa` (web UI files for nginx), `gsad` (the web UI's HTTP server; it depends on gvmd, not the other way), `nginx` (the TLS front of gsad and the only service that publishes ports, so nothing of Greenbone listens on a port of the box), `gvm-config` (nginx's config and certificate only), `gvm-tools` (an administrator's interactive GMP CLI; the login uses gvmd's own command), `openvas` (prints the scanner config and tails its log: "shows logs of openvas"; ospd-openvas starts the scanner itself).
