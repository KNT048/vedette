| D-518 | **A new box restores a downloaded backup from its first screen, and the decryption key is downloaded once and kept apart, like an emergency kit (S-CORE-1, A13).** (1) **First-run restore** (appliance only): the setup page offers "Restore from a backup" beside creating an organization. Step 1 `POST /core/setup/restore/upload` (public, the setup code in `X-Setup-Code`, the `.tar.gz` of Download backup as the body, cap 4 GiB, read deadline 30 min) reads the archive with the host's own rules, moved to `host/archive` so core and host share them (only `manifest.json`, `vedette.db`, `vedette.key`, in order, regular files, size caps, no paths, links or PAX records), refuses an archive that carries a key (not a file Download backup makes), stages the database in `snapshots/<id>/` with `upload.json` and no `snapshot.json`, and opens it read-only (`immutable`, `trusted_schema` off, `quick_check`) to check it is a Vedette database of a box that finished setup, no newer than this software (409 `schema_newer`, before anything changes), with exactly the triggers, views and virtual tables this software's migrations make at its own versions (a file changed at rest could plant a trigger that runs on the live box, or drop the audit log's append-only ones; review round 1, M1), and with an intact gzip trailer; the answer says what it holds (organization, date, users, two-step users, administrators who can sign in without the key, saved secrets). The box keeps one upload; a new one replaces it; one never restored goes with the 1-hour start-up sweep. Step 2 `POST /core/setup/restore` (public, setup code; key file as base64, optional) refuses a key that is not 32 bytes (`invalid_key`) or opens none of the backup's secrets (`wrong_key`), and without a key a backup that holds secrets needs `confirm_without_key` (the page lists what is lost first: saved secrets must be re-entered, two-step users cannot sign in; and when no administrator can sign in without the key it says the box will not be usable and asks for the key). Then core writes the key and `snapshot.json`, so the upload becomes a snapshot of the host contract (host-api 6.11), the host imports it with the existing `backup.create {manual}` (label "Uploaded backup of <date>"), and the restore is D-377's (`startRestore`: a snapshot of the fresh box becomes `pre_restore` and is put back when the restored data does not start). **No new host command and no second restore mechanism**; a new host accepts the import because it is an ordinary manual backup. `GET /core/setup/restore` (public) gives only `status` and `error` while setup is open, `done` once it is done (no more than `GET /setup` says). Both steps are closed once setup is done (409 `already_setup`), go through the setup-code limiter of D-75, and hold one first-run lock with `POST /core/setup`, which also answers 409 `busy` while a restore runs (setup and a first-run restore never overlap; M2); a key given with a backup that holds no secret is not used (nothing to check it against; the box keeps its own); and write audit rows as user `setup` (`data.restore_upload`, `data.restore_import`, `data.restore`; on success they are replaced by the restored database, which records `data.restore_done`). Container-only install: no helper, so the page says so and shows the `docs/INSTALL-CONTAINER.md` §6 commands, as Settings → Data does. (2) **Key aside** (A13-2): Settings → Data → Backup says the file cannot restore secrets or two-step sign-in without the key and offers **Download decryption key**: `POST /core/data/key` (admin; current password, then a fresh two-step code when on, as for a restore; audit `data.key_download`) answers the 32 bytes of `vedette.key` as `vedette-key-<date>.key`, the same file the manual RUNBOOK steps put back, and nowhere else (never logged, never in another response). An administrator who signs in only with SSO has no Vedette password to confirm with: the page says an administrator with a password must download it (an SSO step-up is deferred). (3) A13-1: the Data page reads the list of backups again when a restore it saw running ends. **Not chosen:** a password-protected backup with the key inside (Home Assistant's way; it needs a key-derivation and archive format change in host and core, and a password a customer can forget; the separate key file gives the same "two things to keep" without new crypto); a new host command `backup.import` (the host would have to read an uploaded archive from core's tree; `backup.create` of a core snapshot already does the job under the existing D-87 contract); multipart upload (ogen spools parts over 32 MiB to `/tmp`, a 64 MiB tmpfs in core's container); restore without the setup code before setup (anyone on the LAN could replace the box's data). | Home Assistant onboarding has "Restore from backup" on its first screen, and its encrypted backups come with an "emergency kit" holding the encryption key that the user is told to keep apart (https://www.home-assistant.io/common-tasks/general/#backups, https://www.home-assistant.io/blog/2025/01/03/release-20251/); UniFi offers restore from a backup file while setting up a new console (https://help.ui.com/hc/en-us/articles/360008976393); OPNsense and pfSense restore an uploaded configuration file from the GUI, and pfSense warns that encrypted configs need their password (https://docs.opnsense.org/manual/backups.html, https://docs.netgate.com/pfsense/en/latest/backup/restore.html).
