# Vedette operations runbook

Written 2026-11-11 against the code on `main`. Box architecture: an appliance (`vedette-host` + Podman/Quadlet containers; OS releases: Ubuntu 24.04, Ubuntu 26.04, Debian 13; networking with netplan + networkd), with the network/SPAN configured by `vedette-host`. Where the product does not do something yet, exactly one line says `not yet: …`; nothing is guessed and no screen that does not exist is described.

Convention: **Symptom → Check → Fix → Verify**; verify by effect (the service runs, the port is open, the API answers), not by exit code. Do not SSH in, edit the configuration by hand and leave it: the Quadlet units, `host.conf` and the trap configuration are all generated from the code/DB, so a hand edit is overwritten or refused by the host. UI labels are kept in English as in the current GUI.

Every command below runs as root on the box. Podman is **rootful**, so `podman` must also run as root. Names: systemd services `vedette-host`, `vedette-core`, `vedette-sensor`, `vedette-scan`, `vedette-honeypot`; containers with the same names.

**Quick status** (use before every other section):

```sh
systemctl is-active vedette-host vedette-core                      # active active
podman ps -a --format '{{.Names}} {{.Status}}'                    # vedette-core ... (healthy)
curl -ks -o /dev/null -w '%{http_code}\n' https://127.0.0.1:8443/api/v1/setup   # 200
podman port vedette-core                                           # 8443, 514, 6514 on all addresses; 8444, 8765 only on 127.0.0.1
ss -Hltnup | awk '$5 ~ /:(8443|8444|8765|514|6514)$/'              # who is listening on Vedette's ports (§1.1 step 4)
journalctl -u vedette-core -u vedette-host -n 100 --no-pager
```

## 1. Installation

### 1.1 Appliance (full features)
- Requirements (checked by the `install.sh` preflight; if one fails it stops and **changes nothing**): root; Linux with systemd as PID 1 (not an ordinary container); Ubuntu 24.04, Ubuntu 26.04 or Debian 13; amd64 or arm64; the clock set; ports 8443, 8444, 8765 (TCP) and 514 (UDP and TCP), 6514 (TCP) not in use by anyone (rsyslog with imudp/imtcp enabled holds 514: turn off its network input first; a reinstall on a box that is already installed does not check ports); no other Vedette present (`host.conf`, the `vedette-host` package, the `vedette` user, the `vedette-*` containers); **at least 6 GiB free under `/var`**. RAM below 4 GiB gives a warning, not a stop (8 GiB recommended). NIC: one card with an IP is enough; SPAN needs an additional card with no IP, and a wired network (Wi-Fi does not support SPAN or macvlan traps).
- Install with one script, which can be run again (idempotent):
  ```sh
  curl -fsSLO https://github.com/KNT048/vedette/releases/download/v<version>/install.sh && sudo sh install.sh
  sh install.sh --help          # options: --network-handover | --uninstall --yes [--keep-data]
  # through a pipe, pass options with: curl -fsSL <url> | sudo sh -s -- --network-handover
  ```
  (Keep the `install.sh` file: §1.3 and §3 run it again. Uninstalling does not need the release values in the script, so any copy will do.)
  The script does, in order: preflight → install the **missing** apt packages (it does not upgrade packages that are already there) → download the `.deb` of the exact release and check the sha256 written into the script → write `/etc/vedette/host.conf` from the real user id → (optionally) hand over netplan → `vedette-host -bootstrap` (checks the minisign signature of the index and manifest, the cosign signature of the images that is inside the manifest, and pulls images by digest) → start `vedette-host` and `vedette-core`, and wait up to 300 s for healthy. Running it again after an interrupted run continues the repair; only `--uninstall --yes` removes. By default it **does not touch the box's network**; `--network-handover` only when netplan has exactly one wired DHCP card, and it only writes files without applying them at once (applied at the next boot or when confirmed in Box network). Without `--network-handover`, Settings → Box network still opens but Save is refused (409 `net_backend_unsupported`; the installer calls it "read-only").
- Verify the install (by effect):
  1. `systemctl is-active vedette-host` prints `active` and `test -S /run/vedette/host.sock` succeeds (socket 0660 `root:vedette`).
  2. `podman ps` shows `vedette-core` healthy: `podman inspect --format '{{.State.Health.Status}}' vedette-core` (Podman 4.x: `{{.State.Healthcheck.Status}}`) prints `healthy`.
  3. `curl -ks https://127.0.0.1:8443/api/v1/setup` returns 200, and also returns 200 at `https://<management IP>:8443/api/v1/setup` from another machine on the LAN.
  4. `podman port vedette-core` prints exactly the lines of the `core` unit (`host/ops/quadlet.go`): `8443/tcp -> 0.0.0.0:8443`, `8444/tcp -> 127.0.0.1:8444`, `8765/tcp -> 127.0.0.1:8765` (MCP), `5514/udp -> 0.0.0.0:514`, `5514/tcp -> 0.0.0.0:514` and `5515/tcp -> 0.0.0.0:6514` (syslog and syslog TLS). **Check the ports on the machine:** `ss -Hltnup | awk '$5 ~ /:(8443|8444|8765|514|6514)$/'` prints 8443 on all addresses (`0.0.0.0`/`*`), 8444 and 8765 only on `127.0.0.1`, 514 as both `udp` and `tcp` and 6514 `tcp` on all addresses: rootful podman reserves the published ports, so `ss` sees them (a trial install, `docs/INSTALL-TEST.md` step 3; the preflight and `--uninstall` of `install.sh` also read the ports with `ss`). The process column (`users:((…))`) belongs to podman; the name of another program (for example `rsyslogd` on 514) means that program is holding the port and Vedette receives nothing there. 8444 or 8765 on an address other than `127.0.0.1` is wrong: report the error, do not fix the unit by hand. A published port does not mean someone is listening: 8765 answers only when `mcp-server` is on, 514/6514 when `logs` is on, whether or not a source exists yet (6514 when the box has an HTTPS certificate) (§10). There is no other Vedette port (22/80/445/1433/3389 are open only on the trap IP when `honeypot` is on).
  5. The images passed the signature check: `/var/lib/vedette-host/containers/versions-core.json` exists (this file is written only when `-bootstrap` exits 0); with a wrong signature `-bootstrap` refuses and **starts nothing** (the installer prints "vedette-host refused the release").
- Unsupported OS: the script stops, prints the reason and "Nothing was changed". A trial install on a real box with a folder built with `make install-artifacts` and a temporary key: `docs/INSTALL-TEST.md` (a test channel, for the team only; the test channel and the customer channel are not mixed, and switching channel requires `--uninstall --yes` first).
- not yet: a real release. `install.sh` in the repository has three version/sha256 values left blank, so it stops with "not tied to a release"; the real signing keys and pushing images are still to do.
- not yet: an ISO or VM image (later).
- not yet: RAM/disk measurements under real load. The design size of 4 cores / 8 GB / 64 GB SSD for the target of 1,000 devices (`DEPLOYMENT.md` §4) has not been measured; the installer only enforces 6 GiB free.

### 1.2 Container only (existing Docker/Podman)
- A full customer guide (in English): `docs/INSTALL-CONTAINER.md`: the files in `deploy/compose/container-only/` (`vedette.env`, `compose.yaml`, `compose.sensors.yaml`, `compose.syslog.yaml`), install, update, back up, uninstall. `deploy/compose/compose.yaml` (the parent folder) is only a dev environment (`make dev-sensors`) and is not used to run for real.
- **The master key and the data live in the volume `vedette_data`** (compose project `name: vedette` + the volume `data` of `compose.yaml`, mounted at `/var/lib/vedette` of `core`): `vedette.db`, `vedette.key`, the self-signed certificate, `logs.db`. The two volumes `vedette_creds-passive`, `vedette_creds-active` hold only the sensors' credentials, and `core` rewrites them from `vedette_data` on every start: they need no backup. There is no `vedette-host`, so there is no backup on the machine: a backup is copying the volume while `core` is stopped, with the commands of `docs/INSTALL-CONTAINER.md` §6 (Settings → Data of this build shows exactly those commands, for Docker or Podman): `docker compose --env-file vedette.env stop core`; a `debian:trixie-slim` container pinned by digest (`DEBIAN_IMAGE` of `deploy/containers/pins.env`; the test `TestInstallGuideUsesThePinnedDebianImage` keeps the guide in line, so copy the command from there, not from here), `--network none`, mount `vedette_data:/data:ro`, run `umask 077 && tar czf /backup/vedette-data.tgz -C /data .`; then `start core`. Podman on a machine with SELinux needs `:Z` on the target folder. The file `vedette-data.tgz` (root, 0600) holds the master key: keep it like a password. Verify: `tar -tzf vedette-data.tgz` contains `./vedette.db` and `./vedette.key`. Restore: the same §6 (`down --volumes` or a new machine, `create core`, extract into the volume, `start core`).
- An appliance is different: the `core` data is the machine's `/var/lib/vedette` directory (the line `Volume=<core_data>:/var/lib/vedette` of the `core` unit, `host/ops/quadlet.go`), not a podman volume; the three Quadlet volumes `vedette-creds-passive`, `vedette-creds-active`, `vedette-hp-log` (tmpfs) hold no key. Appliance backup: §5.
- A port that another program already holds (8443, 514, 6514): do not edit the release's compose files; write your own `compose.ports.yaml` file with `ports: !override` and the consequences of each port (the box's link still says `:8443`, 8444 must be kept when running the sensors, the firewall, self-call protection): `docs/INSTALL-CONTAINER.md` §4 "Other host ports". Appliance: the ports are fixed in the unit and cannot be changed; the `install.sh` preflight stops when a port is held.

### 1.3 Uninstall and delete data
The right way for a box built by `install.sh`: **run again the script that built it**.
```sh
sh install.sh --uninstall              # only says what it would remove, does nothing
sh install.sh --uninstall --yes        # uninstall; DELETES the DB and the master key (cannot be undone)
sh install.sh --uninstall --yes --keep-data   # uninstall but keep /var/lib/vedette*, /etc/vedette and the users
```
- **Reinstalling after `--keep-data`.** Run `install.sh` of the same channel (release or test build, per `/var/lib/vedette-install/owner`; a different channel makes the script refuse and tell you to `--uninstall --yes`, a command that DELETES the kept data) and of the same or a newer version, and Vedette comes back with its old data and users: setup does not ask again and the old administrator can sign in. `--keep-data` removes the units and images but keeps `/var/lib/vedette-host`, in which `containers/versions-core.json` records the `core` version that last ran on that data. When the next install sees the record but no unit any more, it: (1) refuses at once in the preflight, changing nothing, when the script's version is **older** than that version (`this box keeps the data of Vedette <version> … newer than the release of this script`: the core migrations only go forward; use the `install.sh` of that version or a newer one); (2) deletes the host's container records (`containers/versions-*.json`, `pulled-*.json`, `transition-*.json`, `containers/units/`; the data, the backups, the release index and the host package records are kept) and then bootstraps the script's version, pulling the images again (the images were removed, so it needs the network as at the first install). Before deleting, the script writes that version to `/var/lib/vedette-install/kept-release` and removes the note only when the bootstrap is done, so a run that fails midway still keeps the refusal of an older version. A newer version: the script warns that `core` will migrate the data up and it cannot go back; this path has **no** `pre_update` backup like Settings → Updates, so make a backup (Settings → Backups) **before** uninstalling. A run in which the `core` unit is missing while the record remains (deleted by hand) also bootstraps again. `vedette-host -bootstrap` does not run while the daemon is running (`daemon_running`, code 6): the script stops `vedette-host` itself before the bootstrap (`stopping vedette-host for the bootstrap`; honeypot has `Requires=` on the host so it stops too) and starts both again afterwards, even if the run fails.
- Removes: containers, images, networks and volumes (including the `vedette-zap` container, the `vedette-zap` network, the nft table `inet vedette_zap` and the ZAP image with the exact pinned digest), the Quadlet units, the `vedette-hp` namespace, the `vedette-host` package and the apt packages that the script itself installed (only when nobody else needs them), restores `ip_forward` and the nft tables as they were, then deletes `/var/lib/vedette`, `/var/lib/vedette-host`, `/var/lib/vedette-honeypot`, `/var/lib/vedette-creds`, `/etc/vedette`, `/var/log/vedette-host`, the users and groups `vedette`, `vedette-sensor`, and the `containers:` lines in `/etc/subuid`, `/etc/subgid` if the script itself added them. If apt would have to remove more packages than that set, the script does not remove more and says so (this sentence is only about apt packages). A netplan that was handed over is restored to the old file (applied at the next boot).
- **The apt packages that will be given back.** The dry run `sh install.sh --uninstall` (still needs root) **does not print package names**: it only prints the names of the list files ("the packages this script asked apt for (listed in /var/lib/vedette-install/asked-packages) and the ones apt installed for them or for an update of vedette-host (…/installed-by-us, …/selfupdate/installed-by-us), each when nothing else needs it") and then stops with `ERROR: run again with --yes to do it` (exit code 1, nothing changed). Read the lists by hand:
  ```sh
  cat /var/lib/vedette-install/asked-packages            # packages the script asked apt to install (only those missing at install time)
  cat /var/lib/vedette-install/installed-by-us           # every apt package installed NEW for that run, dependencies included
  cat /var/lib/vedette-host/selfupdate/installed-by-us   # apt packages newly installed when vedette-host upgraded itself (added Depends); usually this file does not exist
  cat /var/lib/vedette-install/removed-packages          # apt packages removed at install time (only systemd-timesyncd is allowed): uninstalling Vedette installs it again
  ```
  How they are recorded: the script's two files are written **before** apt runs, from `apt-get -s` (the `Inst` lines of packages that are not yet present; a package that is only upgraded does not go in); a package that was already on the machine at install time never goes in the list. `asked-packages` can only contain `ca-certificates curl podman chrony netplan.io nftables iptables iproute2 procps unattended-upgrades passwd conntrack` and `netavark aardvark-dns catatonit` (when the distribution has them). The host's file (0600, one name per line) is written by the self-upgrade before it installs a new package (`host/ops/selfupdate.go` `recordAddedPackages`); if the file is a symlink the script ignores it.
  At `--yes` (`install.sh` `purge_added_packages`): purge `vedette-host`; `apt-mark auto` the packages of `asked-packages` that are still installed; the candidates = `asked-packages` + the two `installed-by-us` files, **except** a package marked manual (`apt-mark showmanual`, read after the `auto` step); purge each candidate that `apt-get -s autoremove --purge` considers surplus (repeat at most 6 passes); if a purge would drag in a package outside that set it stops with `not purging the packages the installer added: apt would also remove …`. The remaining packages of the two `installed-by-us` files (for example a package that another package only Recommends) are purged when purging it does not drag in a package outside the list, otherwise it prints `kept <package>: another package depends on it`. Finally it installs `removed-packages` again. `--keep-data` does exactly the same and then empties the lists (the host's file is deleted).
  For the operator: read the lists **before** `--yes` and note the packages the machine still needs (do not edit those files: they are the installer's state). A package that is only in `installed-by-us` (not in `asked-packages`): `apt-mark manual <package>` before `--yes` keeps it, because the script drops every package that is manual from the candidates and from the later purge pass. A package in `asked-packages` (they are also in `installed-by-us`): the script sets `auto` again before it reads the manual flag, so `apt-mark manual` does not keep it (an accepted limitation); after `--uninstall --yes` reinstall it with `apt-get install <package>`. Reinstalling `podman` does not bring back a deleted `/var/lib/containers` (see below: back up other containers first). `chrony`, installed by the script, is always turned off (`systemctl disable --now`) whether or not it is purged: to keep it, after uninstalling run `apt-get install chrony` (if it was purged) and then `systemctl enable --now chrony`. Verify after uninstalling: `dpkg-query -W -f='${Package} ${db:Status-Status}\n' <package>` prints `installed` for each package you want to keep.
- **The exact list: which packages are removed and which stay** (`install.sh` `purge_added_packages`, `podman_pkgs`, `podman_stays`):

  | Fate | Packages |
  |---|---|
  | Always purged | `vedette-host` |
  | Purged when apt sees them as surplus (`autoremove`) **and** purging does not drag in a package outside this set | the lines of `asked-packages` (can only be `ca-certificates curl podman chrony netplan.io nftables iptables iproute2 procps unattended-upgrades passwd conntrack netavark aardvark-dns catatonit`; a package that was already there at install time has no line) and the lines of the two `installed-by-us` files that are not `apt-mark manual` |
  | Stay when podman stays | `podman crun runc conmon netavark aardvark-dns catatonit containers-common golang-github-containers-common nftables iptables` and every installed package that `podman` Depends on or Recommends, following the whole tree; the script `apt-mark manual`s those of them that it asked for. Podman stays when: rootful podman still has a container, pod, network (other than `podman`, `vedette-int`), volume or named image that is not Vedette's; podman does not answer within 60 s; `--keep-data` is used; podman was not installed by the script or `vedette-host` (it is the administrator's); or apt cannot purge it |
  | Always stay | every package that is not in the three files (already on the machine before the install); a package that is only in `installed-by-us` and is manual; a package that prints `kept <package>: another package depends on it` |
  | Installed again | the lines of `removed-packages` (can only be `systemd-timesyncd`) |

  Preview on the box (root, read-only, changes nothing):
  ```sh
  cat /var/lib/vedette-install/asked-packages /var/lib/vedette-install/installed-by-us /var/lib/vedette-host/selfupdate/installed-by-us 2>/dev/null | sort -u   # candidates
  apt-mark showmanual | sort -u          # a candidate that is only in installed-by-us and appears here stays
  apt-cache depends --recurse --installed --no-suggests --no-conflicts --no-breaks --no-replaces --no-enhances podman | grep -E '^[a-z0-9][a-z0-9+.-]*$' | sort -u   # the tree part of the "stay when podman stays" list
  podman ps -a --external --format '{{.Names}}'; podman pod ps --format '{{.Name}}'; podman network ls --format '{{.Name}}'; podman volume ls --format '{{.Name}}'; podman images --format '{{.Repository}}'
  #   podman stays if there is still a name outside: containers vedette-{core,sensor,scan,honeypot,greenbone}; the podman, vedette-int networks;
  #   volume vedette-{creds-passive,creds-active,hp-log}; image <none>, localhost/podman-pause, localhost/vedette-scan-nmap,
  #   {ghcr.io/knt048,localhost}/vedette-{core,sensor,honeypot,scan,greenbone}
  ```
  The dry run does not print this list. When podman was installed by the script (or `vedette-host`) and stays, the last line of the uninstall says why (`kept podman, the packages it runs with and /var/lib/containers: …`); an administrator's podman stays without that line.
- **Other people's podman is kept:** after removing Vedette's containers, volumes, networks and images, the script asks rootful podman whether anything that is not Vedette's remains (containers including stopped ones, pods, networks other than `podman`/`vedette-int`, volumes, named images). If there is anything, if podman does not answer (fail closed), or if it ran with `--keep-data` → it does **not** purge `podman` and the packages it runs with (crun, conmon, netavark, aardvark-dns, catatonit, the packages podman Depends on and Recommends), does **not** touch `/var/lib/containers`; packages the script installed by name are `apt-mark manual`; when there are foreign containers/pods, netavark's IP forwarding and nft tables are also kept. The last line says what is kept and why, for example `kept podman, the packages it runs with and /var/lib/containers: 21 containers … that are not Vedette's use it (greenbone-…)`. With `--keep-data`, podman and those packages remain in `asked-packages`/`installed-by-us`, so a later full uninstall (when podman has nothing else) still purges them. To remove the kept podman yourself: first remove whatever still uses it (`podman ps -a`, `podman volume ls`, `podman images`; the OpenVAS feed and DB are volumes), then `apt-get purge podman`, then `apt-get autoremove`; the script no longer suggests `podman system reset` because that command also deletes the OpenVAS volumes. OpenVAS (Greenbone's compose project) is never removed; `podman.socket` is turned off again only when `vedette-host` turned it on (the marker `/var/lib/vedette-host/greenbone-podman-socket.enabled`). When podman stays, `nftables`, `iptables` and every package podman Recommends (following the tree) also stay, even with the administrator's own podman; the `containers:` lines in `/etc/subuid`/`/etc/subgid` are also kept. A Vedette network, volume or image that a foreign container is using is not removed with `-f`: it stays with a warning (`podman ps -a --filter network=vedette-int`). Every podman command at uninstall has a 60 s `timeout`; a command that hangs → podman is kept and the rest is removed.
- **Careful, this is wider than Vedette:** if the script itself installed `podman`, podman has **nothing but Vedette's**, there is no `--keep-data`, **and apt purged it** in the step above, the script deletes **all** of `/var/lib/containers` and `/run/containers`, and then the directories that the packages and podman created for `vedette-int` (`/etc/containers/networks`, `/etc/containers/systemd/users`, `/etc/containers/systemd`, `/etc/containers/registries.conf.d`, `/etc/containers`, `/var/lib/cni/networks`, `/var/lib/cni`) **only when they are already empty** (`rmdir`, deepest first, never deleting content) and no installed package owns them (`dpkg-query -S`): a directory that still has files belongs to someone else and stays. A `podman` that apt **keeps** (another package needs it, or it was marked manual after the install) is the administrator's: the script does not touch `/var/lib/containers`, `/run/containers` or those directories; the `vedette-*` images, containers, volumes and networks are still removed as above. If the script installed `chrony` it turns it off (purging `chrony` runs the postrm of dh_apparmor, which deletes the empty directories `/etc/apparmor.d/disable`, `local`, `force-complain` of the `apparmor` package; while the `apparmor` package is still installed, the script puts back whichever directory was there before, with the same mode; a box with no `apparmor` package has that directory only because of the purged profile and it is not put back); it deletes the system accounts that the added packages created (for example `_chrony`). If there are other containers on the machine, back them up first.
- `apt remove vedette-host` or `apt purge vedette-host` (not through the script) only removes the binary, the units and the enabled state. **The data stays intact, even after `purge`**: the DB and master key `/var/lib/vedette`, the backups and host state `/var/lib/vedette-host`, `/var/lib/vedette-honeypot`, `/etc/vedette/host.conf`, the Quadlet units `/etc/containers/systemd/vedette-*`, the users and groups, the subuid/subgid lines. The master key cannot be recreated: lose it and every stored secret is lost.
- A hand-installed box without the `vedette-host` package, without `host.conf` and without `/var/lib/vedette-install` (only then does the script say "nothing to remove"; a box that has the package gets the normal removal from `sh install.sh --uninstall --yes`): there is no script; do it by hand in exactly this order, with no way back: `systemctl stop vedette-honeypot vedette-scan vedette-sensor vedette-core vedette-host vedette-int-network vedette-creds-passive-volume vedette-creds-active-volume vedette-hp-log-volume` (the last four units must be stopped, otherwise they block the next install); `podman rm -f vedette-honeypot vedette-scan vedette-sensor vedette-core`; `ip netns delete vedette-hp`; `rm -f /etc/containers/systemd/vedette-*`; `systemctl daemon-reload`; `podman network rm -f vedette-int`; `podman volume rm -f vedette-creds-passive vedette-creds-active vedette-hp-log`; remove the images by exact name `ghcr.io/knt048/vedette-<service>`, `localhost/vedette-<service>` (service: core, sensor, honeypot, scan, greenbone) and `localhost/vedette-scan-nmap` (`podman images`, `podman rmi -f <id>`; other `localhost/vedette-*` images belong to the customer, do not remove them); `apt purge vedette-host`; then delete each directory above and `userdel`/`groupdel` the two accounts. Do not delete the `containers:` lines in `/etc/subuid` if the machine still has other containers that use `--userns=auto`.
- Verify (as §1.1 steps 3–4): `ss -Hltnup | awk '$5 ~ /:(8443|8444|8765|514|6514)$/'` prints nothing (any line that remains is another program; the script also warns `port <n> still listens` for 8443, 8444, 8765); `curl -ks -o /dev/null -w '%{http_code}\n' --max-time 5 https://127.0.0.1:8443/api/v1/setup` and the same command with `https://127.0.0.1:8444/` print `000` (nobody answers any more; if the script removed the `curl` it installed, try 8443 from another machine on the LAN at `https://<management IP>:8443/api/v1/setup`); `podman ps -a` (while `podman` remains) shows no `vedette-*`, so there is no container left to publish a port for `podman port`; `ls /run/netns` has no `vedette-hp`; (without `--keep-data`) `getent passwd vedette` is empty and `/var/lib/vedette` is gone.
- Delete the data but keep the software: Settings → Data → Delete all data (see §5.4).

## 2. First start
The initial setup is done entirely in the GUI, with no SSH.
- **Get the address and the setup code.** At the end `install.sh` prints `open: https://<IP>:8443` and `setup code: XXXXX-XXXXX-XXXXX-XXXXX` (4 groups of 5 characters, single use). If you lost that screen: `journalctl -u vedette-core -o cat --no-pager | grep setup_code | tail -n 1`. The box prints the code again at every start until the first administrator is created; after that the code is deleted and no longer printed. A missing or wrong code makes `/setup` return 403 `invalid_setup_code`. The TLS certificate is self-signed: accept it once; it follows the management address, and if the address changes accept it again.
- **Order of screens** (four steps): Terms of use (read `TERMS.md`, tick "I have read, understood and agree to the terms of use"; Continue is disabled until ticked) → Account (organisation name, administrator, setup code) → Network (LAN range, the prefix length is mandatory) → Modules (the Small business, Mid-size business or Custom bundle; a module that needs another module pulls it in); **Finish setup** at the Modules step and then Home. After that, still in the GUI: Settings → Alert channels (the first alert channel; Home reminds "No alert channel yet" until one channel is on), Settings → General (timezone, organisation name), My account (turn on two-step with an app or an email code; the product does **not force** it), Settings → Feeds.
- **Safe defaults.** Optional modules are off until the bundle you choose turns them on: Small business turns on feeds, inventory, notify, sensor-passive, findings, mitigation, honeypot, reports; Mid-size adds sensor-active, scan, exposure, logs, ai. `response` (response actions on devices) and `mcp-server` are in no bundle: off; the execution switch of `response` is its own switch, also off. Active scanning runs only within the scope whose ownership you have confirmed and agreed to.
- **Box network** (Settings → Box network). Management address: Save asks for confirmation first (409 `confirm_required`), and then applies at once with a **5-minute confirmation window** (fixed): open the GUI at the new address, sign in again, press confirm; if you do not confirm in time, or the box restarts before confirmation, the box **returns to the old address by itself**. On every change the host ARP-probes the new static address and refuses if it is taken (`address_conflict`). SPAN: the "SPAN capture" card chooses the port (no IP, listen only; the management card cannot be used), chooses "What Vedette reads" (DNS queries, TLS server names, HTTP hosts, Connection metadata), "Exclusions". A box whose netplan has not been handed over (§1.1) refuses Save (`net_backend_unsupported`). A box with a netplan generated by cloud-init (a cloud image, a Proxmox template: `/etc/netplan/50-cloud-init.yaml` matches the card by MAC address and renames it) has Box network **read-only by design in v1**: `install.sh --network-handover` does not accept that netplan (it prints "Box network is not available on this box" and does not touch the network); change that box's address with cloud-init or the hypervisor (accepting cloud-init's netplan: after v1).
- **Verify:** sign-in works (and asks for a code when two-step is on); Home shows data with a timestamp; in Settings → Feeds every enabled source has a "Last fetch" within `interval_hours` + 60 minutes (feeds INV-9; the box pulls straight from each source over HTTPS, there is no signed `index.json` for feeds); Home does not say "0 newly exploited" when the CISA list could not be loaded (it reports `never_loaded` with the error).

## 3. Upgrading Vedette software
- Upgrade the `core`/`sensor`/`scan`/`honeypot` images from the GUI (S-CORE-2; `modules/core/updates_check.go`, `updates_run.go`, `updates_auto.go`): Settings → Updates; the Vedette software is **one** release for every image. "Check" (operator) downloads and verifies the signed index and manifest from `https://github.com/KNT048/vedette/releases/download`; channel `stable` or `beta`, manual or automatic mode (admin); a new version is offered only when the box is in the cohort currently being rolled out ("not in the rollout yet (cohort …)"). "Apply" (admin) is one run: `container.pull` for every installed service, `core` **first** (the host makes a `pre_update` backup, a health gate, and automatically returns to the old unit when not healthy: run `reverted`, no other service has changed), then `container.start` for the services that are on (a sensor/worker is never newer than `core`; `core` accepts their proto and the one just before). A service that fails after `core` has changed returns to the old version by itself and keeps running with the new `core`: the run is `failed`, `core` is on the new version (there is a history line), and that service comes up at the next update; to bring the whole box back to the old version use Rollback. A service whose module is off is only pulled, not started. Automatic mode checks every 6 hours ± 30 minutes and installs only in the maintenance window (§6). If update checks are turned off in Privacy, no request is sent (409 `check_off`). not yet: a real release to upgrade to; an offline bundle (`/core/updates/bundle` is in the contract but has no handler yet).
- Available now: running the `install.sh` of the new release again upgrades the `vedette-host` package; when the script sees that it has already bootstrapped (there is a `versions-core.json`) it **skips the bootstrap** and leaves the containers alone. The new package restarts `vedette-host` by itself if it is running (postinst `try-restart`; a stopped unit stays stopped). `core` does not depend on the host so it is not restarted; `vedette-honeypot` has `Requires=vedette-host` so it restarts together. Verify: `/usr/lib/vedette/vedette-host -version` equals the script's version **and** `systemctl show -p ActiveEnterTimestamp vedette-host` is a time after the script run; `systemctl is-active vedette-host` prints `active`; `podman inspect --format '{{.State.StartedAt}}' vedette-core` is unchanged (core was not restarted). (An older version does not restart itself: then run `systemctl restart vedette-host`.)
- A box installed with an older version (the honeypot log is a directory on disk): the old `core` and `honeypot` units do not change by themselves. You must run `vedette-host -bootstrap -force-units` for **both `core` and `honeypot` in the same pass**; the two units share the tmpfs volume `vedette-hp-log`, so one unit that still has the old bind makes every hit disappear without an error (bootstrap refuses to write a single unit while the other still has the old bind). Verify: one touch of a trap shows up in Honeypot → Hits.
- A unit written by the previous host version (the template from when the honeypot log became a volume; `host/ops/quadlet_legacy.go` `migrateUnits`): the new host rewrites it with the current template at startup (audit line `unit_migrated`) without restarting the container; the new text takes effect at the service's next restart (the image step of an update, a `container.start` with restart, or a reboot). **Except** a unit for which the current template publishes one more port of the machine (`core`: `6514` or `127.0.0.1:8765` with an old unit that does not have that port yet): at startup the host does **not** rewrite that unit, whether the port is free or busy; every time the host starts it writes one audit line `container.start` `unit_migration_deferred` with `ports` (e.g. `["8765/tcp"]`), no daemon-reload, and a reboot still runs the old unit (without the new port). The unit moves to the new template only at the next `container.start` that **restarts** the service (the image step of a software update) or at `container.rollback` (Rollback): just before restarting, the host checks the new port; if another program is listening on that port the command is refused with `412 port_in_use` (the message names the port and the process, the unit and the container do not change, and the old service keeps running; during an update the run stops at the `core` step with the box on the old version; if the port was taken while the `pre_update` backup was being made, that backup is still in Settings → Data, harmless). Then: `ss -ltnup 'sport = :8765'` (or `:6514`) finds the program, stop it or move it to another port, then Apply again. Verify: `grep -r unit_migrated /var/log/vedette-host` (the host's audit log; for a unit that adds a port, `grep -r unit_migration_deferred` shows which port is waiting) and, after a restart caused by the image step of an update (not a reboot), `podman inspect vedette-core --format '{{.HostConfig.PortBindings}}'` has the ports of the new template (e.g. `6514/tcp`, `8765/tcp`). A hand-edited unit is never rewritten: `412 unit_unsafe`; look at it and then `vedette-host -bootstrap -force-units`.
- Downgrading `vedette-host` by hand (`dpkg -i` of an older package after the newer one has rewritten the units with its template): the old version does not know the new template, so every container command gets `412 unit_unsafe`; run `vedette-host -bootstrap -force-units` (stop `vedette-host` first) so that the old version rewrites its units. Downgrading to a version that has no AppArmor profile for containers is more urgent: a unit that has moved to the new template has the line `ContainersConfModule=/usr/lib/vedette/apparmor-containers.conf`, a file that the older package deletes when it replaces the package, so **every container breaks at the next restart** (Podman reports a missing module); the old version's `-bootstrap -force-units` rewrites the units without that line (the profile `/etc/apparmor.d/vedette-container` remains as an old conffile, harmless). Verify: `container.start` of each service no longer has `unit_unsafe` and `grep -L apparmor-containers /etc/containers/systemd/vedette-*.container` lists all the units.
- Changing the id of the `vedette`/`vedette-sensor` accounts (`core_uid`, `sensor_gid` in `host.conf`) after install: not supported automatically; while the key volumes are still there, `container.start` and bootstrap (including `-force-units`) refuse with `unit_unsafe` ("credential volumes were made for"), because Quadlet sets a volume's owner only when it creates it and the host does not chown what `core` has written. Do it by hand, in exactly this order: `systemctl stop vedette-scan vedette-sensor vedette-core vedette-host` (bootstrap refuses while the daemon runs); with `v` being `vedette-creds-passive` and then `vedette-creds-active`: `d=$(podman volume inspect --format '{{.Mountpoint}}' $v)`, `ls -la "$d"` (only regular files, no links; if there is anything odd, stop), `chown -R --no-dereference <new core_uid>:<new sensor_gid> "$d"`; `rm /etc/containers/systemd/vedette-creds-passive.volume /etc/containers/systemd/vedette-creds-active.volume` (the host rewrites them with the new ids); `vedette-host -bootstrap -force-units` with exactly the release documents that are running (the units carry the new ids), then `systemctl daemon-reload` and `systemctl start vedette-host vedette-core vedette-sensor vedette-scan`. A box installed without being able to build the `scan` image (bootstrap could not reach `deb.debian.org`: the installer prints `skipped scan: … No unit was written for it`, `host/ops/bootstrap.go`) **has no `vedette-scan` unit**: `test -e /etc/containers/systemd/vedette-scan.container` fails; leave `vedette-scan` out of the two `systemctl` commands above (otherwise `systemctl` reports that unit not found). Verify: `stat -c '%u:%g' "$d"` is the new id, `podman inspect vedette-core --format '{{.Config.User}}'` is `<new core_uid>:<core_gid>`, and `journalctl -u vedette-sensor --since -5min` has no error reading `/var/lib/vedette-creds/sensor.pem`.
- Operating system updates of the box: see §6 (really run).

## 4. Rollback
- Software rollback: Settings → Updates → "Rollback" (admin; `POST /core/updates/rollback`, `modules/core/updates_run.go`): one run that takes every enabled service that moves in step with `core` back to the `previous` version, `core` last, and switches the update mode to manual. When the running version declares `rollback.safe=false`, the dialog warns "Data written since the update is lost." and requires a confirmation tick (otherwise 409 `confirm_required`); the host restores the DB from the `pre_update` backup. There is no console path: the host's `container.rollback` accepts commands only from `core` (the socket is open only to the exact uid and cgroup of `vedette-core`, root cannot call it), and there is no `vedette-host` command for this; if `core` does not come up, the software cannot be rolled back (data: §5.3, §5.8).
- Rolling back **data** by hand from a backup: §5.3. Rolling back a management address change: automatic if not confirmed in time (§2).
- After an unfinished failure of a unit change where the host could not restore the data of `core`: §5.5.

## 5. Backup and restore

### 5.1 What is and is not included
- **In the backup:** a consistent SQLite snapshot of `vedette.db` (`VACUUM INTO`, nothing filtered) together with `manifest.json`: the configuration of every module, users **with their argon2id password hashes** (no plaintext passwords), devices, findings, the audit log, the `logs` configuration (sources, retention, SIEM). **No master key**: encrypted secrets (AI/feed keys, tokens, channel passwords, TOTP keys) cannot be opened without the key. Keep the file as sensitive data (the password hashes of every administrator could be cracked offline).
- **Not in the backup:** `logs.db` (the log lines received; backup, restore and rollback do not touch it); the master key `/var/lib/vedette/vedette.key` in a downloaded backup; the raw honeypot log; the TLS leaf certificate (`vedette-selfsigned.*`, regenerated, same CA). The box's own CA **is inside** the backup (a `core_secret` row of `vedette.db`): restoring together with `vedette.key` keeps the CA and enrolled machines do not have to be reinstalled; restoring without the master key creates a new CA and machines must run the install command again; images (pulled again); the Quadlet units (regenerated from the code).
- **Master key** `/var/lib/vedette/vedette.key`: download it once with Settings → Data → **Download decryption key** (an administrator, the current password and the two-step code if any; the file `vedette-key-<date>.key` is exactly the 32 bytes of `vedette.key`; audit "Download the decryption key") and keep it somewhere other than the backup (whoever has both can read the secrets). If the key is lost, the stored AI keys, feed keys, tokens and channel passwords cannot be decrypted and must be entered again, **and every user who turned on two-step cannot sign in** (the TOTP key is also encrypted with the master key); restoring onto a new machine without copying the old key makes the box create a new key.

### 5.2 Creating a backup
- Manual: Settings → Data → Backup → Download backup (administrator; at most once a minute, otherwise 429). Every download also leaves a `manual` backup on the host.
- Automatic: before every OS patch install, the host creates a `pre_os_update` backup (with the key, only on the machine, not downloadable).
- Where they are stored and how many (host): `/var/lib/vedette-host/backups/<id>.tar.gz` (0600) with `index.json`; at most 3 `pre_*` backups are kept (every `pre_*` kind counted together) plus every backup that a `versions-*.json` file or the unit-transition log still points to (that backup does not count towards the 3 and is not deleted), and at most 10 `manual` backups (the oldest is deleted); no selective deletion.
- not yet: an automatic daily backup, an external folder (USB/NFS), a configurable number of backups kept.
- Verify: the downloaded file is larger than 0 and `tar -tzf vedette-backup-<date>.tar.gz` lists `manifest.json` and `vedette.db`; `ls -l /var/lib/vedette-host/backups` has a new backup.

### 5.3 Restore
- **Same box (GUI):** Settings → Data → **Backups on this box** → **Restore** on the backup you want back; the dialog requires "I understand", the current password (and the two-step code). Before replacing, the box snapshots the current data as a **Before restore** backup (the 3 newest are kept) and restores it by itself if the restored data does not start (`reverted`). A `manual` backup without a key uses the box's current key.
- **New box (GUI):** install a new box (§1.1), open the page, get the setup code (§2), press **Restore from a backup** at the first step of the wizard. Choose the file `vedette-backup-<date>.tar.gz` (Download backup, §5.2) and, if you have it, the file `vedette-key-<date>.key` (§5.1). **Check the backup** uploads and checks it (only three members, a size cap of 4 GiB, no paths or links, `quick_check`, not newer than the software running: `schema_newer`), and then states the organisation, the date, the number of users, and **when there is no key** what is lost (stored secrets must be entered again; two-step users cannot sign in; if no administrator can sign in the box is unusable until one is reset from the console, §7). After a restore without the key: a user with an authenticator app who types the right password gets 403 `twofa_reset_required` (the message asks them to have an administrator reset it in Settings → Users), and never gets in with the password alone; an administrator without two-step presses **Reset two-step sign-in** for that person, who then signs in and turns it on again. Users with email codes need an email channel whose password is entered again (otherwise 503 `twofa_email_unavailable`, which an administrator can also reset). SSO returns 409 `sso_secret_lost` until an administrator enters the client secret again. The box's own HMAC keys (device cookies, email codes, unknown email references in the audit log, approval link keys, the OpenVAS GMP password) are recreated on the spot at first use (each key writes a WARN log and an audit line `box-key.replace` that names the purpose and never the key): old device cookies and approval links stop working. The same signs (`box-key.replace`, `twofa_reset_required`) without any restore mean `vedette.key` was lost and the box created a new master key at startup (a container install with a key path outside the volume, a moved data directory missing the key): put the right `vedette.key` back (§5.1) before anyone resets two-step. **Restore**: a wrong key (it opens none of the backup's secrets) is refused before anything changes; the box takes the backup in as a `manual` backup "Uploaded backup of <date>" and then restores as above (Vedette restarts, the page reconnects by itself) → "Your data is back" → sign in with the password of the old box. A container-only install: the page shows the commands of `docs/INSTALL-CONTAINER.md` §6 (there is no helper).
- **Verify:** sign in with the old account; Devices and Findings match the old box; Settings → Data → Backups on this box has a new Manual backup (from the restore; the Decryption key column says "Included" when the key was supplied) and a Before restore backup; Settings → Audit log has "Restore of a backup ended" (`data.restore_done`, detail `done`; this line is written when an administrator first opens Settings → Data after the restore, not written automatically at startup); with the key, Settings → Alert channels → Send test arrives and two-step users can sign in; without the key the AI/feed/channel keys show that they need to be entered again. If the restored data does not start, Data says "The restored data did not start correctly …" and the box returns to how it was (the Before restore backup).
- **Manual restore (only when `core` cannot start, so there is no GUI: §5.8, §5.5).** Do exactly what the host does; the box stops serving while you do it. `<uid>` and `<gid>` are `core_uid` and `core_gid` in `/etc/vedette/host.conf`.
  1. Before stopping anything, check that the backup is not newer than the software running: `tar -xzOf <backup>.tar.gz manifest.json` (see `db_schema`; the host does this check, `schema_newer`, and when done by hand you must do it yourself); do not restore a backup that is newer. Then `systemctl stop vedette-core`.
  2. Put the current DB aside outside `/var/lib/vedette`: `mkdir -p /root/vedette-before-restore && mv /var/lib/vedette/vedette.db* /root/vedette-before-restore/`.
  3. Extract into a temporary folder of root, **not** straight into `/var/lib/vedette`: `mkdir -p /root/restore && tar -xzf <backup>.tar.gz -C /root/restore vedette.db`.
  4. Put it in place: `install -m 0600 -o <uid> -g <gid> /root/restore/vedette.db /var/lib/vedette/vedette.db`. Same box: keep the existing `vedette.key`. **A new box:** put the downloaded key file (§5.1) in place as `vedette.key` with `install -m 0600 -o <uid> -g <gid> vedette-key-<date>.key /var/lib/vedette/vedette.key`. Without the key every secret must be entered again **and every user who turned on two-step cannot sign in** (the TOTP key and the SMTP password are encrypted with the master key); if every administrator has two-step on, the box is unusable (§7).
  5. `systemctl start vedette-core`.
  Verify as above; if the DB is newer than the software (an unknown schema) or damaged, `core` does not come up: `journalctl -u vedette-core -n 100`; put the old files back from `/root/vedette-before-restore` and start again. After a restore `logs.db` is still the current data: log lines of a source that the restored configuration no longer knows still show by id and expire by retention (harmless).
- The `exposure` egress IP is valid for 30 days from the last time it was seen: restoring onto another machine makes the new box detect its IP again by itself (auto-detect mode), with no manual confirmation unless that mode is off.
- **Restore drill** on a clean machine every quarter: build a new machine (§1.1), restore with **Restore from a backup** (above), check that the number of devices and findings matches the original; record the result in your own operations log (the project team).

### 5.4 Export, download logs, delete data (Settings → Data, administrator)
- **Export JSON:** every data table, no secrets, capped at 256 MiB (beyond that the file stops early and is still valid JSON, `truncated:true`).
- **Download logs:** eight kinds (audit, ai_activity, response, scan_probes, alerts, device_logs, known_bad, honeypot), JSON or CSV, by date. Platform logs (the container journal) are not here: `journalctl -u vedette-core` (and the other units). `device_logs` has its own cap of 32 MiB (the newest lines are kept, with a line marking that it was cut).
- **Delete all data:** type the exact organisation name + the current password + the two-step code (if any). It deletes all data, users, **every backup on the host** and `logs.db`, replaces the master key with a new one, and then `core` stops by itself and Quadlet builds a new box (the page is unreachable for a few seconds, the wizard opens again with a new setup code). The box's own CA is lost too: §5.7 (the self-generated TLS certificate is reissued under the new CA, `notSignedBy` in `cmd/vedette/boxca.go`). Kept: the TLS certificate that the box owner supplied (`-tls-cert`), the system journal, the network configuration, the raw honeypot log. Without a helper (`vedette-host`), `kept` says `host_backups`; with a helper that does not answer it is refused with 502 and **nothing is deleted**. Refused with 412 `transition_pending` while a unit change is pending: §5.5.

### 5.5 `core_data_unrecoverable`: the host could not restore the core's data
- **Symptom:** a command that touches `core` returns 412 `transition_pending` with the words "See the RUNBOOK entry core_data_unrecoverable"; `core` stands still (it may be stopped).
- **Check:** `grep core_data_unrecoverable /var/log/vedette-host/audit.jsonl | tail -n 1` (records `service`, `run_id`, `db_revert`, `aside`, `backup_id`); `ls -la /var/lib/vedette` (look for `vedette.db.rollback`, `vedette.key.rollback`, `*.quarantine-*`); `cat /var/lib/vedette-host/containers/transition-core.json` (`"unrecoverable": true`, `aside` is exactly the names that were moved to `<name>.rollback`).
- **Fix (command):** `systemctl stop vedette-host vedette-core` (the command refuses while the host runs: exit code 6; when `core` has not stopped: `core_running`). Then run `vedette-host -recover-core-data` **with no other flag**: it only prints and changes nothing (it does not even write `/var/log/vedette-host/audit.jsonl`): the `core_data` path, the `<name>.rollback` copies that the journal says were moved (with size and time), the `*.quarantine-*` and `*.replaced-*` files (the command **never** touches them), and two choices. Choose one:
  - `-use rollback`: put the `.rollback` copies back (renaming, inside `core_data` itself); a file that occupies the name is kept as `<name>.replaced-<time>`, not deleted; when `vedette.db` comes back, any existing `-wal`/`-shm`/`-journal` are moved aside the same way. Order: move **all** the files occupying names aside first, then put back the key and `-wal`/`-shm`, **the database last** (a crash midway never leaves a database next to a WAL of another version); progress is written in `containers/transition-core.json` itself (the `recover` field). It can put back only when the `core` unit pins exactly the version to which the `.rollback` copies belong (the report prints both). Use it when the new data of the change was damaged midway and the old version is the right one.
  - `-use current`: keep every existing file as it is and only delete the journal. Use it when the files that exist now are the right ones.
  Adding `-use rollback` (or `current`) **without** `-yes`: prints exactly what it would do and changes nothing (it is still a dry run). Adding `-yes` makes it act; the command writes an audit line `core_data_recover_start` **before** changing anything (if it cannot write, it changes nothing: `audit_unavailable`), then `core_data_recovered` when done (`command: recover-core-data`), deletes `containers/transition-core.json`, and starts **nothing**: then `systemctl start vedette-host vedette-core`. The command refuses and changes nothing when: the journal is not `unrecoverable` (`not_unrecoverable`: the host handles it itself when it runs), the journal is damaged (`journal_invalid`), `core_data` is a symlink or the parent chain is unsafe or a `.rollback` copy is not a regular file (`core_data_invalid`), `-use rollback` with no copy at all (`no_copy`: the journal is a restore-from-backup kind, use `-use current` or §5.3), or the `core` unit pins a version that `versions-core.json` cannot explain (`versions_mismatch`), the `.rollback` copies belong to a different version from the unit (`unit_mismatch`: put the right unit back first, `containers/units/core.prev`), or a copy of `-wal`/`-shm` remains while the copy of `vedette.db` is missing (`db_copy_missing`: never put a WAL next to a different database). If `-use rollback` crashes midway (or the version step is damaged), run exactly **`-use rollback`** again: it finishes from where the journal recorded (`recovery_in_progress` refuses `-use current` at that point; if `core` has run between the stop and the rerun, meaning a live file sits where a copy is about to be put back, the command stops with `core_ran_since` and changes nothing: look at the `vedette.db*` and `*.replaced-*` files, restore a backup (5.3) or choose `-use current`); **keep `core` stopped** until it is done (systemd may start it at boot). If you are not sure which files are the right ones, stop, restore per §5.3 and only then run `-use current`.
  - The manual path (when the command cannot be used): `mkdir -p /root/vedette-unrecoverable && cd /var/lib/vedette`; move every existing `vedette.db`, `vedette.db-wal`, `vedette.db-shm`, `vedette.db-journal` that is **not** in `aside` to `/root/vedette-unrecoverable/` (the WAL of another database meeting the old database would damage it; `host/ops/coredata.go` `putAsideBack` does exactly this); for each name in `aside` that still has a `.rollback` copy: move the existing file of the same name there and then `mv <name>.rollback <name>`; delete `/var/lib/vedette-host/containers/transition-core.json`.
- **Verify:** `vedette-core` healthy, `/api/v1/setup` returns 200, sign-in works, the data matches the copy you trust.
- When `core` **is running**, there is a GUI path: Settings → Data → Backups on this box → **Restore** (§5.3) calls `backup.restore`, which goes through the `unrecoverable` journal and deletes it when the restore is done (host-api §6.12). The `-recover-core-data` command above is the path when `core` stands still.

### 5.6 vedette-host self-update stopped half way
- **Symptom:** a `host.self_update` run ends `failed` with `rollback_failed` or `self_update_interrupted` (or `host_restarted` when `journal.json` cannot be read at host startup: the host then also turns on the write gate, because the applier may still be running dpkg); every write command of the host returns 409 `transition_pending` ("An update of the system helper has not ended cleanly"); or the host does not answer after a self-upgrade.
- **Check (root):** `ls -la /var/lib/vedette-host/selfupdate /var/lib/vedette-host/selfupdate/packages /var/lib/vedette-host/selfupdate/staged`: `journal.json` (the upgrade: `from`, `to`, `phase`, `attempt`, `reason`, the applier's `log`), `versions.json` (the `current` and `previous` versions that were kept), `started.json` (which host ran after READY), `packages/vedette-host_<version>_<amd64|arm64>.deb` (the package kept), `staged/<sha256>.deb` (the package about to be installed), `applier` (a copy of the old binary). `cat /var/lib/vedette-host/selfupdate/journal.json`; `dpkg-query -W -f='${Version} ${db:Status-Status}\n' vedette-host`; `dpkg --audit`; `journalctl -u vedette-host-upgrade -u vedette-host --since -3h`; `systemctl status vedette-host-upgrade` (if the applier is still running, **wait** for it to stop: do not `systemctl stop` it, it could cut dpkg off midway; `RuntimeMaxSec=60min` limits it).
- **Fix:** once the applier has stopped, reinstall **exactly the `from` version** of the journal from the kept file (the SHA-256 must equal the journal's `from.sha256`: `sha256sum`): `dpkg -i /var/lib/vedette-host/selfupdate/packages/vedette-host_<from>_<arch>.deb` (a half-finished package is also completed this way; not `dpkg --configure -a`, that command touches other packages). Dependencies that apt pulled in for the new version stay (nothing is removed). Then delete `journal.json` and `applier` (and `staged/*`), `systemctl restart vedette-host`.
- **Verify:** `dpkg-query` prints the `from` version `installed`; `/usr/lib/vedette/vedette-host -version` equals that version; `systemctl is-active vedette-host` prints `active`; `cat /var/lib/vedette-host/selfupdate/started.json` has `version` = that version; a write command (Settings → Updates → Check) no longer gets `transition_pending`. A new version that dies before reading the journal **and** a box that restarts inside the applier's window (an accepted limitation) are also fixed exactly as above.

### 5.7 The box's own CA: purge, restore without the key, downgrade
The box's own CA is a `core_secret` row (purpose `core_box_ca`) in `vedette.db`, encrypted with the master key `vedette.key`. Machines that enrolled an agent pin this CA; the TLS leaf (`vedette-selfsigned.*`) is signed by it and is remade by itself. Every time the CA is replaced, an ERROR log and an audit line `box-ca.replace` are written (Audit: "Replace box certificate authority (enrolled agents must run the install command again)"); see also §8.5.
- **After Delete all data (§5.4):** the DB and the master key are replaced, so the CA row is lost; at the next start `core` makes a **new CA** (audit line `box-ca.create`, a new row). The browser warns about the certificate again (accept once, as in §2). Every machine that enrolled an osquery agent runs the one-line install command again (Agents). The file `vedette-selfsigned-ca.*.quarantine-<unix>` (if any, §11) is also cleaned up by the purge.
- **Restore without the right `vedette.key` (§5.3, a new box or a key that was recreated):** the CA row in `vedette.db` cannot be decrypted, so `core` makes a new CA and seals it in a **new row**, leaving the old row alone (ERROR log `the box CA could not be kept and was replaced`, `reason=cannot_decrypt`; audit `box-ca.replace`). Enrolled machines must run the install command again. **To get the old CA back:** `systemctl stop vedette-core`, put the right `vedette.key` that you kept outside the box (§5.1) into `/var/lib/vedette/` with `install -m 0600 -o <uid> -g <gid>`, `systemctl start vedette-core`: the box loads the old row again (the new row cannot be decrypted with that key), the new leaf chains to the old CA, machines enrolled before the incident run normally again; machines enrolled while the new CA was in use run the install command once more. Verify: `journalctl -u vedette-core -n 100` has no ERROR about the CA after the start, and `curl -k https://<IP>:8443/intake/ca.pem` (or the Agents page) returns the old CA.
- **Downgrading to a version that does not store the box's CA in the DB:** the old version cannot read `core_box_ca`, so it creates its own CA in the two files `/var/lib/vedette/vedette-selfsigned-ca.crt/.key`; every agent enrolled at that time runs the install command again. **Upgrading again** to a version that stores the CA in the DB: the box goes back to the CA sealed in the DB (the row is intact and can be decrypted with the master key in use) and deletes those two files; agents enrolled during the downgrade (pinning the CA of the two files) have to run the install command once more. Verify after upgrading again: `ls /var/lib/vedette/vedette-selfsigned-ca.*` shows no file (`.quarantine-*` is a different matter, §11).

### 5.8 `vedette.db` is damaged: `core` does not start (INV-32)
- **Symptom:** `vedette-core` does not come up or is not healthy; the unit has `Restart=always`, so systemd restarts it and the log line repeats. `journalctl -u vedette-core -o cat --no-pager | grep "failed SQLite's check" | tail -n 1` prints a JSON line `"level":"ERROR","msg":"the database failed SQLite's check; not starting","error":"store: the database is damaged: quick_check failed: <up to 20 errors, separated by ;>"` (or `"error":"store: quick_check: …"` when SQLite cannot read the file at all; `core/store/store.go` `pragmaCheck`). Right after opening `vedette.db`, before migrations and any write, `core` runs `PRAGMA quick_check(20)` and exits non-zero if there are errors (`cmd/vedette/main.go`, `store.QuickCheck`): it fails closed and does not overwrite the damage. An error opening the file (permissions, disk full) is a different log: §8.5.
- **There is no automatic restore**, except in one case: a `core` software update whose release declares `rollback.safe=false`, where the new `core` is not healthy within 120 s, so the host restores the old unit **and** the DB from the `pre_update` backup of that very run (`host/ops/update.go`). With `rollback.safe=true` (the host only puts the unit back; the old `core` meets the same damaged DB), damage outside an update (power loss, disk) or after `os.install` (the run is `failed`, the installed packages stay): the box stands still until you do the steps below. `logs.db` is not checked and is unchanged in every step below.
- **Check:** `systemctl stop vedette-core` first (so that it stops restarting). If there is a `/var/lib/vedette-host/containers/transition-core.json` with `"unrecoverable": true`, that is §5.5 (`vedette-host -recover-core-data`); do §5.5 first. Outside that case `vedette-host` has **no console command that restores a backup** (`-recover-core-data` with no journal only prints `nothing to recover: core has no unfinished change on record`; `backup.restore` accepts commands only from `core`, and `core` is dead, so the GUI path of §5.3 is not available either): restore by hand following "Manual restore" in §5.3. Find the copy to use:
  - A backup on the host: `ls -lt /var/lib/vedette-host/backups/*.tar.gz` (newest first); `cat /var/lib/vedette-host/backups/index.json` for `kind` (`pre_update`, `pre_os_update`, `pre_restore`, `manual`), `created_at`, `includes_secrets`. If the damage came after `os.install`, the `pre_os_update` backup of that run is the last one taken before the box was touched.
  - A snapshot left over in `core_data`: `ls -la /var/lib/vedette/snapshots/` (a `<32 hex>/` folder). Normally there is none: `core` writes a snapshot just before a host command that needs a backup (`pre_update`, `pre_os_update`, …), the host copies it into `backups/` and then `core` deletes it; one remains only when `core` died midway. Use only a folder **that has a `snapshot.json`** (the file written last; without it the snapshot was only half written): `cat .../snapshot.json` gives `created_at`, `db_schema`, `includes_key`; the `vedette.db` in it is a complete `VACUUM INTO` copy, with no `-wal`/`-shm`. Copy it out of `/var/lib/vedette` **before** starting `core`: at startup `core` deletes snapshots older than 1 hour (`modules/core/snapshot.go` `sweep`).
- **Fix:** choose the newest copy and follow "Manual restore" in §5.3 steps 1–5 (step 2 puts aside the damaged `vedette.db-wal`/`-shm` too: do not delete them, keep them for investigation); for a snapshot, step 1 reads `db_schema` in `snapshot.json`, skip the extraction step and put it in place directly with `install -m 0600 -o <uid> -g <gid> /var/lib/vedette/snapshots/<id>/vedette.db /var/lib/vedette/vedette.db` (same box: keep the existing `vedette.key`). A backup taken from a DB that was already damaged may also be damaged: `core` will refuse again with the same log line; then stop `core`, put that file aside and try the next older copy. Data after the time of the chosen copy is lost.
- **No usable copy left: start over.** `systemctl stop vedette-core`; `mkdir -p /root/vedette-damaged && mv /var/lib/vedette/vedette.db* /root/vedette-damaged/`; `systemctl start vedette-core`: `core` creates a new `vedette.db`, the wizard opens again with a new setup code (get it as in §2). The existing master key is kept but all configuration, users and secrets are lost; the box's own CA lives in the DB so it is a new CA (§5.7): machines that enrolled an agent run the install command again. `logs.db` and the backups on the host remain intact (until Delete all data).
- **Container only (`docs/INSTALL-CONTAINER.md`):** the same log line, read with `docker logs vedette-core 2>&1 | grep "failed SQLite's check" | tail -n 1` (`podman logs …` works too). `restart: unless-stopped` makes `core` restart forever, so stop it first: `docker compose --env-file vedette.env stop core` (keep exactly the list of `-f` files in use). There is no `vedette-host`, so there is no backup or snapshot on the machine: the restore is your own `vedette-data.tgz` (with `vedette.key` included) per §6 of that guide, into a new volume: `docker compose --env-file vedette.env down --volumes` (this also deletes the damaged volume; if you want to keep it for investigation, copy it out first with the backup command of §1.2), then `create core`, extract, `start core`. Do not extract over the old volume: a leftover damaged `vedette.db-wal` would be applied to the copy you just restored. With no copy at all: `down --volumes` and then `up -d` is a new box (the master key and `logs.db` are lost as well), with a new setup code in `docker logs vedette-core`.
- **Verify:** `vedette-core` healthy (while the DB is still damaged it is never healthy) and `/api/v1/setup` returns 200; sign in (or the wizard when you started over); the data matches the time of the chosen copy.

## 6. Operating system updates
Really run through `vedette-host`, only on the Appliance kind. Settings → Updates, the block "Operating system of this box".
- **Check first:** "Check now" (the box **does not check by itself the first time**: until you press it, `GET /core/updates/os` returns 200 with `os` null and the page says "The box has not looked for operating system updates yet. Click Check now." (before that it was 409 `no_check_yet`); installing before a check is still 409 `no_check_yet`). It shows: Distribution, Kernel, Standard support (expiry), the number of pending packages and of security packages, whether a Reboot is needed and because of which package, "Automatic security updates".
- **A fixed list of commands:** `vedette-host` runs only `apt-get` with a package list that it recomputes itself from the apt state; the GUI has no path to run an arbitrary command, and there is no release-upgrade command (the host never runs `do-release-upgrade`).
- **Install:** "Install security updates" or "Install all updates" (administrator). The host makes a `pre_os_update` backup first, runs apt, and then checks health (`core` answers); progress shows in "Latest install run". Refusals: `dpkg_locked` (another apt holds the lock; try again after 60 s), `low_disk` (under 1 GiB free in `/var`), `dpkg_inconsistent`. If the health check fails the run is `failed` and the installed packages are **not** removed automatically; the DB can be rolled back from the `pre_os_update` backup (§5.3 by hand).
- **Maintenance window and reboot:** Maintenance window (Any time or Only in a window: days and hours). When "Automatic security updates" is on, `unattended-upgrades` installs security patches on apt's own timer, **not** within Vedette's window. Reboot: "Reboot now" or "Schedule reboot" (the start of the next window or a time you choose; it must fall inside the window if one is set); the host refuses after 3 reboots in 24 hours (every reboot the host itself performs counts, scheduled ones too, not just "Reboot now").
- **After a reboot:** `vedette-host` comes up first, then `core`, then `sensor` and `scan` (only when their module is on: `core` reconciles at its own startup and drops the `[Install]` of a container whose module is off) and `honeypot` (only when the module is on: when off the host drops its `[Install]`). Verify: `systemctl is-active vedette-host vedette-core`; `podman ps` healthy; `ls /run/netns` has `vedette-hp` (created by the host at startup) when traps are used; Settings → Box network: SPAN reports "Receiving mirrored traffic" again; the Honeypot page: the trap IP answers again.
- **Upgrading the OS release (Ubuntu 24.04 → 26.04):** guidance only ("Release upgrade to … is available"); the box does not do it by itself. Only the three releases in §1.1 are supported: after upgrading the OS to a release outside the list, the host's apt commands are refused (`not_appliance`); after the upgrade, re-check each effect in the section above.

## 7. Resetting an administrator's 2FA
Use this when a person loses their 2FA device (or, for a user with email codes, when the email channel is broken).
- **The path that exists:** **another** administrator goes to Settings → Users → "Reset two-step sign-in" for that person. The real effect: that person's two-step is turned **off** (they are not forced to enrol again at once), all of their sessions are revoked, and the audit line `user.2fa_reset` is written; they sign in with the password alone and turn it on again themselves in My account. An administrator cannot reset their own 2FA (400). If they also forgot the password: "Reset password" issues a temporary password (shown exactly once, but valid for 72 hours) and forces a change at the first sign-in. Both run in the GUI; there is no path through email.
- **Prevention:** always keep at least **two** administrators who sign in with a password (an SSO administrator does not count, so that a broken IdP cannot lock the box owner out).
- **No administrator can sign in** (the only one lost their phone/mailbox, or forgot the password): on the machine running Vedette, `docker exec vedette-core /vedette reset-admin <email>` (container-only install; Podman: `podman exec …`) or `sudo podman exec vedette-core /vedette reset-admin <email>` (appliance). It works while `core` is running (the same container, the same `/var/lib/vedette`). The real effect: it prints a temporary password (72 hours, must be changed at sign-in), two-step is turned **off**, every session of that person ends, and the audit line `user.console_reset` is written (actor `console`). Only for an active administrator who uses a password; an unknown email, an ordinary user, an SSO account or a disabled account is refused. The failed-sign-in counter lives in the memory of `core`: if there were many wrong guesses just now, wait for the delay to run out (at most 10 minutes) or restart `core`.
- **Verify:** sign in with the temporary password → the "Choose a new password" screen; Settings → Audit log has the line "Reset an administrator from the box console"; My account → Two-step sign-in "Off".
- There is no back door in the web interface.

## 8. Troubleshooting

### 8.1 SPAN sees no traffic
Check in this order, from cheap to expensive:
1. Settings → Box network → "SPAN capture", the block "Mirrored traffic now" (Packets per second, "Other devices seen (MAC addresses)", Last packet) and the conclusion line (refreshed every 5 seconds): "Only the box's own traffic" = only the box's own MAC is seen, the mirror is not on or the destination port is wrong; "Nothing is arriving" (`no_traffic`) = the link is up but there are no packets; "No cable signal" (`no_link`) = no cable is plugged in; "The listener did not start" (`sensor_unreachable`) = the box saved the port but cannot yet tell the sensor (try again after a few seconds; if it persists, check the `vedette-sensor` container at step 5: turning `sensor-passive` off and on does not restart the container).
2. The SPAN card has link, **no IP**, and is listening: `ip -o link show <card>` has `LOWER_UP`; `ip -4 addr show dev <card>` is empty; when it is listening `ip -d link show <card>` has `promiscuity 1` (or `cat /sys/class/net/<card>/flags` has bit 0x100); `ip link` usually does **not** print the word `PROMISC` because the sensor turns it on through its own socket, not the host. `ip -s link show <card>` shows RX increasing while the mirror runs.
3. The port-mirroring configuration on the switch (mirror both directions; the destination port is exactly the port plugged into the SPAN card; per-vendor instructions in Box network).
4. "Exclusions" do not hide all the traffic you need to see; at least one item in "What Vedette reads" is selected (SPAN cannot be turned on with nothing selected).
5. The `sensor` container is running and healthy: `podman ps --filter name=vedette-sensor`; `podman inspect --format '{{.State.Health.Status}}' vedette-sensor` prints `healthy` (the heartbeat to `core` is younger than 60 s); `grep -E 'AddCapability|Network' /etc/containers/systemd/vedette-sensor.container` has `AddCapability=NET_RAW` and `Network=host` (the unit is generated by the host, do not edit by hand); `journalctl -u vedette-sensor -n 100 --no-pager`. The `sensor-passive` module must be on. If `podman ps --filter name=vedette-sensor` is empty while the module is on, `core` will turn it on again (retrying at 10 s, 30 s, 2 minutes and then 10 minutes; the reason is in `journalctl -u vedette-core`), or turn the module on again to try at once.
- **Verify:** Packets per second > 0, "Other devices seen" ≥ 1, the line "Receiving mirrored traffic"; new DNS/SNI appears in the device data.
- VM: the vSwitch must allow promiscuous mode and forged MACs (VMware "Promiscuous Mode", Hyper-V "MAC address spoofing"), otherwise SPAN and decoys stay silent (`DEPLOYMENT.md` §4).

### 8.2 A feed fails
- **Symptom:** Settings → Feeds shows which source fails, since when and with what error; Home reports KEV `never_loaded` with the error, or data older than `interval_hours` + 60 minutes.
- **Check** (the box pulls from each source directly over HTTPS 443, not through the project's GitHub; a failing source keeps its old data, records the error, backs off the retry time and does not bring the job down): Internet access and DNS from the box itself (`curl -s -o /dev/null -w '%{http_code}\n' --max-time 30 <source URL in Settings → Feeds>`); the system time (`timedatectl show -p NTPSynchronized --value` prints `yes`; `chronyc -n -c sources` has a source); a custom feed has a valid URL (`https`; `http` only for an internal host) and an authentication secret that has not expired (only the last 4 characters are shown: enter it again in Settings → Feeds); a response over 5,000,000 bytes is skipped (the error shown: "The source is larger than 5000000 bytes; Vedette would skip it."); the CISA list, on 403/5xx/timeout, is pulled again from the fallback `cisagov/kev-data` (the line "Answered by …" under the CISA row says which side answered).
- **Proxy:** `feeds` **does not use** the proxy environment variables (`modules/feeds/fetch.go:70`), so a box that can reach the Internet only through a proxy cannot pull feeds (not yet: proxy support for feeds). What does have proxy support: the host's `podman pull` through `[engine] env` in `/etc/containers/containers.conf` (`DEPLOYMENT.md` §2) and the AI provider.
- **Fix:** per the causes above; force a pull in Settings → Feeds ("Fetch now" per source; for a disabled feed, 409 `feed_disabled`).
- **Verify:** that source reports success, "Last fetch" is a recent time, Home no longer warns.

### 8.3 Approvals do not arrive
"Approval" = a request to approve a device or a response action, sent to an alert channel.
- **Check:** Settings → Alert channels: whether the channel is on and "Last test" succeeded (press "Send test"); the "All sent messages"/History table records every send attempt with its error (a friendly sentence); "Quiet hours" and "Grouping window" (a `critical` message is never grouped; during Quiet hours it goes at once only when "Still send Critical right away" is on, otherwise it is held until the period ends); a Telegram token, a Slack `xapp-`/`xoxb-` token or an SMTP password that has expired or been revoked (only the last 4 characters are shown: enter it again); the network blocks the way to the channel provider (Telegram, Slack, Zalo or the customer's SMTP): switch to another channel; the `notify` module is on (when off nothing is queued and events received while off are dropped); a generic webhook must not point at the box itself.
- An approval message **never runs an action** without an approval in the GUI or the button/code/link of exactly the right approver; the `response` module and the execution switch are off by default.
- **Fix:** per the cause; for a channel that carries only a link (email, Zalo OA) the approver opens the link to approve inside Vedette.
- **Verify:** "Send test" is received; a real approval request reaches the channel and the decision appears in Settings → Audit log.
- not yet: a real personal Zalo sign-in (the QR button in the GUI is simulated, the real API returns 400 `bad_secret`; how to do it is still to be chosen). Slack and Telegram use Approve/Reject buttons (the box opens an outbound connection and opens no inbound port).

### 8.4 High CPU
1. Which container: `podman stats --no-stream` (default limits: `core` 2 CPU, `sensor` 1, `honeypot` 0.5, `scan` 2 with a low weight); `top` for `vedette-host` and processes outside containers.
2. `scan` (nuclei/nmap) is running: the "Vulnerability scans" page (`/scans`) → "Stop now"; reduce "Speed" (the "Schedule and safety" tab); move it into a time window.
3. `sensor` on a SPAN with heavy traffic: add "Exclusions", remove items from "What Vedette reads" (Box network).
4. `logs`: syslog arriving too fast from one source: check for a sender in a loop (each source is rate limited; lines from an undeclared source are dropped and counted); `logs.db` has its own writer and cleans in chunks of 10,000 lines; beyond the 4 GiB cap the oldest lines are cleaned down to 90%.
5. `ai`: calls to the provider follow the monthly token budget (`monthly_budget`); see the activity log. Right after "Delete all data", the next start compacts the DB (`VACUUM`), which costs CPU and disk for a few minutes.
- Turning off a module you do not need (Settings → Modules: off = no routes, no jobs, data kept) is the safest way to reduce load; a few cleanup jobs by retention period still run while off (§10).
- **Verify:** `podman stats --no-stream` is below the threshold you set; Settings → Modules shows exactly the modules that are on; the Scans page has no run left.

### 8.5 `core` does not come up or is not healthy
- **Check:** `podman inspect --format '{{.State.Health.Status}}' vedette-core`; `journalctl -u vedette-core -n 200 --no-pager`; `df -h /var` (a full disk is a common cause: the installer requires ≥ 6 GiB); `systemctl is-active vedette-host` (the host must come up before `core`); `ls -ld /var/lib/vedette` (0700, owner `vedette`).
- **Fix:** for space, free some; for the log `the database failed SQLite's check; not starting` (a damaged DB) see §5.8; if the DB cannot be opened or is newer than the software see §5.3; then `systemctl restart vedette-core` (not `podman restart`: the unit is managed by the host).
- **Verify:** healthy within 60–300 s and `/api/v1/setup` returns 200.
- The log `the box CA could not be kept and was replaced; enrolled agents must run the install command again` (ERROR; the `reason` field says why): the box's own CA could not be decrypted (a restore with a different master key), was damaged or about to expire, so it was remade; core still comes up; the audit log has the line "Replace box certificate authority". If it was the old CA file of a version that did not store the CA in the DB, the two files are at `/var/lib/vedette/vedette-selfsigned-ca.{crt,key}.quarantine-<unix>`. Servers that enrolled an agent must run the one-line install command again; browsers need to do nothing. The log `the box CA was moved into the database (core_secret); its files are removed` (INFO): at the first start after an upgrade, the old CA was sealed into `vedette.db`, the same CA, nothing to do. The log `the box CA is not available; the certificate in use is kept` (WARN): the CA could not be read (a database error) or the leaf certificate could not be written (disk full, a read-only folder); the certificate in use keeps working, fix the disk/permissions and then wait 10 minutes or restart.
- `core` does not come up after the machine starts, `journalctl -b -t quadlet-generator` reports `requested Quadlet unit vedette-hp-log.volume was not found` (or `vedette-hp-log-volume.service` fails: `systemctl status vedette-hp-log-volume`, `journalctl -u vedette-hp-log-volume`): the `core` unit needs the honeypot's tmpfs volume `log/` even when the `honeypot` module is off. The file `/etc/containers/systemd/vedette-hp-log.volume` is written by the host only on the `container.start` or bootstrap of `core`/`honeypot`: write it again with a `container.start` of `core` with `restart`, then `systemctl daemon-reload`. Verify: `podman volume inspect vedette-hp-log` has `type=tmpfs` and `systemctl is-active vedette-core`.
- No container comes up (`core` included), and `journalctl -u vedette-core` (or `-u vedette-scan`, …) reports `AppArmor profile "vedette-container" specified but not loaded`: every unit selects the AppArmor profile `vedette-container` of the `vedette-host` package, and Podman refuses a container when AppArmor is on and the profile is not loaded. **Check:** `grep vedette-container /sys/kernel/security/apparmor/profiles` (there must be one line `vedette-container (<mode>)`, usually `(enforce)`); `ls -l /etc/apparmor.d/vedette-container /etc/apparmor.d/disable/vedette-container`; `journalctl -u apparmor -b`; the audit log has `apparmor_profile_missing` with a `reason` (`disabled`, `file_missing`, `parser_missing`, `load_failed`, `not_listed_after_load`, `profiles_unreadable`) from the host's most recent start, or `apparmor_profile_loaded` when the host has loaded it again. **Fix:** a missing file (the conffile was deleted and dpkg does not put it back by itself) → reinstall from the package that `install.sh` keeps on the box (no apt source has `vedette-host`, so `apt-get install --reinstall vedette-host` cannot find the package): `dpkg -i --force-confmiss --force-confdef --force-confold /var/lib/vedette-host/selfupdate/packages/vedette-host_$(/usr/lib/vedette/vedette-host -version)_$(dpkg --print-architecture).deb` (if that file is missing, for example after a self-update that stopped midway, download `vedette-host_<version>_<architecture>.deb` of exactly the `vedette-host -version` version from the release page, **check its `sha256sum` against the value `VEDETTE_DEB_SHA256_AMD64`/`_ARM64` in the `install.sh` of the same release**, and only then run the same `dpkg -i` command on it); if there is a disable link (`aa-disable`) → `rm /etc/apparmor.d/disable/vedette-container`; then `apparmor_parser --replace --skip-read-cache --write-cache /etc/apparmor.d/vedette-container` (or `systemctl restart vedette-host`, which loads it at startup when the kernel lacks it) and `systemctl restart vedette-core` (then the other services). Do not choose `apparmor=unconfined` or delete the `ContainersConfModule=` line: a hand-edited unit is no longer the host's (INV-17). **Verify:** `grep '^vedette-container (enforce)' /sys/kernel/security/apparmor/profiles`, `systemctl is-active vedette-core`, and `journalctl -k | grep 'operation="signal"'` has no new lines.
- `vedette-host` does not come up with an error about `/run/vedette` (only after upgrading from an old unit that had `RuntimeDirectory=`; a freshly built box does not hit it): `systemctl stop vedette-host && rmdir /run/vedette`, then `systemctl start vedette-host` **and** `systemctl restart vedette-core` (core still has the old deleted directory mounted) — or reboot the machine. Verify: `test -S /run/vedette/host.sock` and Settings → Updates → "Check now" works (no 502).

### 8.6 The passive web scan (ZAP) does not run (`zap.baseline`)
The "Not checked" line of the External exposure page gives the reason; the host writes the details to the journal.
- **"is being downloaded"**: the first Scan now against a website makes the host pull the ZAP image (~1.2 GB compressed, ~2 GB on disk, needs ≥ 4 GiB free under `/var/lib/containers`); scan again after a few minutes. Check: `podman image exists ghcr.io/zaproxy/zaproxy@sha256:9624669db72f54d86c4b46a7064518bd9bf79d8c61a4c31befa9923489f328af && echo present`; the pull result is in `/var/log/vedette-host/audit.jsonl` (`zap_image_pulled` / `zap_image_pull_failed` with `reason`).
- **"still cleaning up"** (`zap_cleaning_up`): the container of the previous run could not be removed or was not proven gone, so the host keeps the nft table (the fence outlives the container). Check: `podman ps -a --filter name=vedette-zap`, the line `zap_cleanup_incomplete` in `/var/log/vedette-host/audit.jsonl`; `podman rm -f vedette-zap` and then scan again (the host removes the table at the next run or the next start). A `vedette-zap` container without the label `io.vedette.owner=vedette-host` belongs to someone else: the host does not touch it, and the scan reports "network fence".
- **"network fence"**: `podman network inspect vedette-zap` must show the label `io.vedette.owner=vedette-host`, bridge `vedette-zap0`, no `options`, `internal: false`, one IPv4 subnet, `dns_enabled: false`, `ipv6_enabled: false`; another `vedette-zap` network created by someone else is not touched by the host: `podman network rm vedette-zap` and then scan again (the host recreates it). `journalctl -u vedette-host | grep zap.baseline` gives the reason.
- **While it runs** (at most 7 minutes per site): `podman ps --filter name=vedette-zap`, `podman stats --no-stream vedette-zap` (cap 1 GiB), `nft list table inet vedette_zap` (only one accept rule to exactly `ip:port` and one drop rule per chain). After the run there is no container, no table, and no `/var/lib/vedette-host/zap/wrk` left; if the host died midway, the next start cleans up (the marker `zap/active`).
- **Configuration:** ZAP runs with the traditional runner (`zap-baseline.py --autooff`): the spider is not processed, no form is submitted, one thread; the Automation Framework runner (the image's default) ignores those options. The traditional runner ends with **exit code 3 and no report** when ZAP cannot reach the site (an error accessing the first page), when it sees no URL, or when ZAP fails to start; the site's line is then "Passive web scan (ZAP) failed …" and the host's error is "ZAP ended without a report (exit code 3): …". The host does not keep ZAP's output, so code 3 does not name any cause; the most common case is that the site cannot be reached from the box: see the bullet "when the site works from outside" below and its `curl` test.
- **Measuring memory:** the container's peak is `memory.peak` in its cgroup while it runs (`cat /sys/fs/cgroup/machine.slice/libpod-$(podman inspect -f '{{.Id}}' vedette-zap).scope/memory.peak`); exit code 137 ("memory limit") means ZAP hit 1 GiB.
- **Nothing goes to zaproxy.org:** `tcpdump -ni vedette-zap0 not host <the site's ip>` while it runs must not see any packet leaving (DNS, zaproxy.org); the nft rule drops them before they leave the box.
- **"Passive web scan (ZAP) failed" (host error "ZAP ended without a report (exit code 3)") when the site works from outside** (a known limitation; an older version phrased this as "ZAP reported no page"): the nft rule matches the destination address after DNAT, so (a) a router without NAT loopback (hairpin) does not send the packet from the box back to the site through the public IP, and (b) when the box itself holds the public IP (a VPS) and the site's port is published by podman, the packet's destination is changed before the forward rule; both are blocked by the fence (safe closure). Test (a) from the box: `curl -sk -o /dev/null -w '%{http_code}' https://<ip>:<port>/`; if it does not answer, turn on NAT loopback on the router. This test says **only** about (a): the `curl` packet takes the box's own OUTPUT path (nat-output DNAT and local delivery), so in case (b) it answers while ZAP is still blocked; there is no simple test for (b) yet and it awaits the `ct original` fix.
- **"now points at other addresses"** (`zap_name_moved`, only that site, other sites still run): the site's name no longer resolves to exactly the IP that the surface scan saw (the record changed, or a CDN/load balancer returns a different set of addresses each time); scan again to check the site at its current address. `dig +short A <name>` gives the current address.
- **Uninstalling when the ZAP container is stuck**: `--uninstall` removes the table `inet vedette_zap` only when podman clearly says there is no `vedette-zap` container; the sentence "Vedette's ZAP container vedette-zap could not be removed" means the container, network, ZAP image, nft table and podman stay: `podman rm -f vedette-zap` and then run `--uninstall` again.
- **A box with Docker** (the `DOCKER-USER` chain, FORWARD policy DROP): the host has not added a rule for `vedette-zap0`, so ZAP cannot reach the site ("Passive web scan (ZAP) failed", code 3 with no report).

## 9. Incident response: a vulnerability in Vedette itself
Vedette is a security product, so a vulnerability in it is an incident (`SECURITY.md`). The commitments that exist: acknowledgement within 2 working days; a fix or mitigation within 14 days (critical) / 30 days (high); every security patch has an advisory (GHSA, CVE where appropriate), goes through the product-advisory channel and shows in the application.

| Step | Task | Who |
|---|---|---|
| 1. Intake | A private report through GitHub Security Advisories; no discussion in a public issue/PR. Record the time received. | maintainer |
| 2. Confirm and triage | Reproduce on the newest version and on the released version; score CVSS, record the affected versions and modules; whether it is being exploited. | maintainer + module owner |
| 3. Temporary mitigation | If there is no fix yet: instructions to turn off the affected module (Settings → Modules), change the configuration, block the port. | maintainer |
| 4. Fix | Work on a private branch (an advisory private fork); add a test that repeats the bug; review by a second person; do not reveal details in public branch/commit names before release. | module owner |
| 5. Release | The normal release process with a shortened cohort, a cosign signature, the product-advisory channel; **the maintainer tags by hand**. | maintainer |
| 6. Announce | Publish the GHSA (+ CVE), a Security section in the changelog. not yet: an in-application banner for boxes running an affected version (needs `core` software update and an advisory in the index). | maintainer |
| 7. Revoke | A release (or one image) with a severe defect: withdraw it with a signed index that revokes it, §9.1; the host **refuses** to pull or switch to a revoked version, digest or key (`release_revoked`, `key_revoked`, `previous_revoked`), and a box that runs it shows the reason. | maintainer |
| 8. After the incident | Record the root cause, add a test/rule that prevents a recurrence, close the advisory. | maintainer |

- A leaked signing key (minisign/cosign): not yet: a procedure for revoking a key and issuing a new one (the real keys have not been created; the recovery path when the key in use is leaked).
- A leak of a user's secrets caused by a Vedette bug: notify them so they change the API keys/tokens they configured (AI, feed, channel); Vedette does not keep keys in clear text (AES-256-GCM, the last 4 characters shown).

### 9.1 Withdrawing a published release

A published version is never changed, and a channel's `latest` never goes down in an ordinary release. To take a release (or one of its images) back, publish an index that revokes it: `revoked[]` rows of kind `release` or `image_digest` (`docs/specs/update-manifest.md` §8). The index is numbered and signed like the weekly refresh, so every box takes it at its next update check. Maintainer's machine, from a clean clone of `main`.

**What boxes do once they have the index.** A box below the withdrawn release is never offered it and the host refuses to pull it; if the channel moved back to an earlier release, a box below that one is offered it as usual. A box that **runs** the withdrawn release keeps running it: Settings → Updates says the version has been withdrawn, with the reason you write (with `block_install_and_warn`, the default, as a banner on every page for every role), its update check says "up to date" until a higher release is published, and the admin can use Rollback (refused only when the previous release is withdrawn too). Nothing rolls back by itself; `rollback_if_possible` is refused by the tool for that reason. The rows are carried into every later index (refreshes and releases), so a withdrawal is permanent unless an index signed by the backup key drops it.

**Steps** (rehearse them first: steps 1-4 into a scratch `RELEASE_OUT`, then delete it; only step 5 changes what boxes see):

1. The live index and the withdrawn release's manifest, each with its `.minisig`: `gh release download index -p 'index.json*' -D /tmp/live` and `gh release download v<bad> -p 'release-manifest.json*' -D /tmp/bad`. When the channel should move back, the earlier release's manifest too: `gh release download v<good> -p 'release-manifest.json*' -D /tmp/good`.
2. Build the index (`dist/release` must hold no manifest of an earlier run):
   `WITHDRAW_REASON='<one line every box shows>' make release-withdraw RELEASE_PREV_INDEX=/tmp/live WITHDRAW_RELEASE=<bad> WITHDRAW_MANIFEST=/tmp/bad/release-manifest.json CHANNEL_MANIFEST=/tmp/good/release-manifest.json`
   - One image only: `WITHDRAW_DIGEST=sha256:<digest>` instead of (or with) `WITHDRAW_RELEASE`; the digest must be in a `WITHDRAW_MANIFEST` release.
   - The withdrawn release is a channel's latest, so the tool requires a decision for that channel: `CHANNEL_MANIFEST` (move back to an earlier release of the same channel that is not withdrawn), or `HOLD_CHANNEL=<channel>` (the channel keeps naming the withdrawn release and its boxes are offered nothing until the next release; the only choice when the channel has no earlier release).
   - `WITHDRAW_ACTION=block_install` shows only a note on the Updates page instead of the banner.
   - Refused: a version or digest without its signed manifest, a manifest that is not the one the live index announces, a row the index already has, the same row twice, a channel decision for a channel whose latest is not withdrawn, a move to a release that is not lower or is withdrawn too.
   - With the fixed release ready, withdraw in the same index as the release instead: `release index -manifest … -revoke-release <bad> -revoked-manifest … -revoke-reason …` (its channel moves on to the fix, so no channel decision is needed).
3. Sign with the key in use: `security find-generic-password -s vedette-release-minisign -a "$USER" -w | make release-sign MINISIGN_KEY=$HOME/.vedette-release-keys/minisign.key MINISIGN_BIN=$(command -v minisign) PASSPHRASE_STDIN=1`. When the key in use is the problem (leaked or lost), do not sign with it: the withdrawal goes into the rescue release (`docs/RELEASE_KEYS.md`, "Rescue release"), whose `release index` takes `-revoke-key` and `-revoke-release`/`-revoke-digest` together and is signed with `RELEASE_SLOT=rescue`.
4. `make release-verify RELEASE_PREV_INDEX=/tmp/live RELEASE=1`: the box's verifier over the new index; the line says `WITHDRAWAL index` and lists each row it adds (`revokes release <bad>`) and each channel it moves (`channel stable <bad> -> <good>`). It refuses a channel that goes down without the release it offered being withdrawn.
5. `make release-publish RELEASE_PREV_INDEX=/tmp/live PUBLISH=1`: uploads only `index.json` and its signature to the release `index`.
6. Verify by effect: download the live index again and run `go run ./scripts/release verify -dir <it> -prev-index /tmp/live`; on a test box on the withdrawn release, Settings → Updates → Check shows the withdrawn notice with the reason. The assets of `v<bad>` stay as they are: boxes that run it still read its manifest (for Rollback), and a published version is never changed. A vulnerability also gets its advisory (step 6 above; `-advisory` adds it to the same index).

All modules share `vedette.db`, except where stated. Turning a module off = no routes, no jobs, no port; data is kept; other screens say clearly where data is missing because a module is off. A deliberate exception: the cleanup job by retention period (`Housekeeping`) still runs while off, only to delete expired data.

- The `sensor` and `scan` containers follow the module switch like honeypot: turning the module on makes `core` ask the host to turn the container on (and keep `[Install]` so it comes up again after the machine starts), turning it off stops it and drops `[Install]`. If the host refuses or has not answered, `core` retries (10 s, 30 s, 2 minutes, then every 10 minutes) and writes the reason to `journalctl -u vedette-core`. Do not `systemctl start/stop` by hand: `core` will put them back in the state of the module.
- Syslog from the LAN on an appliance: devices send to `<management IP>:514` (UDP/TCP) or `:6514` (TLS); `NET_BIND_SERVICE` is not needed because inside the `core` container it listens on 5514/5515 (`host/ops/quadlet.go`, `cmd/vedette` `-syslog-port`). Rootful Podman keeps the sender's IP through the publish (checked in a lab on 2026-11-12); rootless has not been measured. A box upgraded from an old unit that does not have the line `6514:5515/tcp` yet (the old template `host/ops/testdata/units/legacy/1-core.container`) receives it at the image step of the next software update (the host checks the port and then rewrites the unit when `core` restarts), not at host startup or reboot (`unit_migration_deferred`).
- `mcp-server` on an appliance: an MCP tool running **on the box itself** calls `http://127.0.0.1:8765/mcp` with a token (Settings → MCP server), only when the module is on. The `core` unit publishes `127.0.0.1:8765` (never a LAN address); a box upgraded from an old unit gets that line after the image step of the next software update (at host startup or reboot the unit does not change); with an old `core` image that has no MCP server on this port, under the new unit MCP is still unreachable (8443 is not affected). Other machines reach MCP through an SSH tunnel or a reverse proxy that the customer builds; Vedette opens no port to the LAN.
- `agent-intake` (osquery, Wazuh): really run on 2026-11-12 on Podman: an osqueryd 5.12.1 (x86_64 Debian 13, installed with exactly the one-line command) and a Wazuh 4.9.2 (manager + agent, read-only account) both produced devices and package lists in the inventory. An osquery device appears after the first report: osquery runs each query on the clock (on the hour, with an offset) so the first report can arrive after up to an hour, and packages received before the `interfaces` query only enter the inventory at the next report (≤ 1 hour more). **The PowerShell script for Windows has not been proven on a real Windows Server**: the first run (Windows Server 2025, 2026-11-14) failed at TLS (`curl.exe` could not verify the box's CA), which has been fixed (the script calls the box with .NET, pinning the embedded CA), awaiting a rerun (the GUI says "Not yet proven"); Linux is x86_64 only.
