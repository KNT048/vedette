| D-496 | **A trap incident's "Times" is the number of connections the trap saw, read from the honeypot when the page is built (S-HP-1, walk 5 finding M5-190).** A second connection from the same source to the same trap inside the fold window raises `hp_hits.conn_count` and adds a line to the hit but emits no event (honeypot INV-17), so notify's own count (one per `honeypot.hit.created`) stayed 1 and the incident showed "Times 1x". Notify now has a narrow optional port `Config.Hits` (`HitConnections(ctx, []HitRef{ID, At})`, `modules/notify/types.go`), wired in `cmd/vedette/notify.go` over the honeypot's existing public read that carries `conn_count` (`ExportHits`, one window of exactly the hit's time per hit; no other read returns it and notify reads no honeypot table). `GET /notify/incidents` and `/notify/incidents/{id}` show `count + (conn_count - 1)` for a trap incident (the hit its link names counts its connections, not once; each later hit of the same incident is still one). One export per distinct hit time, streamed. Honeypot off, port nil, or a read error: notify's own count, one log line, no error to the page. The weekly report counts incidents, not times, so it is unchanged. Why not an event: `honeypot.hit.updated {id, conn_count}` was asked of the honeypot owner and does not exist yet; reading at render needs nothing from them and shows the right number now. Upgrade path (`ponytail:` at the port): when that event exists, notify keeps the count itself and the port goes. Limit: connections folded into a later hit of the same incident are not counted (only the hit the link names is read). Sources: top-tier alert tools (PagerDuty, Opsgenie, Datadog) show the number of occurrences folded into one alert as the alert's count, so the fold must not hide the repeats. |
