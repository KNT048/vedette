| D-267 | **Docker's FORWARD drop: `vedette-host` keeps four rules in `DOCKER-USER`, bound to the bridge `vedette0` and the `vedette-int` subnet.** Docker sets the iptables filter FORWARD policy to DROP when it enables IP forwarding; netavark (Ubuntu 26.04) keeps its rules in its own nftables table and an accept there is not final, so on a box with Docker the GUI on 8443 and syslog 514 are unreachable from the LAN (#297) and the containers cannot reach the internet. Decision: install.sh gives the network a fixed bridge name (`PodmanArgs=--interface-name=vedette0` in `vedette-int.network`; probed on Podman 4.9 of Ubuntu 24.04, 5.x of 26.04 and 5.4 of Debian 13: `PodmanArgs=` works on all three, Quadlet `InterfaceName=` only from 5.7). Only when the chain `DOCKER-USER` exists, `vedette-host` (at start and every 30 s, idempotent: `iptables -C`, then `-I DOCKER-USER <position>` so the order is fixed) holds, in this order: `-i vedette0 -o docker0 -j RETURN` and `-i vedette0 -o br-+ -j RETURN` (Docker keeps protecting its own networks from Vedette's containers: the packet goes on to Docker's chains), `-o vedette0 -d <subnet> -m conntrack --ctstate DNAT,ESTABLISHED,RELATED -j ACCEPT` (published ports and replies) and `-i vedette0 -s <subnet> -j ACCEPT` (the containers' traffic out); all four carry `--comment vedette-int`. What they accept: packets that enter or leave through `vedette0` from or to the subnet; apart from the two RETURNs, wherever those packets go. Not accepted: anything not through `vedette0`, so a LAN host cannot spoof a vedette-int source into Docker's networks. An administrator's own DOCKER-USER rules must stand above ours (the host adds a missing rule inside its own block and never reorders). The subnet (only 172.30.x.0/24, like install.sh) and the bridge name are read from the Quadlet file (`net/netip`), never from a request; a network file without the bridge name (an older install) is left alone with one log line, a re-install is needed (pre-release: no migration); the host never inserts beside vedette-int rules in a form it does not know. Exec only through the allowlisted `/usr/sbin/iptables` with a closed argv grammar. A stop leaves the rules; `install.sh --uninstall` deletes all four; `install.sh` checks them by effect and, with FORWARD DROP and no `DOCKER-USER` (ufw, firewalld, own firewall), only warns what to allow. No `After=docker.service` in the unit: a hung Docker start would hold the appliance down at boot, and the 30 s loop already covers Docker starting later. Rejected: switching netavark to the iptables driver (changes Podman for every other network on the box; 24.04 and 26.04 differ), `sysctl ip_forward=1` before Docker starts (changes the customer's Docker isolation, does not fix a running Docker), `install.sh` refusing on a box with Docker (a legitimate choice, and the box would still break when Docker is installed later), a source-only accept (it bypasses Docker's isolation of the customer's containers and accepts a spoofed source from the LAN; review round 1, M1). | Sources: Docker, [Packet filtering and firewalls](https://docs.docker.com/engine/network/packet-filtering-firewalls/) (the drop policy when Docker enables forwarding; DOCKER-USER is the chain for the administrator's rules); LXD, [Prevent connectivity issues with LXD and Docker](https://documentation.ubuntu.com/lxd/en/latest/howto/network_bridge_firewalld/#prevent-connectivity-issues-with-lxd-and-docker) (interface-bound ACCEPT rules for the bridge in DOCKER-USER); Fedora, [Changes/NetavarkNftablesDefault](https://fedoraproject.org/wiki/Changes/NetavarkNftablesDefault) (rootful Podman beside Docker loses connectivity; the fix is an iptables accept for the Podman traffic). | 2026-11-11 |
