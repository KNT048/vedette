| D-605 | **Alpine's fixed package releases come from data, not a hand copy: a built-in distribution feed `alpine-osv` reads OSV.dev's Alpine ecosystem (Alpine's secdb, converted by OSV.dev) and findings reads the first fixed release per branch from it; it is fetched only while a device states Alpine Linux (kien, option C: each OS vendor's own data inside Vedette's matcher; replaces the releases D-604 (5) copied by hand).** (1) **Source:** `https://osv-vulnerabilities.storage.googleapis.com/Alpine/all.zip`, one file for every Alpine branch OSV.dev lists (`Alpine:v3.2` … `Alpine:v3.24`; **no edge**: OSV.dev does not convert secdb's edge), 9,244,018 bytes and 10,859 records on 2026-11-17, 124 of them CISA KEV CVEs with 1,472 rows kept. A "fixed" event is the first fixed apk release of the source package on that branch (the higher in apk order when secdb lists two, 13 KEV rows), secdb's `0` is "not affected"; a release apk cannot read (`1.9.5p2-r0`, 22 rows of 2 KEV CVEs) drops that branch's row only, since a missing row never proves "not affected". CVE-2026-123158 checked against secdb itself: the nine branches v3.16 9.0_p1-r6 … v3.24 10.3_p1-r2 match; secdb's edge 10.6_p2-r0 is not in OSV.dev, so an edge device is decided as a branch without a row (D-604 as amended by #961's review). (2) **Licence:** secdb is CC BY-SA 4.0 (Alpine's licence file); OSV.dev's data sources page lists the same licence for its Alpine conversion and states no other terms; open data, usable with attribution; share-alike only for adapted data the project shares (it shares four unmodified records as a test fixture, attributed). (3) **Gate (D-570 without the first fill):** fetched only while the inventory has a device whose own OS statement says Alpine Linux: the OS a person set (inventory INV-41, which wins), else its agent's, else its SNMP answer (`findings.StatesAlpine`), never nmap's or DHCP's guess; unlike Ubuntu and Debian there is no first fill, and a device list Vedette cannot read (or the inventory off) never opens it, so a box without an Alpine device never contacts Google Cloud Storage; the first device that states Alpine wakes the pull at once. Until the data is loaded (the feed on and holding no row: never filled, or every pull failed) such a device's Alpine-only CVEs stay a question ("Alpine's fixed releases are not loaded yet"), never an NVD finding; only with the feed off does NVD decide (review r1 M1 of #968). Then once a day, conditional on `ETag`/`Last-Modified`, at most 32 MiB on the wire, 50,000 files and an 8 MiB directory (read from the end record before the directory is parsed), 1 MiB per record, 64 MiB unpacked; a format change (no Alpine record name, no `Alpine:vX.Y` ecosystem) fails the pull, never stores nothing; a withdrawn record keeps nothing; two files of one CVE reject it. KEV CVEs only (no tier rows: the plan reads no apk package). (3b) **Attribution where it decides:** a finding's evidence names "Alpine Linux's security database, https://secdb.alpinelinux.org/v3.23/main.json (CC BY-SA 4.0), through OSV.dev". (4) **What leaves the box:** a plain GET with the box's IP and `User-Agent: Vedette/<version>`; Google (OSV.dev's host) can tell the box runs Alpine Linux and when, not which release or package (PRIVACY flow 1). (5) **Why OSV.dev and not secdb directly:** one file covers every branch, new branches need no code change, and the same OSV reader carries into the other distributions (post-v1 #963); secdb would be two files per branch (main, community) whose list of branches changes twice a year.
