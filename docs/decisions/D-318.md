| D-318 | The honeypot `log/` is a Quadlet volume of type tmpfs (`vedette-hp-log.volume`: `Type=tmpfs`, `Device=tmpfs`, `Options=size=64m,nr_inodes=1024,nosuid,nodev,noexec`), written by `vedette-host` from constant text before the `core` or `honeypot` unit. The honeypot mounts it read-write with `:U`, core read-only; it replaces the bind of `/var/lib/vedette-honeypot/log`, so a taken-over container can no longer fill the filesystem of `vedette.db` (it gets ENOSPC at 64 MiB or 1024 files). Logs are lost when core and honeypot are both stopped (reboot, or a honeypot restart while core is down: every line core has not read yet); accepted. core and honeypot share the volume, so they must change units in one run: bootstrap refuses to write one of them while the other still binds the old directory. Left open: a taken-over container can still write to disk through stdout/stderr into journald, bounded by `SystemMaxUse` (10% of the filesystem, at most 4 GiB), not by this cap. | Why tmpfs: core tails every line into its database and its reader restarts cleanly when the file is replaced or cut (honeypot INV-16), so the log is a transport, not a record; Kubernetes does the same for scratch data (`emptyDir` with `medium: Memory` and `sizeLimit`, https://kubernetes.io/docs/concepts/storage/volumes/#emptydir) and Podman documents this exact form (`podman volume create --opt device=tmpfs --opt type=tmpfs --opt o=size=2M,nodev,noexec`, https://docs.podman.io/en/latest/markdown/podman-volume-create.1.html; Quadlet `.volume` keys `Type=`, `Device=`, `Options=`, https://docs.podman.io/en/latest/markdown/podman-systemd.unit.5.html). A named volume (not `Tmpfs=` of the container) is needed because core must see the same filesystem. Cost: pages count against RAM and the writer's 256 MiB cgroup (64 MiB at most; OpenCanary rotates 10 MiB x 3, about 40 MiB). No new package, no root step beyond the unit the host already writes, same on Ubuntu 24.04/26.04 and Debian 13 (Quadlet from podman 4.4). Not chosen: (1) a loop-mounted ext4 image (fallocate, mkfs, mount, fsck and loop devices as new host steps and failure modes, to keep a log nobody needs after reboot); (3) a Podman volume with `size=` on xfs project quotas (Podman documents `size` for tmpfs and xfs only; default Ubuntu/Debian root is ext4, so it fails on the target OS); (4) `--storage-opt size=` (limits the container's writable layer, not a bind or volume, and also needs xfs/overlay quotas); a `Mount=type=tmpfs` or `Tmpfs=` inside the honeypot unit alone (private to that container, core cannot read it); a systemd `.mount` unit shipped in the .deb (works, but a second place for ordering with Quadlet, an escaped file name and a package file the host-deb tests would police, for the same result); (5) OpenCanary to stdout/journald (core would have to read the journal, a new privilege and a new parser of attacker-controlled text; the journal cap `SystemMaxUse` is shared with all other units). T-Pot does none of this: it relies on a logrotate cron and host disk (https://github.com/telekom-security/tpotce), which is the gap this closes. Proof by effect (rootless podman, same volume options, `:U`): a 100 MiB write stops at 64 MiB with ENOSPC, file number 1024 fails with ENOSPC, a second container mounting it `:ro` under another uid reads the writer's file and gets "Read-only file system" on write. Rootful proof (UserNS=auto, reboot, apt upgrade) is a lab line in `.ai/deferred/feat-honeypot.md`. Addendum (#486, 2026-11-12): the honeypot unit also says `ContainersConfModule=/usr/lib/vedette/honeypot-containers.conf`, a containers.conf module `[containers] default_sysctls = [{append=false}]`. The container joins `vedette-hp`, a namespace owned by the host's user namespace, from its own (`UserNS=auto`); crun may not write a sysctl of that namespace from there, so Ubuntu 26.04's default `net.ipv4.ping_group_range=0 0` (`/usr/share/containers/containers.conf`) failed every start (`OCI permission denied`, exit 126; reproduced on 192.168.18.141, podman 5.7.0, crun 1.21, and cleared by the same text given as `CONTAINERS_CONF_OVERRIDE`). Only the honeypot: core has its own netns on `vedette-int`, sensor and scan run `Network=host` (Podman sets no network sysctl there); all three keep the distribution's defaults. The file is constant text shipped in the `vedette-host` .deb (`deploy/deb/honeypot-containers.conf`, 0644 root, under `/usr/lib/vedette` beside the binary, like the vendor files of `/usr/lib/sysctl.d`, and inside the folders the install and uninstall diffs already list), so dpkg installs, upgrades and purges it and `install.sh --uninstall` needs no step of its own; not written by `vedette-host` (a writer, a removal and an identity check for a file that never changes). Absolute path, so a module of the same name under `/etc/containers/containers.conf.modules` cannot shadow it. `ContainersConfModule=` is a Quadlet key from Podman 4.8 (in podman-systemd.unit(5) of v4.8.0, absent in v4.7.0: https://github.com/containers/podman/blob/v4.8.0/docs/source/markdown/podman-systemd.unit.5.md), so the floor moves from 4.4 to 4.8 in `install.sh` and the package `Depends` (Ubuntu 24.04 has 4.9, 26.04 5.7, Debian 13 5.4: no supported box changes). Not chosen: `Environment=CONTAINERS_CONF_OVERRIDE=` in `[Service]` (works, but it is a process-wide override; the module is Quadlet's documented per-unit key); `--sysctl` in `PodmanArgs` (adds a sysctl, cannot remove a default); changing the box-wide `containers.conf` (changes the administrator's other containers). | 2026-11-12 |
