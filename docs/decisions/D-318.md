| D-318 | The honeypot `log/` is a Quadlet volume of type tmpfs (`vedette-hp-log.volume`: `Type=tmpfs`, `Device=tmpfs`, `Options=size=64m,nr_inodes=1024,nosuid,nodev,noexec`), written by `vedette-host` from constant text before the `core` or `honeypot` unit. The honeypot mounts it read-write with `:U`, core read-only; it replaces the bind of `/var/lib/vedette-honeypot/log`, so a taken-over container can no longer fill the filesystem of `vedette.db` (it gets ENOSPC at 64 MiB or 1024 files). Logs are lost when the box reboots (and if core and honeypot are both stopped); accepted. | Why tmpfs: core tails every line into its database and its reader restarts cleanly when the file is replaced or cut (honeypot INV-16), so the log is a transport, not a record; Kubernetes does the same for scratch data (`emptyDir` with `medium: Memory` and `sizeLimit`, https://kubernetes.io/docs/concepts/storage/volumes/#emptydir) and Podman documents this exact form (`podman volume create --opt device=tmpfs --opt type=tmpfs --opt o=size=2M,nodev,noexec`, https://docs.podman.io/en/latest/markdown/podman-volume-create.1.html; Quadlet `.volume` keys `Type=`, `Device=`, `Options=`, https://docs.podman.io/en/latest/markdown/podman-systemd.unit.5.html). A named volume (not `Tmpfs=` of the container) is needed because core must see the same filesystem. Cost: pages count against RAM and the writer's 256 MiB cgroup (64 MiB at most; OpenCanary rotates 10 MiB x 3, about 40 MiB). No new package, no root step beyond the unit the host already writes, same on Ubuntu 24.04/26.04 and Debian 13 (Quadlet from podman 4.4). Not chosen: (1) a loop-mounted ext4 image (fallocate, mkfs, mount, fsck and loop devices as new host steps and failure modes, to keep a log nobody needs after reboot); (3) a Podman volume with `size=` on xfs project quotas (Podman documents `size` for tmpfs and xfs only; default Ubuntu/Debian root is ext4, so it fails on the target OS); (4) `--storage-opt size=` (limits the container's writable layer, not a bind or volume, and also needs xfs/overlay quotas); a `Mount=type=tmpfs` or `Tmpfs=` inside the honeypot unit alone (private to that container, core cannot read it); a systemd `.mount` unit shipped in the .deb (works, but a second place for ordering with Quadlet, an escaped file name and a package file the host-deb tests would police, for the same result); (5) OpenCanary to stdout/journald (core would have to read the journal, a new privilege and a new parser of attacker-controlled text; the journal cap `SystemMaxUse` is shared with all other units). T-Pot does none of this: it relies on a logrotate cron and host disk (https://github.com/telekom-security/tpotce), which is the gap this closes. Proof by effect (rootless podman, same volume options, `:U`): a 100 MiB write stops at 64 MiB with ENOSPC, file number 1024 fails with ENOSPC, a second container mounting it `:ro` under another uid reads the writer's file and gets "Read-only file system" on write. Rootful proof (UserNS=auto, reboot, apt upgrade) is a lab line in `.ai/deferred/feat-honeypot.md`. | 2026-11-12 |
