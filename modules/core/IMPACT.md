# Core — Change Impact Map


## Modifying: Settings › Scanning › History (`GET /scanning/history`, `ScanningConfig.History`, `HistoryRun`; INV-40 (5))
- **cmd/vedette/scanninghistory.go** builds every row from sensor-active `Jobs` and exposure `RecentScans`; a new field of `HistoryRun` (or a new outcome) needs its builder there, `web/src/features/scanning/contract.ts` (`HistoryRun`), the mock (`scanning/mocks.ts` `historyStore`) and `scanning/LastChecks.tsx` (`HistoryOutcome`).
- **The rule of the list**: a row's text says only what its run stored; a source that cannot say more must not invent it (an SNMP read is "n of m answered", never the targets it meant to reach).
- **`?asset=`**: the device page's Last checks (`scanning/LastChecks.tsx`, `useScanningHistory`) read it; `ScanningConfig.History` takes the device id ("" = every run). The jobs record addresses, not devices: the match is the device's address now.
- **Cost**: the SPA reads it every 30 s while a device page is open (`useScanningHistory`); the sources are bounded (sensor-active one indexed read per kind, exposure one read of `exp_snapshot`), core keeps the newest 200.

## Modifying: schedules (`core/schedule`, `ScheduleHandlers`; INV-42)
- **A module adopting schedules** registers a `schedule.Owner` on `deps.Schedules` in `buildServices` (before `serve` calls `Start`, which saves the defaults that are on). An owner with one schedule per subject calls `EnsureTx` when it creates the subject and `schedule.DeleteTx` when it deletes it, in the same transaction. Its `Start` runs inside the schedule's transaction: queue a run with `CreateTx` and pass `f.Trigger`, `f.By`, `f.ScheduleID`; return `schedule.Skip(reason)` to skip with a reason.
- **`Next`** is the one function of a due time: a change of it changes every stored `next_due_at`, which `Start` brings up to date with `Recompute` at the next start (the self-check fails until then). Its table test covers summer time, month ends and windows over midnight.
- **The organization's time zone**: whatever writes `core_org.timezone` calls `schedule.Recompute` in the same transaction (today `PUT /core/general`).
- **`core/server/modules.go`** maps `/schedules` to core (and `web/src/lib/apiModules.ts`, `api/route-modules.json`).

## Modifying: runs (`core/run`, `RunHandlers`; INV-41)
- **A module adopting runs** registers its `run.Kind` on `deps.Runs` while it is built in `buildServices` (before `serve` calls `Start`: the restart recovery resumes only the kinds it knows), queues with `CreateTx` in the transaction that writes its own rows keyed by `run_id`, and reports through `Exec` (steps, items, log). A resumable kind must skip the steps that are `done` when `Exec.Resumed`.
- **Resume vs ResumeWaiting**: `Resume` is the person's button (a waiting run, or a stopped one with work left of a resumable kind). Code that starts on its own what it read as waiting (a window tick, a scan worker heartbeat, a queue drain, a pass that gave way) calls `ResumeWaiting`, which queues only a run that still waits in the same transaction: with `Resume` there, a person's Stop pressed between the read and the resume is undone.
- **The lane** is the database's guard: two kinds that must never run together share a lane; a kind with its own lane runs beside the others. Changing a kind's lane changes what can run at once.
- **`core_run` columns** are read by `run.Run`/`run.Detail` (the API, the web contract `web/src/features/scanning/contract.ts` `Run`, `RunDetail`, its mock `runsStore`), `export_policy.go` and `run.Invariants`. A new state is a new value of `run.Statuses` and `RUN_STATUSES` together (shape check only, no table rebuild).
- **`core/server/modules.go`** maps `/runs` to core (and `web/src/lib/apiModules.ts`, `api/route-modules.json`).

## Modifying: `modreg.Registry` (`core/modreg`) — in practice: `modreg.Load(fs.FS) ([]Manifest, error)`, `modreg.New(ctx, Config{DB, Audit, Manifests, Version, Clock, Log, ContainerOnly}) (*Registry, error)`, `(*Registry).Enabled(id) bool`, `ContainerOnly() bool`, `List() []State{ID, Tier, Depends, Enabled, EnabledAt, Available}`, `Enable(ctx, tx, actor, id, withDeps) (Change, error)`, `Disable(ctx, tx, actor, id) (Change, error)`, `Publish(Change)`, `OnChange(func(id string, enabled bool))`, `Change{Enabled, Affected}`, `ErrManifest`
- **There is no standalone `Enable(ctx,id,withDeps)` function**: `Enable/Disable` run inside the caller's transaction (writing `core_module` + `core_audit` `module.enable|disable` in the same tx, `actor` = email) and return a `Change`. **Call `Publish(Change)` only AFTER the tx commits** (it updates the cache + calls `OnChange`); if the tx rolls back, drop the `Change` and the cache does not change. The enable/disable decision reads `core_module` inside the tx (under the write lock), not the cache. `Publish` ignores a Change older than the Change already applied (commit order).
- **`Enabled(id)`**: an id with no manifest (a module not in this build) = off; `kind: component` (`host`) = present, with no switch and no `core_module` row; tier `core` is always on. `Enable`/`Disable` of a core module → 400 `core_module`; an unknown id or a component → 404 `not_found`; a missing dependency → 409 `missing_dependencies` + `missing[]` (including transitive dependencies, dependencies first) and nothing changes, unless `withDeps`.
- **Install mode**: `Config.ContainerOnly` (= an empty `-host-socket` flag, `cmd/vedette/main.go`) is the only source of the install mode; `ContainerOnly()` serves `GET /modules`, `GET /core/setup/modules` (`install`) and inventory's `box` job (the model of "This box"). A module with `needs_host: true` in its manifest (honeypot, scan-credentialed) has `Available=false` on a container-only build and `Enable` returns 409 `not_appliance` before anything else (nothing is written), even when it is a dependency being enabled along (`withDeps`); disabling is still allowed. `Load` rejects a manifest that has `needs_host` together with `default: on`. Changing this → `TestNeedsHostOnContainerOnly`, `TestSetupOnContainerOnly`.
- **Manifest**: `Load` reads `<directory>/MANIFEST.yaml` (skipping a directory that begins with `_`), checks id = the directory name, tier ∈ core/standard/optional, depends exist and are not components, no cycle, exactly one module with `tier: core` (a component does not count), the `core` module does not depend on a module outside tier core, a module on by default does not depend on a module off by default, `default:` accepts true/false/on/off (missing = on for core, off for the rest). Startup inserts the missing rows from `default` (`ON CONFLICT DO NOTHING`, never overwriting an administrator's choice) and repairs a `core` row that was turned off.
- **Every module with an optional dependency** (`feeds→inventory`, `inventory→notify`, `findings→notify`, `mitigation→ai`, `scan→exposure`…): call `Enabled` before using it. Changing the semantics → the wrong degraded mode.
- **`core/server`** (the module gate: a route of a disabled module = 404 exactly like an unknown route) and **`core/jobs`** (`ModuleChanged` through `OnChange`) read `Enabled`; the **SPA** (`web/src/lib/modules.ts`, `ModulesSection`) reads `GET /modules`, and the disable button shows `affected`.
- **`core_module`, `core_job_run`** (core's tables in `0001_core.sql`): `core_module.version` records `Config.Version` when the row is inserted.

## Modifying: `server` (`core/server`) — `server.New(Config{API oas.Handler, Auth Authenticator, Modules ModuleGate, Log, MaxBody, BodyLimits, PublicPerMinute}) (http.Handler, error)`, `Prefix = "/api/v1"`, `Authenticator{Authenticate(*http.Request) (Principal, error); CheckCSRF(*http.Request, Principal) error}`, `ErrNoSession`, `Principal{ID, Email, Role, PasswordChangeRequired}`, `PrincipalFrom(ctx)`, `WithPrincipal`, `RequestIDFrom(ctx)`, `ModuleOf(routes.Operation) string`, `Fallback{oas.UnimplementedHandler; Log}` (has `NewError`), `servertest.Auth/Gate/StandardUsers` (fakes for tests)
- **Layer order** (outside in): `server.Envelope` (recover a panic → request id: always newly generated, the client's id is dropped, kept if an outer Envelope already set it → security headers: CSP, nosniff, no-referrer, `Cache-Control: no-store`) → `Origin` check → body cap (413 `too_large`) at the largest level across all operations → route lookup with `FindPath` (404) → the operation's own cap: `Config.MaxBody` (1 MiB) unless `Config.BodyLimits[operationId]` raises/lowers it (a module declares it in `moduleWiring.BodyLimits`: the feed pattern 5 MB; a wrong operationId → `server.New` refuses). After that: **a non-public route**: `Authenticate` (401) → module gate (404) → role from `routes.Operations` (403) → CSRF for POST/PUT/PATCH/DELETE (403 `csrf_invalid`) → ogen; **a public route**: module gate (404) → ogen. The module gate comes AFTER authentication so that a client that is not logged in cannot tell whether a module is on or off (both give 401). Role/gate/CSRF are not in the handler.
- **`Origin` check** (`checkOrigin`, run before routing so it does not reveal which routes/modules exist): every POST/PUT/PATCH/DELETE, including public ones, if it has an `Origin` header it must equal exactly the scheme+host of the request itself (`https` on a TLS connection, otherwise `http`; `X-Forwarded-*` is not trusted), and a wrong one or two headers → 403 `csrf_invalid`. A request with no `Origin` (curl, agents, osquery) passes; the CSRF token is the second layer. **Host allowlist** (against DNS rebinding): `server.HostAllowlist`, 421 `misdirected_request` (INV-9).
- **`cmd/vedette`**: `topHandler` wraps `server.Envelope` around the whole `ServeMux` so the mux's 307 (`/api/v1`, `//`, `..`) and a 404 outside the API also carry security headers + `X-Request-Id`. A `-listen` that is not loopback (127.0.0.0/8, `::1`, `localhost`) is served over TLS (the box owner's certificate, or a self-signed pair signed by the box's CA; INV-9, INV-33). The scheduler runs on a child ctx cancelled on every exit path of `serve`; it waits for the scheduler for at most 10 s (a job that ignores the ctx cannot hold the process).
- **`core/auth`** installs `Authenticator`; ogen still requires the cookie `__Host-vedette_session` to be present before calling `HandleSession` (it only confirms that a principal is already in the ctx).
- **Module handlers** return only `*apierr.Error` for business errors; any other error → 500 `internal`, logged with the request id, with no content returned. A write handler takes the actor from `server.PrincipalFrom(ctx)`.
- **Route → module mapping** (`modules.go`): by default the ogen tag, overridden by path prefix (`/findings`, `/scans`, `/scans/credentialed` → `scan-credentialed`, `/core/oidc`, `/auth/oidc` → `auth-oidc` (longer than `/auth`), `/core/mcp` → `mcp-server`, `/install|intake|inventory/agents` → `agent-intake`, `/inventory/sensors` → `sensor-passive`, `/inventory/snmp` → `sensor-active`, `/core/network` → `host`, `/detection/alerts` → `ids`, `/detection|runs|scanning|schedules|auth|me|modules|setup` → `core`) and by **exact path patterns** in `core/api/routes` (`/findings/{id}/applied|ai` → `mitigation`; a pattern match beats every prefix). Adding an override prefix = changing the 404 gate of a whole group of paths; the test `TestEveryOperationMapsToAModuleWithAManifest` catches a module with no manifest; `TestModuleOfMatchesTheContracts` (`core/server/modules_test.go`) lists by hand every path pattern from the "Endpoints owned" section of every `CONTRACT.md` and fails when a new route has no owner or `ModuleOf` drifts from the contract (`GET /core/auth-options` is present in both core and auth-oidc: assigned to core because the login page needs it when SSO is off).
- **The composite handler** in `cmd/vedette/handler.go`: `server.Fallback` + each module's handler struct at the same depth; two modules that install the same operation = a compile error (ambiguous selector). Adding a module = embedding its handler struct there, built from `deps`.
- **The module list in the binary** (`cmd/vedette/modules.go`): `deps{Log, DB, Reg, Secrets, Audit, Clock}` is built once in `serve` and handed to the handler constructors and `Jobs` of every module; `wiredModules()` lists `{ID, Migrations, Jobs}` in dependency order (core first; `TestWiredModulesFollowDependencies` compares with the manifest's `depends`). `migrateAll` runs the migrations of every module in the binary, on or off (DATA_MODEL §5.6); `addJobs` rejects a job that declares a `Module` other than its own module. Adding a module = one line here + embedding the handler; `main.go` is not edited.

## Modifying: `auth` (`core/auth`; the HTTP handler is part 2) — `auth.New(Config{DB, Secrets, Audit, Mailer, Clock, Log, Argon2, MaxHashing, HashWait}) (*Service, error)`; `Service.Sessions` (`*Sessions`, installs `server.Authenticator`) and `Service.Codes` (`*EmailCodes`)
- **Passwords**: `Params{Memory, Time, Threads}.Hash/Verify` (the bare functions `HashPassword`/`VerifyPassword` are not in the API: they bypass the argon2 cap; they exist only in `export_test.go`), `DefaultParams` (argon2id m=64 MiB, t=3, p=2; PHC string `$argon2id$v=19$…`, 16-byte salt, 32-byte key), `ValidatePassword(pw, email) *apierr.Error` (12–256 characters, ≠ email, not easy to guess: common password roots, ≤ 3 distinct characters, digit/letter/keyboard runs, the name in the email (a copy for the mock: `web/src/features/core/util.ts` `guessablePassword`, keep the two lists equal); `weak_password`), `NewTempPassword()`, `(*Service).HashPassword(ctx, pw, email)` (checks the policy and then hashes with the configured parameters, under the argon2 cap). A hash read from the DB is bounded (m ≤ 256 MiB, t ≤ 10, p ≤ 16): a maliciously planted row does not make login eat all RAM. `needsRehash` is true when the parameters differ from the configuration: `Login` rehashes in the same transaction. **Changing `DefaultParams` = every user is rehashed at their next login**, with no migration.
- **Sessions**: the cookies `__Host-vedette_session` (HttpOnly) + `__Host-vedette_csrf` (readable) — `Secure; SameSite=Strict; Path=/`, no `Domain`, `MaxAge` 7 days (`Issued.Cookies()`, `auth.ClearCookies()`); a 32-byte base64url token, and the DB keeps only the SHA-256 (`token_hash`, `csrf_hash`). `Authenticate` reads the role from the DB **every time**: expiry by 4 hours idle (`IdleTimeout`) or 7 days absolute (`AbsoluteTimeout`), revoked → `server.ErrNoSession`; a locked user → 403 `disabled`; `last_seen` is refreshed at most once a minute and **never queues behind the writer**: one refresh runs in the background at a time, a request waits at most 50 ms (if the writer is busy it is skipped and redone next time; a write failure is only logged). `CheckCSRF` looks up the session again by cookie and compares the SHA-256 of `X-CSRF-Token` (constant time), and the principal must be the session's owner. API: `Create(ctx, tx, userID, device string, ip netip.Addr)` (stores the real address), `Lookup`, `CurrentID(r)`, `List`, `Revoke(ctx, actorEmail, userID, sessionID)` (404 `not_found` if it does not belong to that person), `RevokeOthers`, `RevokeAllForUser(ctx, tx, userID)`, `Logout(ctx, token)`.
- **`Login(ctx, LoginRequest{Email, Password, Code, IP, UserAgent}) (LoginResult, error)`** per INV-8: `LoginRequest.IP` is a `netip.Addr` (the handler does `netip.ParseAddrPort(r.RemoteAddr)` itself; an invalid address is a programming error, and there is no shared key to fall back to). Flow: the attempt is counted against the (IP, email) limit right at the start (parallel attempts cannot slip past each other) → password (always runs one argon2, even for an unknown email, under the concurrency cap: 503 `server_busy`) → 2-step (a separate per-account counter) → one transaction that **reads the user again and refuses** if the password/key/2-step kind has changed, then creates the session + `last_login` + the TOTP step + rehash (`UPDATE … WHERE cred_version = <the value checked>`; `core_user.cred_version` rises on every real password change/reset, so two logins that both upgrade the hash do not make each other fail) + `auth.login`. `twofa_required` is a 401 `*apierr.Error` with `method` (+ `sent_to`, `resend_after` for email). A failure writes `auth.login_failed` for both a real account and an unknown email (the same work at the writer, so that response time does not reveal which email has an account; an unknown email is written as `unknown email <16 hex>` with user `unknown`, the 16 hex being an HMAC-SHA-256 with the key `core_audit.unknown_email_key` in `core/secrets` (people often paste a password into the email field, and the audit chain cannot be deleted); the audit grows with the number of attempts, bounded by the wrong-login limit and the handler's public-endpoint limit). `ResendCode(ctx, email, password string, ip netip.Addr)`. **The argon2 cap** (`hashgate.go`): at most `Config.MaxHashing` (default `min(GOMAXPROCS/2, GOMEMLIMIT/4/Argon2.Memory)`, at least 1; core's Quadlet unit must set `GOMEMLIMIT`) hashes/checks at the same time (64 MiB each; core is limited to 2 GiB, DEPLOYMENT §2.6), waiting at most `Config.HashWait` (2 s), with a queue of `4 × MaxHashing`; beyond that 503 `server_busy` + `retry_after` 3; an attempt refused because of being busy is refunded and does not count as a wrong guess; rehashing after login is skipped when busy. `Service.HashPassword(ctx, password, email)` takes a ctx. **The login limit** (`ratelimit.go`): 10 wrong attempts, less than 15 minutes apart, per (IP, email; IPv6 counted per address, cap 10, and per (/64, email), cap 100; an IPv4-mapped address counts as IPv4) → 429 `rate_limited` + `retry_after` 30 s doubling up to 10 minutes; password guesses and 2-step code guesses are counted **before** checking (`begin`) and refunded when correct (`refund`, which also returns the waiting time that this very attempt just set, and resets the entry to 0); the per-account counters (`twofa`, `account`) live in their own map and are never evicted; when the client map is full, entries that are not blocked and have the fewest wrong attempts are evicted first; the 2-step code also has a separate counter per account, not per IP (10 wrong / 15 minutes), so rotating the source address does not evade it; it is kept in process memory (lost on restart). Changing the password/turning off 2-step for the user who is logged in shares the per-account counter, also counting first. `ChangeOwnPassword`, `DisableTwoFA`, `ConfirmTOTP`, `ConfirmEmail2FA` check again inside the write transaction (`callerRefusal`): locked → 403 `disabled`, `keepSessionID` already revoked/expired → 401 `unauthenticated`; the first two also compare `cred_version` (changed → 400 `wrong_password`).
- **`VerifyTwoStep(ctx, userID, code, purpose, summary) (StepUp, error)`** (INV-22): the caller is `modules/response` (through the `TwoStep` gate that `response` defines; nil → 403 `twofa_required`). Changing the signature or the error codes (`code_required`, `twofa_required` 403, `invalid_code`, `rate_limited`, `twofa_email_unavailable`) affects `response` INV-16. Shared with login: `checkTOTP`/`last_step`, the limiter `twofaKey`, `core_email_code` (a code bound by the hash domain). `codeHash` has an extra domain parameter; changing it breaks codes that are waiting. The approval code is sent through `StepUpMailer` (an optional interface beside `CodeMailer`; `notify` installs `SendStepUpCode` (`CodeMailer`); a mailer that does not install it makes an approval email return 503 `twofa_email_unavailable`). The column `core_email_code_send.kind` separates the budget of 5 codes/hour. Tests: `core/auth/stepup_test.go`.
- **`CodeMailer`** (`Available(ctx) bool`, `SendCode(ctx, to, code) error`): **implemented by the `notify` module** (FORBID-2: core does not import notify); `main` passes it in `Config.Mailer`, nil = not usable. `notify` must not log the code. `Available` false or `SendCode` failing → 503 `twofa_email_unavailable` (login) or 409 `email_channel_not_ready` (turning on 2-step), the code just stored is deleted and the send is not counted.
- **TOTP**: `NewTOTPSecret`, `TOTPCode(secret, step)`, `VerifyTOTP(secret, code, now, lastStep) (step, ok)`, `TOTPStep`, `SecretBase32`, `OTPAuthURI`; the key is in `core/secrets` (purpose `core_user_totp`); `Service.StartTOTP/ConfirmTOTP(ctx, userID, currentSessionID, code) (Issued, error)/StartEmail2FA/ConfirmEmail2FA(…) (Issued, error)/DisableTwoFA(ctx, userID, currentSessionID, password) (Issued, error)/ResetTwoFA`; `ChangeOwnPassword` also returns `(Issued, error)`. Changing the password and turning 2-step on/off by the user themselves calls `Sessions.Replace(ctx, tx, userID, currentSessionID)` in the same transaction: every session ends, the session in use is replaced with a new one (the same device + address, a new token) and the handler resets the cookie with `renewSession`; `ConfirmTOTP` counts each code on the per-account 2-step counter and cancels the pending key after 5 wrong codes (`too_many_tries`; an in-memory counter of 5); an admin resetting 2-step ends every session of that person, in the same transaction. Turning on 2-step checks the state again inside the transaction (`UPDATE … WHERE twofa_method IS NULL`): of two parallel confirmations only one succeeds, and the other gets 409 `already_on`. An email code stores `code_hash` = HMAC-SHA-256 with the key `core_email_code.hmac_key` in `core/secrets` (created at first use). A code already accepted cannot be reused: `AdvanceTotpStep` runs inside the login transaction (6 simultaneous requests with the same code, only one succeeds).
- **Users (INV-7)**: `CreateUser(ctx, tx, actor, NewUser{Name, Email, Role, PasswordHash})` (inside the caller's transaction: also used for `POST /core/setup`; an email/name with control characters → 400 `invalid_email`/`invalid_name`; a duplicate email, even when two creations race → 409 `duplicate`), `UpdateUser(ctx, actorID, actorEmail, targetID, UserPatch)` (`self_disable`, `last_admin` computed on the state after the change, a lock ends every session), `ResetPassword` (returns the temporary password exactly once, ends every session of that person), `ChangeOwnPassword`, `GetUser`. Error codes: `docs/API_CONVENTIONS.md` §3.3.
- **Every change writes `core_audit` in the same transaction** (`auth.login`, `auth.login_failed`, `auth.logout`, `auth.session_revoke`, `auth.sessions_revoke_others`, `auth.code_resend`, `auth.reauth_failed` (a wrong password when changing the password or turning 2-step on/off), `account.password`, `account.2fa_start|on|off`, `user.create|role|disable|enable|password_reset|2fa_reset|console_reset`); `detail` never contains a password, code, token or key.
- **Reset from the console**: `(*Service).ConsoleReset(ctx, email) (temp string, sessionsEnded int, err error)` for the command `vedette reset-admin <email>` (`cmd/vedette/resetadmin.go`, run beside the serving process in the same container; not through HTTP, with no route). Only an active administrator who uses a password (not SSO); one transaction: a temporary password (72 hours, must be changed at login), turning off 2-step (`clearTwoFA`), ending every session, audit `user.console_reset` with the actor `console`. Errors are sentences for the console (an ordinary `error`, not `apierr`). The in-memory login counters of the running process are not cleared.
- **`authtest`** (`core/auth/authtest`): `New(t) *Env` (a migrated DB, a fake clock, a fake mailer, cheap argon2), `Env.User`, `Env.Login`, `Env.Count`: used for handler tests in part 2; `authtest.New(t, func(*auth.Config)...)` allows editing `Config` (for example `MaxHashing`). The tests in the package also have `auth.SetHashProbe` (only in the file `export_test.go`) to measure how many argon2 runs happen at once.
- **All modules**: only need `server.PrincipalFrom(ctx)`; no module reads `core_user`/`core_session` (FORBID-5).

## Modifying: exporting and deleting data (INV-14, INV-28: `modules/core/{handlers_data,handlers_purge}.go`, `modreg.Registry.Reset`, `store.DB.Compact`, `cmd/vedette/{modules,wiring,main}.go`)

## Modifying: `events` (`core/events`) — in practice: `events.NewBus(log, ...Option) *Bus` (`WithTimeout(d)`, default `DefaultTimeout` 5 s), `(*Bus).Subscribe(name, Handler) (unsubscribe func())`, `Publish(ctx, Event{Name, Data}) error`, `Flush(ctx, *Outbox)` (runs handlers under the request's context with cancellation removed, still with a timeout per handler: when a change has committed, a client disconnecting must not make the event drop), `Outbox{Add, Len}`, `Handler = func(ctx, Event) error`, `ValidName`, `ErrInvalid`

## Adding: `core/pki` + `core/sensorlink` (the sensor protocol, INV-24)
- **API**: `pki.Open(ctx, Options{DB, Secrets, Audit, Now, Log}) (*Authority, error)`; `(*Authority).Start(ctx, dir)`, `.Renew(ctx, dir)`, `.SerialValid(role, serial)`, `.ClientCAs()`, `.ServerCertificate(hello)`, `.CACertPEM()`; `pki.WriteBundle(dir, role, data)` (chowns the file to the group of the role directory: if core does not belong to that group it writes an error, not silently leaving the file in the wrong group; dropping `--group-add` from the `core` unit breaks this). `sensorlink.NewServer(Options{Identity, Backend, ModuleOn, Now, Log, BodyTimeout, HeaderTimeout}) (*Server, error)` with `.Handler()`, `.TLSConfig()`, `.HTTPServer(addr)`; `sensorlink.NewClient(ClientOptions)` with `SendObservations`, `Config`, `Jobs`, `PassiveHeartbeat`, `ActiveHeartbeat`, `PostResult`, `Stats`; `Backend` (the interface that `cmd/vedette` (`sensorBackend`) implements; it has `JobRunning(id) bool`, asked before reading the result body), `Server.Serve(listener)`, `PendingListener`, `Identity` (implemented by `*pki.Authority`).
- **Connection cap per role**: `TLSConfig()` has a `GetConfigForClient` that counts each connection against the role of the certificate at handshake and fails the handshake when the role has no share left (`MaxConnsPassive`/`MaxConnsActive`; only connections of `PendingListener` are counted, with the share returned at `limitConn.Close`; counting against a role also takes the connection out of the pool of connections still in handshake, `limitConn.promote`), and `HTTPServer` sets `ReadTimeout`; whoever builds a separate `http.Server` around `Handler()` (like `httptest` in a test) is not counted against the per-role cap. The TLS configuration uses one fixed session-ticket key shared by the replicas. Changing `MaxConns` or the two role shares must keep `MaxConnsPassive + MaxConnsActive < MaxConns`. Every new refusal in `serve()` before reading the body must go through `refuse`/`closeAfter` (HTTP/1 only).
- **Callers**: `cmd/vedette/sensorwire.go`: `pki.Open` once, `Authority.Start` before listening on `-sensor-listen`, the daily `sensor-cert-renew` job calls `Authority.Renew`, `ModuleOn` from `modreg`, `Server.HTTPServer(addr)`; `Backend` is `sensorBackend` (embedding `sensor-passive` for the `passive` role, `sensor-active`'s `Dispatcher` for the `active` role); `cmd/vedette-sensor` (uses `sensorlink.Client`). `sensorlink.ValidVersion` is the shared SemVer rule for the heartbeat and for `core`'s build version.
- **Table** `core_sensor_cert` (in `0001_core.sql`, prefix `core_`), `core_secret` purpose `core_sensor_ca`.
- **Generated code**: `core/store/queries/sensorcert.sql` → `core/store/coredb/sensorcert.sql.go` (`make generate`).
- **Secrets**: the purpose `core_sensor_ca` is read only in `core/pki/ca.go` (`secrets.Restrict` in `pki.Open`); each `secrets.Store` can `pki.Open` only once, like `conn.New`: building two `Authority`s on one Store will error. A leaf's key never enters the DB or a log; it lives only in memory until written into the bundle.
- **Dependencies**: `core/sensorlink` uses only the standard library + `internal/jsonstrict` (checked by a test); `core/pki` → `core/sensorlink` (the types `Role`, `ClientRole`), `core/secrets`, `core/store`, `core/store/coredb`. No new dependency (`go.mod` unchanged), no new outbound data flow (loopback `127.0.0.1:8444`; `PRIVACY.md` unchanged).
- **Changing the order of request checks, the caps, or adding a wire field** = changing `docs/specs/sensor-protocol.md` §6/§7/§9 and raising `X-Vedette-Proto` (strict decoding), setting `ProtoPrevious` to the old release and keeping `core` able to serve the old side (a new request field is optional; when changing a reply, return the old form to the `ProtoPrevious` side), and setting the `min_upgrade_from` of that release; adding an error code = adding it to the `codes` table of `errors.go` and §7.

Test: `TestReserveClosesAPurposeBeforeAnyHolderRestrictsIt`. Two tests that scan the source tree (`core/conn` `TestOnlyCredNamesTheCredentialPurpose`, `core/pki` `TestOnlyPKINamesTheCAPurpose`) walk **every** directory that has Go files (including `content/`, `scripts/`), and `core/pki` is exempt only for two needles about `Restrict`/`Opener`, never `"core_connection"`.
- **New audit actions** (groups `sensor-ca`, `sensor-cert`; actor `system`): `sensor-ca.create`, `sensor-ca.replace`, `sensor-cert.issue`, `sensor-cert.retire`. The group names use a hyphen because `core/audit` does not accept an underscore.
