| D-383 | **Trap and decoy state come from what the box did, and the decoy IP is cleared only while every trap is off (S-HP-1, real-install QA 2026-11-12).** (1) Clearing the decoy IP (`PUT /honeypot/config` with an empty `secondary_ip`) is refused with 409 `traps_on` while any trap is on; the box never turns traps off behind the owner's back, and a trap cannot be switched on with no IP (re-checked inside the write transaction). Chosen over "clearing turns the traps off" because AWS refuses to release an Elastic IP that is still associated (https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/elastic-ip-addresses-eip.html), Azure refuses to delete a public IP that is attached to a resource (https://learn.microsoft.com/en-us/azure/virtual-network/ip-services/public-ip-addresses), and the Thinkst Canary console wants a Canary disabled before it is deleted (https://help.canary.tools/): an explicit order beats an implicit state change. (2) `Trap.state` and `Decoy.state` are `off`, `listening`, `conflict`, `starting`, `stopping`, `failed`: reported from the host (the container runs with the service on and the host holds the address), never inferred from the switch; `failed` carries the host's plain reason. (3) A refused address is asked again three times, then every 10 minutes, and again when the wanted set changes, so ten failing decoys cannot use the host's 10 writes a minute. (4) The inventory not having discovered anything yet means the spare-IP hint says "not checked", not "unused". | 2026-11-12 |
