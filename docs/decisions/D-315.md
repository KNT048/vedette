| D-315 | **Lab VMs on the Ubuntu dev box: plain QEMU/KVM with passt, no libvirt; `lan` mode only over a wired NIC (`scripts/dev/lab-vm.sh`, `docs/LAB-VM.md`).** (1) **What**: Ubuntu 24.04 and Debian 13 cloud images, one VM up at a time, 2 vCPU / 2560 MiB, a 20 GiB qcow2 overlay on a read-only base image, a cloud-init NoCloud seed (`cloud-localds`: user `lab`, passwordless sudo, key-only SSH, no default user). For the LAB checks of v1 criterion 3 (WP-31 list, WP-08 install/upgrade/rollback, the lab lines in `.ai/deferred/`). Dev tooling, not product code. (2) **Plain QEMU, no libvirt**: libvirt's system daemon brings `virbr0` with nft NAT rules (a host firewall change, forbidden on this box) and needs root for every operation; QEMU runs rootless once the user is in `kvm`. (3) **Network = passt** (`passt --one-off` + `-netdev stream`, needs QEMU ≥ 7.2): user mode, no host interface, route or firewall change; SSH only on `127.0.0.1:22404` (ubuntu2404) / `:22013` (debian13); the VM reaches the LAN and the Internet through the host's sockets. Known passt defaults kept: the guest gets the host's IPv4 address and the gateway address maps to the host's loopback (that is how the host's `127.0.0.53` resolver serves the VM's DNS), so the VM can reach services bound on the host's loopback and cannot reach the real router at the gateway address; acceptable for a VM that runs our own code. `--log-file` is not used: passt's AppArmor profile denies reading it back (measured 2026-11-12, `apparmor="DENIED" operation="open" profile="passt"`). (4) **`lan` mode** (`sudo lab-vm.sh lan-up <nic>`, `start <vm> --lan`, `lan-down`): a second guest NIC on a **macvtap in `passthru` mode** named `vlab0` (the only link the script creates or deletes), its `/dev/tapN` handed to `$SUDO_USER`. Passthru, not bridge: decoys (M7, L9, honeypot lab lines) put extra MACs on the guest NIC, and only passthru forwards all traffic to the one endpoint and puts the NIC in promiscuous mode so "virtio guests [can] change MAC address or set promiscuous mode" (`ip-link(8)`, iproute2 on the box, read 2026-11-12); bridge mode delivers only the macvtap's own MAC. Because passthru takes every frame of the NIC, `lan-up` refuses a NIC that holds a default route or a global address of the host. It refuses a **wireless** NIC (`/sys/class/net/<nic>/wireless` or `phy80211`): an 802.11 station in managed mode may only send frames with the MAC it associated with; "most Access Points (APs) will reject frames that have a source address that didn't authenticate with the AP" (https://wiki.debian.org/BridgeNetworkConnections, "Bridging with a wireless NIC", read 2026-11-12), so the VM's and the decoys' MACs never reach the LAN (carrying other MACs needs 4-address/WDS mode on both ends, not something a lab can count on). It refuses a NIC with no carrier, and a virtual NIC. The host cannot talk to the guest over macvtap (frames do not loop back through the NIC); SSH stays on the passt NIC. Not verified on a real box yet: whether NetworkManager leaves an externally created macvtap alone. On this box `enp2s0` has no carrier and the uplink is Wi-Fi, so `lan` mode needs a cable and a wired NIC the host does not use. (5) **One root step**, `sudo scripts/dev/lab-vm.sh setup`: apt-installs only the missing ones of `qemu-system-x86 qemu-utils cloud-image-utils passt netcat-openbsd openssh-client curl gpg gpgv` (`--no-install-recommends`), refuses versions below the floors written in the script (Ubuntu 24.04's: qemu 1:8.2.2, cloud-image-utils 0.33, passt 0.0~git20240220), adds `$SUDO_USER` to `kvm`, prints what changed, never touches the network. QEMU then runs under `sg kvm -c` until the next login, so no re-login is needed. (6) **Images**: Ubuntu `https://cloud-images.ubuntu.com/noble/current/noble-server-cloudimg-amd64.img`, `SHA256SUMS` verified with `SHA256SUMS.gpg` against the pinned primary key `D2EB44626FDDC30B513D5BB71A5D6C4C7DB87C81` ("UEC Image Automatic Signing Key", the signature's issuer fingerprint read with `gpg --list-packets`; key from `/usr/share/keyrings/ubuntu-cloudimage-keyring.gpg` or keyserver.ubuntu.com, only a `VALIDSIG` of that fingerprint passes). Debian `https://cloud.debian.org/images/cloud/trixie/latest/debian-13-generic-amd64.qcow2` with `SHA512SUMS` only: **Debian publishes no signature for cloud images** (listing of `latest/` and of the dated build `20261111-2659/`, 2026-11-12, holds only `SHA512SUMS`; no `genericcloud` build is published for trixie there), so HTTPS to cloud.debian.org is the trust anchor. Bases are stored as `~/.cache/vedette-lab/images/<vm>-<hash16>.qcow2`, mode 0444, never overwritten, so an overlay keeps its base when the vendor publishes a new image. (7) **Rules in the script**: one lab VM up at a time (pidfile checked against `/proc/<pid>/cmdline`, plus a lab QEMU without a pidfile); `start` refuses when MemAvailable < 2.5 GiB + 1.5 GiB headroom or when the box would pass 90% of its memory with the VM up; every step has a timeout; `stop` = QMP `system_powerdown`, then SIGTERM after 90 s, then SIGKILL; `destroy` removes only `~/.cache/vedette-lab/<vm>`; a dedicated SSH key `~/.cache/vedette-lab/id_ed25519` (the user's own key is not reused) and the VM's SSH host key made before the first boot, so `StrictHostKeyChecking=yes` from the first connection; state never in `/tmp`. `scripts/dev/lab-vm-test.sh` (shellcheck, argument parsing, dry-run argv, one-VM rule, memory guard, `lan-up` refusals on a fake sysfs) runs in `make check` and `make verify-go-static`.
