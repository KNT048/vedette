| D-515 | **A switch heard by LLDP under its chassis MAC and seen by ARP and scans at its management address is one device; a product with no device has no device type (W1-37, W9-1; inventory INV-28).** (1) **What LLDP carries.** The chassis ID (subtype 4 = the base MAC), the port ID, the system name, the description (model and OS by the walk-4 layouts), the capabilities, and the management address TLV (8), which `capture/lldp.go` does not read. On the N100 the Juniper row had no host name, so only the MAC block ties the two rows. (2) **The join** runs in inventory `Record` on every device a batch touched: (b) the same host name (LLDP system name), case-insensitive, on exactly one device with an IP; (c) the chassis MAC is the base of a block: same first five bytes, the other device's MAC 1..0x7f above (N100: base :80, management :ff). Only a **discovered device with a MAC and no IP and a network kind** (switch, router, ap, firewall) joins (never two devices that both have IPs, never the box, never a declared device), only into a device with an IP and a MAC of the **same OUI**, never with a locally administered (random) MAC, and only when exactly one device fits. **Rule (a), the LLDP management address, is not built now:** the passive engine runs in the `sensor` container and reaches core over the sensor protocol, decoded strictly (unknown field → 400), so carrying the address is a protocol bump (6) with the D-410 `min_upgrade_from` release rule, for a case (b) and (c) already cover on the walk; it is in `.ai/deferred/w1-37.md`. (3) **The merge** keeps the IP device's id, address and MAC; observations move (the chassis MAC stays as a `mac` observation marked `evidence='chassis'`, which never becomes the MAC and makes a later frame naming only that MAC find this device, so no new row and no "new device" incident every frame); software and open ports move; approval, suspicious flag, notes and scan choices carry over when the IP device has none; model and OS from LLDP win by the usual observation rules; one audit row `inventory.merge` ("<row> is the same device: <rule>"); `inventory.asset.deleted` for the old row (findings drops its rows) and `inventory.asset.updated` with `match` for the kept device (findings matches it again). The duplicate already on a box is fixed by the next LLDP frame it hears (sent again at most every 15 minutes, at once after a restart): no migration, no one-time job. (4) **W9-1**: a product declared with neither IP nor name ("Microsoft Office (no device)") gets no computer type (pc, server, web) from the catalog or from feeds' "I have this"; an appliance type (FortiGate → firewall) stays, because there the product is the device and mitigation reads declared firewalls/routers.
