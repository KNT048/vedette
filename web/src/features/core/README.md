# features/core

Stories: S-CORE-1 (modules, 409 turn on together), S-CORE-2 (updates, rollback, bundle), S-CORE-3 (users, roles, OIDC, audit, 2FA), S-CORE-4 (privacy, 12 flows, anonymous signal), S-MCP-1, initial setup (`/setup`), account (`/account`).
Provides: the `/settings/:section` frame (lists `settingsSections` by role and module), the sections general, modules, users, connections (`ConnectionsSection`, S-AI-7 and S-RESP-4), audit, updates, privacy, mcp, data. API: `/api/v1/core/*` (public: `setup`, `setup/modules`, `auth-options`; SSO: `/auth/oidc/start`, `/auth/oidc/callback` and the page `/sso/callback`). The first setup asks for a **one-time setup code** (a real box prints it into the log; the mock accepts `setup-code-demo`, `MOCK_SETUP_CODE` in `mocks.ts`); turning on two-step (app or email) asks for the **current password**, so the Account screen has one password field above the two choices.
Two-step sign-in: an authenticator app (QR drawn with `uqr`) or an email code sent to the sign-in email, only when the email channel of the notify module is configured and on; an admin can reset two-step for a user. Email code: 6 digits, 10 minutes, single use, 5 wrong attempts, resend after 60 s, 5 sends/hour.
**Preview build only:** because no real email is sent, the mock also returns `preview_code` in `twofa` of the sign-in's code step (200, `ok: false`) and in the responses of `/core/account/2fa/email/start` and `/auth/login/resend-code`; the UI shows a note "Preview build: the email would contain …" only when `VITE_API_MOCK !== 'off'`. The real backend never sends this field; it is not in the contract schema.
Consumes: `settingsSections` of other modules. Mock: real TOTP (RFC 6238), simulated SSO sign-in, simulated bundle signature.
