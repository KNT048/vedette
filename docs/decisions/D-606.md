| D-606 | **An osquery device never asks a person for a version the machine can tell: SQL Server's release row takes the instance's build from its setup registry (PatchLevel), else the build every component of the release agrees on; NVD's SQL Server release names are read by build major (N100 DESKTOP-55UKKFV 2026-11-17, J3; amends INV-20's reading of D-169 (1), "no registry table").** (1) **The case:** SQL Server setup writes one Uninstall entry for a whole release, "Microsoft SQL Server 2022 (64-bit)", without a DisplayVersion; osquery's `programs` (and Wazuh) give it as it is, pkgmap keys it to CISA's "Microsoft \| SQL Server", and findings asked the person under "Needs your input" (2 KEV CVEs) while the same install listed 13 components at 16.0.1000.6. (2) **Class (N100 copy 2026-11-17):** 14 of 2,139 agent rows have no version, all on DESKTOP-55UKKFV; only one is a release row with versioned components of the same install, and only it has a KEV key (SQL Server; the other 13 are single-entry programs: BatteryBar, BatteryMon, an HP LaserJet driver, App Compat Fix DB, Bandicam MPEG-1 Decoder, NIASpeedMeter, Tftpd64, update_server, Ezviz Studio, iTax Viewer, iReasoning MIB Browser, Liên Minh Huyền Thoại, Syncthing). Office Click-to-Run ("Microsoft 365 - en-us" 16.0.20527.20196), the Visual Studio installer rows and SSMS 21 carry their version; no Exchange. Repo fixtures: none. So the authoritative source is added for SQL Server only; Office C2R (`HKLM\SOFTWARE\Microsoft\Office\ClickToRun\Configuration\VersionToReport`) and Visual Studio (vswhere / `state.json`) are not read, since their rows already carry the version the machine states (D-169: read only what is needed). (3) **Source 1, the machine:** the Windows `programs` query becomes one compound SELECT whose first arm reads one registry value, `PatchLevel` under `HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Microsoft SQL Server\MSSQL%\Setup` (column `sql_setup` = the key), and whose second arm is the program list. One query, so the value comes in the same snapshot as the list: no node state, no migration, and "I updated it" and the first report ask for it with the list. The mapper gives the release row the lowest PatchLevel of its family (MSSQL16 → 16.0.x.y; several instances: the lowest is affected by everything a higher one is), confidence 0.95, and the release's other rows pkgmap maps to the same product (the RsFx Driver) keep their own name, because their version is a component's and would keep open what an update fixed. (4) **Source 2, the components** (Wazuh, an agent before this config): the build every component of the release names, only with "SQL Server <year> Database Engine Services" among them and the build in the release's family; components that disagree (an update that changed some, a service pack's 13.2.5026.0) leave the row without a version, as before; confidence 0.9. (5) **Cumulative updates:** a CU installs as a patch of the components' MSI packages; Microsoft documents PatchLevel as the current build and Version as the original one, and does not document that a CU changes the components' DisplayVersion (a 2022 CU16 host whose WMI/MSI data still read 16.0.1000.6 is reported by Broadcom). Source 2 can therefore only be the RTM build or the true build: the RTM build over-reports CVEs a CU or GDR fixed (the safe side), and Source 1 replaces it at the next report. A false "not affected" from Source 2 would need a CVE NVD lists only for a CU-branch range above a component build the components still show; no KEV SQL Server entry has one today, and osquery's Source 1 removes the case. (6) **findings:** an exact NVD configuration `microsoft:sql_server:<year>` ("2014:sp3") is compared by build major (2008 10, 2008 R2 10, 2012 11, 2014 12, 2016 13, 2017 14, 2019 15, 2022 16, 2025 17): another major is a certain No, the same major Unknown (the build does not name the service pack), a typed year that year; never Yes for a build. Without it, SQL Server 2022's row would have been a product finding ("cannot compare 16.0.1000.6 with 2014") for both of N100's CVEs (CVE-2019-1068, CVE-2020-0618, NVD lists 2012–2017 only).
