| D-598 | **One machine is one device: a phone or laptop with a private Wi-Fi address is joined by its host name, an osquery node by the node the box enrolled; never two machines with burned-in MACs by name (issue #829, J2; inventory INV-31, agent-intake INV-12).** (1) **The N100 case.** kien's MacBook (private Wi-Fi address `b2:f0:09:…`, locally administered bit set) became three devices (.145, .137, .138), each with a "new unknown device" incident: the inventory finds a device by MAC then IP, and macOS, iOS, Android and Windows pick a new random MAC per network or per day, after which DHCP gives a new address. (2) **The name rule** (`sameMachine`, run with the D-515 join on every device a sensor batch, a software list or a service list touched): two rows are one machine when **both** carry a locally administered (private) MAC and neither a universally administered (burned-in) one, so a row known only by address, a declared row without a MAC and a server are never taken over (review #831 H1); both carry the same host name (first label, any case; not generic or system-made: regexes for `iphone`, `macbook-pro` with or without a Bonjour number (`MacBook-Pro-2`), `localhost`, `raspberrypi`, the D-515 defaults…, and the prefixes `galaxy-`, `pixel-`, `desktop-`, `laptop-`, `win-`, `android-`…; not shorter than 3, not a UUID, not built from an address); they state no other model or OS; exactly one other row qualifies; and **they were not online at once**: when both hold different addresses, the row last seen earlier must have gone silent before the other first appeared and for 5 minutes (a rotation never shows the old and new address together; two "Johns-iPhone", cloned VMs do; review #831 M2). Kept row: declared, else approved, else older; it takes the newer address unless a person declared it; the newest MAC wins by the usual observation rules; the approval never moves (review H1 of #722). A row created in the same batch is never announced; an older one is announced merged and deleted, so notify closes its incident (D-554) and findings moves its findings (D-515). (3) **Agent identity**: agent-intake hints a report with `osquery:<node id>` (the id the box gave the node, not a value the machine chose). Order for a report: node → address (the TCP source, checked against the node's interfaces, INV-12) → new row; never the MAC or host name the agent claims, which are self-declared (D-265 (4)). The node is bound to the device its report reached by address only when that device has no node bound (a binding is never overwritten: a reused DHCP lease must not steal another node's device; agent-intake releases the binding of a node it deletes on re-enrolment, revoke and prune, `observe.AgentReleaser`) and every MAC any source saw on it is one this node reports in the same batch (review #831 M4). Its later reports find that device and move it to the new address, except a spoof: when the bound device's MAC is burned in and the node's batch does not report it, the binding is dropped, logged, and the report goes by address (review #831 M3; agent-intake records the card's MAC before every package list, so a list cannot skip the check). A row an agent made before it was bound, which then lost its address to the device that owns the MAC the agent named, and that device are one (`agentOrphan`: three sources agree); the kept row follows the same order, so an enrolment's approval stays (review #831 L5). Sensors keep MAC → IP (the MAC comes from the wire). SNMP answers attach by the address of the approved device the round targeted (no new rule needed); sysName feeds the name rule; engineID is not read today. Portnox documents the symptom one-to-one ("multiple records for the same physical device") and the test we use: second hex digit 2, 6, A or E is a randomized address (https://doc.portnox.com/topics/kb_mac_address_randomization).
