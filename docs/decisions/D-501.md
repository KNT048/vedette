| D-501 | **A scan identifies the devices, or says per device exactly why it could not (P0-A; customer walks 1–2 W1-6, W1-7, W2-4; beta feedback item 27: every scan of devices known only by IP/MAC ended "Matches 0"). Revised after the Opus review of PR #660 (H1–H3, M1–M4, L1–L5).** (1) **Scan now identifies first** (scan `Config.Identify` → sensor-active `IdentifyDevice`): for each device a person picked, the Active discovery nmap device scan runs at once, records what it finds in the inventory (source `nmap`), the findings module matches it (the bus is synchronous), and only then does the run read the device's findings and send templates. Schedules and KEV rescans do not identify (discovery does, in its window). **Changes D-84 (1) for a person's pick only**: the window does not apply (Scan now already ran "without waiting for the time window"); a device of **unknown kind** gets a fourth nmap shape, **`versions`** (`-sS -sV`, no `-O`, top 1000 ports, `--host-timeout 30m`) at a quarter of the rate instead of the gentle scan: the pick is the consent (D-126 (2) already lets that pick send nuclei templates, heavier than `-sV`), only `-sV` can tell what runs on it, and OS detection (malformed TCP/IP probes) is the riskiest probe for an OT stack, so it stays out; a **fragile** device still gets only the gentle scan (D-45); `regular_scan=never` is refused even before its gentle scan (D-126 (1)); hand-declared devices, the box and its decoy addresses (`ProtectedIPs`), scanning off, unconfirmed scope, out of scope and no IP are refused and said. One nmap at a time: an identification waits up to 2 minutes for discovery, then says `busy`, and the rest of that run says `busy` at once. A stop by sensor-active itself (the device, the discovery settings or the module changed; turning the module off stops it) skips that device and the run goes on; only the run's own Stop now stops the run. (2) **Per-device result** `ScanRun.identification[]` (`found[]` in words; `reason` null when software **with a version** was recorded, else `host_down`, `no_open_ports`, `filtered`, `no_version`, `os_unconfirmed`, `os_low_confidence`, `gentle_only`, `timed_out`, `busy`, `unavailable`, `declared_by_hand`, `scanning_off`, `not_approved`, `out_of_scope`, `scope_not_confirmed`, `box`, `regular_scan_never`, `no_ip`, `not_scanned`; `note` the box's sentence with what to do), shown in the run's "View results" dialog. (3) **An OS nmap guessed raises no finding** (review H1, the false-CVE flood kien named): the OS of a fingerprint is recorded (OS field, kind, and one software row for display) only at accuracy ≥ 85, and that row is a **guess**: no version (the version in an osclass CPE is the OS generation, `iphone_os:15`, `linux_kernel:5`, `fortios:7.2`, not a release; the CPE is stored without it) and **no KEV match keys**, so it matches nothing until a person adds the OS with its version on the device page (the same step as "I have this" of D-484: a person states what runs). Before, a Windows PC got the key `microsoft|windows` (175 CISA entries) and a Linux box with SSH `linux|kernel` (32). A service's `o:` CPE stands in for the OS only when `-sV` read a version from that service. nmap device types phone, VoIP phone/adapter, PDA, media device, power-device → `iot` (no phone kind yet; the catalog files iOS/Android as iot; the two-level type list is a later group), broadband router → router, print server → printer; "general purpose" gives a kind only for Windows (pc; server when its name says so) and iOS/Android (iot): Linux, the BSDs, Unix and macOS give none, so a guess never lifts a device out of "unknown, careful" (review H2). A gentle scan never replaces the software list. Curated catalog rows name the CPEs nmap prints (`cpe` field: iOS/iPadOS, macOS, Windows, Windows Server, Linux kernel, Android, FortiOS), so a confirmed or agent row with such a CPE gets the same KEV keys as the product added by hand. (4) **Passive hints already collected**: DHCP option 60 of a known client → OS hint 0.4 (MSFT, android-dhcp-N, dhcpcd, udhcp; never a vendor or version: it names the DHCP client); LLDP Telephone bit → `iot` 0.6, read before Bridge.
