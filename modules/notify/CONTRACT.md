- **INV-4**: Each channel receives only messages with severity ≥ the channel's `min_severity` (`critical|high|medium|low`). **The severity of a finding's notice is its alert severity** (`AlertSeverity(cvss, layer)`): the CVSS band raised to the floor of the urgency layer: layers 1–2 (attackers use the flaw) are `critical`, layers 3–4 at least `high`, a higher band is kept, an unknown band takes the floor (the first-run summary takes the floor of its worst layer). So "Medium and above" and "High and above" receive every finding that enters layers 1–4, "Critical only" the exploited ones and the critical scores, and an exploited finding is never held for the grouping window (INV-6: critical is never grouped). Before, a KEV-listed flaw with a CVSS of 2.7 was dropped silently by "Medium and above", and an exploited one of CVSS medium waited an hour (`TestAlertSeverityIsTheCVSSBandRaisedToTheLayerFloor`, `TestEveryFindingEnteringLayersOneToFourIsToldOnceAndAtOnce`).
- **INV-5**: Quiet hours: `from≠to` when enabled, may cross midnight; `allow_critical=true` lets `critical` messages through. Other messages are held until the end of the quiet hours and then sent grouped. Hours follow the box's time zone (`core_org.timezone`, default `Asia/Ho_Chi_Minh`), never the process's time zone. `TestContract_INV5_QuietHoursHoldThenReleaseGrouped`
- **INV-6**: From the moment a finding matches to the moment a message is sent: ≤ 60 minutes applies to `critical` messages (S-ALERT-1; `critical` is never grouped). `high` and below follow the configured grouping window (15/60/240 minutes). Every send attempt records `SendRecord {channel, to, at, ok, error?}` (the error is a friendly sentence, never the raw text of the server/provider; SMTP is never called "HTTP"); there is no send without a record (exception INV-17: a message rate limited several times has only one "Delayed" line, then the result line), even when the run is cancelled midway (the record is written under a non-cancelled context, 10 s limit). **Semantics on interruption**: alert messages are *at least once*: a row that was claimed but not yet attempted goes back to `pending` and is sent in the next pass; a row that had started sending (`sending`) with no record yet is **not** sent again, it is recorded as "may or may not have been sent" so the user can press Resend. A message with an approval link is *at most once*. Each channel has its own goroutine (a slow channel does not hold up another); within a channel `critical` goes first and at most 20 messages per pass, the rest wait for the next pass.

## Forbidden
- **FORBID-1**: Sending a vulnerability message that does not match a device.
- **FORBID-2**: Returning or logging a channel secret; putting a secret into a log export.
- **FORBID-3**: Approving an action by reply mail, or by GET.
- **FORBID-4**: Opening an inbound port for a chat channel.
- **FORBID-5**: Executing an approved action itself (that belongs to `response`).
- **FORBID-6**: Sending data outside the channels the customer configured (PRIVACY flow 5). The Microsoft/Google token services (INV-15, INV-16) receive only token requests, never message content.

## `alerts` log source (core INV-13)
`Service.ExportAlerts(ctx, from, to, w)` is the `alerts` source of `GET /core/logs/export` (`cmd/vedette/logexport.go`): `notify_send` from `from` to `to` (both ends inclusive, time 0 = open), oldest first, one JSON per line `{id, kind, ref_id, channel, to, at, ok, error, what, link}`; it is not a hash chain. It does not export `message` (the whole message kept for resending) or the `recipient` column; `to` keeps exactly the value the History screen shows (for a message sent privately to an approver that is their address, for example an email), adding nothing. `link` is cut down to the path (no scheme, host, query, fragment; after `/approve/` it becomes `…`), and when `to` is a URL it is cut down to `scheme://host`: there is never a token in the file even though the stored copy keeps no token. A module that is off still exports (the data is kept). `TestExportAlertsIsTheDeliveryLogByDateRangeWithoutTokens`, `TestLogExportAlertsComesFromNotifyAndCarriesNoToken`.

## Behaviour when off
No routes, no jobs; no message goes out. The Incidents page disappears; the "who was told" panel on the finding page disappears; `core` reports email 2FA `module_off`; `response` has no approval channel (it depends on `notify`). Channel configuration and history are kept. **Exception**: the `retention` job (`Housekeeping: true`, hourly) runs even when the module is off and deletes only history older than 1 year (DATA_MODEL 4.4): `notify_send` with `at` older than 1 year, `notify_incident` that is `resolved` with `handled_at` (or `last_seen` if missing) older than 1 year (its devices go with it), `notify_notice` created more than 1 year ago unless a queue row still refers to it or a send newer than the cut-off still covers it (a `resolved` incident is also kept when a send newer than the cut-off points to it, for example a resend). This limit is published on the Incidents page and the History screen: "History and resolved incidents are kept for 1 year." It never deletes a `new`/`acknowledged` incident, or `notify_pending`. Each pass that deletes something writes one audit entry `notify.retention` with the counts; if nothing is deleted nothing is written. No route, gate or outbound connection. `TestRetentionDeletesOnlyHistoryOlderThanAYear`, `TestRetentionIsAHousekeepingJob`. `Publish`, `OpenIncident` and `SendApprovalRequest` called while off return `ErrModuleOff` and queue nothing (PRE-6); events received while off are dropped. **Turning back on**: the first `Flush` run after the module is turned back on deletes the `notify_pending` rows in state `pending` whose `created_at` is older than 24 hours (measured from when they were queued, not from when it was turned off) and writes one audit entry `notify.stale_dropped` with the count; if there are no old rows nothing is written. The module knows it was turned on through `modreg.Registry.OnChange` (asserted from `Config.Modules`, no change to `core`); restarting the process does not count as turning back on. `TestEnableDropsQueuedNoticesOlderThan24h`, `TestEnableKeepsRowsAt23hAndAuditsNothingWhenNothingIsOld`, `TestNoDropWithoutEnable`.

## Mismatches / open questions
- ~~Quiet hours: is a non-`critical` message held until the end of the hours or dropped?~~ Settled: held, and when the hours end one message grouped by product is sent; `critical` goes at once when `allow_critical`, otherwise it is held too.
- ~~The match key for merging incidents~~: `kind + source + target`, SHA-256 hash, merged only into an incident that is **not `resolved`**; a repeat after it was `resolved` is a new incident. Only a new incident is sent; a repeat only raises `count`/`last_seen` (not sent again, no audit written).
- Interruption semantics: see INV-6. A `claimed` row older than 15 minutes (the box stopped before attempting to send) goes back to `pending`; a `sending` row older than 15 minutes is recorded as "may or may not have been sent" and not sent again.
- Reopening a `resolved` incident when a newer incident with the same key is already open: 409 `already_open` (an existing code, §3.3) with the open incident's `open_id` in the error body (`TestContract_INV10_ReopenWhileANewerOneIsOpen`).
- `notify.approval.decided {request_id, decision, approver, channel}` is emitted from the Telegram button, the Slack button and the personal Zalo reply code (`request_id` comes from `DecisionResult.RequestID`): `decision` is `response`'s `Status` (`approved|pending|rejected`), `approver` is the ID of the person who pressed/sent on the platform.
