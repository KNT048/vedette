| D-453 | **vedette-host never reboots while a logind block inhibitor of shutdown is held (apt installing): it reads logind's lock list itself before every reboot and refuses, waits or reports instead.** Measured on Debian 13.7 and Ubuntu 26.04.1: while apt installs, APT holds a logind lock ("APT is installing or removing packages", what `shutdown` / `shutdown:sleep`, mode `block`, uid 0), and `systemctl reboot` from a system service fails with "Operation denied due to active block inhibitor"; before this the host only logged it while `os.reboot now` had already answered `succeeded`, and a scheduled reboot was dropped, so the box silently did not reboot. **logind enforces this for root only from systemd 257** (Debian 13, Ubuntu 26.04). On systemd 255 (Ubuntu 24.04, a supported platform) `logind_check_inhibitors` returns at once for euid 0 and `verify_shutdown_creds` ignores locks of the caller's own uid, and APT's lock is uid 0 like the host, so logind lets the reboot through and it cuts dpkg: there the host's own read is the only guard (review M1, round 1). (1) **Reading the locks**: `busctl --system --json=short call org.freedesktop.login1 /org/freedesktop/login1 org.freedesktop.login1.Manager ListInhibitors`, one new exact argv in the exec allowlist (`/usr/bin/busctl`, systemd package, already a Depends); `--json` exists since systemd 240 (Ubuntu 24.04 has 255, Debian 13 257, Ubuntu 26.04 259). A lock blocks a reboot when its mode is exactly `block` and `shutdown` is one of its `what` words; `delay` (unattended-upgrades' shutdown hook) never refuses, and `block-weak` (systemd 257) is ignored by logind for root. The parser is fail-closed: exactly `{"type":"a(ssssuu)","data":[[[what,who,why,mode,uid,pid],...]]}`, no unknown field, no trailing data, at most 8192 locks and 1 MiB, otherwise the list is **unknown**, never partial. `who`/`why` come from any local program: printable ASCII only without quotes, angle brackets, ampersand, backquote or backslash (others become `?`), spaces collapsed, at most 64/120 bytes, no trailing space. One read takes at most 3 s inside `os.reboot`'s Check (the server bounds a Check at 5 s) and 10 s elsewhere. (2) **Unknown means allow, logged once** (WARN on the first unknown after a good read): on systemd 257+ logind still refuses a locked reboot; **on 255 an unknown list means the host reboots without protection from apt**, as every release before this one did. Refusing on unknown would leave the box unable to reboot whenever busctl or its output breaks; the lab confirms the output shape on all three releases. (3) **`os.reboot now`**: `Check` refuses with a new `409 reboot_inhibited` whose message names who and why. (4) **Before every `systemctl reboot`** (a "now" reboot, a scheduled one, every retry) the host reads the list again; a lock there means no call, and the wait below. (5) **Scheduled reboot**: when its time comes, the list is read first, outside the reboot mutex and before the write gate goes up; a lock postpones it like a running command (`rebootRetryBusy`, 1 minute), the schedule stays (`reboot_scheduled_at`), `reboot_waiting_inhibitor` is audited once per schedule, and the existing 24-hour expiry bounds the wait. (6) **The wait of a started reboot** (a lock seen just before the call, or `systemctl reboot` refused by logind with a lock in the list read again; systemctl's localized stderr is never parsed): tries again every 30 s for up to 30 minutes from the start, raising the `rebooting` write gate again at every try so nothing new starts (`os.reboot.cancel` included), audits the wait once, then gives up with `reboot_failed` `{reason: inhibited, who, why}`, clears `Pending` and lowers the gate; any other failure is `reboot_failed` `{reason: systemctl_failed}` at once, as before. (7) **Host restart during the wait**: `reboot.json`'s pending reboot carries `issued` (set once `systemctl reboot` is accepted). A host start on the same boot keeps the gate only for an issued reboot younger than 10 minutes (the box is shutting down); any other same-boot pending reboot is audited `reboot_failed` `{reason: host_restarted, issued}` and cleared, never re-armed, so no later boot reports a misleading `reboot_completed`. (8) **Never** `--check-inhibitors=no`, `--force` or `-i`; and **not** `--check-inhibitors=yes` either: on 255 it also refuses while another user has a session open, which an admin's SSH login always is. (9) **Core and GUI**: no change in this PR; they learn only from the host's audit and log today. Spec text (host-api §6.4) and a deferred line describe the follow-up: core maps `reboot_inhibited` to a 409 with the host's cleaned text, and `GET /v1/state/os` gains `reboot_wait` and `reboot_failed` for the Updates page. | Why: rebooting while dpkg configures can leave packages half-configured; the lead's lab showed `systemctl reboot --force` cutting dpkg mid-configure, which the self-update applier survived but other apt runs may not, and Ubuntu runs unattended-upgrades by default, so a night reboot can meet apt. Nobody in the reference set forces past the lock: systemd says a block lock "inhibits operations entirely until the lock is released" and only a privileged user may override it (https://systemd.io/INHIBITOR_LOCKS/); APT takes the lock precisely so that halts and reboots wait for package operations (Ubuntu bug 1820886, https://bugs.launchpad.net/ubuntu/+source/apt/+bug/1820886); unattended-upgrades' `Automatic-Reboot` runs `/sbin/shutdown -r <time>` after its own run with no flag to ignore inhibitors and only logs when it fails (https://github.com/mvo5/unattended-upgrades/blob/master/unattended-upgrade, `schedule_shutdown`). The root exemption of systemd 255 is the reviewer's reading of `logind_check_inhibitors` and `verify_shutdown_creds` in systemd v255 (review M1); the lead checks it on an Ubuntu 24.04 VM. The lead's brief also names Synology DSM and pfSense/OPNsense refusing a reboot while their own update runs and needrestart, which restarts services and leaves reboots to the admin; not re-verified here, and none of them is cited as forcing. Not chosen: `systemd-inhibit --list` (no JSON even in systemd 259, free-text columns that cannot be split reliably); speaking D-Bus in Go (a new dependency for one read-only call); parsing systemctl's stderr (localized and not a contract); `systemctl --check-inhibitors=yes` (above); refusing on an unknown list (above); retrying a "now" reboot forever (the gate would block core's writes indefinitely); re-arming a waiting reboot after a host restart (the caller who asked for it may be gone; reporting is safer than rebooting later on a stale request). Limits: on 255 a lock taken between the host's last read and logind's handling of the call (milliseconds) is not seen; on 255 an unknown list gives no protection; a lock held for more than 30 minutes after a "now" reboot ends in `reboot_failed`, and the operator reboots again; a scheduled reboot that waits longer than 24 hours expires (`reboot_schedule_expired`); `who`/`why` text that is not ASCII shows as `?`; the result depends on apt taking the lock (APT has done so since at least 1.6.11, per the bug above). | 2026-11-12 |
