# Auth-OIDC Contract

> Tier: optional (off by default) · Story: S-CORE-3 · Last verified: 2026-11-21 (every sentence checked against the code)
> The GUI lives under `core` (`web/src/features/core/{contract,ssoFlow,mocks}.ts` and `web/src/features/core/{UsersSection,SsoCallbackPage}.tsx`, section Settings → Users, the page `/sso/callback`). The backend is a module of its own.
> The mock skips the IdP: the mock's `authorize_url` is the `/sso/callback` page itself with a code, and the user at the IdP is `MOCK_IDP_USER`.

## Invariants (always true)
- **INV-1** The sign-in flow is **authorization code + PKCE S256**, always with a 256-bit `state` and `nonce`. ID token checks: the signature against the issuer's JWKS with an **asymmetric algorithm** RS256/384/512, PS256/384/512, ES256/384/512 (intersected with `id_token_signing_alg_values_supported`; `none` and HS* are always refused), `iss` = the stored issuer, `aud` contains `client_id`, `azp` if present = `client_id`, with several `aud` an `azp` must be present, `exp` not passed (1 minute of clock skew), `nonce` = the flow's nonce. Keys are taken only from the discovery `jwks_uri` (the header's `jku`/`x5u`/`jwk`/`x5c` are ignored), `kty` fits `alg`. The ID token comes only from the response of the token endpoint over TLS, never from the browser, so an unknown `kid` is not controlled by an outsider (go-oidc reloads the stored provider's key set only when it meets an unknown `kid`). `SSOIdentity.Issuer` is the configured issuer (already matched with `iss`). The `discovery_failed` message is a fixed sentence by error kind and does not copy what the other side returned. Discovery is kept in memory for 1 hour; Test and saving the configuration refresh it. `TestContract_INV1_*`. Any mistake → 400 `sso_failed`, no session is created, `auth.login_failed` with detail `SSO: id_token`. Discovery cannot be read at `start` or `callback` → 502 `idp_unreachable` (at `callback` it records `SSO: token`); the token endpoint refuses the code → 400 `sso_failed`, `SSO: token`.
- **INV-2** `issuer` must be **https** (the trailing `/` is dropped); `client_id` 1..200 characters; `client_secret` 8..1024 characters; `scopes` 1..10 words per RFC 6749 §3.3, must include `openid`; `groups_claim` matches `^[A-Za-z0-9_.:/-]{1,64}$`; `default_role` ∈ {viewer, operator, admin, null}; `role_map` ≤ 10 rows `{group ≤ 256 characters, a valid role}`, a row with an empty group is dropped. A mistake → 400 (`invalid_issuer`, `invalid_client`, `invalid_secret`, `invalid_scopes`, `invalid_claim`, `invalid_role`, `too_many`).
- **INV-3** `client_secret` is stored through `core/secrets` (AES-GCM), the API returns only `secret_last4`; empty on edit = keep the old secret (SYS-4) **only when the issuer, client_id and CA (INV-12) are unchanged** (removing the CA still keeps it: it only narrows trust); changing one of the three without re-entering the secret → 400 `invalid_secret` (otherwise the real secret would go to the token endpoint of the new issuer). The token endpoint receives the secret in exactly one way: `client_secret_basic` (default) or `client_secret_post` when discovery declares only that; any other way → `discovery_failed`. The secret and every IdP token (code, access, ID, refresh) never enter logs, exports, backups or audit. A secret sealed with another master key (a restore without the decryption key, #812) → `start` and `callback` return 409 `sso_secret_lost` (not forwarded to the IdP, no 500, `auth.login_failed` with detail `SSO: client_secret` at callback) until an administrator re-enters the secret.
- **INV-4** The SSO button shows only when the module is on **and** an `issuer` exists (`GET /core/auth-options` → `{oidc: true}`); this public endpoint reveals nothing else.
- **INV-5** **Browser binding, no new cookie**: `POST /auth/oidc/start` stores an `oidc_flow` (the SHA-256 of `state` and `binding`, the nonce, the PKCE verifier, `redirect_uri`, a 10 minute expiry) and returns `{authorize_url, binding}`; `POST /auth/oidc/callback` needs the exact `binding`; the flow is deleted at the first callback whether right or wrong; an unknown, used, expired or wrong-binding flow → 400 `sso_expired`. At most 1000 unfinished flows (the oldest is dropped, a safety net); `start` and `callback` each per address (IPv6 per /64) 30 times / 15 minutes → 429 `rate_limited`; `start` also per IPv6 /48 100 times / 15 minutes, and for the whole box 300 times / 10 minutes (below 1000, so a flood of `start` from many addresses never pushes out a flow that is waiting; the refusal says "Too many SSO sign-ins are starting on this box…, or sign in with your email and password", with a log warning at most once a minute; a start is counted only when all three limits let it through, the /48 key and the budget are not dropped when the key table is full: `TestOneSlash48CannotResetItsCountByFloodingKeys`). `TestContract_INV5_FloodCannotPushOutASignInInProgress`. An unknown `state` returns `sso_expired` **without** an audit line (so the log cannot be filled); for a real flow every refusal is recorded.
- **INV-6** `redirect_uri` is **pinned at `PUT /core/oidc`**: the origin of the saving request (the process's scheme + `Host`) + `/sso/callback`; `GET /core/oidc` returns the pinned value (never saved: the value that will be pinned from this request). A `start` from another origin → 409 `sso_wrong_address` (`address` = the right origin); a `redirect_uri` is never built from the `Host` of a request that is not signed in. A flow keeps `issuer`, `client_id`, `redirect_uri` from its start; at `callback` if one of the three differs from the current configuration → 400 `sso_expired`.
- **INV-7** **The identity is (`iss`, `sub`)**. The role = the highest role among the `role_map` rows whose group is in the `groups_claim` claim of the ID token (a top-level key of exactly that name, not a path; a string or an array of strings; only the first 200 groups are considered, a group longer than 256 characters is dropped, not truncated); no row matches → `default_role`; `null` → 403 `no_access`, no account is created. The role is written back at **every** SSO sign-in (`user.role`, detail `<old role> to <new role> (SSO groups)`) and when the role changes that person's old sessions end; `no_access` for an existing account ends all its sessions.
- **INV-8** First time: creates an `sso` account (no usable password, `user.create` with detail `SSO`). An email (the `email` claim, compared in lower case; missing or `email_verified=false` → 403 `email_unverified`; with the `email_verified` claim absent a new account can still be created but cannot be re-linked) that matches a password account, or an SSO account of the same issuer with a different `sub` → 409 `email_in_use`, not linked; matching an SSO account of another issuer → re-linked to the new (`iss`, `sub`) **only when `email_verified=true`** (`user.sso_relink`), otherwise 409 `email_in_use`. Email and name do not follow the IdP after creation. A disabled account → 403 `disabled` even if the IdP lets it through.
- **INV-9** A successful SSO sign-in creates a session **like a password sign-in** (`__Host-vedette_session` + `__Host-vedette_csrf`); it **does not** set or read `__Secure-vedette_device`; it does not go through the box's two steps (the IdP handles MFA).
- **INV-10** Every successful/failed SSO sign-in, and saving and testing the configuration, writes `core_audit` (SYS-3): `auth.login` `SSO`, `auth.login_failed` `SSO: <state|binding|token|client_secret|id_token|no_access|email_in_use|email_unverified|disabled>`, `oidc.update`, `oidc.test` (detail `ok` or `failed`), `user.create` `SSO, role <role>`, `user.role` `<old role> to <new role> (SSO groups)`, `user.sso_relink`. The display labels are in `audit.action` of `web/src/locales/en/core.json`.
- **INV-11** Data from the IdP (discovery, JWKS, the token response, claims) is untrusted (SYS-6): ≤ 1 MiB, 10 s, type checks, fail closed; the `issuer` in discovery must equal the stored issuer; the authorization/token/jwks endpoints must be https; redirects are not followed (SYS-7).
- **INV-12** **The IdP's CA**: `ca_pem` is optional; when present, every call to the IdP (discovery, JWKS, the token endpoint) goes through a client of its own with `RootCAs` = the system roots + those CAs, under the same limits as INV-11; the box's other calls do not trust this CA; never `InsecureSkipVerify`. Checked at the edge when saving: only `CERTIFICATE` PEM blocks without headers, 1..5 of them, total ≤ 64 KB, each `basicConstraints CA:TRUE` and not expired (the expiry date in the message uses the organisation's time zone, `core/orgtime`), no text outside the blocks; a mistake → 400 `invalid_ca`, nothing is stored. The normalised PEM is stored (it is not a secret); GET returns `ca_pem` and `ca_certs [{subject, expires_at}]`. A PUT without `ca_pem` = keep; `""` = remove. Changing the CA drops the discovery cache (the cache is also tied to the CA). Adding or changing a CA needs the secret to be re-entered (INV-3), removing a CA does not. `oidc.update` records the detail `ca added|removed|changed: sha256:<fingerprint>…` when the CA changes. Text before a block, a broken block (pem.Decode skips ahead to the next BEGIN) and a normalised copy longer than 64 KB → `invalid_ca`. `TestContract_INV12_PrivateCA` (an httptest IdP that the system roots do not trust: it fails without a CA, Test and sign-in pass with one, it is kept when the field is left out, and fails again when removed), `TestContract_INV12_CARefused`, `TestContract_INV12_CAChangeNeedsTheSecret`.

## Preconditions (before the call)
- **PRE-1** `PUT /core/oidc`, `POST /core/oidc/test`, `GET /core/oidc`: admin role, module on.
- **PRE-2** `POST /core/oidc/test`: the configuration is saved (400 `not_configured`).
- **PRE-3** `POST /auth/oidc/start` and `callback`: module off → no route (404, SYS-5); on but no `issuer` yet → 400 `oidc_off`.

## Postconditions (sau khi xong)
- **POST-1** A successful `test` returns `{ok:true, endpoints:{authorization, token, jwks}}` read from `/.well-known/openid-configuration`; if it cannot be read → 502 `discovery_failed` naming the network path from the box to the IdP.
- **POST-2** A successful sign-in: a session like POST-1 of the password sign-in, `last_login` is updated, audit per INV-10; the SPA goes to the `next` kept in sessionStorage (only a path inside the app).
- **POST-3** Saving the configuration: the next sign-in uses the new configuration; existing sessions are not cut; a waiting flow of the old issuer/client returns `sso_expired` (INV-6).

## Forbidden (never)
- **FORBID-1** The implicit flow, hybrid, the password grant; dropping PKCE; PKCE `plain`.
- **FORBID-2** Returning `client_secret` or an IdP token through the API/log/export.
- **FORBID-3** Granting a higher role than the result of `role_map`/`default_role`; linking to a password account by email.
- **FORBID-4** Calling the IdP when the module is off or there is no `issuer`.
- **FORBID-5** Accepting an `issuer` or a discovery endpoint that is not https; accepting a symmetric `alg` or `none`.
- **FORBID-6** Adding cookies (legal rule); setting a password for an SSO account (reset, change password, turning on two-step → 409 `sso_user`); changing the role of an SSO account in Users (409 `sso_user`).

The SPA page `/sso/callback` is the `redirect_uri`: the IdP sends the browser back there, and the page sends `POST /auth/oidc/callback`.

## Tables owned
`oidc_config` (issuer, client_id, a secret encrypted through `core/secrets` purpose `oidc_config.client_secret`, scopes, groups_claim, default_role, role_map, redirect_uri, `ca_pem`), `oidc_flow` (waiting flows, INV-5). The SSO identity (`sso_issuer`, `sso_subject`), users and sessions belong to `core` (`core_user`, `core_session`), only through `core/auth.SSOSignIn`, `RefuseSSO`, `CountSSOUsers`.

## Events
- **Emits**: none (audit through `core`). **Receives**: none.

## When the module is off (SYS-5)
No SSO routes (`/auth/oidc/*`, `/core/oidc*`), the SSO button disappears (`auth-options.oidc=false`), the IdP is not called. The configuration is kept as is. SSO accounts still exist but cannot sign in until it is turned on again (they have no password); the GUI says the number of these accounts (`sso_users`) in the turn-off dialog. Existing sessions are kept until they expire.

## Dependencies
- **DEPENDS ON**: `core` (users, sessions, roles, audit, `core/secrets`, per-address limits).
- **DEPENDED ON BY**: `core` (the sign-in page asks `auth-options`; the last-administrator rule counts only administrators who use a password).
