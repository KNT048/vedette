# Response — Change Impact Map

> Package `modules/response`; the names below are the names in the code: `Evaluate`/`fire` (engine.go), `Approve`/`approve`/`runItem` (requests.go; `runItem` is the only place that sends a step to a device; `claimItem`/`failStuck` record the "running" state), `Fill`/`CheckValue`/`ValidateTpl` (params.go), `appendLog`/`VerifyLog` (service.go, plans.go), `FetchBlocklist`/`renderBlocklist` (blocklist.go), `Propose` (propose.go). A **high-risk** module: every change to the blocking gates (INV-1…16) needs contract tests and must be stated clearly in the commit.

## Modifying: `Evaluate(ctx)` / `fire` (matching rules, building requests) — the event sources
- **logs** (`log_threshold`): `PollLogs` (logthreshold.go) through `Config.LogCounts` (`cmd/vedette` `responseLogCounts`: `SourceNames`, `Counts`, `TopAddresses`); changing the return type or the cap of 50 of `TopAddresses` (`logs.MaxTopAddresses`) changes `LogAddress`/`logTopAddrs`; changing the signatures of `logs` (profiles, the pattern finder) makes stored rules no longer match (logs IMPACT "The signature is the key"); changing `logs.CountsMinWindow` (5 minutes) changes `logMinWindow` and the refusal sentence. `evalCondition` has a separate branch for `count_window` of `log_threshold` (comparing the event's `window`/`threshold`); `planAction` refuses "Not available" (`tool_unavailable`) when a `log_threshold` event has no `source_ip` (no single address reached N) while the parameter `ip` uses it; the templates `tpl-vpn-ban` (`fgt_ban_ip`) and `tpl-ssh-acl` (`cisco_acl_deny`) block by `{{trigger.source_ip}}`; other triggers keep INV-10 (an empty address = `invalid_target`).
- **honeypot** (`honeypot.hit.created` → `honeypotEvent`, events.go; changing a payload field in `modules/honeypot` `HitEventData` changes the trigger; dropping the field `unconfirmed` makes pre-approved rules run on the source of a UDP packet that can be spoofed), **logs** (`logs.ioc_hit.detected` → `iocEvent`: changing a payload field of `IocHit` in `modules/logs` changes the trigger `ioc_connection`; `logsIocEvidence` for `Evidence.IocHit`; `src_ip` is checked with `signature.LocalOK` of logs, so the LAN device rule of the two modules always agrees), **findings** (`findings.finding.created|status_changed`), **inventory** (an unapproved device), **exposure** (`exposure.port.opened` → `portEvent`: `cmd/vedette` `exposurePortsOpened`/`openedPorts` reads exposure's `Snapshots`, `Diff`, `SnapshotOf` and compares the label `"<ip>:<port>"` of the `port` entry in `Diff.Added` with the `PortRow` row of the same day; changing the format of that label, the date key of the snapshot or `SnapshotCreatedEvent` in exposure changes the trigger `new_port`, `TestExposureSnapshotOpensNewPorts` catches it; `heldForAuto` holds the pre-approval of an action on that address, `TestNewPortPreApprovalNeverActsOnTheAddress`), **logs/signature** (`PublicDest` for the destination of `iocEvent`: loosening logs' list of special networks loosens the trigger too), **schedule** (`schedule_min` of the rule, read in `Evaluate`): renaming/changing the type of a trigger field → the conditions and parameters `{{trigger.field}}` of existing rules no longer match, and the rule goes quiet. The field catalogue (`/response/triggers`) is a contract with the GUI.

## Modifying: `Approve` / `approve(ctx, who, id, pick, code, auto, linkOpt)` — 4 callers
- **HTTP** `/response/actions/{id}/approve` (app; a high-risk AI request needs `TwoStep`); **chat channels** (Slack Socket Mode, Telegram long polling, personal Zalo) through the gate `notify.Config.Decisions` → `DecideFromChat`; **email link** `/response/approve/{token}` → `DecideByLink` (email only; Zalo OA does not exist yet); **the rule engine** (`via=auto`, INV-5 only). Every path shares one approval function; the channel × risk policy (INV-3) is checked there, not in `notify`. Changing the order of the gates (INV-9) or the two-person condition → changes who can cause a change on a device; the tests `TestContract_INV2_*`, `INV16_*` are required.

## Modifying: `RequestProposal` and the shape of `resp_plans.steps[].proposal` (the AI plan job)
- A proposal only contains `action_id` + typed `params` (+ `ttl_min`, `asset_id`, `asset_name`); every command/path/body is built by `planAction` from the catalogue at view time and at request time. The plan job must write exactly this form; a proposal carrying a command/path/body is refused `tool_not_allowed`.

## Modifying: `Planner`, `Critical`, `savePlan`
- `Config.Planner` (cmd/vedette `responsePlanner` over `ai.Service.RunJob`, the `response-plan` job) and `Config.Critical` (findings + inventory + feeds): nil = no new plans, `ai_available=false`. `aboutTheDevice` only accepts the device's IP, checked in both `checkDraft` and `RequestProposal`; loosening it (names, CIDR, interface...) needs evidence that binds the value to the device. Editing `checkDraft` is editing the gate of every AI plan: everything stored must go through `planProposal`; adding a field to `storedProposal` must update `TestPlanStoresActionIDAndCheckedValuesOnly`. The `plan` job is added to `Jobs()` (3 jobs).
- A device a person ignored is out of response: cmd/vedette `responseCritical` (through `findings.Views`, and its device read) lists no plan target for it, and `responseDirectory.Finding` answers not found for its findings, so no `finding` rule fires, no stored plan is listed or approved, and it is no evidence. The urgency pass emits no rise for it either. `TestWiringAnIgnoredDeviceIsSilentUntilItIsWatchedAgain`.
- **The plan job has no per-day cap of its own; it holds 3 findings per 5-minute run (the batch fuse, `maxPlansPerRun`) and backs off 1 h → 6 h → 24 h per finding (`planBackoff`). The overall limit is the monthly token budget of `ai` (stops at 100 %, warns at 80 %); `ErrPlanUnavailable` (budget used up `budget_reached`, fuse `rate_limited`, no profile) stops the run without backing off the findings. Test: `TestPlanBackoffAndNoDailyCap`.

## Modifying: `PlannerStatus`, `PlannerFinding`, `keepStatus`, `noActionReason` (planner_status.go)
- `PlanOpen` records the run state (kept in memory under `limitMu`) at each decision point; `savePlan` additionally returns the refusal reason (one caller: `PlanOpen`), `sendPlan` returns the answer of `Propose` for the state (one caller). Changing a decision point of the job → changing the corresponding result/sentence here, the copies of the sentences in `web/src/features/response/mocks.ts` (`PLAN_*`), and the test `planner_status_test.go`.
- Readers: `Plans` (GET /response/plans `planner`, viewer role) → the GUI `AiSetup.tsx` (`InboxWhy`). Changing the shape = changing `contract.ts` (`PlannerStatus`) → `api/openapi.json` → `core/api/oas` in the same PR. `GET /response/triggers` has `ai_evidence` (from `data/triggers.json`); the GUI uses it to say which triggers the AI can use.
- Nothing changes in behaviour: no extra AI call, no DB write, no gate change; the refusal sentence of a provider never goes into the state (only the ai module's sentence through `ErrPlanUnavailable`).

## Modifying: `Directory`, `ConnectionInfo` (cmd/vedette)
- `Directory.DevicesOfKind` feeds the never-touch list (router, firewall) and **must read with no limit on the number of rows** (`cmd/vedette` calls `inventory.DevicesOfKind`, not `Devices` which is cut at `inventory.MaxListed` newest rows first: the oldest device, usually the gateway, would fall off the list); a read error = the action is refused. `Directory.Device` also feeds the subject of an AI proposal (the finding's asset): a lookup error = refused. A device of another kind is also not in the list, so do not change the `kind` router/firewall without notice. `ConnectionInfo.UpdatedAt` must change whenever a connection is edited (address, credentials, tools): it is in the fingerprint stored per item (INV-9 `connection_changed`). `Connections` is provided by `core/conn` (an adapter in `cmd/vedette`); `connFP` is `conn.Fingerprint` (a vector shared with `core`); `updated_at` of `core_connection` only changes with security fields. Changing the list of security fields or the fingerprint formula = every pending request is refused `connection_changed` after the upgrade (accepted, stated in the PR).
- `ConnectionInfo` is built by `cmd/vedette` (`responseConnections`) from `core/conn`; `connFP` is `conn.Fingerprint(id, kind, target, updated_at)` (the shared vector `TestConnFPIsTheSharedVector`), so changing it turns every pending request into `connection_changed`. **`(*Service).ChangesInForce(ctx, connectionID) (bool, error)`** is the gate `conn.Config.InUse`: it reads `resp_actions.items` (`connector_id`, and `status = executed`, or `state_unknown = 1` (an explicit flag of an item whose step was sent but whose result is not known: the sweep or the step deadline sets it, a late result clears it; never comparing text), or `pending` with `running_at` set); changing the shape of an item or the meaning of a state changes the condition for 409 `in_use` when deleting a connection. Test: `modules/response/conn_test.go`.

## Modifying: `Executor.Execute(ctx, DeviceStep) (DeviceResult, error)` — 1 caller (`execute`, from `runItem`/`undoItem`)
- `cmd/vedette` installs `Executor` with `responseExecutor{w}` wrapping `core/conn/write` (no other package imports this package, FORBID-1); `DeviceStep` carries `ConnectionID, ConnFP, Phase, Tool, Lines, Method, URL, Body, Headers, Args` and `DeviceResult` is `{Status, Detail, Output}`; `Output` is only to compare `precheck_refuse`/`expect` and then be dropped (INV-22). `cmd/vedette/response.go` (`responseExecutor`, `responseConfig`) is the only place that imports `core/conn/write` (the import-scanning test `TestContract_FORBID1_*` in `core/conn/write`); `cmd/vedette/conn.go` fills `ConnectionInfo.NotReady`. Changing any of the following changes the contract between `response` and the writer: `DeviceStep`/`DeviceResult` and the `StepStatus` values; `execRec` (stored in the JSON `items`, adding a field means old items do not have it: handle as an item of an old version); `buildExec`/`stepOf` (changing how it is built means changing `buildChange`/`callOf`/`cliOf` too so that the approver sees exactly what is sent); `carryOutDevice`, `undoOnDevice`, `stepProblem` (how each `StepStatus` is recorded); `claimItem` (rereads the connection, `Connections.List` is called inside the write transaction: do not write in this gate). `device.go` (`carryOutDevice`, `stepProblem`, `undoOnDevice`, `recheck`, `readBack`, `resolveUnknown`, `execMatches`) is where each `StepStatus` is decided; `Settings.StoppedAt` (set/cleared in `EmergencyStop`/`ResetBreaker`) blocks every step that touches a device; `itemRec.ConnIdent`, `UndoUnclear` and `RequestItem.StateUnknown` (in the API: contract.ts `state_unknown`, the GUI Roll back button) are new data; the banned-command list lives in one place at `core/conn/cliban` (changing it changes both response and the writer, and the mock copy `cli-ban.sample.json`); `RestCall.headers` and `Change.Rest` are built from `stepOf` (changing `stepOf` changes what the approver sees). The writer repeats: the list of forbidden headers (`transport.ForbiddenHeader`), forbidden characters in commands (`shellChars`), leftover placeholders, only `GET` with no body for reads.
- It calls the connection's **write tool**. This is the single point of FORBID-1; do not add a second caller. **It must respect `ctx`** (carrying the item's deadline): `execute` runs it in a goroutine and stops waiting at the deadline, writes "State unknown" and releases the device step lock; an `Execute` that ignores `ctx` may still send a step afterwards, and its result is dropped. An `Execute` that panics becomes an error, not a process crash. Changing the signature → check every place that writes logs (`executed`/`failed`) and `verify`.

## Modifying: `Tpl`, `ValidateTpl`, `precheckProblem`, `needsPrecheck`, `actionFP`, `resp_catalog.precheck*`
- **Catalog editor (GUI + `checkCatalog`)**, **the template library** (`data/action-templates.json` and the mock copy `action-templates.sample.json`, a test for library drift), **seed** (`seedCatalog` refreshes `precheck`, `precheck_refuse`, `verify.expect` of built-in rows on every startup, not touching `enabled`/`ai_may_propose`/`connection_id`), **`unavailable`** (the reason "not available yet": a runtime value, `{interface}` missing a pre-check), **`actionFP`** (changing its formula or fields means every pending request is refused when approved; editing the refusal strings/`expect`/pre-check of a custom action cancels its pending requests), **the writer** (`Exec` stores the filled-in version of `precheck`/`run`/`rollback`/`verify` and compares `precheck_refuse`/`expect` with the output; changing the 5 × 80 / 200 limits here changes `contract.ts`, the GUI's `logic.ts`, `api/openapi.json` too).
- Changing the list of forbidden headers (`forbiddenHeader`) must change `logic.ts` (`forbiddenHeader`) too; `core/conn/write` repeats this check before sending.
- **core/netguard**: `forbiddenAddr`/`refusedTarget`/`checkWebhookURL` of `webhook_call` take the metadata points, metadata names, `Always`, `Forms` (transition forms, NAT64 learned through ipv4only.arpa), `Own` (Vedette itself) and `OwnText` from there; `Config.MachineAddrs`/`SelfAddrs` are wired by `cmd/vedette` to `machineAddrs`/`vedetteSelf` (like notify): dropping them = the machine running Vedette on port 8443 is no longer refused, and a decoy becomes a valid webhook destination; changing `core/netguard` changes this webhook's guard (notify, feeds, logs, ai still have their own copies until they switch over).
- Adding a column to `resp_catalog` must add it to `catCols`, `scanCat`, `saveCat` and `seedCatalog` at the same time (four places); `precheck_expect` is a column of `resp_catalog` like the other two.
- `readonly.go` (`cliProblem`, `readBackProblem`, `normalizeOutput`, `precheckVerdict`, `readBackHolds`) + `core/conn/cliban/cli-ban.json` (and the mock copy `web/src/features/response/templates/cli-ban.sample.json`, a drift test): changing the banned-command list or the rule for comparing output changes the contract with the writer (the executor calls `normalizeOutput`/`precheckVerdict`/`readBackHolds` with the device output and then drops the output, INV-22). `normalizeOutput` must keep case sensitivity and must not loosen matching.
- `portLikeParams` (`params.go`): adding a new parameter kind that can name a port means adding it here.

## Modifying: `TriggerField{Min, Max, Choices}`, `data/triggers.json`, `condValueProblem`
- **GUI** (`web/src/features/response/contract.ts` `TriggerField`, `logic.ts` `condProblem`/`condValueProblem`, the mock `data.ts`): the Rule form checks the same sentence as the box and shows it under the field; changing a range or a sentence in Go means changing `logic.ts` + `data.ts` in the same commit. `api/openapi.json` + `core/api/oas` are regenerated when the field shape changes.
- **Stored rules, templates (`rule-templates.json`)**: narrowing a range so that a template violates it → `loadData` fails and the box does not start; a stored rule that violates it is made by `storedCondsOK` to match nothing (`Evaluate`, `handleInTx`) until it is saved again (toggling on/off on the card is also saving again, so it meets 400 until edited). Narrowing a range quietly turns off rules that use an old value: write it in the release notes. `triggers.test.ts` compares `triggers.json` with `data.ts`.

## Modifying: `Fill(text, values, transport) (string, error)` / `CheckValue(type, v)` (INV-14)
- **Rule engine**, **Catalog editor** (checking templates on save), **Simulate**, **AI proposals**: changing the allowed character set or the escaping rules → may open a way for command injection from an attacker's data (a host name, a domain name). The fuzz must be run again with hostile trigger data.

## Modifying: `Propose(ctx, ProposeBody) (ProposeResult, error)` (INV-15)
- **ai** (the Go gate `Service.Propose(ProposeBody{Trigger, ActionID, Params, Confidence, Evidence ≤ 10, Why ≤ 400})` with the actor `ai:response`; `POST /response/ai/proposals` only in the preview): changing the thresholds (0.8, 7 days, 2/hour 5/day, 50%/10) → changes the volume of requests approvers receive; the thresholds are contract constants (`AI_MIN_CONFIDENCE`, `AI_REPEAT_DAYS`).

## Modifying: `appendLog(kind, actor, detail)` / `VerifyLog` (INV-19)
- **`GET /response/log`**: the `ts` field of `LogEntry` is `z.string()` in `contract.ts`, not `iso`: changing it back to `date-time` makes ogen re-encode the time, dropping the milliseconds, and the served string cannot be verified again (`cmd/vedette` `TestResponseLogServesTheHashedTimestamp`).
- **`/core/logs/export?categories=response`**: `Service.ExportLog` reads `resp_log` by day and writes the columns of the chain (`id, ts, kind, actor, detail, prev_hash, hash`, no `seq`); changing a column that is in the hash makes the downloaded file impossible to verify offline (`TestExportLogKeepsTheChainAndTheRange`).
- **core/logs export** (`response`): the hash formula is a contract with the offline verifier and the GUI (`logic.ts`); changing it → old chains cannot be verified again. **ai** has its own chain (see `ai` open question 2).

## Modifying: `renderBlocklist` + token (blocklist.go)
- The content type `text/plain; charset=utf-8` comes from the contract (`response: 'text'` in `contract.ts` → `web/src/lib/openapi.ts` → the ogen encoder), not set by hand in the handler.
- **The customer's firewall** (FortiGate External Block List, Palo Alto EDL, pfSense/OPNsense URL Table, MikroTik fetch) pulls this URL: changing the format (one IP per line) or the path → the customer's firewall stops updating without reporting an error. Regenerating the token invalidates the old address at once.
- **Restore without the decryption key:** a token sealed with a different master key (`secrets.IsWrongKey`) is **not replaced when read**: `GET /response/blocklist` → 409 `secret_lost` (a sentence saying the firewall still uses the current address, press Regenerate token); `FetchBlocklist` only compares the hash so the firewall can still pull the old address. The Block list card shows that sentence and keeps the Regenerate token button. `RegenerateToken` (an administrator's action) replaces the token as usual, adding a WARN and the audit `box-key.replace` (the actor is the administrator). An approval link signed with a key that cannot be opened (`secrets.IsWrongKey` on the error of `LinkTokens.Verify`) is an invalid link (`unknown`), not a 500.

## Modifying: `Settings` (envelope: breaker, multi-target, maintenance, expiry, AI gates)
- Every JSON field of `Settings` must be in `Settings` of `contract.ts`: ogen checks the box's own answer, an unknown field → 500 (`stopped_at`; tested through the handler `TestResponseSettingsReadableAfterEmergencyStop`).
- **GUI Settings → AI response**, **notify** (a channel ready to approve = `ready`): changing a value range → the GUI's `SettingsInput` and OpenAPI.

## Modifying: the `resp_*` tables (`migrations/sqlite/0001_response.sql`) and `data/*.json`
- **`modules/core/export_policy.go`** (`GET /core/data/export`): every column of every `resp_*` table must be classified there, `cmd/vedette` `TestExport_PolicyClassifiesEveryColumn` is red until that is done; `resp_tokens` and `resp_link_codes` are not exported (`skipAll`). `docs/SCHEMA.sql` is the merged schema of every module (`cmd/vedette/schema_test.go` keeps it matching the migrations). `core/logexport` reads the `resp_log` chain through `ExportLog` (the `response` catalogue). `core/server` masks the token in `/response/approve/{token}` and `/response/blocklist/{token}.txt` in the access log (`secretSegments`: `/approve/`, `/blocklist/`): changing the path shape means changing both places.
- **`data/triggers.json`, `data/action-templates.json`, `data/rule-templates.json`**: `scripts/ci/classify.go` ties them to `web/src/features/response/triggers.test.ts` and `templates/*.sample.json` (Go reads the GUI's sample files); changing one side means changing the other in the same commit.

## Disabling this module
- The Response page, the Respond button (Findings, Incidents), the AI plan on Findings: "the module is off".
- **The customer's firewall that pulls the blocklist gets 404 and keeps the copy it loaded** (no block is removed). An action that has already run with a TTL does **not** undo itself while off.
- `notify`: sends no approval requests; `Decide` from chat is refused. `ai`: `Propose` is refused (module off), the `response-plan` plan is still an AI job but has nowhere to be displayed. `core/conn`: connections can still be edited/deleted; `ChangesInForce` still reads `resp_*` to refuse deleting a connection that still has a change in force.
- `resp_*`, `resp_log` are kept; the log export is still available.

## Modifying: `claimItem`, `finishItem`, `failStuck` (requests.go: the life cycle of an item)
- `claimItem` is the single compare-and-set that allows a step to be sent: it rereads the execution switch, the breaker and the maintenance window **inside the transaction** that marks `running`. `failStuck` only fails an item by the `running` mark it read (`itemOutcome.sweep/ifRunning`); `finishItem` gives the real result of `runItem` (`fromRun`) in place of the sweep's \"State unknown\". Adding a new gate for `runItem` = adding it to `claimItem` too, not only `gateItem`. The action fingerprint (`actionFP`: template + risk) is a gate of `gateItem`; adding a field to the catalogue that affects the template/risk means adding it to `actionFP` and to the cancellation condition of `ChangeAction`.

## Modifying: `publishable` (the table `notPublishable`) and `inventory.DevicesOfKind`
- **blocklist** (the list published to the customer's firewall), **admin view** (does not list entries that cannot be published). The same table decides `not_publishable` at rule save time (a fixed value, `checkRule`), at planning time (`notPublicMsg` in `planAction`), when handing actions to the AI (`offeredFor`), at run time (`carryOut`) and when cleaning the store at startup (`dropUnpublishable`): loosening the table = a new `blocklist_add` gets through every path and the AI plan of that device is given the blocking action; tightening the table = a stored AI plan with that address becomes the status `not_publishable`, a pending request is refused at run time, an old entry is deleted at the next startup. Changing `fire` (only dropping the `not_publishable` action, keeping other actions) = changing which part of a rule still runs. The mock `web/src/features/response/engine.ts` (`isPublishable`) must change with it. `inventory.DevicesOfKind`/`KindDevice` is the inventory's neutral read for the never-touch list (see the inventory IMPACT).

## Gates and adapters between `response` and `cmd/vedette`
- **`Notifier.Approvers(ctx, channel)` + `Notifier.RequestApproval(ctx, ApprovalMessage{RequestID, Title, What ≤ 4 KiB, Risk, InAppOnly, Channels, Expires}) (sentTo, err)`** called after commit with a 60 s limit (`queueSend` → `sendApproval` runs in the background, at most 2 at once, not holding `s.mu`, not inside a write transaction; `Service.Close` in `cmd/vedette` `main` stops it); `cmd/vedette` `responseNotifier` is wired to `notify.SendApprovalRequest` (`Channels`, `InAppOnly`) and `notify.ApprovalChannels`. Changing `InAppOnly`/`Channels` = changing who receives approval buttons or links; tests INV-4, INV-16, POST-5.
- **`LinkTokens{ID, Verify}`, `RecordToken`, `LinkView`, `DecideByLink`**: `Verify` = `notify.VerifyApprovalLink` (`cmd/vedette` `responseLinks`); `RecordLink`/`RecordReplyCode` are the `response` side of `notify.TokenRecorder` (`cmd/vedette` `notifyTokens`, reading `d.Response` when asked because notify is built first; the table `resp_tokens` v2). Changing `approve`/`reject` (the parameter `tok`) = changing when a token is burned: `tokenGate` at the start of the transaction, `burnToken` after every gate. Changing the order of checks of `DecideByLink` (INV-4) = changing who can approve by email.
- **`DecideFromChat(ChatDecision{Channel, ExternalID, RequestID, Approve, Code}) (ChatOutcome{Status, Approvals, Required, Message}, error)` and `RecordReplyCode`** (`chat.go`): the only caller is the `notify` listener through `notify.Config.Decisions` (the adapter `responseDecisions` in `cmd/vedette/response.go`, reading `d.Response` when asked; an API error → `DecisionResult.Status` = the error code, only `approved|pending|rejected` is a recorded decision). With personal Zalo `RequestID` is empty: `response` compares the code hash (`replyCodeHash`, `approval-tokens.md` §7.1) with the records of exactly `(zalo-personal, ExternalID)`. `approve`/`reject` are shared with the app and links: `linkOpt` carries both the Zalo code (`kind="code"`) and the Slack/Telegram button (no token, only a recheck of person/channel under the lock); `Actor.Chat` changes the actor text in the log. Changing this function, the order of the gates or `tokenGate`/`burnToken` = changing who can approve from chat and changing the burning of codes; `Decide` answers at once and the item runs in the background (`runDetached`): changing this changes what the person who pressed the button has to wait for; chat's own rate table (`chatlimit.go`). The tests `TestChat_*`, `TestForbid4_NoCode` are required.
- **`TwoStep.Verify(ctx, userID, code, purpose, summary) error`** = `core/auth.VerifyTwoStep` through `cmd/vedette/response.go`; `purpose` = `response.approve.<id>`, `summary` is built by `approveSummary` from the stored request (≤ 200 characters, one line); errors returned unchanged; nil = refuse 403 `twofa_required`. Changing `purpose`/`summary` → the email code is tied to a different request, the line the approver sees differs; changing the order of the gates in `aiStepUp` → a code is spent for nothing or a refusal is skipped.
- **The quality breaker:** `qualityTrips` (≥ 5 decisions among the 10 latest AI requests and more than half rejected) → `ai.paused_at`; changing the thresholds changes how often the AI is stopped; `resp_hints` is only for people to read (INV-18), nothing reads it to change rules or the prompt.
- **`Evidence{IocHit, ConfigRead}`, `Planner{Available, Plan, Proposed}`**: `cmd/vedette/logsioc.go` installs `IocHit` (`logsIocEvidence`, with no `Connection`), `ConfigRead` = `ai.Service.ConfigRead` (the table `ai_read`, id = the read record, with the connection id, no more than 24 hours old) because the existence of a read tool proves nothing, and `Planner` (`Proposed`: changing `SentProposal` changes the AI log row); nil = invalid evidence (422 `evidence_invalid`) / no plan. `AIActions(ctx)` is what `ai` builds the tool schema from: changing the shape of `AIAction`/`AIParam` changes the tools of `ai`. `ProposeResult` is narrow (`ProposedRequest`): adding a field to it that shows the AI more must be reviewed for security. The map from trigger → kind of evidence (`ai_evidence` in `triggers.json`) decides which triggers the AI can use.
- **`ChangesInForce(ctx, connectionID) (bool, error)`**: `core/conn` calls it before deleting a connection (409 `in_use`); a read error = refuse the deletion.

## Modifying: `ActionRequest.masked`, `credentialHeader`, `approvalMessageText`, `ApprovalMessage.NoChatButtons`, `callText`, `capDetail`
- **Callers**: every handler that returns `ActionRequest`/`Simulation`/`ApprovalView` (`handlers.go`), `sendApproval` (`links.go`) → `cmd/vedette` `responseNotifier.RequestApproval` → `notify.SendApprovalRequest` (`NoChatButtons`; `notify` only complies, and a `kind=approval` message allows `What` up to 3000 characters, other messages 1000), every `step()` row (the log limit + SHA-256). Changing `callText` = changing the text in the hash chain of `resp_log` for new rows (old rows do not change).

## Modifying: `carryOutDevice`, `keepBefore`, `runAndRead`, `notThisStep`, `itemRec.PresentBefore`, `claimItem` (the running mark it returns) (device.go, requests.go)

- **Behaviour**: an unclear `run` whose read-back finds the text was there before does not become `executed` with an auto-undo time: it is `failed`, not counted as in force (`ChangesInForce`), cannot be undone from here. An item with no read-before record: `executed` with no auto-undo time (a manual undo is still open). A clear `run` on a change that already exists: `executed` with no `remove_at`.
