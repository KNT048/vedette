# Findings — Change Impact Map

## Modifying: `Transition`, `Finding`, `Trigger`, the vocabularies (`Resolution`, `Via`, `Verified`, `DetectionBasis`, `EventKind`, `QuestionKind`)
- Every change of the handling goes through `Transition`; a new state or trigger needs its row in `transition_table_test.go`, and the
  database CHECKs, `Finding.Validate` and the selfcheck invariants must agree. A new value of an open vocabulary is added to its list
  (`Vias`, `DetectionBases`, `EventKinds`, `QuestionKinds`): the selfcheck vocabulary rules read the lists.
- Readers of the older model (`legacy.go`: the current endpoints, notify, the AI context, MCP, reports, response) see the change
  through `LegacyStatus`, `record` and `legacyEvent`.

## Modifying: `applyMatch`, `detectionOf`, `goneVia`, `questionsOfMatch` (the match write)
- `goneVia` decides patch credit: a change here moves `TestCredit_*` and the fixture count test. The inventory's `MatchSoftware`
  (`ReportedSource`, `MarkedBy`, the effective reading first) is its input.

## Modifying: `schemeJudge`, `schemedSpans`, `namesLine`, `oracleTrains`, `distroCandidates` (vendor rows and distribution fixes, M-9)
- The matcher and `FixOf` read the vendor's rows through the same `schemeJudge`: a change moves which findings exist and the fix they
  store together. `TestCount_VendorRowsAndDistributionFixes` (per ecosystem), `TestFixCount_FindingsWithTwoFixedVersions`, the golden
  tests, and `cmd/vedette` `TestMatchSet_*` (the adapter's `Schemed`, `SchemeCVEs`, `DistroCVEs`).
- A new scheme is declared in `content/catalog/products` (`scheme`, `record`) and written in `core/versionscheme`; feeds then leaves the
  product's record rows to it (`recordSkipped`) and reports their changes as `feeds.ranges.updated`.

## Modifying: `classify`, `classified`, `RiskOf`, `RiskMap`, `AssetRisk`, `riskyUpdate`, `risk` and `risks` of to-fix and plan (INV-26)
- **One rule**: the marker is `RiskOf` of To fix's own classification (`actionable`, `Planned`), never a cheaper test of its own (#949: a ranking shortcut showed red for findings only in Needs your input, and a different count from the card). Change To fix and the marker changes with it, by design.
- **Cost and freshness**: `classified` does To fix's per-device work for every device once per change (`gen`, `plan.ver`, the feeds switch, `riskTTL`) and serves both the To fix page (display cap `ToFixLimit`) and every marker; a new input to To fix's classification must also move that key. `ToFix(…, id)` stays uncached (the device's own page).
- **inventory** shows it on the Devices list, the device page and the CSV (inventory INV-40, through cmd/vedette `findingCounts.RiskByAsset`) and filters on it (`?risk=`).
- **web**: `features/inventory/RiskMarker.tsx`; the Findings page (device column and filter from `risks`, To fix cards from each card's `risk`) and Recommended updates (`risk` of each item); the mocks' `deviceRisk`/`riskOfCard` mirror `RiskOf`.

## Modifying: `Finding.ShownConfidence`, `ConfScan`, `ConfVersion`
- **One rule** for the confidence every reader is given: a confirmed finding is never below `ConfScan`; the stored column keeps the match's value. Readers: `newRow` (GET /findings, /findings/{id}, the web's export), **cmd/vedette** `mcpFinding` (mcpserver.go) and `aiFindingRow` (ai.go). A new reader of `Record.Confidence` must use `ShownConfidence`. The web mock `findings/mocks.ts` `row` mirrors it.

## Modifying: `ServiceConfig.SafeCheck`, `KevInfo.HasTemplate`, `UpdateAction.Checkable`
- **One answer** to "a safe check exists": the template pack the scan plans with (cmd/vedette `safeCheckFor`, `Pack.ForCVE` of `content/nucleipack`), set in the binary's `findingsFeeds.KevInfo` and `ServiceConfig.SafeCheck`. Readers: the finding page's "Run the check" (`suspectedWhy`), To fix and Needs your input (`checkable`), mitigation guidance, the AI context, and the web's device page (`scanning/DeviceActions.tsx` `useVulnCheckable`). A pack update changes them with the scan, by design. The matcher's age and name rules still read `Vuln.HasTemplate` (the feed flag).

## Modifying: which rows the matcher reads, `pkgBuilt`, `pkgTierItem`, `debPkg` (INV-28)
- **inventory** owns which row describes a software (INV-50: `MatchInput` leaves the other rows of a software out). Findings reads `Asset.Software` as given; a findings-side ranking of sources, or a new adapter that builds `Asset` from another inventory read, would make one surface describe a software by another row than the rest (cmd/vedette `TestStrongestRow_EveryCombination`). A finding stored on a row inventory now leaves out is matched on the effective row at the next match (its `software_id` moves); the web's entered-release result reads every line of the software (`EnteredRelease.tsx` `softwareRowIds`, from the device detail's lines, `DeviceDetail.asset.software`).
- **cmd/vedette** (ai.go: the mitigation and Ask context, `Assets`, `Finding`; mcpserver.go: `Assets`, `Asset`) reads the device's lines from inventory (`Device.Software`, `Device.Running`: one row per line, the lines a person marked not installed left out), never `MatchInput` (inventory's `TestGuard_SoftwareReadingsAreReadOnlyThroughTheLine`); `aiMatched` takes the finding's `software_id` first. `feedsInventory.Distros` builds its `Asset` with `findingsAsset` (the matcher's rows, vendor and product included).
- `pkgBuilt` (an agent's package row; a person's package release on a Linux distribution or in a distribution's format): the finding page, To fix, the weekly report and the assistant say "install the distribution's security updates" instead of an upstream release.
- Plan: `PlanItem.distro` (contract.ts `PlanItem.distro`, `api/openapi.json`, `core/api/oas`; web `fix.ts` `plan.action.distroNamed`, mocks `tiers.ts`/`findings/mocks.ts`): a package of a distribution whose data Vedette does not read gets one item "install <distribution>'s security updates" (`pkgTierItem`); its CVEs count for the risk marker like any plan item. `distroRows` (so `DevicePackages`, `DeviceDistro` and the feeds' pull of `ubuntu-osv`/`debian-tracker`, feeds INV-22) also takes a Debian release a person gave (`debPkg`, source package `debSourceName` when inventory kept none; such a guessed name decides the plan only when the feeds hold rows under it, `byDistroData`, else NVD).

## Modifying: `deviceOS`, `deviceSoftware`, `withoutCoveredWindows`, `osRow.reads`, `OSVersion` (INV-4c (2))

## Modifying: `findings.Service.DeviceMerged(ctx, tx, lifecycle.Merge)` and `MergeCommitted` (INV-7)
- **Caller**: the inventory, inside its own write transaction, through `core/lifecycle` (registered by `cmd/vedette/devicelifecycle.go` `registerLifecycle`), before the merged row is deleted and whether or not the module is on. It must write only through `tx` (never `db.Write`: the writer is held) and publish nothing; the plan in memory follows in `MergeCommitted`. An error rolls the inventory's merge back. `ServiceConfig.Lifecycle.FindingFolded` (mitigation, response) runs before a folded finding is deleted: a module that keeps rows by finding id and is not a participant loses them to the FK cascade.
- **`ServiceConfig.Applied`** (binary: `mitigationApplied` đọc `mit_applied` through the merge's own `tx`): đổi bảng hay nghĩa "đã áp dụng" của mitigation là đổi finding nào thắng khi hai thiết bị cùng có một CVE. Nil = không finding nào được coi là đã áp dụng.

## Match pass over the catalogue and the fix resolver
- `Feeds.MatchSet` (cmd/vedette `findingsFeeds.MatchSet`) reads feeds' `RangeProducts`, `Ranges`, `RangesOf`, `Catalogue`, `DistroFixesFor`,
  `Range.MatchRow`; a change of their shape changes what the pass compares.
- feeds `Deps.Pins` = `findings.PinnedCVEs`: dropping it lets the catalogue age out a finding's CVE (selfcheck `findings.cve_in_catalogue`).
- Readers that still compute a fix of their own (finding page `FixedInFor`, list row `RowFixes`, To fix, the plan, the report's
  `FixedInForAll`) move to the stored fix with the view of the finding; until then the list row may name a later release than the stored fix.
- **The urgency pass** (`RateUrgency`: job `urgency` every hour, after each device's match write, and on `ids.alert.detected`):
  `Urgency(cve, facts, target, attacks, now)` is the one rule of the five layers; the pass stores the layer through `Transition`
  (`urgency_changed`), raising and lowering. Ports (`ServiceConfig.Urgency`): feeds' `UrgencyReader` (signals of the feeds that are on,
  with the first-load mark; an exploited list's entry always counts, so a listed CVE never rates below the match pass's start layer),
  ids' `ReadAttacked` while the ids module is on, `Loads` (notify's `FirstRunAt`, feeds' `CatalogueLoaded`). `Devices` (Internet exposure) is not wired until the reasons
  are shown. Changing a port's meaning changes stored layers: run `vedette selfcheck` (`findings.urgency_recomputed`).
- Alerts: every rise of an open finding into a more urgent layer of 1–4 is `findings.finding.urgency_raised`, emitted only by the urgency
  pass (the match pass leaves an existing finding's layer to it, then runs it). `Tell` decides news / a line of a first-run summary
  (`findings.urgency.first_run`) / old news; the latter two go out under the Backlog mark, which notify only counts. `created` means a new
  finding only: a consumer that acts on a finding becoming exploited (response, the SIEM export, To review) listens to `urgency_raised`
  with `to` ≤ 2 too.
- **Readers of the urgency layer**: `Row.urgency` (the finding's layer, 1..5) and `SummaryItem.urgency` are in the API (`contract.ts` FindingRow, SummaryItem); the "Fix first" list ranks the most urgent layer first. To fix (`classify`, `DeviceUpdates`) lists layers 1 to 4 only (`Announced`); the risk marker (`RiskOf`) and the card's "exploited CVEs to fix" count the CVEs of layer 1 and 2 (`UpdateAction.Layers`, `DeviceUpdates.actionable`). Outside this module the notice texts, alert links, response `kev` flag, exposure counts, reports, MCP and AI context read the layer too; `TestReadersNeverCallAFindingAboveLayerTwoExploited` (cmd/vedette) counts any reader still treating a finding above layer 2 as exploited.
