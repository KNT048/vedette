# Inventory Contract

> Tier: standard · Story: S-INV-1, 2, 3, 5 (+ the "Do you have it?" column of S-FEED-1) · Last verified: 2026-11-21 (every sentence checked against the code)

Source of behaviour: `web/src/features/inventory/{contract,mocks,validate}.ts`. Code: `modules/inventory` (`Service` is the only writer, `Handlers` for the module's 25 operations). Sensors/agents write through `core/observe` (`Sink`, `SoftwareSink`, `ServiceSink`), not importing this package. The agent part (osquery, Wazuh, `/install/*`, `/intake/*`) in the same `contract.ts` belongs to `agent-intake`; the sensor part (`/inventory/sensors*`) belongs to `sensor-passive`.

## Invariants
- **INV-1**: Observations are append-only, never overwritten (`inv_observation`; a trigger blocks changing a value in place). The "in use" value of a field is chosen by DATA_MODEL §5.1: **manual = declared > agent > snmp > nmap = scan > passive** (OS: the device's LLDP statement ranks between snmp and nmap, and of two nmap OS readings the newer scan wins, INV-44), then the higher `confidence`, then the newer `seen_at`, then the smaller `id`; for `hostname` alone: a readable name beats a UUID-like name (or 32 hex digits) even before the source rank, unless one of the two is `manual`. For `mac` alone: the MAC seen **last** wins, whatever the source, unless one of the two is `manual` (the MAC is where the device answers now: an old nmap MAC cannot keep a changed private Wi-Fi address as the device's MAC). A `passive` `model` with no letter at all ("0,1,2") never wins (an all-digit model from SNMP, an agent, a person is a part code, kept as is). The only exception: an observation that repeats exactly (device, field, source, value) moves `seen_at` and keeps the higher `confidence`. `confidence ∈ [0,1]`; `summary.source` = the source of the most trusted value (vendor, model, OS), `summary.confidence` = that of the weakest value; a device that has no vendor, model or OS yet (only seen through ARP) takes the hostname and MAC in use instead, so the list still says which sensor saw it (`TestSummaryOfADeviceSeenOnlyByARP`). An untrusted source (`core/observe`) can never be `manual`. A person's corrected OS (INV-41) is the one `manual` `os` row of the device: setting another or clearing it deletes that row (audited); the only other path that deletes a `manual` observation is Use detected (INV-47: every manual observation of one field); the stored declared OS (INV-45) is source `declared`, made and deleted by the system. `TestContract_INV1_ObservationsAppendOnly`
- **INV-2**: Every write to `inv_*` goes through `inventory.Service` (sensors, agents, feeds do not write directly).
- **INV-3**: There is exactly one asset with `is_box=true` ("This box"), created at install (both sample data and a clean install), packages taken from dpkg with confidence 1.0; `DELETE` on it → 409 `box_device` (S-INV-5). `EnsureBox` creates/updates it; the address is taken from the management port per vedette-host state/net (`cmd/vedette/boxaddr.go`, empty when there is no host), the machine name is the OS machine name that vedette-host reports (`GET /v1/info` `hostname`, checked against RFC 1123; `cmd/vedette/boxname.go`), `vedette` when the host has no valid name (the host has never answered since `core` started: keeping the name of the existing row, a new row gets `vedette`), and `core`'s own name when there is no host (container-only: the compose `hostname: vedette`) (`TestBoxRowAndLogsPageUseTheHostName`), the OS is the release that vedette-host reads from `/etc/os-release` (`GET /v1/info` `os.distro`/`os.release`, checked again in `core`: only `ubuntu`/`debian`, a numeric release; `cmd/vedette/boxname.go` `boxOS`) turned into an `os` observation of source `agent` ("Ubuntu 26.04"), so that `findings` considers NVD entries that only name an OS release (CVE-2021-3493) for the box as for a machine that has an agent; no host or a host that has not answered ⇒ keep the OS of the existing row (`cmd/vedette` `TestBoxCarriesItsOSForTheMatcher`), the model "Security box (appliance)" or "Security box (container-only)" by install type (`BoxInfo.ContainerOnly` from `modreg`) (the module's `box` job runs as soon as the module is on); packages are taken through `BoxPackages` (`cmd/vedette` reads `GET /v1/state/packages` of vedette-host, mapped like osquery's `deb_packages` table by `agentintake.MapDebPackages`), a read from the source `box` (ranked equal to `agent`, INV-54), confidence 1.0, every hour (the `box` job) and right after a successful OS update (`OSConfig.Installed` wakes the `box` job). `BoxPackages` returning `nil` (an old host, no read command yet; or dpkg in the middle of a change: the host 409 `packages_changing`) or an error → keep the existing list, never wiping it (`TestContract_INV3_NoListFromTheHostKeepsTheBoxSoftware`); the box's list is never cut: longer than 5,000 entries (the cap for one device) → the whole list is refused, keeping the old list (`TestContract_INV3_ATooLongBoxListKeepsTheBoxSoftware`); the container-only build has no `BoxPackages` so no packages (the device page says so). **The box's open services**: the box is never scanned by its own sensor, so `RefreshBoxServices` (the same `box` job, every hour, a failure of the package part or the port part does not block the other) writes the ports that `Config.BoxPorts` returns (`cmd/vedette` `boxPorts`: vedette-host `GET /v1/state/ports`, host INV-9b; name = the Vedette unit or the program) as services of the box row, source `agent`, confidence 1.0, through the same `checkServices` boundary of INV-23, written by the box's id (the box's address never becomes a device, INV-17); the list replaces the box's `agent` rows, rows of other sources stay; `nil` (an old host) or an error → keep as is; the container-only build has no `BoxPorts` so no services (`TestContract_INV3_TheBoxListsItsOwnOpenPorts`). A row of source `agent` does not become a nuclei target (scan INV-14) and does not reach the AI provider (`cmd/vedette` `aiScanned`, PRIVACY: the gate is what scanning reads). An empty Services tab says who lists ports: the box itself (container-only: does not list), the machine's agent (having observations or software of source `agent`), or the scanning sensor.
- **INV-4**: Manual declaration: `ip` a unique IPv4 (409 if duplicate), `name` ≤ 64 characters with no `<` `>`, `vendor/product` ≤ 64, `version` ≤ 40 characters consisting only of letters, digits, `. - + ( )` and spaces; duplicate software on the same device → 409 `duplicate_software`. Only software with `source=manual` can be deleted (400 `not_manual`).
- **INV-5** (INV-37): A manually declared device (`origin=manual`) is not scanned and not read by SNMP **until a person turns that source on for that device** on the Sources card (`scan_source`/`snmp_source` = `on`); the default (NULL) is off, `first_scan_at=null`.
- **INV-6**: LAN ranges (`lan_ranges`): at most 16; each range **must have a prefix** (400 `no_prefix`, no guessing /24), no host bits (`host_bits`), only RFC 1918 private ranges or the RFC 6598 shared range `100.64.0.0/10` (`core/localnet.Prefix`; the rest of 100/8 is public; `public_range` with the sentence "… is not an internal range (10.x, 172.16-31.x, 192.168.x, 100.64-127.x). …", pointing the way to `exposure`), not overlapping (`overlap_range`); keeping exactly the prefix the person typed.
- **INV-7**: Turning on active scanning (`active.enabled=true`) needs ≥1 range, ≥1 day and `scope_confirmed=true`; stores `scope_confirmed_at/by`. `days ∈ 1..7` (1=Monday), `from≠to` (may cross midnight), `rate ∈ 1..1000` packets/second, `exclusions` are IPv4 or CIDR with no host bits.
- **INV-8**: A fragile device: a kind in `fragile_kinds` or `fragile=true`, **and a device not yet classified (`kind=unknown`, which may be fragile)**, is scanned lightly **exactly once** when first seen (`first_scan_at` set), after that only passively (reason `fragile_passive_only`, or `unclassified_passive_only` while the kind is still `unknown`) unless `regular_scan=allow` or the kind ∈ `regular_scan_kinds` (kind `unknown` belongs to no kind: only when a person/passive data sets the kind, or `allow`); `regular_scan=never` beats the per-kind setting **and applies to every device kind**: a device that is not fragile with `never` is also only scanned lightly once and then passively (reason `regular_scan_never`, conservative like the "do not scan" per asset of Tenable OT). The machine running Vedette (`is_box`) is refused with the reason `box`. `regular_scan_kinds ⊂ fragile_kinds`.
- **INV-9**: A new device seen by a sensor: `approved=false`, goes into the "pending" row (S-INV-3); always emits `inventory.asset.discovered {asset_id, notify, learning}` with `notify` = `notify_new` at that time (on ⇒ `notify=true`; `sensor-active` still needs the event to scan a fragile device for the first time so it is not silent when off) and `learning` per INV-28.
- **INV-10**: Adding a product matches `feeds` at once through the interface `KEV` (`kev_cves`); the match key of a software row is the product's key in the core/productid catalogue (`matchKeys`, INV-54), stored in no table. The event `inventory.match.changed {asset_id, cve, basis}` only for a newly matched CVE (not emitted on removal); `basis="product"` (KEV does not yet have an affected range so no `version`), never "confirmed" (only `scan` confirms). The `kev_cves` number returned on add comes from the catalogue (every CVE ever exploited), the CVE list comes from `feeds`. `kev_cves` of `SoftwareLine` (`GET /inventory/devices/{id}`, INV-50) is **every KEV CVE of the product, with no version comparison**: not a finding; empty on a row that the user says is not installed (`not_installed`). The Software tab of the device page does not show `kev_cves`: each row says what it needs from `GET /findings/to-fix?asset=` of findings (INV-25, joined by `software_id`); findings uses `kev_cves` to know which software a CVE belongs to (`softwareFor`).
- **INV-11**: Deleting an asset also deletes its findings (`findings_count` is shown before deleting).
- **INV-53** (device lifecycle in one transaction; `core/lifecycle`): every write that deletes a device (`DeleteDevice`, `ForgetBoxOwned`) or merges two rows of one machine (`joinSame`, `Merge`, both through `joinAs`) calls the registered participants (`Config.Lifecycle`: findings, mitigation, notify, response, sensor-active, connections, feeds, ids, agent-intake; the last two on a merge only) inside the inventory's own write transaction, before the device row goes; an error of any of them rolls the whole write back. A merge loses nothing: a software line both rows hold (same product and train) is folded into into's line (`foldSoftware`: every reading of from's line moves to it, of two readings of one source and instance the newer stays; into's line is settled again) and `lifecycle.Merge.Software` maps each removed line id to the one that stays (the folded line is deleted after the participants ran, `dropFoldedLines`); an open port both hold is folded the same way (`foldServices`); the lines left move with their ids. The events `inventory.asset.merged`/`deleted` still go out after the commit, for notifications only.
- **INV-12**: The catalogue `GET /inventory/catalog`: returns at most 30 entries with `total`; curated entry ids are fixed, an entry from KEV is `kev:<vendor>:<product>`; it contains every vendor/product pair that has ever been in KEV + common SMB products; free-form entry is still allowed. A curated entry takes its KEV keys from the `kev_match` fragments of `curated.json` through `productid.FragmentMatch` (`Catalog.keysFor`): matching by whole word, not by fragment of a word; a trailing `*` is the whole product family; a name in the list that names several products only falls on exactly the products it names; each fragment names both vendor and product (`TestCuratedRows_LinesCarryOnlyTheirOwnNames`, `TestCuratedRows_EveryFragmentNamesAProduct`). **One data source for both web and Go**: `content/catalog/curated.json` (the curated list) and `kev-products.json` (the embedded KEV pairs: used when the `feeds_vuln` table is still empty or `feeds` is off, otherwise the pairs come from `feeds` through `KEV.Products`); the search algorithm has two copies (`catalog.ts`, `catalog.go`) kept in sync by `content/catalog/search-golden.json` (`TestContract_INV12_CatalogMatchesTheWebGolden` + `catalog.golden.test.ts`); the `kev_match` fragment matching rule also has two copies (`core/productid/fragment.go`, `catalog.ts`) kept in sync by `content/catalog/fragment-parity.txt`.
- **INV-13**: CSV import ≤ 200 KB and ≤ 500 rows; a bad row is reported by row number, valid rows are still added; the header needs a `name` or `product` column; a file with no device rows → `no_rows`. A short row and an empty separator at the end of a row are accepted; only (a) more cells with text than columns and (b) a single cell that looks as if it was split by a character other than the header's delimiter, together with a stray or unclosed double quote (including on a row that only has whitespace), are a row error (never becoming a device named after the whole line). The product column only matches exactly (`Catalog.find`: id, name, "vendor product", alias, vendor name; matching several products of different vendors → no match), no fuzzy match. A row with a public IP or outside the stored `lan_ranges` is still added and has an entry in the result's `notes`. CSV export is UTF-8 with a BOM.

- **INV-14** (module wiring; returns the new device id): `AddManualDevice(ctx, tx, actor, ManualDevice) (id, error)` runs **inside the caller's transaction** (feeds): the device, the `manual` software, the `core_audit` row `inventory.add_manual` and the event are one commit; the event is held until `Settle(ctx, tx, committed)` (commit → emit, rollback → drop). Every check of `AddDevice` applies (key matching `lower(vendor)|lower(product)`, label ≤ 64 characters with no `<` `>`, an unknown device kind is ignored). One exception: a vendor/product pair **exactly equal to a pair in the KEV list** may be up to 200 characters long (CISA's data, not typed by a person; otherwise "Cisco ASA…" could never answer "I have it"). A manually declared device: `origin=manual`, `approved=true`, never scanned (INV-5); INV-9 (`approved=false`) only applies to a device a sensor saw. `TestAddManualDevice*`, `TestWiringFeedsYouHaveAndIHaveItAreAtomic`.
- **INV-15**: `DevicesRunning` returns "yes" when a device's software carries exactly the product's key; for a "Multiple products" entry only software that declares exactly that product is "yes", a device that has software (or a manufacturer) of the vendor is "maybe" (INV-11 of feeds). The `Display` of each result is the name of the software row carrying that key (a match by vendor: the vendor's row; only the manufacturer matching: the `Display` of `DeviceRefs`), not the device's first row by name. `TestDevicesRunningNamesTheMatchingSoftware`.
- **INV-16**: Each (device, field, source) keeps at most 32 `inv_observation` rows: `Record` deletes older rows (by `seen_at`, then `id`) **in the same transaction** as the insert, so a MAC that keeps changing value does not make the table grow without limit, whichever sensor the source is (including agent-intake). Only `Record` trims; the manual path does not go through it. The trim query uses the prefix of `inv_observation_uq (asset_id, field, source, value)` so it only reads a run of ≤ 33 rows; the winning value is chosen again after each batch so a winning row that is trimmed leaves no dangling reference. Sensors also have their own per-MAC quota (the CONTRACT of sensor-passive, the section "Flood limits"); this is the second layer of protection.
- **INV-17** (honeypot): an address the box answers for itself outside its own device — the decoy IP of `honeypot` — is not a device. `Config.BoxOwnedIPs func(ctx) []netip.Addr` (wired in `cmd/vedette/inventory.go` to `honeypot.Service.DecoyIPs`, read when needed): `Record` and `ReplaceSoftware` **drop** an observation whose IP is in the list (not creating or updating a device, emitting no event), counted in `BoxOwnedSkipped()`; `ProtectedIPs` lists those IPs so `sensor-active`'s sweep does not probe them. With no function nothing changes. A device that **already exists** at that IP (before the IP became the box's) is still a device: honeypot treats it as a `conflict` and removes the IP, which then no longer belongs to the box. **The MAC decides**: an observation at the box's IP is only dropped when it has no MAC, has the box's own MAC (the NIC and the decoy macvlans, `Config.BoxOwnedMACs`, wired to vedette-host's `state/net` through `hostMACs` in `cmd/vedette/inventory.go`), or when the box's MAC is not known yet (the host has not answered, no host: drop); a foreign MAC at a decoy IP is **another machine that took that IP** (DHCP, a static IP an intruder set) and is recorded as a device, with a new-device alert, and then honeypot sees `conflict` at once at the `Apply` triggered by `inventory.asset.discovered` (otherwise every minute) and removes the decoy. A MAC that is not in the held answer makes the host be asked again once (`fresh`, at most every 2 s) before being treated as a device: a just-added decoy has a new macvlan MAC. **The decoy is held by the host**: a foreign MAC is only a device when the host **is holding a decoy at exactly that IP with a different MAC** (`Config.BoxDecoyMACs`, IP → MAC from the same `state/net` answer, `hostMACs.Decoys`); an IP belonging to the box where the host has not yet listed a decoy (a Trap IP just added, a link that just came up answering ARP; the namespace being rebuilt) means that frame is the box's and is dropped. Tests: `TestContract_INV17_AForeignMACOnADecoyAddressIsADevice`, `TestContract_INV17_ADecoyComingUpIsNoDevice`, `TestContract_INV17_TheBoxsOwnDecoysAreForgotten`, `TestHoneypotTrapIPFramesAreNeverDevices` (cmd/vedette). **The decoy MAC per `honeypot.ExpectedMACs`**: `BoxDecoyMACs` gives, for each IP belonging to the box, the decoy MAC it has/will have (host `state/net`, overridden by `honeypot.ExpectedMACs` because the host answer in memory may be older: the MAC the host gave at the latest `Apply`, the remembered MAC, or `""` when the address is being added and the MAC is not yet known). At an IP belonging to the box, only a frame with no MAC, the box's MAC, or exactly that MAC (`""` = any MAC while being added) is the box's; **any other MAC is a machine at that address, even when the host holds no decoy there** (a Trap IP that was refused, broken, not yet delivered: a laptop using an address the customer chose is still a device). An observation that has a MAC but no IPv4, where that MAC is a decoy MAC → the box's. `BoxOwnedIPs` also includes the address of every Trap IP that is on when honeypot is on. `ForgetBoxOwned(ctx, since)` (honeypot calls it on each `Apply`, `since` = when each Trap IP was turned on, not earlier than when the module was turned on): deletes rows that are not approved, not added by hand, not the box, **first seen from that Trap IP's `since` onward** (older rows are real machines, kept), at that address with no MAC or the box's MAC, or with no IP where the MAC is that Trap IP's decoy MAC; the condition is checked again inside the delete transaction itself (a row that was just approved is kept), audit `inventory.delete` by `system`, events as `DeleteDevice`; it only asks the host when such rows exist. `TestHoneypotTrapIPFramesAreNeverDevices` (cmd/vedette). `TestBoxOwnedAddressIsNoDevice`, `TestNoBoxOwnedProviderChangesNothing`, `TestHoneypotDecoyAddressesAreNotDevices` (cmd/vedette).

- **INV-18**: `DevicesOfKind(ctx, kinds)` returns **every** device of those kinds (id, hostname, IP, MAC, kind), sorted by id, with **no row limit** (unlike `Devices`: at most `MaxListed`, newest first) and read-only; empty `kinds` → empty; a read error → an error, never a short list. `response` uses it for the never-touch list (INV-10 of response). - **INV-19**: `AssetIDs(ctx)` returns the id of **every** device (except those a person ignored, INV-38), **with no kind filter and no row limit**, sorted by id, read-only; a read error → an error, never a short list. `findings` uses it for the reconcile job (a short list would make it delete the findings of devices that still exist). Test: `TestAssetIDsListsEveryDeviceOfEveryKind`.
- **INV-20**: `KindDevice` additionally carries `Approved` and `KindSource` (the source of the observation that gave the kind; empty when the kind is the default `unknown`). `TrustedKind()` is true when `KindSource` is `manual` or `agent`, or is `snmp`/`nmap` **and** the device is approved. A kind declared only by passive frames (SSDP, LLDP, DHCP, mDNS) is never trustworthy enough, even for an approved device (a later LLDP frame changing the label to router); a kind from the nmap of an unapproved device is not either (nmap runs in the untrusted `scan` container and the target shapes the answer). `PatchDevice` with the device's **current** kind still writes a `manual` observation when the current source is other than `manual`: that is how an operator vouches for a router declared only by passive frames. Test: `TestDevicesOfKindTellsWhereTheKindCame`; the filtering side: `cmd/vedette` `responseDirectory.DevicesOfKind`, test `TestResponseDirectoryIgnoresARouterOnlyAPassiveFrameClaimed`. **Union guard** (`trustedKindUnion`): `DevicesOfKind(kinds)` also returns every device that has **any** machine-trusted `kind` observation (agent, or snmp/nmap of an approved device) in `kinds`, whatever the current kind is; then `Kind`/`KindSource` are those of that observation (agent first, then snmp, nmap; newest first). SNMP ranks above nmap so it can change the current kind, but it can only **add** a device to the never-touch list, never remove one: a machine in between answering a router's SNMP as a printer cannot make the router blockable. **A person's explicit choice wins**: a machine observation **older** than the device's newest `manual` kind does not count; the manual kind (always the current kind) decides: a person setting "printer" takes the device off the list, setting "router" keeps it; a machine observation **newer** than that choice still brings the device back (the union only adds), never being a way out (like Lansweeper, runZero: a manual override beats the fingerprint). Test `TestNeverTouchIsTheUnionOfTrustedKinds`. `BoxIPs(ctx)`: only the address of the box itself (the `is_box` device) and `Config.BoxOwnedIPs` (the decoys), the part of `ProtectedIPs` that nothing may probe, including reading the SNMP of a fragile device.
- **INV-21**: `AddressInUse(ctx, ip)` (a device that is not the box has this IP), `AddressMap(ctx)` (IP → id of every device), `KnownMACs(ctx)` (the MAC of every device that has a MAC), `AllDevices(ctx)` and `BoxName(ctx)` read the **whole table** or exactly one row, with no `MaxListed` limit, read-only; a read error → an error, never a short result. - **INV-22**: `cleanText` (untrusted observations) refuses C1 controls (U+0080–009F), bidi controls (U+202A–202E, U+2066–2069), zero-width characters (U+200B–200D, U+2060, U+FEFF) and the tag block (U+E0000–E007F); in general **every** format character (Cf: including LRM/RLM/ALM, U+2061–2064, U+206A–206F) and every Default_Ignorable_Code_Point (`observe.Ignorable`: variation selectors U+FE00–FE0F, U+E0100–E01EF, soft hyphen U+00AD, U+180B–180F, Hangul fillers), the same table as honeypot and account names; a default-ignorable character that is **not** a format character (a variation selector such as the U+FE0F of an emoji in a device name, U+034F, fillers) is **dropped** before checking (`stripIgnorable`, like honeypot), while for a format character the value is refused; NBSP and combining marks are still accepted. In a software list (`UpsertSoftware`, `ReplaceSoftware`), an entry that has such a character is **dropped on its own and logged**, the other entries are still stored; an entry that is bad in another way is still refused (PRE-2). Tests: `TestCleanTextRefusesInvisibleCharacters`, `TestUpsertSoftwareDropsOnlyTheItemWithAnInvisibleCharacter`.
- **INV-23**: Open services (`inv_service`, `asset.services`) are only written through `ReplaceServices(hint, source, scope, items)` or `AddServices` (a partial look, like a light scan: new ports are added, a port that already exists from that source moves `seen_at`, keeping the name/product/version/confidence **unless** the entry names a product (the `-sV` following sensor-active's weekly all-ports scan: the name, product, version, confidence of that port are updated), deleting no row) (`observe.ServiceSink`); **`ReplaceServices` has a scope** (`observe.ServiceScope`, like `ReplaceSoftware` has `scope`): an empty `scope` is the source's whole list; `Ports` are the TCP port ranges the scan looked at (at most 2000 ranges, 1..65535) and only TCP rows within them are replaced, rows of other ports are kept, an entry outside the scope or not TCP is refused (`ErrInvalid`); `NoVersions` (a scan that only probes open ports) keeps the name/product/version of an existing port unless the entry names a product; `KeepFor` deletes a row outside the scope that the source does not see again after that long (at most 90 days); **`read_at`** (a nullable column of `inv_service`) is the last time the source read the name/product/version of the port: every entry of a list that reads versions (`ReplaceServices` without `NoVersions`: a normal scan, the `-sV` following an all-ports scan with the scope being exactly the ports it read, an agent report) sets it equal to the `seen_at` of the write, including an entry that names no product; may be empty; text goes through `stripIgnorable` + `cleanText` like software, an entry with an invisible character is dropped on its own and logged, INV-22), `confidence ∈ [0,1]`; **at most 1000 services per list** (one device, one source: the `--top-ports 1000` of a normal scan; No event is emitted, no audit is written (nobody listens to port changes yet). **Kept 90 days**: the job `service-prune` (every 6 hours, Housekeeping: running even when the module is off, only deleting) deletes rows whose `seen_at` is older than 90 days (`PruneServices`) and writes one audit row `inventory.services_pruned` (the row count) when at least one is deleted; the GUI says this in the Open services section. ## Preconditions / Postconditions
- **PRE-1** (`Record(ctx, []observe.Observation)` / `RecordObservation`): `source ∈ {agent,snmp,nmap,passive,scan}` (not `manual`), `field ∈ {hostname,mac,vendor,model,os,kind}`, `confidence ∈ [0,1]`, a value of 1–200 printable characters (MAC normalised `aa:bb:..`, kind is an id of `content/devicetypes`, INV-27), a device hint that has a MAC or an IPv4; at most 5000 observations per batch; the whole batch is one transaction (one bad row = nothing stored, the error wraps `ErrInvalid`; an error caused by one row is `*observe.ErrRejected{Index, Err}` so the sender can drop exactly that row and send the rest: `TestRecordNamesTheRefusedItem`). **POST-1**: observations are added; an asset is created if the MAC/IP is new (`approved=false`); `last_seen` is updated. Look up by MAC first, then IP; a device that already has a different MAC loses the IP (DHCP changed owner), including a manually declared device that has a MAC attached or an agent; a manually declared device that only has an IP gets the first burned-in MAC seen at that IP within 72 hours after the person declared it (INV-35). `TestContract_POST1_…`
- **PRE-2** (`UpsertSoftware(assetID, items, source)`, `ReplaceSoftware(hint, source, scope, items)`): the asset exists (or is created per the hint); `source` is a source that may send a list (`observe.ValidSoftwareSource`: `osquery`, `wazuh`, `box`, `snmp`, `nmap`, `scan`, `passive`; not `manual`, not `agent`). **POST-2**: the readings of that source (within `scope` when present) are replaced exactly by the list, and then each row touched is resolved again (INV-54); readings of another source, including a person's, are not touched; an identical list emits nothing; a change emits `inventory.software.changed` and `inventory.match.changed` for newly matching CVEs.
- **PRE-2b** (`ReplaceServices(hint, source, items)`, `AddServices`): the hint has a MAC or an IPv4, `source ≠ manual`, the entries pass INV-23. **POST-2b**: the device is found by MAC and then IP, otherwise created unapproved (like `ReplaceSoftware`, with `inventory.asset.discovered`); that source's `inv_service` is replaced exactly by the list (a row that is in the list updates its name/product/version/confidence and `seen_at`, a row that is not is deleted; rows of other sources are not touched); an empty list deletes all rows of that source; the device's `last_seen` moves forward. `Detail`/`Devices` return exactly these rows (`reads.go` `loadServices`).
- **PRE-3** (`ScanPolicy(assetID)`): the asset exists. **POST-3**: returns `{allowed, rate, reason}` per INV-5, 7, 8 and `exclusions` (reason: `ok`, `first_gentle_scan` (rate 1), `box` (discovery never scans the machine running Vedette; only a person choosing it in "Scan now" of the `scan` module scans it, PRE-3b), `declared_by_hand`, `no_ip`, `scanning_off`, `scope_not_confirmed`, `out_of_scope`, `fragile_passive_only`, `unclassified_passive_only`, `regular_scan_never` (`regular_scan=never` means never scanning actively after the first gentle scan, for every device kind, including a server that is not fragile)); `InScope(ip)` is true when ip ∈ `lan_ranges` ∖ `exclusions`. The time window is judged by the scheduler of `sensor-active` (needing the organisation's time zone). `MarkFirstScan` sets `first_scan_at` after the first gentle scan. `ProtectedIPs(ctx)` returns the addresses that **may not be probed by a probing scan** (by IP, not by MAC): the box, manually declared devices, `regular_scan=never`, and fragile/unclassified devices that have had their gentle scan and are not yet allowed regular scans. `TestContract_INV8_UnclassifiedDevicesAreScannedOnceGently`, `TestContract_INV8_ProtectedIPs`.
- **PRE-3b** (`VulnScanPolicy(ctx, assetID, explicit)`): the asset exists; `explicit=true` only when a person hand-chose exactly this device in "Scan now" (the caller writes `core_audit` with the person's name: that is consent for this device alone). **POST-3b**: returns the same `ScanDecision` as POST-3, but the `scanning_off` switch of `sensor-active` does **not** apply (the `scan` module has its own switch). The box itself: `explicit=false` → refused `box` (the schedule and KEV rescans never scan the box, whatever `regular_scan` is); `explicit=true` → goes through exactly the checks below like every device, at normal rate. `ScanPolicy` (discovery, `sensor-active`) and `ProtectedIPs` (the sweep) still always block the box and the decoy IPs. Always refused, even when `explicit`: `no_ip`, `scope_not_confirmed`, `out_of_scope` (like `InScope`), `regular_scan_never` (`regular_scan=never` is absolute for vulnerability scanning). A fragile, unclassified (`kind=unknown`) or manually declared (`origin=manual`) device: `explicit=false` (the schedule, KEV rescans) → refused `fragile_passive_only` / `unclassified_passive_only` / `declared_by_hand`; `explicit=true` → allowed, fragile and unclassified at `max(1, rate/4)` packets/second, a manually declared one that is not fragile at the normal `rate`. Exception: a fragile or unclassified device that has `regular_scan=allow` (or kind ∈ `regular_scan_kinds`, INV-8) is scanned at the normal `rate` even when `explicit=false`; a manually declared device never (INV-5). It never calls `MarkFirstScan` (the first gentle scan belongs to discovery). `TestContract_VulnScanPolicy_*`.
- **POST-3c** (`ScanDecision.Careful`, `ScanDecision.IP`, only set by `VulnScanPolicy`; `ScanPolicy` leaves zero): when allowed, `Careful` = a fragile device or `kind=unknown` (even when `regular_scan` allows scanning at the normal `rate`: on the safe side, the caller decides whether to go slowly), `IP` = **the address the decision was made for** (from the same read as the other facts, not read again); when refused both are zero. `VulnScanPolicies(ctx, assetIDs, explicit)` returns exactly the result of `VulnScanPolicy` for each id but reads the settings once and the devices in one query; at most `MaxPolicyBatch` (4096) ids, more → `ErrInvalid` (not cut); an id that does not exist is **absent** from the map, not breaking the whole batch. `TestContract_VulnScanPolicy_CarefulAndIP`, `TestContract_VulnScanPolicies_*`.
- **POST-3d** (`ScanDecision.Fragile`, `.Unclassified`, `.Never`, only set by `ScanPolicy`, for every device that has passed origin, address and scope): a fragile device / `kind=unknown` / `regular_scan=never`. `sensor-active` chooses the scan template for the identification of Scan now from it (never → refuse; fragile → a gentle scan; unknown kind → the `versions` template at ¼ rate).
- **POST-2d** (`ReplaceSoftware`): a `Guess` entry (an OS that nmap guessed from a fingerprint) is stored (reading `os_guess`) and shown, but a row that only has it has **no KEV key at all**, so it produces no finding; a person adding an OS with a version on the device page is the confirmation step, so `AddSoftware` does not treat a guess row (a row with no key) as a duplicate (`duplicate_software` only for a row that has another reading). A `Guess` may **have a version** (Windows states its release and build through NTLM, `10.0.22631`, but does not state the monthly patch): the version is stored and shown, the key is still absent. `TestNmapCPEGetsTheCatalogKEVKeys`, `cmd/vedette` `TestNmapOSGuessRaisesNoFindingUntilAPersonConfirmsIt`.
- **POST-2c** (`ReplaceSoftware`): an entry that has a CPE (not a `Guess`) but has no KEV key belongs to the product of the curated catalogue entry whose `cpe` names the `part:vendor:product` of that CPE (`content/catalog/curated.json`: `o:apple:iphone_os` → the keys of "iOS / iPadOS"), like a manual declaration; if no entry names it, it is the product `vendor|product` of itself. A catalogue read failure → logged. `TestNmapCPEGetsTheCatalogKEVKeys`. The default probing-scan window is 22:00–05:00.
- **PRE-4** (`PATCH /inventory/devices/{id}`): `operator`. **POST-4**: editing `kind/fragile` adds a `manual` observation, not deleting the old value; `name` sets `user_name` (INV-36), not an observation.
- **PRE-5** (`PUT /inventory/settings`): `admin`, through INV-6/7. **POST-5**: `scope_confirmed_at` is kept if the ranges do not change; emits `inventory.settings.changed`.
- **PRE-5b** (`SetupScope(ctx, tx, actor, ranges, confirmed)`): only `core` calls it, inside the write transaction of `POST /core/setup` (the gate `core.SetupScope`); `ranges` go through INV-6 (an error is an `*apierr.Error`, and the caller's transaction fails with it). **POST-5b**: `lan_ranges` = `ranges` after INV-6 (host bits dropped, duplicates dropped); `scope` = `{confirmed_at: now, confirmed_by: actor}` when `confirmed`, empty when not; when `confirmed`, **`active.enabled=true`** (the commitment at install time is consent to scan; before that active scanning stays off), when not `confirmed` it is kept as is; other settings are kept; no separate `core_audit` row (core's `core.setup` row records the number of ranges); `inventory.settings.changed {scope: scan}` is only emitted at `Settle(tx, committed=true)` (dropped on rollback), like `AddManualDevice`. `TestSetupScopeBecomesTheScanScope`, `TestSetupScopeRefusesWhatTheScopePageRefusesAndRollsBackWithTheCaller`.

## Forbidden
- **FORBID-1**: Overwriting or deleting an old observation.
- **FORBID-2**: Deleting the "This box" device.
- **FORBID-3**: Guessing the prefix of a network range.
- **FORBID-4**: Another module reading/writing `inv_*` tables directly.
- **FORBID-5**: Sending asset data out of the box (unless `ai`/`notify` is configured, through that module).

## Mismatches / open questions
- `PUT /inventory/settings` per the mock: a range with host bits ("10.0.18.5/24") is brought back to the network address (`Masked()`) and reported in `adjusted: [{from, to}]`; duplicates/overlaps are judged on the brought-back value, so `host_bits` never happens for a range (keeping the prefix length the person typed). `exclusions` stay strict: host bits are refused `bad_exclusion`.
- `SettingsInput` has `scope_confirmed_at/by` (inherited from `InventorySettings`): the server ignores the value the client sends (there is a test), setting it itself per POST-5.
- An empty `ip`: the API returns `"—"` like the mock/contract (DATA_MODEL question 10 settled per the contract); the DB stores NULL.
- An IP with a leading zero (`192.168.01.5`) is refused `bad_ip`: the backend uses strict `netip` because `01` can be read as octal (ambiguous), while the mock accepts it. The same reason for network ranges (`bad_cidr`).
- Schema constraints (length, enum, number of ranges ≤ 16, `days` 1..7…) return `400 invalid` with a full `field`, not `bad_*` like the mock.
- CSV export writes one `core_audit` row (`inventory.export`, containing no data).
- The two CSV files (`/inventory/export.csv`, `/inventory/import-template.csv`) return `Content-Type: text/csv; charset=utf-8`, `Content-Disposition: attachment; filename="vedette-devices-YYYYMMDD.csv"` (the template: `vedette-devices-template.csv`) and `Cache-Control: no-store` through `server.Exchange.SetContentType` (ogen's generated encoder says octet-stream); only on success. `TestHandlersRolesAndShapes`.
