(4) **GMP login:** the admin user's password is 24 random bytes in core/secrets (48 hex), made on the first up and set by the host on every up with gvmd's own documented command (`gvmd --user=admin --new-password=…` as the user gvmd), retried while gvmd migrates, so a wiped volume (W4-1) gets it back. It travels in the args of greenbone.up (redacted in the audit by its key) and its only exposure is that argv in the box's process list for about a second, to local users of the box, never to a container: gvmd has no stdin or file option, and GMP's modify_user would need the old password, which a wiped or foreign database does not give. Never logged, never in an error. (5) **Down / uninstall:** Down = `compose stop`, volumes kept; turning OpenVAS off on the page, and switching the External exposure module off while OpenVAS is enabled, call Down (the module on again starts it); `install.sh --uninstall` never touches the project, its containers, images, volumes, the provider package or the socket folder, and podman stays with them (W4-1). (6) **LEAN-1, only what Vedette uses:** off by `profiles: [disabled]` in the override, each safe because nothing that runs depends on it and Vedette's path (GMP to gvmd over the socket, ospd-openvas scanning, the feed services) never uses it: `gsa` (web UI files for nginx), `gsad` (the web UI's HTTP server; it depends on gvmd, not the other way), `nginx` (the TLS front of gsad and the only service that publishes ports, so nothing of Greenbone listens on a port of the box), `gvm-config` (nginx's config and certificate only), `gvm-tools` (an administrator's interactive GMP CLI; the login uses gvmd's own command), `openvas` (prints the scanner config and tails its log: "shows logs of openvas"; ospd-openvas starts the scanner itself).
